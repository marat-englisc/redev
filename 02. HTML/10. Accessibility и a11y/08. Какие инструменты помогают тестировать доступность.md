# Какие инструменты помогают тестировать доступность?

> [!NOTE]
> Доступность тестируют сочетанием автоматических инструментов, ручной проверки клавиатуры, скринридеров, DevTools и проверки контраста. Автоматические проверки полезны, но не покрывают весь пользовательский опыт.

## Вопрос

Какие инструменты помогают тестировать доступность и что они не могут проверить?

## Главное

Нет одного инструмента, который гарантирует полную доступность. Хороший процесс сочетает несколько уровней.

```text
automated checks
  + keyboard testing
  + screen reader testing
  + contrast review
  + manual UX review
```

## Автоматические инструменты

| Инструмент | Что помогает найти |
| --- | --- |
| Lighthouse | Общие accessibility-проблемы и быстрый аудит |
| axe DevTools | Ошибки ARIA, label, контраста, ролей |
| WAVE | Визуальный отчет по доступности страницы |
| HTML validator | Ошибки разметки и неправильную вложенность |
| eslint-plugin-jsx-a11y | A11y-проблемы в JSX-проектах |

Автоматические проверки хорошо ловят явные проблемы, но не всегда понимают смысл интерфейса.

## Ручная проверка клавиатурой

Проверь страницу без мыши:

- `Tab` двигает фокус вперед;
- `Shift + Tab` двигает фокус назад;
- `Enter` и `Space` активируют контролы;
- `Esc` закрывает модалки или меню, если это ожидаемо;
- фокус видим;
- нет ловушки фокуса.

```css
:focus-visible {
  outline: 3px solid #2563eb;
  outline-offset: 2px;
}
```

## Скринридеры

Полезно проверить страницу хотя бы в одном скринридере:

- NVDA на Windows;
- VoiceOver на macOS и iOS;
- TalkBack на Android.

Что слушать:

- понятно ли называются кнопки;
- есть ли label у полей;
- логична ли структура заголовков;
- можно ли перейти к `main` и `nav`;
- озвучиваются ли ошибки и статусы.

## Проверка контраста

Контраст можно проверять через:

- DevTools;
- WebAIM Contrast Checker;
- Figma-плагины;
- axe;
- ручной просмотр на разных экранах.

Важно проверять не только основной текст, но и placeholder, disabled-состояния, фокус, hover и ошибки.

## Тестирование в коде

Для E2E и component-тестов полезно искать элементы по доступным ролям и именам.

```js
await page.getByRole("button", { name: "Сохранить" }).click();
await expect(page.getByRole("status")).toContainText("Сохранено");
```

Если тест не может найти кнопку по роли и имени, это часто сигнал, что с доступностью элемента что-то не так.

## Что важно помнить

- Автоматические проверки находят лишь часть проблем; смысл alt, логику порядка и удобство виджетов проверяет человек.
- Доступность можно проверять в тестах: `vitest-axe` в компонентных тестах и `@axe-core/playwright` в e2e.
- Быстрый ручной тест: пройти сценарий только клавиатурой и затем со включенным скринридером.
- Подробно про автоматизацию — в разделе Тестирование: [Как тестировать доступность](<../../14. Тестирование/07. Другие виды тестирования/02. Как тестировать доступность.md>).

## Мини-шпаргалка

- Автоматические инструменты ловят не все.
- Клавиатурная проверка обязательна.
- Скринридер показывает реальный опыт части пользователей.
- Контраст нужно проверять отдельно.
- DevTools помогает смотреть accessibility tree.
- Тесты по ролям и именам поддерживают доступную разметку.
