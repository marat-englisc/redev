# Формы и параметризация в Playwright

> [!NOTE]
> Для форм используют `getByLabel`, `getByRole`, `fill`, `check` и `selectOption`, а результат проверяют через web-first assertions. Параметризация превращает спроектированные классы и границы в отдельные понятные тесты, не смешивая разные причины отказа.

## Вопрос

Как автоматизировать проверки валидации формы? Почему недостаточно проверить только disabled у кнопки?

## Пример на учебном стенде

Запусти [QA Lab](<../15. Практика QA/01. Как запустить локальный учебный стенд QA.md>). Его поле «Название» создаёт задачи пользователя A. Пример использует полный URL и не требует `baseURL`.

```ts
import { test, expect } from '@playwright/test';

for (const title of ['', '   ', 'x'.repeat(81)]) {
  test(`название длиной ${title.length} отклоняется`, async ({ page }) => {
    await page.goto('http://127.0.0.1:3007');
    await page.getByLabel('Название', { exact: true }).fill(title);
    await page.getByRole('button', { name: 'Добавить', exact: true }).click();
    await expect(page.getByRole('alert')).toHaveText(
      'title must contain 1..80 characters'
    );
    await expect(page.getByRole('listitem')).toHaveCount(0);
  });
}
```

Нужен свежий сервер без задач A; иначе ожидание нуля неверно. В итоговой лабораторной подготовка учитывает исходное состояние и очищает данные. Нельзя рассчитывать на порядок запуска файлов.

## Контролы и проверки

```ts
// Примеры API для формы, где эти контролы существуют:
await page.getByLabel('Согласен с условиями').check();
await expect(page.getByLabel('Согласен с условиями')).toBeChecked();
await page.getByLabel('Страна').selectOption('ru');
await expect(page.getByLabel('Страна')).toHaveValue('ru');
```

`fill` заменяет значение поля. `pressSequentially` нужен для поведения, зависящего от отдельных клавиатурных событий. После сохранения проверяй наблюдаемый результат и при необходимости reload, а не только то, что поле содержит введённый текст.

## Что важно помнить

- Серверная валидация проверяется отдельными API-тестами: HTML-ограничения можно обойти.
- `toHaveText` ждёт нужный текст; получение `textContent()` и обычное сравнение даёт снимок одного момента.
- Ошибка должна быть связана с действием, а не остаться от предыдущего ввода.
- Название каждого параметризованного теста должно быть уникальным и объяснять данные.

## Мини-шпаргалка

Кейсы из тест-дизайна → отдельные тесты → семантические локаторы → действие → ошибка/успех → сохранение.
