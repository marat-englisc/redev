# Flaky-тесты и борьба с ними

> [!NOTE]
> Flaky-тест — тест, который то проходит, то падает без изменений в коде. Причины: гонки с асинхронностью, зависимость от времени и порядка, общие данные, внешние сервисы, анимации. Лечат причину, а не добавляют паузы и бесконечные retries.

## Вопрос

Что такое нестабильные тесты? Какие у них причины и как их исправлять?

## Основная идея

Нестабильный тест опаснее отсутствующего. Команда привыкает перезапускать CI «пока не позеленеет» и перестаёт доверять красному статусу. Однажды настоящая ошибка пройдёт с пометкой «опять flaky».

Типичные причины и решения:

| Причина | Пример | Решение |
| --- | --- | --- |
| Гонка с асинхронностью | проверка до ответа сервера | `findBy`, web-first assertions, ожидание ответа |
| Фиксированные паузы | `sleep(1000)` на медленном CI | ожидание условия вместо времени |
| Время и дата | тест падает в полночь или 31-го числа | `vi.setSystemTime`, `page.clock` |
| Случайность | `Math.random`, случайный порядок | фиксированный seed или мок |
| Общие данные | два теста меняют одну задачу | уникальные данные на тест |
| Зависимость от порядка | тест работает только после другого | изоляция, сброс состояния |
| Внешние сервисы | нестабильный staging API | мок сети, контрактные тесты |
| Анимации и переходы | клик по движущейся кнопке | отключить анимации, `reducedMotion` |
| Ресурсы CI | таймауты под нагрузкой | меньше параллельных воркеров, быстрые тесты |
| Утечки между тестами | незакрытые таймеры, моки | `restoreMocks`, `useRealTimers`, cleanup |

Процесс работы: воспроизвести (`--repeat-each=20` в Playwright, `--sequence.shuffle` в Vitest), найти причину по trace и логам, исправить. Если исправить быстро нельзя, тест временно помечают и заводят задачу, а не оставляют мигать.

## Пример

```ts
// Плохо: зависимость от реального времени
it('показывает «сегодня» для сегодняшнего заказа', () => {
  render(<OrderDate date={new Date()} />);
  expect(screen.getByText('сегодня')).toBeInTheDocument(); // упадёт около полуночи
});

// Хорошо: время зафиксировано
it('показывает «сегодня» для сегодняшнего заказа', () => {
  vi.useFakeTimers();
  vi.setSystemTime(new Date('2026-05-10T12:00:00'));
  render(<OrderDate date={new Date('2026-05-10T09:30:00')} />);
  expect(screen.getByText('сегодня')).toBeInTheDocument();
  vi.useRealTimers();
});
```

```ts
// Playwright: поиск нестабильности и отключение анимаций
// npx playwright test todos.spec.ts --repeat-each=20
test.use({ contextOptions: { reducedMotion: 'reduce' } });

test('часы в браузере зафиксированы', async ({ page }) => {
  await page.clock.setFixedTime(new Date('2026-05-10T12:00:00'));
  await page.goto('/orders');
  await expect(page.getByText('Сегодня, 12:00')).toBeVisible();
});
```

## Что важно помнить

- `retries` в CI — страховка и сигнал, а не лечение. Playwright помечает тесты, прошедшие со второй попытки, как flaky в отчёте.
- `trace: 'on-first-retry'` сохраняет запись именно тех запусков, которые упали.
- Тест, который падает только в CI, часто зависит от часового пояса, локали или скорости машины. Фиксируйте `TZ` и `locale`.
- Чем меньше зависимостей у теста, тем он стабильнее — ещё один довод за интеграционные тесты с MSW.

## Мини-шпаргалка

Flaky = падает без изменений кода. Причины: асинхронность, время, общие данные, порядок, внешние сервисы. Ждём условия, а не время. Фиксируем время, данные — уникальные. Retries — не лечение.
