# Авторизация и подготовка данных в e2e

> [!NOTE]
> Вход через форму в каждом тесте медленный и повторяется. В Playwright логинятся один раз в setup-проекте, сохраняют cookie и localStorage в файл `storageState` и переиспользуют его во всех тестах. Данные создают через API или фикстуры, а не кликами по интерфейсу.

## Вопрос

Как не проходить логин в каждом e2e-тесте? Как готовить тестовые данные?

## Основная идея

Если 50 тестов начинаются с заполнения формы входа, прогон замедляется на минуты, а поломка формы роняет все тесты сразу. Форму входа достаточно проверить одним отдельным тестом.

**storageState** — снимок cookie и localStorage после входа. Setup-проект Playwright выполняется перед остальными: логинится и записывает состояние в `playwright/.auth/user.json`. Основные проекты указывают `storageState` и стартуют уже авторизованными. Файл с сессией нельзя коммитить — его добавляют в `.gitignore`.

**Подготовка данных** — каждому тесту нужны свои данные, чтобы тесты были независимы и могли идти параллельно. Варианты:

- создать запись через API в `beforeEach` или фикстуре (`request.post('/api/todos')`);
- использовать уникальные значения: `Задача ${Date.now()}` или `randomUUID()`;
- сбрасывать тестовую БД перед прогоном (seed);
- для редких ответов (ошибка оплаты) — мокать сеть через `page.route`.

**Фикстуры** Playwright (`test.extend`) — способ объявить переиспользуемую подготовку: «авторизованная страница», «задача, созданная для теста». Фикстура выполняет setup и teardown вокруг теста.

## Пример

```ts
// e2e/auth.setup.ts
import { test as setup, expect } from '@playwright/test';

const authFile = 'playwright/.auth/user.json';

setup('вход тестового пользователя', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill(process.env.E2E_USER_EMAIL!);
  await page.getByLabel('Пароль').fill(process.env.E2E_USER_PASSWORD!);
  await page.getByRole('button', { name: 'Войти' }).click();
  await expect(page.getByRole('heading', { name: 'Мои задачи' })).toBeVisible();

  await page.context().storageState({ path: authFile });
});
```

```ts
// playwright.config.ts (фрагмент)
projects: [
  { name: 'setup', testMatch: /.*\.setup\.ts/ },
  {
    name: 'chromium',
    testIgnore: /.*\.setup\.ts/,
    use: { ...devices['Desktop Chrome'], storageState: 'playwright/.auth/user.json' },
    dependencies: ['setup'],
  },
],
```

```ts
// e2e/fixtures.ts
import { test as base, expect } from '@playwright/test';

type Fixtures = { todo: { id: string; title: string } };

export const test = base.extend<Fixtures>({
  todo: async ({ request }, use) => {
    const title = `Задача ${crypto.randomUUID()}`;
    const response = await request.post('/api/todos', { data: { title } });
    expect(response.status()).toBe(201); // по контракту учебного API
    const todo = await response.json();
    try {
      await use(todo);
    } finally {
      const removed = await request.delete(`/api/todos/${todo.id}`);
      expect([204, 404]).toContain(removed.status());
    }
  },
});
export { expect };
```

```ts
// e2e/todo-edit.spec.ts
import { test, expect } from './fixtures';

test('переименование задачи', async ({ page, todo }) => {
  await page.goto('/');
  const item = page.getByRole('listitem').filter({ hasText: todo.title });
  await item.getByRole('button', { name: 'Переименовать' }).click();
  await page.getByLabel('Название').fill('Купить молоко');
  await page.getByRole('button', { name: 'Сохранить' }).click();
  await expect(page.getByText('Купить молоко')).toBeVisible();
});
```

Встроенная фикстура `request` получает `baseURL` и начальное `storageState` из конфигурации, поэтому запросы стартуют с сохранёнными cookies. Это отдельный APIRequestContext: последующие изменения cookies страницы не синхронизируются с ним автоматически. Для общего актуального cookie-хранилища используют `page.request` или `page.context().request`. Токен из localStorage не превращается в Bearer-заголовок API-запроса автоматически.

## Что важно помнить

- Учётные данные тестового пользователя хранятся в переменных окружения или секретах CI, не в коде.
- Тестовая БД и окружение должны быть отделены от production.
- Для тестов с разными ролями создают несколько файлов состояния: `admin.json`, `user.json`.
- Если сессия истекает, setup-проект перезапустится при следующем прогоне.
- `storageState` не сохраняет sessionStorage; IndexedDB при необходимости включают отдельной опцией поддерживаемой версии Playwright. Общий файл состояния не изолирует серверные данные аккаунта между тестами.
- Пример теста прав с двумя пользователями есть в разделе Next.js: [Как тестировать fullstack-приложение и права доступа](<../../07. Next/14. Тестирование и публикация/04. Как тестировать fullstack приложение и права доступа.md>).

## Мини-шпаргалка

Логин один раз → `storageState` → переиспользование. Данные — через API и фикстуры `test.extend`, уникальные имена. Сессию не коммитим.
