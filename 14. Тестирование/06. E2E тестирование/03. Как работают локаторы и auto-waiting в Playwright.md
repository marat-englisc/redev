# Локаторы и auto-waiting в Playwright

> [!NOTE]
> Локатор — ленивое описание способа найти элемент: `page.getByRole('button', { name: 'Войти' })`. Он ищет элемент заново при каждом действии. Действия ждут, пока элемент станет видимым, стабильным и доступным, а web-first assertions повторяют проверку до таймаута. Поэтому ручные задержки не нужны.

## Вопрос

Что такое локаторы в Playwright? Как Playwright ждёт элементы? Почему нельзя использовать `waitForTimeout`?

## Основная идея

Локатор не находит элемент в момент создания. Это «рецепт поиска», который выполняется при каждом действии или проверке. Если React перерисовал кнопку, локатор найдёт новую. В старых подходах ссылка на DOM-узел становилась устаревшей.

Перед действием Playwright проверяет **actionability**. Для `click` элемент должен быть:

- прикреплён к DOM;
- видим;
- стабилен — не анимируется;
- получает события — не перекрыт другим элементом;
- включён — не `disabled`.

Если условия не выполнены, Playwright ждёт до таймаута действия. **Web-first assertions** (`await expect(locator).toBeVisible()`, `toHaveText`, `toHaveURL`) тоже повторяются до таймаута (по умолчанию 5 секунд). Поэтому `await page.waitForTimeout(2000)` не нужен и вреден: тест либо медленный, либо всё равно нестабильный.

Приоритет локаторов похож на Testing Library:

| Локатор | Когда |
| --- | --- |
| `getByRole(role, { name })` | основной выбор |
| `getByLabel` | поля формы |
| `getByPlaceholder` | поле без label |
| `getByText` | неинтерактивный текст |
| `getByAltText`, `getByTitle` | изображения, title |
| `getByTestId` | когда нет семантики (атрибут `data-testid`) |
| `locator('css')` | крайний случай |

Локаторы можно уточнять: `.filter({ hasText })`, `.filter({ has: locator })`, `.nth(i)`, `.first()`, цепочкой `row.getByRole('button')`. По умолчанию локатор **строгий**: если найдено несколько элементов, действие упадёт с ошибкой. Это защищает от клика «не туда».

## Пример

```ts
import { test, expect } from '@playwright/test';

test('удаление заказа из списка', async ({ page }) => {
  await page.goto('/orders');

  const row = page.getByRole('row').filter({ hasText: 'A-102' });
  await row.getByRole('button', { name: 'Удалить' }).click();

  const dialog = page.getByRole('dialog', { name: 'Удалить заказ?' });
  await expect(dialog).toBeVisible();
  await dialog.getByRole('button', { name: 'Да, удалить' }).click();

  await expect(row).toHaveCount(0);
  await expect(page.getByRole('status')).toHaveText('Заказ удалён');
});

test('ожидание ответа сервера', async ({ page }) => {
  await page.goto('/profile');
  const saved = page.waitForResponse((r) => r.url().includes('/api/profile') && r.ok());
  await page.getByRole('button', { name: 'Сохранить' }).click();
  await saved;
  await expect(page).toHaveURL(/\/profile$/);
});
```

Плохие варианты:

```ts
await page.waitForTimeout(3000);                       // магическая пауза
expect(await page.getByText('Готово').isVisible()).toBe(true); // проверка без повторов
await page.locator('div > div:nth-child(3) .btn').click();      // хрупкий CSS
```

`isVisible()` возвращает значение один раз и не ждёт. Нужно `await expect(locator).toBeVisible()`.

## Что важно помнить

- `await` ставится перед `expect`: `await expect(locator).toBeVisible()`.
- `page.route` позволяет замокать ответ API в e2e — полезно для редких ошибок сервера.
- `codegen` и UI mode подсказывают устойчивые локаторы.
- Для Shadow DOM локаторы по умолчанию проходят внутрь открытых shadow root.

## Мини-шпаргалка

Локатор = ленивый рецепт поиска. Действия ждут actionability. `await expect(locator).toX()` повторяется до таймаута. `getByRole` в приоритете. `waitForTimeout` — нет.
