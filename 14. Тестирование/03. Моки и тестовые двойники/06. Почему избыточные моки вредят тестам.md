# Почему избыточные моки вредят тестам

> [!NOTE]
> Каждый мок — допущение «эта часть работает так, как я думаю». Чем больше моков, тем меньше тест проверяет настоящий код, тем сильнее он привязан к реализации и тем чаще остаётся зелёным при сломанном приложении.

## Вопрос

Почему не стоит мокать всё подряд? Где проходит граница?

## Основная идея

Представим тест страницы заказа, в котором замоканы `useCart`, `useUser`, `api.createOrder`, дочерний компонент `OrderSummary` и `useNavigate`. Тест проверяет, что `createOrder` вызван. Но настоящий `useCart` может возвращать сумму в копейках, а мок — в рублях. `OrderSummary` может падать при пустом адресе. Тест всё равно пройдёт: он проверяет сам себя, а не приложение.

Проблемы избыточного мокинга:

- **ложная уверенность** — мок расходится с реальностью, и никто этого не замечает;
- **хрупкость** — переименование внутреннего хука ломает десятки тестов, хотя поведение не изменилось;
- **сложность** — подготовка моков занимает больше строк, чем сам тест;
- **тестирование моков** — проверки вида «мок вернул то, что ему сказали вернуть».

Практическое правило: **мокайте границы, которые не контролируете, и оставляйте настоящим всё, что контролируете**. Граница — сеть, время, случайность, браузерные API без реализации, сторонние сервисы (оплата, аналитика). Собственные компоненты, хуки, store и утилиты лучше использовать по-настоящему.

## Пример

```tsx
// Плохо: замокано почти всё приложение
vi.mock('./useCart', () => ({ useCart: () => ({ items: [], total: 0 }) }));
vi.mock('./OrderSummary', () => ({ OrderSummary: () => <div>summary</div> }));
vi.mock('@/shared/api');

it('создаёт заказ', async () => {
  render(<CheckoutPage />);
  await user.click(screen.getByText('Оформить'));
  expect(api.createOrder).toHaveBeenCalled();
});
```

```tsx
// Лучше: настоящие компоненты и store, замокана только сеть (MSW)
it('создаёт заказ и показывает номер', async () => {
  server.use(
    http.post('/api/orders', () => HttpResponse.json({ id: 'A-102' }, { status: 201 })),
  );
  const user = userEvent.setup();
  renderWithProviders(<CheckoutPage />, { cart: [{ id: '1', title: 'Чайник', price: 1500, qty: 1 }] });

  expect(screen.getByText('Итого: 1 500 ₽')).toBeInTheDocument();
  await user.click(screen.getByRole('button', { name: 'Оформить' }));

  expect(await screen.findByText('Заказ A-102 оформлен')).toBeInTheDocument();
});
```

Второй тест ловит ошибки в расчёте суммы, в `OrderSummary`, в формировании запроса и в обработке ответа.

## Что важно помнить

- Мокать тяжёлые дочерние компоненты (карта, график, редактор) иногда оправдано — но это осознанный компромисс.
- Если для теста приходится мокать много модулей, у компонента, вероятно, слишком много ответственности.
- Моки ответов API лучше строить по реальной схеме: общие фабрики, типы из OpenAPI, валидация через Zod.
- Контрактные тесты и e2e закрывают риск расхождения моков с настоящим бэкендом.

## Мини-шпаргалка

Мок = допущение. Мокаем границы: сеть, время, сторонние сервисы. Свой код — настоящий. Много моков → хрупкий тест и подозрение на архитектуру.
