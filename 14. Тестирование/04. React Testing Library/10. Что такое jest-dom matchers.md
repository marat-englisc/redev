# jest-dom matchers

> [!NOTE]
> `@testing-library/jest-dom` добавляет в `expect` matchers для DOM: `toBeInTheDocument`, `toBeVisible`, `toBeDisabled`, `toHaveTextContent`, `toHaveValue` и другие. Они делают проверки читаемыми и дают понятные сообщения об ошибках. Работают и с Jest, и с Vitest.

## Вопрос

Зачем нужен jest-dom? Какие его matchers используются чаще всего?

## Основная идея

Без jest-dom проверки пишут через свойства DOM: `expect(button.disabled).toBe(true)`, `expect(el.textContent).toContain('...')`. При падении сообщение выглядит как `expected false to be true` — непонятно, что произошло. jest-dom выводит элемент и объясняет: «Received element is not disabled: <button>Сохранить</button>».

Кроме того, matchers учитывают семантику. `toBeDisabled` проверяет не только атрибут `disabled` у самого элемента, но и `disabled` у родительского `fieldset`. `toBeVisible` учитывает `display: none`, `visibility: hidden`, `opacity: 0`, атрибут `hidden` и скрытых родителей.

Подключение в Vitest — одна строка в setup-файле: `import '@testing-library/jest-dom/vitest'`.

## Основные matchers

| Matcher | Что проверяет |
| --- | --- |
| `toBeInTheDocument()` | элемент есть в документе |
| `toBeVisible()` | элемент виден пользователю |
| `toBeEmptyDOMElement()` | у элемента нет содержимого |
| `toBeDisabled()` / `toBeEnabled()` | интерактивность |
| `toBeRequired()` | поле обязательное |
| `toBeInvalid()` / `toBeValid()` | `aria-invalid` или невалидность по constraint validation |
| `toBeChecked()` / `toBePartiallyChecked()` | checkbox, radio, switch |
| `toHaveFocus()` | элемент в фокусе |
| `toHaveTextContent(text)` | текстовое содержимое (подстрока или RegExp) |
| `toHaveValue(value)` | значение input, select, textarea |
| `toHaveDisplayValue(value)` | отображаемое значение, в том числе для select |
| `toHaveAttribute(name, value?)` | атрибут |
| `toHaveClass(...names)` | CSS-классы (использовать осторожно) |
| `toHaveStyle(css)` | вычисленные стили |
| `toHaveAccessibleName(name)` | доступное имя |
| `toHaveAccessibleDescription(text)` | доступное описание (`aria-describedby`) |
| `toHaveFormValues(values)` | значения всех полей формы по `name` |
| `toContainElement(el)` | вложенность элемента |

## Пример

```tsx
it('настраивает доставку', async () => {
  const user = userEvent.setup();
  render(<DeliveryForm />);

  const courier = screen.getByRole('radio', { name: 'Курьер' });
  const address = screen.getByRole('textbox', { name: 'Адрес' });

  expect(address).toBeDisabled();

  await user.click(courier);

  expect(courier).toBeChecked();
  expect(address).toBeEnabled();
  expect(address).toBeRequired();
  expect(address).toHaveFocus(); // компонент переводит фокус на адрес

  await user.type(address, 'Казань, ул. Баумана, 1');
  expect(screen.getByRole('form', { name: 'Доставка' })).toHaveFormValues({
    method: 'courier',
    address: 'Казань, ул. Баумана, 1',
  });
});
```

## Что важно помнить

- jsdom не загружает внешние CSS-файлы, поэтому `toBeVisible` видит только inline-стили, атрибуты и стили, вставленные в документ.
- `toHaveClass` и `toHaveStyle` проверяют реализацию — используйте, только если класс или стиль и есть поведение.
- `getByRole('form')` находит `<form>` только при наличии доступного имени (`aria-label` или `aria-labelledby`).
- `.not.toBeInTheDocument()` используется вместе с `queryBy`.

## Мини-шпаргалка

Есть → `toBeInTheDocument`. Видно → `toBeVisible`. Доступно → `toBeEnabled` / `toBeDisabled`. Текст → `toHaveTextContent`. Поле → `toHaveValue`, `toBeChecked`, `toBeInvalid`. Фокус → `toHaveFocus`.
