# SQL и логи для junior QA

> [!NOTE]
> SQL помогает проверить сохранённые данные и связи, логи — проследить обработку события. Начинать нужно с SELECT, JOIN, фильтров и агрегации. Важно знать схему, окружение и момент чтения: асинхронная обработка и реплики могут давать задержку.

## Вопрос

Как проверить, что API создал один заказ и правильные позиции? Что искать в логах при ошибке 500?

## Пример схемы

Пусть есть `orders(id, user_id, status, total)` и `order_items(id, order_id, quantity, unit_price)`. На тестовом стенде после создания заказа 901:

```sql
SELECT id, user_id, status, total
FROM orders
WHERE id = 901;

SELECT order_id, SUM(quantity * unit_price) AS items_total
FROM order_items
WHERE order_id = 901
GROUP BY order_id;

SELECT o.id, o.status, COUNT(i.id) AS item_count
FROM orders AS o
LEFT JOIN order_items AS i ON i.order_id = o.id
WHERE o.id = 901
GROUP BY o.id, o.status;
```

`LEFT JOIN` сохраняет заказ даже при отсутствии позиций. `COUNT(i.id)` считает позиции; `COUNT(*)` в такой связке может посчитать строку без совпавшей позиции. Значения `NULL` проверяются через `IS NULL`, а не `= NULL`.

Сумма позиций не обязана совпадать с `orders.total`, если в total входят скидка, доставка и налоги. Сначала уточни модель данных.

## Логи

```text
2026-10-27T10:15:32Z ERROR request_id=req-42 route=POST:/orders
dependency=inventory status=timeout duration_ms=3000
```

Сопоставь request ID из ответа с серверной записью. Запиши окружение, временной интервал с часовым поясом, endpoint, роль и условие. Timeout зависимости объясняет направление поиска, но первопричину ещё нужно исследовать.

## Что важно помнить

- Не изменяй данные прямым UPDATE ради подготовки, если это обходит бизнес-правила и события.
- В учебной работе достаточно доступа на чтение к тестовой БД.
- Дубликаты после JOIN могут отражать связь один-ко-многим, а не дефект данных.
- «Сразу не видно в БД» требует проверки транзакции, асинхронности и источника чтения.

## Практика

Найди пользователей с более чем одним заказом через `GROUP BY user_id HAVING COUNT(*) > 1`. Затем объясни, почему фильтр по агрегату нельзя перенести в обычный WHERE.

## Мини-шпаргалка

ID из API → SELECT → связи и суммы → request ID → логи → сопоставление с контрактом.
