# Тест-дизайн формы с нуля

> [!NOTE]
> Проверки формы начинают с требований и пользовательской цели. Затем выделяют поля, классы, границы, зависимости, состояния и риски. Позитивный сценарий, ошибки, сохранение на сервере и восстановление после сбоя должны иметь наблюдаемые ожидаемые результаты.

## Вопрос

Перед вами форма регистрации без готовых тестов. С чего начать и как объяснить выбор проверок?

## Условия задачи

Email обязателен и уникален без учёта регистра по согласованному правилу продукта. Пароль — 8–20 ASCII-символов; повтор должен совпасть. Нужно согласие с условиями. Успех создаёт аккаунт и открывает страницу входа. Учётные данные не должны попасть в URL и журналы приложения.

## Разбор

| Слой | Проверки | Почему |
| --- | --- | --- |
| Основной путь | новый email, корректный пароль, согласие | достижимость цели |
| Классы | пустые поля, неверный email, занятый email | разные правила отклонения |
| Границы | пароль длиной 7/8/9/19/20/21 | ошибки ограничений |
| Зависимости | несовпадение повтора, отсутствие согласия | взаимосвязь полей |
| Сервер | запрос без клиентской валидации | UI можно обойти |
| Сбои | timeout, 500, повтор отправки | восстановление и дубли |
| Представление | клавиатура, фокус ошибки, узкий экран | доступность и удобство |

Не нужно перепроверять всю спецификацию email регулярным выражением собственного сочинения. Нужно выяснить контракт продукта и получить согласованные примеры: Unicode, пробелы, максимальная длина и нормализация.

## Как выбрать порядок

Сначала проверяем доступность стенда и базовую регистрацию. Затем правила обязательности и границы, после — зависимости, повторы, сбои и расширенную совместимость. Для задач безопасности нужны отдельные согласованные проверки: например, ограничения попыток и поведение с занятым email.

## Пример полноценной проверки

Данные: уникальный `qa-<id>@example.test`, пароль длиной 8, согласие включено. Действия: отправить форму, открыть вход и войти созданными данными. Ожидания: создан один аккаунт, показана страница входа, вход успешен. Пароль маскируется в доказательствах.

## Что важно помнить

- Не смешивай несколько некорректных полей в первой проверке каждого правила.
- UI-ошибка без проверки отсутствия созданной записи может скрыть частичный успех сервера.
- Общий кейс «проверить регистрацию» не показывает покрытие.

## Мини-шпаргалка

Требования → поля → классы/границы → зависимости → состояния → сервер → риски → порядок.
