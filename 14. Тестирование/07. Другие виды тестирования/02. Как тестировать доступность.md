# Тестирование доступности

> [!NOTE]
> Доступность проверяют в три слоя: запросы Testing Library по ролям в обычных тестах, автоматический аудит axe-core (jest-axe, `@axe-core/playwright`, аддон Storybook) и ручная проверка с клавиатурой и скринридером. Автоматика находит только часть проблем.

## Вопрос

Как автоматически проверять доступность интерфейса? Что можно поймать тестами, а что нет?

## Основная идея

**Первый слой — обычные тесты.** Если тест ищет `getByRole('button', { name: 'Удалить задачу' })` и `getByLabelText('Email')`, он уже проверяет, что у кнопки есть доступное имя, а поле связано с label. Тесты навигации с клавиатуры (`user.tab()`, `toHaveFocus()`) проверяют порядок фокуса и ловушки фокуса в модальных окнах.

**Второй слой — axe-core.** Библиотека от Deque проверяет DOM по правилам WCAG: контраст, `alt` у изображений, связи label, корректность ARIA-атрибутов, уникальность `id`, иерархию landmark-областей. Интеграции:

| Инструмент | Где работает |
| --- | --- |
| `jest-axe` / `vitest-axe` | компонентные тесты в jsdom |
| `@axe-core/playwright` | e2e в настоящем браузере (в том числе контраст) |
| `@storybook/addon-a11y` | каждая история Storybook |
| `eslint-plugin-jsx-a11y` | статический анализ JSX |
| Lighthouse | аудит страницы в DevTools и CI |

В jsdom нет настоящего рендера, поэтому проверки контраста там не работают — их делают в браузере.

**Третий слой — ручная проверка.** Автоматика не оценит, понятен ли текст ссылки, логичен ли порядок чтения, сообщает ли скринридер об обновлении корзины и удобно ли пользоваться интерфейсом без мыши. Нужны проход с клавиатурой и проверка в NVDA, VoiceOver или TalkBack.

## Пример

```tsx
// компонентный тест: vitest-axe
import { render } from '@testing-library/react';
import { axe } from 'vitest-axe';
import * as matchers from 'vitest-axe/matchers';
import { SignUpForm } from './SignUpForm';

expect.extend(matchers);

it('форма регистрации не имеет нарушений a11y', async () => {
  const { container } = render(<SignUpForm />);
  expect(await axe(container)).toHaveNoViolations();
});
```

```ts
// e2e: @axe-core/playwright
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('страница каталога соответствует WCAG AA', async ({ page }) => {
  await page.goto('/catalog');
  const results = await new AxeBuilder({ page })
    .withTags(['wcag2a', 'wcag2aa'])
    .analyze();
  expect(results.violations).toEqual([]);
});
```

```tsx
// клавиатура и фокус в модальном окне
it('возвращает фокус на кнопку после закрытия модалки', async () => {
  const user = userEvent.setup();
  render(<DeleteTodo />);
  const trigger = screen.getByRole('button', { name: 'Удалить' });

  await user.click(trigger);
  expect(screen.getByRole('dialog')).toBeInTheDocument();

  await user.keyboard('{Escape}');
  expect(screen.queryByRole('dialog')).not.toBeInTheDocument();
  expect(trigger).toHaveFocus();
});
```

## Что важно помнить

- Отсутствие нарушений axe не означает, что интерфейс доступен.
- Ошибки axe лучше чинить, а не отключать правила. Если правило отключено, оставьте комментарий с причиной.
- Проверяйте состояния: открытое меню, ошибку формы, модалку — не только начальный экран.
- Про ARIA и семантику подробнее в разделе HTML: [Что такое ARIA](<../../02. HTML/10. Accessibility и a11y/06. Что такое ARIA (Accessible Rich Internet Applications).md>).

## Мини-шпаргалка

Слой 1 — `getByRole` + клавиатура в тестах. Слой 2 — axe: `vitest-axe`, `@axe-core/playwright`, Storybook a11y. Слой 3 — ручная проверка и скринридер. Контраст — только в браузере.
