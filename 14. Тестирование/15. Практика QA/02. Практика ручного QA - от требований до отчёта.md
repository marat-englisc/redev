# Практика ручного QA: от требований до отчёта

> [!NOTE]
> Учебная работа должна показать полный цикл: анализ контракта, риски, тест-дизайн, документы, выполнение и выводы. Число найденных дефектов не главный критерий. Важнее обоснованное покрытие и воспроизводимые результаты.

## Вопрос

Как собрать первый проект ручного тестировщика для портфолио и проверить себя перед собеседованием?

## Задание

Запусти [QA Lab](<01. Как запустить локальный учебный стенд QA.md>) сначала в обычном режиме. Подготовь артефакты своими силами, затем сравни с разбором.

1. Выпиши минимум 5 вопросов к продукту и 5 рисков.
2. Создай чек-лист из 12–15 проверок с ожиданиями.
3. Напиши 6 подробных кейсов: создание, граница, неверный тип API, сохранение done, удаление, чужой объект.
4. Выполни проверки, фиксируя окружение и фактические результаты.
5. Включи учебный дефект QA_BUG и оформи баг-репорт.
6. Верни обычный режим, проведи retest и целевую регрессию.
7. Напиши итоговый отчёт с ограничениями.

## Разбор тест-дизайна

| Риск / правило | Проверки |
| --- | --- |
| Название 1–80 после trim | пустое, пробелы, 1/2/79/80/81 ASCII-символов |
| Тип title | число, null, отсутствующий ключ, массив вместо объекта |
| Сохранение | создать, отметить done, reload, сверить GET |
| Права | A создаёт; B читает, изменяет, удаляет тот же ID |
| Удаление | 204, повторный GET 404, список без ID |
| Ошибки UI | API недоступен, нет ложного сообщения об успехе |

Вопросы: можно ли повторять названия, нужен ли порядок сортировки, как обрабатывать эмодзи, требуется ли ограничение числа задач, какая политика повторного удаления? Часть ответов уже есть в учебном контракте; явно отделяй установленное от предложений по развитию.

## Пример найденного учебного дефекта

```text
Заголовок: POST /tasks принимает title длиной 81 вместо ограничения 80
Окружение: localhost:3007, QA_BUG=1, Node <фактическая версия>
Данные: title = 81 ASCII-символ 'x', Bearer qa-a
Шаги: отправить POST; прочитать созданную задачу по ID.
Ожидание: 400, задача не создана по контракту.
Факт: 201, GET возвращает title длиной 81.
Влияние: нарушение верхнего ограничения данных.
```

Не называй это реальным production-инцидентом: дефект включён специально. После исправления проверь 79/80/81 и пустое название, а не только один пример.

## Критерии самопроверки

- Другой человек может выполнить кейс без твоих подсказок.
- У каждого ожидания есть основание в контракте.
- Прогон различает failed и blocked.
- Проверки прав подтверждают отсутствие изменения чужой задачи.
- Отчёт содержит непроверенные области: например, реальная аутентификация и нагрузка отсутствуют в стенде.

## Мини-шпаргалка

Требования → риски → техники → кейсы → выполнение → баг → retest → отчёт.
