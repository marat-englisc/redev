# Практика Postman: CRUD, границы и права

> [!NOTE]
> Хорошая учебная коллекция проверяет самостоятельные сценарии: основной CRUD, валидацию, отсутствие токена и изоляцию владельцев. Для каждой проверки нужны конкретный статус, значимые поля и контроль побочных эффектов.

## Вопрос

Как показать на интервью, что вы умеете тестировать API через Postman, а не только отправлять GET?

## Задание

Используй [QA Lab](<01. Как запустить локальный учебный стенд QA.md>) в обычном режиме. Создай environment `QA local` и коллекцию из папок:

```text
01 Health
02 CRUD A
03 Validation
04 Access A and B
05 Cleanup
```

В CRUD проверь create/read/update/read/delete/read-gone. В Validation включи длины 0/1/79/80/81, пробелы, неверные типы и malformed JSON. В Access используй два токена и один известный ID владельца A.

## Разбор прав

1. A создаёт объект, получает 201 и ID.
2. GET этого ID с токеном B → 404 без содержимого задачи.
3. PATCH `{done:true}` с токеном B → 404.
4. DELETE с токеном B → 404.
5. GET с токеном A → 200, `done=false`, исходный title.
6. DELETE с токеном A → 204.

Шаг 5 важен: один статус отказа ещё не доказывает, что сервер не изменил объект перед формированием ошибки.

## Пример assertion доступа

```js
pm.test('Чужой объект не раскрывается', () => {
  pm.response.to.have.status(404);
  const body = pm.response.json();
  pm.expect(body.error).to.equal('not found');
  pm.expect(body).not.to.have.property('title');
});
```

Для запроса без токена ожидается 401. Убери наследование auth и убедись в фактически отправленных headers, иначе можешь тестировать другую ситуацию.

## Что должно попасть в результат

Коллекция, безопасное окружение, JSON-таблица тестовых данных, инструкция запуска и отчёт с версиями. Добавь описание, почему запросы зависят друг от друга внутри CRUD и как запускаются остальные папки.

Для каждой позитивной строки валидации нужен cleanup. Для failed Create нельзя использовать старый ID. Нельзя на уровне коллекции проверять «всегда 200», потому что негативные статусы ожидаемы.

## Критерии самопроверки

- Повторный прогон не зависит от задач предыдущего.
- Ошибочное ожидание делает test красным.
- В режиме QA_BUG=1 кейс длины 81 падает.
- После возврата обычного режима он проходит.
- Отчёт не выдаёт время одного запроса за нагрузочное исследование.

## Мини-шпаргалка

CRUD + типы/границы + отсутствие auth + чужой объект + уборка + воспроизводимый запуск.
