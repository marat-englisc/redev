# Вопросы QA: от нуля до junior+

> [!NOTE]
> На собеседовании QA важны понятные определения, примеры и ход рассуждения. Для junior нужно уметь анализировать требования, выбирать проверки, оформлять дефекты и работать с HTTP/API. Junior+ дополнительно объясняет независимость тестов, SQL, автоматизацию и ограничения выбранного покрытия.

## Вопрос

Какие вопросы и практические задачи стоит разобрать перед собеседованием на тестировщика?

## База: ответ и пример

| Вопрос | Что должно прозвучать |
| --- | --- |
| Что такое тестирование? | получение информации о качестве и рисках, поиск дефектов; пример проверки покупки |
| QA и QC? | процессы обеспечения качества и контроль результата; ответственность всей команды |
| Семь принципов? | смысл каждого и практическое действие, а не только список |
| Verification и validation? | соответствие заданному и пригодность для пользовательской задачи |
| Уровни и виды? | граница системы и проверяемое свойство — разные оси |
| Smoke, retest, regression? | жизнеспособность сборки, подтверждение исправления, побочные поломки |
| Severity и priority? | влияние и срочность; пример опечатки перед кампанией |
| Чек-лист и кейс? | компактное условие против подробных данных, шагов и ожиданий |

## Практика junior

| Задание | Ход рассуждения |
| --- | --- |
| Проверить поле 1–99 | целые/дробные/строки/null, границы 0/1/2/98/99/100, серверная проверка |
| Проверить лифт | назначение, этажи, состояния, двери, ограничения, безопасность, доступность; сначала вопросы |
| Проверить логин | основной путь, ошибки, сессия, выход, серверные права, доступность |
| Оформить баг | контекст, сборка, шаги, ожидание с основанием, факт, влияние, доказательства |
| API вернул 200 | проверить структуру, бизнес-значения, сохранение и отсутствие лишних эффектов |
| Баг не воспроизводится | сравнить данные, роль, версии, флаги, сеть и время |

Задача про лифт или карандаш оценивает подход. Начни с назначения и требований, затем систематизируй проверки. Случайный длинный список не заменяет модель.

## Junior+: вопросы с ограничениями

**Почему два новых browser context не изолируют тесты?** Они разделяют браузерное состояние, но могут менять одну запись в общей БД. Нужны отдельные ресурсы или аккаунты.

**Почему 100% coverage не гарантирует качество?** Код мог выполниться без проверки результата; требования и сочетания могут быть пропущены.

**Pairwise гарантирует все баги?** Нет: покрывает пары выбранных параметров, может пропустить тройку факторов.

**Как проверить права?** Два пользователя, известный чужой ID, прямые read/update/delete, отсутствие утечки и изменений.

**Почему зелёный retry требует внимания?** Возможны гонка данных, зависимость окружения или реальный intermittent-дефект. Нужны trace и классификация.

**Что делает Postman-тест?** Именованно сравнивает фактический ответ с конкретным ожиданием. Send без assertion — только отправка.

**Как выбрать между API и UI?** Правила и границы часто дешевле проверить на API; несколько UI-сценариев подтверждают пользовательский путь. Подмена backend ограничивает вывод.

## Задачи с коротким разбором

1. VIP **или** сумма от 3000 даёт бесплатную доставку. Ответ: таблица четырёх комбинаций, границы суммы и уточнение исключений.
2. Новый заказ → оплачен → отправлен. Ответ: допустимые и запрещённые переходы, повтор команды и побочные эффекты.
3. 10 passed, 2 failed, 3 blocked. Ответ: выполнено 12/15; успешно 10/12 выполненных или 10/15 запланированных. Знаменатель обязателен.
4. За час до релиза сломалась оплата. Ответ: воспроизведение и влияние, быстрая передача фактов, варианты ограничения риска и явное решение ответственного.

## Как оценить готовность

Объясни каждую тему за 30–60 секунд и приведи пример. Затем выполни три лабораторные без копирования разбора. Если не можешь объяснить, почему выбран тест и что его успех доказывает, вернись к модели и контракту.

Грейды различаются между компаниями. SQL, HTTP, Git и чтение логов полезны ручному QA; автоматизация на Playwright может быть преимуществом, но не заменяет тест-дизайн.

## Мини-шпаргалка

Определение → пример → техника → ожидаемый результат → ограничение → следующий шаг.
