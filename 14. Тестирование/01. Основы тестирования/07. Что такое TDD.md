# TDD — разработка через тестирование

> [!NOTE]
> TDD (Test-Driven Development) — подход, в котором тест пишется до кода. Цикл Red — Green — Refactor: написать падающий тест, минимально его удовлетворить, затем улучшить код при зелёных тестах.

## Вопрос

Что такое TDD? Какие у него плюсы и минусы? Применяете ли вы его?

## Основная идея

TDD описал Kent Beck. Работа идёт короткими циклами:

1. **Red** — написать тест на следующее маленькое поведение. Он должен упасть, иначе тест ничего не проверяет.
2. **Green** — написать минимальный код, чтобы тест прошёл. Красота пока не важна.
3. **Refactor** — улучшить код и тесты, не меняя поведения. Тесты остаются зелёными.

Плюсы: тест сразу описывает требование, код получается тестируемым (маленькие функции, явные зависимости), не остаётся непокрытых веток. Падающий тест в начале доказывает, что тест способен поймать ошибку.

Минусы: подход требует навыка, замедляет на старте и плохо подходит для исследовательской работы, когда требования неясны, и для визуальной вёрстки. Во фронтенде TDD чаще всего применяют для чистой логики: валидации, форматтеров, редьюсеров, хуков — и для исправления багов.

**BDD** (Behavior-Driven Development) — развитие идеи: тесты формулируются языком поведения (Given — When — Then) и часто обсуждаются с аналитиками.

## Пример

Шаг Red — тест на валидацию пароля:

```ts
import { validatePassword } from './validatePassword';

it('требует минимум 8 символов', () => {
  expect(validatePassword('short')).toEqual({ ok: false, error: 'Минимум 8 символов' });
});
```

Шаг Green — минимальная реализация:

```ts
export function validatePassword(value: string) {
  if (value.length < 8) return { ok: false, error: 'Минимум 8 символов' };
  return { ok: true };
}
```

Следующий цикл: тест «требует хотя бы одну цифру» → падает → добавляем проверку → рефакторинг, например вынос правил в массив.

## Что важно помнить

- На собеседовании честный ответ лучше идеализированного: «пишу тест первым для логики и при фиксе багов, для UI — после».
- Тест, который ни разу не падал, может быть сломан: проверьте его, временно сломав код.
- TDD — про дизайн кода не меньше, чем про тесты: он вынуждает делать зависимости явными.
- Регрессионный тест при фиксе бага — самая простая форма TDD.

## Мини-шпаргалка

Red → Green → Refactor. Тест до кода, минимальная реализация, затем улучшение. Хорошо для логики и багфиксов, хуже — для вёрстки.
