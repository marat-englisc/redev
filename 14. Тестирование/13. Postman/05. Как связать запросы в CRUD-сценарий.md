# Цепочки запросов и CRUD

> [!NOTE]
> CRUD-сценарий создаёт ресурс, читает, изменяет и удаляет его. ID из успешного ответа передают следующим запросам, а данные очищают после проверки. Зависимая цепочка должна явно начинаться с подготовки и не использовать случайный ID прошлого прогона.

## Вопрос

Как передать ID созданного объекта следующему запросу Postman? Как избежать ложного успеха после неудачного создания?

## Структура папки

```text
Tasks CRUD
  01 Create     POST   /tasks
  02 Read       GET    /tasks/{{taskId}}
  03 Update     PATCH  /tasks/{{taskId}}
  04 Delete     DELETE /tasks/{{taskId}}
  05 Read gone  GET    /tasks/{{taskId}}
```

В pre-request Create очисти `taskId` и подготовь название из урока о скриптах:

```js
pm.collectionVariables.unset('taskId');
pm.collectionVariables.set('createdTitle', 'CRUD учебная задача');
```

Тело Create: `{"title":"{{createdTitle}}"}`. В post-response:

```js
pm.test('Создание успешно и содержит ID', () => {
  pm.response.to.have.status(201);
  const task = pm.response.json();
  pm.expect(task.id).to.be.a('string').and.not.empty;
  pm.expect(task.title).to.equal(pm.collectionVariables.get('createdTitle'));
  pm.collectionVariables.set('taskId', task.id);
});
```

В последующих запросах можно явно прервать подготовку, если ID не получен:

```js
if (!pm.collectionVariables.get('taskId')) {
  throw new Error('Нет taskId: сначала должен успешно выполниться Create');
}
```

## Проверки каждого шага

Read: 200, тот же ID и title, `done=false`. Update с телом `{"done":true}`: 200, `done=true`; затем отдельный GET подтверждает сохранение. Delete: 204 и пустое тело. Read gone: 404. После последнего запроса очисти `taskId`.

## Независимость и уборка

Внутри папки зависимость оправданна целью CRUD-flow. Отдельные тесты прав и валидации готовят собственные ресурсы, чтобы падение одного сценария не блокировало все остальные.

Если Update упал, Delete всё равно нужен как уборка. Для реальных проектов выбирают механизм очистки, отдельный cleanup или время жизни тестовых данных. Успех уборки не должен скрывать исходную ошибку.

## Мини-шпаргалка

Очистить старое состояние → Create → сохранить проверенный ID → Read → Update → Read → Delete → 404.
