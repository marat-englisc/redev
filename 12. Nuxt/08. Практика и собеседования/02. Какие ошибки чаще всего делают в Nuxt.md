# Какие ошибки чаще всего делают в Nuxt

> [!NOTE]
> Самые частые ошибки в Nuxt связаны с тем, что код выполняется на сервере: `$fetch` в `setup` (двойной запрос), `ref` на уровне модуля (утечка данных между пользователями), `window` в `setup` и «лечение» через `ssr: false`, шаблонная строка вместо функции в URL `useFetch` (данные не обновляются), секреты в `runtimeConfig.public`, общий кэш для персональных страниц, токен в `localStorage`, защита только route middleware без проверок в API, 200 вместо 404, мутация `data` как `shallowRef`.

## Вопрос

Какие ошибки чаще всего допускают в Nuxt-приложениях?

## 1. $fetch в setup

```ts
const products = await $fetch("/api/products");             // ✗ сервер + клиент = 2 запроса
const { data: products } = await useFetch("/api/products");  // ✓ через payload
```

## 2. Состояние на уровне модуля

```ts
const user = ref<User | null>(null);                         // ✗ общий для всех запросов сервера
export const useUser = () => user;

export const useUser = () => useState<User | null>("user", () => null); // ✓
```

## 3. window в setup и ssr: false «для починки»

```ts
const width = window.innerWidth;                             // ✗ падение на сервере
export default defineNuxtConfig({ ssr: false });             // ✗ потеря SEO всего сайта
```

```vue
<ClientOnly><MapWidget /></ClientOnly>                       <!-- ✓ -->
```

## 4. Нереактивный URL

```ts
await useFetch(`/api/products/${route.params.id}`);          // ✗ не обновится при смене id
await useFetch(() => `/api/products/${route.params.id}`);    // ✓
```

## 5. Секреты в public

```ts
runtimeConfig: { public: { stripeSecret: "sk_live_..." } }   // ✗ в HTML каждой страницы
runtimeConfig: { stripeSecret: "" }                          // ✓ NUXT_STRIPE_SECRET
```

## 6. Кэш персональных страниц

```ts
routeRules: { "/account/**": { swr: 3600 } }                 // ✗ пользователи видят чужой кабинет
```

## 7. Авторизация через localStorage

Сервер не видит `localStorage` — SSR рендерит гостевую версию, затем клиент перерисовывает (мерцание, mismatch). Сессию хранят в httpOnly-cookie.

## 8. Защита только на клиенте

Route middleware не пускает гостя на `/admin`, но `GET /api/admin/users` без проверки сессии отдаст данные любому. Проверка прав — в каждом серверном обработчике.

## 9. «Мягкие» 404

```ts
if (!product.value) throw createError({ statusCode: 404, fatal: true });  // ✓ вместо пустой страницы с 200
```

## 10. Мутация shallowRef (Nuxt 4)

```ts
data.value.items.push(item);                     // ✗ UI не обновится
data.value = { ...data.value, items: [...data.value.items, item] }; // ✓ или { deep: true }
```

## Ещё

- Последовательные `await` независимых запросов вместо `Promise.all`.
- Composables в колбэках и после `await` в обычных функциях — «Nuxt instance is unavailable».
- `navigateTo` без `return` в middleware.
- Одинаковые ключи `useAsyncData` для разных данных.
- Игнорирование предупреждений hydration mismatch.
- Модули «на всякий случай», раздувающие бандл.
- `process.env` в коде приложения вместо `useRuntimeConfig`.

## Что важно помнить

- Большинство ошибок проявляется только в production под нагрузкой или при SSR — локально в SPA-режиме их не видно.
- Ошибки 2, 5, 6 и 8 — уязвимости, а не просто баги.
- Хорошая привычка — проверять HTML ответа сервера и консоль на hydration-предупреждения.

## Мини-шпаргалка

- `useFetch` вместо `$fetch` в setup.
- `useState` вместо `ref` в модуле.
- `<ClientOnly>` вместо `ssr: false`.
- Функция-URL в `useFetch`.
- Секреты не в `public`, персональное не кэшировать.
- Сессия в cookie, права — на сервере.
- 404 через `createError`.
