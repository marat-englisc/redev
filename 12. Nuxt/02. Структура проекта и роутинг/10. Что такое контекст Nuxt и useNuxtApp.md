# Что такое контекст Nuxt и useNuxtApp

> [!NOTE]
> На сервере Nuxt создаёт **отдельный экземпляр приложения (`nuxtApp`) для каждого запроса**, чтобы данные пользователей не смешивались. Composables Nuxt (`useState`, `useFetch`, `useRuntimeConfig`, `useCookie`, `useRoute`) находят «свой» экземпляр через неявный контекст, который доступен только при **синхронном** вызове в `setup`, плагинах, middleware и других composables. `useNuxtApp()` даёт прямой доступ к экземпляру: `provide`-значения (`$api`), `payload`, хуки, `vueApp`, флаги `isHydrating`. Если контекст потерян (после `await` в обычной функции, в колбэке), его восстанавливают через `nuxtApp.runWithContext()`.

## Вопрос

Что такое контекст Nuxt, зачем нужен `useNuxtApp` и почему composables работают не везде?

## Зачем экземпляр на запрос

```text
запрос пользователя A ──▶ nuxtApp A ──▶ useState("user") → Анна
запрос пользователя B ──▶ nuxtApp B ──▶ useState("user") → Борис
```

Один Node.js-процесс обслуживает много запросов одновременно. Если бы состояние было глобальным, пользователь B мог бы увидеть данные A. Поэтому всё «запросное» состояние привязано к `nuxtApp`.

## Что даёт useNuxtApp

```ts
const nuxtApp = useNuxtApp();

nuxtApp.$api;                 // значения из provide плагинов
nuxtApp.payload;              // данные, переданные с сервера (вместо window.__NUXT__)
nuxtApp.isHydrating;          // идёт ли сейчас гидрация
nuxtApp.vueApp;               // экземпляр Vue-приложения
nuxtApp.hook("page:finish", () => {});
nuxtApp.ssrContext;           // контекст SSR (только сервер)
nuxtApp.runWithContext(fn);   // выполнить fn с контекстом Nuxt
```

## Где контекст доступен

| Место | Контекст |
| --- | --- |
| `<script setup>`, `setup()` | Да, в том числе после `await` (Nuxt трансформирует код) |
| `defineNuxtPlugin`, `defineNuxtRouteMiddleware` | Да, и после `await` |
| Другой composable, вызванный из перечисленного | Да |
| Уровень модуля (вне функций) | Нет |
| Обработчик клика, `setTimeout`, колбэк `$fetch` | Нет |
| Обычная async-функция после `await` | Может быть потерян |

## Ошибка «Nuxt instance is unavailable»

```ts
// ✗ хук $fetch выполняется позже, вне контекста
const api = $fetch.create({
  async onResponseError({ response }) {
    if (response.status === 401) await navigateTo("/login");
  },
});
```

```ts
// ✓ захватить экземпляр при создании и восстановить контекст
export default defineNuxtPlugin((nuxtApp) => {
  const api = $fetch.create({
    async onResponseError({ response }) {
      if (response.status === 401) {
        await nuxtApp.runWithContext(() => navigateTo("/login"));
      }
    },
  });
  return { provide: { api } };
});
```

Тот же приём — для composables, вызываемых после `await` в обычных функциях.

## Хуки жизненного цикла приложения

```ts
nuxtApp.hook("app:created", (vueApp) => {});
nuxtApp.hook("app:mounted", () => {});        // только клиент
nuxtApp.hook("page:start", () => {});
nuxtApp.hook("page:finish", () => {});
nuxtApp.hook("app:error", (err) => {});
nuxtApp.hook("vue:error", (err, instance, info) => {});
```

## Частые ошибки

- Вызывать `useRuntimeConfig()` или `useState()` на уровне модуля.
- Использовать composables в колбэках событий — их нужно вызвать в `setup` и сохранить результат.
- Хранить данные пользователя в обычной переменной модуля — на сервере она живёт между запросами.
- Обращаться к `window.__NUXT__` — в Nuxt 4 его нет, есть `useNuxtApp().payload`.

## Что важно помнить

- Контекст Nuxt — механизм изоляции запросов на сервере; на клиенте экземпляр один.
- Правило: composables вызываются в начале `setup`, результат используется дальше.
- `runWithContext` — способ вернуть контекст в асинхронном коде.

## Мини-шпаргалка

- Один `nuxtApp` на запрос на сервере.
- `useNuxtApp()` → `$provide`, `payload`, `hook`, `isHydrating`.
- Composables — синхронно в setup/plugin/middleware.
- Потерян контекст → `nuxtApp.runWithContext(fn)`.
