# Как работают auto-imports composables и utils

> [!NOTE]
> Nuxt автоматически импортирует API Vue (`ref`, `computed`, `watch`), свои composables (`useFetch`, `useState`, `useRoute`), а также экспорты верхнего уровня из `app/composables`, `app/utils` и `shared/utils`/`shared/types`. В `server/` свои auto-imports: `server/utils` и утилиты h3/Nitro. Composables, использующие контекст Nuxt, можно вызывать только синхронно в `setup`, плагинах, route middleware или других composables — иначе ошибка «Nuxt instance is unavailable».

## Вопрос

Как работают auto-imports composables и утилит и какие у них ограничения?

## Composable

```ts
// app/composables/useCart.ts
export function useCart() {
  const items = useState<CartItem[]>("cart", () => []);
  const total = computed(() => items.value.reduce((s, i) => s + i.price * i.qty, 0));

  function add(item: CartItem) {
    items.value = [...items.value, item];
  }

  return { items, total, add };
}
```

```vue
<script setup lang="ts">
const { items, total, add } = useCart(); // без import
</script>
```

## Утилита

```ts
// app/utils/formatPrice.ts
export const formatPrice = (value: number) =>
  new Intl.NumberFormat("ru-RU", { style: "currency", currency: "RUB" }).format(value);
```

```vue
<template>{{ formatPrice(1200) }}</template>
```

## Что сканируется

| Каталог | Что импортируется | Где доступно |
| --- | --- | --- |
| `app/composables/` | Экспорты файлов верхнего уровня (и `index.ts` вложенных каталогов) | `app/` |
| `app/utils/` | То же | `app/` |
| `shared/utils/`, `shared/types/` | То же | `app/` и `server/` |
| `server/utils/` | То же | `server/` |

Вложенные файлы `composables/user/useProfile.ts` не сканируются — их реэкспортируют из `composables/index.ts` или добавляют каталог в `imports.dirs`.

## Composable или утилита

| Нужно | Выбор |
| --- | --- |
| `ref`, `computed`, `useState`, хуки жизненного цикла | Composable (`useX`) |
| Доступ к `useNuxtApp`, `useRoute`, `useRuntimeConfig` | Composable |
| Чистая функция: формат, расчёт, парсинг | Утилита |
| Нужна и серверу, и клиенту | `shared/utils` |

## Ограничение контекста

```ts
// ✗ вызов на уровне модуля — нет активного экземпляра Nuxt
const config = useRuntimeConfig();

export function useApi() {
  // ✓ внутри composable, который вызывают из setup
  const config = useRuntimeConfig();
}
```

```ts
async function load() {
  await someAsyncWork();
  const route = useRoute(); // ✗ после await контекст может быть потерян
}
```

В `<script setup>`, `defineNuxtPlugin` и `defineNuxtRouteMiddleware` Nuxt сохраняет контекст и после `await` за счёт трансформации кода. В обычных функциях — вызывайте composables до первого `await` или используйте `nuxtApp.runWithContext()` — см. [урок про контекст Nuxt](<10. Что такое контекст Nuxt и useNuxtApp.md>).

## Явный импорт

```ts
import { useFetch, useState } from "#imports";
```

Пригодится в тестах и в файлах вне сканируемых каталогов.

## Частые ошибки

- Вызывать composables на уровне модуля или в `setTimeout`.
- Объявлять `const state = ref()` вне функции composable — на сервере состояние станет общим для всех запросов.
- Ждать, что вложенные каталоги `composables/` сканируются сами.
- Давать composable и утилите одинаковые имена — конфликт auto-imports.

## Что важно помнить

- Auto-imports разрешаются при сборке и типизируются в `.nuxt/imports.d.ts` — это не глобальные переменные.
- Состояние создаётся **внутри** composable, а общее между компонентами — через `useState` или Pinia.
- `server/` и `app/` имеют разные наборы auto-imports.

## Мини-шпаргалка

- `app/composables`, `app/utils`, `shared/*`, `server/utils`.
- Сканируется только верхний уровень.
- Composables — синхронно в `setup`/plugin/middleware.
- `#imports` — явный импорт.
