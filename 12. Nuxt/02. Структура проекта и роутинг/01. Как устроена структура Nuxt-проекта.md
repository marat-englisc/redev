# Как устроена структура Nuxt-проекта

> [!NOTE]
> Nuxt работает по соглашениям: роль файла определяет каталог. В **`app/`** лежит Vue-приложение (`pages`, `layouts`, `components`, `composables`, `middleware`, `plugins`, `utils`, `assets`), в **`server/`** — Nitro (`api`, `routes`, `middleware`, `plugins`, `utils`), в **`shared/`** — код для обеих сторон, в **`public/`** — статика, отдаваемая как есть. Каталоги `.nuxt/` и `.output/` генерируются. Код из `server/` никогда не попадает в клиентский бандл.

## Вопрос

Как устроена структура Nuxt-проекта и что лежит в каждом каталоге?

## Структура

```text
project/
├── app/
│   ├── app.vue             # корневой компонент
│   ├── app.config.ts       # публичная конфигурация UI
│   ├── error.vue           # страница ошибки
│   ├── pages/              # файловый роутинг
│   ├── layouts/            # оболочки страниц
│   ├── components/         # компоненты (auto-import)
│   ├── composables/        # composables (auto-import)
│   ├── utils/              # утилиты (auto-import)
│   ├── middleware/         # route middleware
│   ├── plugins/            # плагины Vue-приложения
│   └── assets/             # CSS, шрифты, картинки — обрабатываются сборщиком
├── server/
│   ├── api/                # /api/* эндпоинты
│   ├── routes/             # серверные маршруты без префикса /api (sitemap.xml, rss)
│   ├── middleware/         # выполняется на каждый HTTP-запрос
│   ├── plugins/            # плагины Nitro
│   └── utils/              # серверные утилиты (auto-import в server/)
├── shared/
│   ├── types/              # общие типы (auto-import)
│   └── utils/              # чистые функции, схемы Zod (auto-import)
├── public/                 # favicon.ico, robots.txt — отдаются по корневому URL
├── content/                # markdown для Nuxt Content (если используется)
├── layers/                 # локальные Nuxt Layers
├── modules/                # локальные модули
├── nuxt.config.ts
└── .nuxt/ .output/         # сгенерированное, не в git
```

## Где что выполняется

| Каталог | Сервер (SSR) | Браузер | В клиентском бандле |
| --- | --- | --- | --- |
| `app/` | Да | Да | Да |
| `server/` | Да | Нет | Нет |
| `shared/` | Да | Да | Если импортирован из `app/` |
| `public/` | — | Отдаётся как статика | — |

Код в `app/` по умолчанию изоморфный: `setup` страницы выполнится на сервере при первом запросе и в браузере при гидрации и клиентских переходах.

## assets или public

| | `app/assets/` | `public/` |
| --- | --- | --- |
| Обработка | Сборщиком: хэш в имени, оптимизация, импорт из кода | Копируется как есть |
| URL | `~/assets/logo.svg` в коде | `/logo.svg` |
| Когда | Стили, шрифты, картинки компонентов | `favicon.ico`, `robots.txt`, файлы с фиксированным URL |

## Правила для shared/

`shared/` нельзя завязывать на окружение: никаких `window`, `document`, `node:fs`, `useRuntimeConfig`, Vue-composables. Только типы, константы, чистые функции и схемы валидации.

## Частые ошибки

- Импортировать `server/utils/db.ts` из компонента.
- Класть картинки, которым нужен хэш для кэширования, в `public/`.
- Путать `app/middleware` (навигация) и `server/middleware` (HTTP).
- Хранить браузерный код в `shared/`.

## Что важно помнить

- Соглашения по каталогам — основа auto-imports и роутинга, поэтому названия папок менять нельзя без настройки.
- `server/` — граница безопасности: секреты, БД и токены живут только там.
- В Nuxt 4 `~` указывает на `app/`, а `server/` и `shared/` — в корне.

## Мини-шпаргалка

- `app/` — UI, `server/` — Nitro, `shared/` — общее, `public/` — статика.
- `pages` → маршруты, `layouts` → оболочки, `middleware` → навигация.
- `server/api` → `/api/*`, `server/routes` → любые пути.
- `.nuxt/`, `.output/` — генерируются.
