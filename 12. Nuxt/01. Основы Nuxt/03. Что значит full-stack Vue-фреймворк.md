# Что значит full-stack Vue-фреймворк

> [!NOTE]
> Full-stack означает, что в одном Nuxt-проекте живут и Vue-приложение (`app/`), и **серверная часть на Nitro** (`server/`): API-маршруты, server middleware, работа с cookies и сессиями, кэш, доступ к БД и секретам из `runtimeConfig`. Общий код (типы, схемы валидации) лежит в `shared/`. Чаще всего Nuxt-сервер используют как **BFF** (backend-for-frontend) — тонкий слой между UI и основными сервисами, а сложную доменную логику оставляют отдельному backend.

## Вопрос

Что значит, что Nuxt — full-stack фреймворк, и когда его серверной части достаточно?

## Основная идея

```text
project/
├── app/       → Vue: страницы, компоненты, composables (выполняется на сервере при SSR и в браузере)
├── server/    → Nitro: API, middleware, plugins (только сервер, не попадает в бандл клиента)
└── shared/    → типы и чистые утилиты для обеих сторон
```

```ts
// shared/types/product.ts
export interface Product {
  id: number;
  title: string;
  price: number;
}
```

```ts
// server/api/products.get.ts
export default defineEventHandler(async (): Promise<Product[]> => {
  const config = useRuntimeConfig();
  return $fetch(`${config.catalogUrl}/products`, {
    headers: { Authorization: `Bearer ${config.catalogToken}` }, // секрет остаётся на сервере
  });
});
```

```vue
<!-- app/pages/index.vue -->
<script setup lang="ts">
const { data: products } = await useFetch("/api/products"); // тип Product[] выводится сам
</script>
```

Nuxt выводит тип ответа `useFetch` прямо из обработчика — типобезопасный контракт без кодогенерации.

## Что удобно делать на сервере Nuxt

- Проксировать и агрегировать запросы к нескольким сервисам (BFF).
- Прятать токены сторонних API от браузера.
- Работать с сессиями и httpOnly-cookies.
- Обрабатывать формы и вебхуки.
- Генерировать sitemap, RSS, OG-картинки.
- Кэшировать дорогие ответы (`cachedEventHandler`).
- Простой CRUD с базой через ORM (Drizzle, Prisma).

## Когда нужен отдельный backend

- Сложная доменная логика и транзакции, своя команда backend.
- Несколько клиентов: веб, мобильные приложения, партнёрское API.
- Фоновые задачи, очереди, долгие процессы — serverless-функции для них не подходят.
- Жёсткие требования к масштабированию отдельных частей.

Тогда Nuxt остаётся UI плюс BFF, а данные берёт из NestJS или другого сервиса.

## Частые ошибки

- Импортировать серверный код (клиент БД) в компоненты — он попадёт в браузерный бандл или сломает сборку.
- Класть в `shared/` код, зависящий от `window` или `node:fs`.
- Писать весь backend в `server/api` без слоёв, валидации и тестов.
- Вызывать свой же `/api` через `$fetch` на сервере с полным URL — Nuxt умеет делать такие вызовы напрямую, без HTTP.

## Что важно помнить

- `server/` никогда не попадает в клиентский бандл — это граница безопасности.
- На сервере `$fetch('/api/...')` к собственным маршрутам вызывает обработчик напрямую, без сетевого запроса.
- BFF — самая частая и самая удачная роль серверной части Nuxt.

## Мини-шпаргалка

- `app/` — UI, `server/` — Nitro, `shared/` — общее.
- `server/api/x.get.ts` → `GET /api/x`.
- Секреты — в `runtimeConfig`, читаются на сервере.
- Nuxt как BFF + отдельный backend для сложного домена.
