# Что изменилось в Nuxt 4

> [!NOTE]
> Nuxt 4 — эволюционный релиз без смены парадигмы. Главное: код приложения переехал в каталог **`app/`** (`server/`, `shared/`, `public/` остались в корне); появился **`shared/`** для общего кода с auto-imports; в `useFetch`/`useAsyncData` `data` стал **`shallowRef`**, значения по умолчанию — `undefined` вместо `null`, вызовы с одним ключом **разделяют** состояние, а данные очищаются после размонтирования последнего потребителя; TypeScript получил раздельные конфиги для app, server и shared и строгий `noUncheckedIndexedAccess`.

## Вопрос

Что изменилось в Nuxt 4 по сравнению с Nuxt 3?

## Структура каталогов

```text
Nuxt 3                    Nuxt 4
├── pages/                ├── app/
├── components/           │   ├── pages/
├── composables/          │   ├── components/
├── layouts/              │   ├── composables/
├── app.vue               │   ├── layouts/
├── server/               │   └── app.vue
├── public/               ├── server/
└── nuxt.config.ts        ├── shared/
                          ├── public/
                          └── nuxt.config.ts
```

`~` и `@` теперь указывают на `app/`. Разделение помогает file watcher'у (не следить за `node_modules` и `.git`) и чётче отделяет клиентский код от серверного. Старая структура распознаётся автоматически; принудительно — `srcDir: "."`.

## Загрузка данных

```ts
const { data } = await useFetch("/api/user");

data.value.name = "Ann";            // Nuxt 4: UI НЕ обновится — data это shallowRef
data.value = { ...data.value, name: "Ann" }; // заменить целиком — обновится

const { data: deepData } = await useFetch("/api/user", { deep: true }); // вернуть глубокую реактивность
```

| Изменение | Nuxt 3 | Nuxt 4 |
| --- | --- | --- |
| Тип `data` | Глубокий `ref` | `shallowRef` (опция `deep: true`) |
| Значение по умолчанию `data`, `error` | `null` | `undefined` |
| Один ключ в нескольких компонентах | Независимые ref'ы | Общие `data`, `error`, `status` |
| Очистка | Данные висели в памяти | Удаляются после размонтирования последнего потребителя |
| `pending` | Отдельный флаг | Вычисляется из `status === "pending"` |
| `getCachedData` | Только при первой загрузке | При каждом запросе, с полем `cause` |
| `refresh({ dedupe })` | `true`/`false` | `"cancel"` / `"defer"` |

Проверки `if (data.value === null)` после миграции нужно заменить на `if (!data.value)` или `=== undefined`.

## Другие изменения

- Каталог `shared/` с auto-imports из `shared/utils` и `shared/types` — для кода, нужного и `app/`, и `server/`.
- Раздельные tsconfig: `.nuxt/tsconfig.app.json`, `tsconfig.server.json`, `tsconfig.shared.json`, `tsconfig.node.json`; проверка типов — `vue-tsc -b --noEmit`.
- `noUncheckedIndexedAccess: true` — `arr[0]` имеет тип `T | undefined`.
- Unhead v2: удалены `hid`, `vmid`, `children` в `useHead`.
- Удалён `window.__NUXT__` — используйте `useNuxtApp().payload`.
- Верхнеуровневый `generate` удалён — настройки prerender в `nitro.prerender`.

## Как мигрировать

```bash
npx nuxt upgrade --dedupe
npx codemod@latest nuxt/4/migration-recipe
```

Codemod переносит файлы в `app/` и правит частые места. Перед мажорным обновлением многие проекты включали `future: { compatibilityVersion: 4 }` в Nuxt 3.

## Частые ошибки после миграции

- Мутировать вложенные поля `data` и не видеть обновлений интерфейса.
- Сравнивать `data.value` с `null`.
- Использовать один ключ `useAsyncData` с разными `transform` в разных компонентах — Nuxt предупредит о конфликте.
- Держать типы для сервера в `app/` — серверный tsconfig их не увидит.

## Что важно помнить

- Новые проекты сразу используют структуру `app/`.
- `shallowRef` для `data` — сознательная оптимизация: большие ответы API не превращаются в глубокие Proxy.
- Общий ключ = общее состояние: это удобно, но ключи нужно давать осмысленно.

## Мини-шпаргалка

- Код приложения — в `app/`, `~` → `app/`.
- `shared/` — общий код с auto-imports.
- `data` — `shallowRef`, по умолчанию `undefined`.
- Один ключ — одно состояние на все компоненты.
- `npx nuxt upgrade` + codemod.
