# Как создать API client через $fetch

> [!NOTE]
> Для внешнего backend создают свой клиент через `$fetch.create({ baseURL, onRequest, onResponseError })` в плагине и отдают его через `provide` как `$api`. В хуках клиента нельзя напрямую вызывать composables — контекст Nuxt там уже потерян: значения (`useCookie`, конфиг) захватывают при создании плагина, а навигацию оборачивают в `nuxtApp.runWithContext()`. Для начальных данных клиент используют внутри `useAsyncData`, а чтобы не повторять это каждый раз, делают обёртку `useAPI` поверх `useFetch` с опцией `$fetch`.

## Вопрос

Как создать API-клиент для внешнего backend в Nuxt?

## Плагин с клиентом

```ts
// app/plugins/api.ts
export default defineNuxtPlugin((nuxtApp) => {
  const config = useRuntimeConfig();
  const token = useCookie<string | null>("access_token"); // захватываем в контексте плагина

  const api = $fetch.create({
    baseURL: config.public.apiBase,
    onRequest({ options }) {
      if (token.value) {
        options.headers.set("Authorization", `Bearer ${token.value}`);
      }
    },
    async onResponseError({ response }) {
      if (response.status === 401) {
        token.value = null;
        await nuxtApp.runWithContext(() => navigateTo("/login"));
      }
    },
  });

  return { provide: { api } };
});
```

## Обёртка useAPI

```ts
// app/composables/useAPI.ts
import type { UseFetchOptions } from "nuxt/app";

export function useAPI<T>(url: string | (() => string), options?: UseFetchOptions<T>) {
  return useFetch(url, {
    ...options,
    $fetch: useNuxtApp().$api as typeof $fetch,
  });
}
```

```vue
<script setup lang="ts">
const { data: orders } = await useAPI<Order[]>("/orders");     // SSR + payload + токен

const { $api } = useNuxtApp();
async function cancel(id: number) {
  await $api(`/orders/${id}/cancel`, { method: "POST" });     // действие пользователя
  await refreshNuxtData();
}
</script>
```

## Где хранить токен

| Хранилище | SSR видит | Защита от XSS |
| --- | --- | --- |
| `localStorage` | Нет — запросы при SSR без авторизации | Нет |
| Cookie, читаемая JS (`useCookie`) | Да | Нет |
| httpOnly-cookie + BFF в `server/api` | Да | Да |

Для Nuxt лучше всего работает httpOnly-cookie: браузер сам отправляет её в `server/api`, а серверный маршрут добавляет токен в запрос к backend. Тогда в клиентском коде токена нет вовсе — подробнее в [уроке про авторизацию](<../05. Server API Nitro и deployment/09. Как сделать авторизацию и передавать cookies при SSR.md>).

## Прокси вместо прямых запросов

```ts
// nuxt.config.ts — браузер ходит на /api/backend/*, Nitro проксирует
export default defineNuxtConfig({
  routeRules: {
    "/api/backend/**": { proxy: "https://backend.internal/**" },
  },
});
```

Плюсы: нет CORS, внутренний адрес backend скрыт.

## Частые ошибки

- `useCookie` или `navigateTo` прямо внутри `onRequest` / `onResponseError` — ошибка «Nuxt instance is unavailable».
- `await $api(...)` в `setup` без `useAsyncData` — двойной запрос.
- Токен в `localStorage` при SSR — сервер рендерит страницу как для гостя, потом клиент перерисовывает (mismatch).
- Хардкод `baseURL` вместо `runtimeConfig.public`.

## Что важно помнить

- Клиент создаётся в плагине — на сервере это происходит для каждого запроса отдельно, поэтому токен одного пользователя не попадёт к другому.
- Начальные данные — через `useAsyncData`/`useAPI`, мутации — прямым вызовом `$api`.
- Самый безопасный вариант для токенов — BFF с httpOnly-cookie.

## Мини-шпаргалка

- `$fetch.create({ baseURL, onRequest, onResponseError })`.
- `provide: { api }` → `useNuxtApp().$api`.
- Composables — вне хуков, навигация — `runWithContext`.
- `useFetch(url, { $fetch: $api })` — обёртка `useAPI`.
- `routeRules.proxy` — прокси без CORS.
