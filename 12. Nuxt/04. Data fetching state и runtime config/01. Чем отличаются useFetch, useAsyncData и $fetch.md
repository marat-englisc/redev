# Чем отличаются useFetch, useAsyncData и $fetch

> [!NOTE]
> `$fetch` — просто HTTP-клиент (библиотека ofetch): делает запрос и возвращает данные, ничего не зная о SSR. `useAsyncData(key, handler)` — composable, который выполняет **любую** async-функцию на сервере, кладёт результат в **payload** и переиспользует его при гидрации, возвращая реактивные `data`, `status`, `error`, `refresh`. `useFetch(url)` — сокращение для `useAsyncData` + `$fetch`: ключ генерируется из URL, опции запроса реактивны. Для **начальных данных страницы** — `useFetch`/`useAsyncData`, для **действий пользователя** (отправка формы, клик) — `$fetch`.

## Вопрос

Чем отличаются `useFetch`, `useAsyncData` и `$fetch` и когда что использовать?

## $fetch

```ts
const user = await $fetch<User>("/api/user");
await $fetch("/api/orders", { method: "POST", body: { productId: 1 } });
```

- Парсит JSON, бросает ошибку на статусах 4xx/5xx.
- На сервере запрос к собственному `/api/*` вызывает обработчик напрямую, без сети.
- Не передаёт результат через payload.

В `setup` это приводит к двойному запросу:

```text
сервер: $fetch → данные → HTML
клиент: setup снова → $fetch снова
```

## useAsyncData

```ts
const { data, status, error, refresh } = await useAsyncData("dashboard", async () => {
  const [stats, orders] = await Promise.all([
    $fetch("/api/stats"),
    $fetch("/api/orders", { query: { limit: 5 } }),
  ]);
  return { stats, orders };
});
```

Обработчик может быть чем угодно: несколько запросов, SDK CMS (`queryCollection` в Nuxt Content), GraphQL-клиент, свой `$api`.

## useFetch

```ts
const { data: products, status } = await useFetch("/api/products", {
  query: { category: "keyboards" },
});
```

Эквивалентно:

```ts
await useAsyncData("$f-auto-key", () => $fetch("/api/products", { query: { category: "keyboards" } }));
```

Дополнительно `useFetch` выводит тип ответа из серверного обработчика и на сервере пробрасывает cookies и заголовки пользователя в запросы к собственному API.

## Что выбрать

| Задача | Инструмент |
| --- | --- |
| Данные страницы с одного эндпоинта | `useFetch` |
| Несколько запросов, SDK, не-HTTP источник | `useAsyncData` |
| Свой API-клиент (`$api`) для начальных данных | `useAsyncData("key", () => $api(...))` |
| Отправка формы, удаление, клик | `$fetch` |
| Запрос в `server/api` к внешнему сервису | `$fetch` |
| Данные нужны только в браузере | `useFetch(..., { server: false })` |

## Возвращаемые значения

| Поле | Смысл |
| --- | --- |
| `data` | Результат; в Nuxt 4 — `shallowRef`, по умолчанию `undefined` |
| `status` | `"idle"` / `"pending"` / `"success"` / `"error"` |
| `error` | Ошибка запроса или `undefined` |
| `refresh()` / `execute()` | Повторить запрос |
| `clear()` | Сбросить `data`, `error`, `status` |

## await или нет

```ts
const { data } = await useFetch("/api/products");      // навигация ждёт данные
const { data } = useFetch("/api/products", { lazy: true }); // навигация не ждёт — нужен loading state
```

## Частые ошибки

- `$fetch` в `setup` для начальных данных — двойной запрос.
- `useFetch` внутри обработчика клика — composable вне контекста `setup`.
- Одинаковые ключи `useAsyncData` для разных данных в разных компонентах — в Nuxt 4 они разделят состояние.
- Мутировать вложенные поля `data` и ждать обновления UI (`shallowRef`).

## Что важно помнить

- Composables (`useFetch`, `useAsyncData`) — только в `setup`, плагине, middleware; `$fetch` — где угодно.
- Payload и ключ — то, что отличает composables от голого `$fetch`.
- На сервере `$fetch` не передаёт cookies пользователя в другие сервисы — для этого есть `useRequestFetch` и `useRequestHeaders` (см. [авторизацию](<../05. Server API Nitro и deployment/09. Как сделать авторизацию и передавать cookies при SSR.md>)).

## Мини-шпаргалка

- `$fetch` — просто запрос, для действий.
- `useAsyncData(key, fn)` — любая async-функция + payload.
- `useFetch(url)` — `useAsyncData` + `$fetch`, ключ из URL.
- Начальные данные — composables, мутации — `$fetch`.
