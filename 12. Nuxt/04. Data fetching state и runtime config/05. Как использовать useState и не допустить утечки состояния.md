# Как использовать useState и не допустить утечки состояния

> [!NOTE]
> `useState(key, init)` — SSR-safe общее состояние Nuxt: ref, который **создаётся отдельно для каждого запроса** на сервере, передаётся клиенту через payload и разделяется всеми компонентами по ключу. Он решает две проблемы: hydration mismatch (значение, вычисленное на сервере, переиспользуется на клиенте) и **cross-request state pollution** — утечку данных между пользователями, когда состояние объявлено переменной модуля и живёт в памяти сервера между запросами. Значение должно быть сериализуемым.

## Вопрос

Как работает `useState` и почему нельзя хранить состояние в переменной модуля?

## Утечка состояния между запросами

```ts
// ✗ app/composables/useAuth.ts
const user = ref<User | null>(null);   // создаётся один раз при загрузке модуля

export function useAuth() {
  return { user };
}
```

```text
10:00:00 запрос Анны   → middleware записала user = Анна
10:00:01 запрос Бориса → user ещё Анна → Борис видит её профиль в HTML
```

В браузере это работает (там один пользователь), поэтому баг легко пропустить при разработке. На сервере модуль загружается один раз на процесс и обслуживает всех.

```ts
// ✓
export function useAuth() {
  const user = useState<User | null>("auth:user", () => null);
  return { user };
}
```

## Как работает useState

```text
сервер, запрос A: useState("auth:user") → новый ref для nuxtApp A → payload A
сервер, запрос B: useState("auth:user") → новый ref для nuxtApp B → payload B
клиент:           useState("auth:user") → значение из payload
```

```ts
const counter = useState("counter", () => 0);       // init выполнится, только если ключа ещё нет
const token = useState("token", () => crypto.randomUUID()); // одинаков на сервере и клиенте
```

## Общее состояние через composable

```ts
// app/composables/useCart.ts
export function useCart() {
  const items = useState<CartItem[]>("cart:items", () => []);
  const count = computed(() => items.value.reduce((n, i) => n + i.qty, 0));

  function add(item: CartItem) {
    items.value = [...items.value, item];
  }

  return { items, count, add };
}
```

Шапка и страница товара вызывают `useCart()` и видят одно и то же состояние.

## Ограничения

- Значение сериализуется через `devalue`: объекты, массивы, `Date`, `Map`, `Set` — да; функции, классы, DOM-узлы — нет.
- Ключ глобален: используйте префиксы (`cart:items`), чтобы не столкнуться с модулями.
- `clearNuxtState("cart:items")` сбрасывает значение (например, при выходе).

## useState или Pinia

| Задача | Выбор |
| --- | --- |
| Несколько простых значений: пользователь, тема, флаги | `useState` |
| Сложная доменная модель с действиями, геттерами, DevTools | Pinia (`@pinia/nuxt`) |
| Значение для SSR, которое не должно меняться при гидрации | `useState` |
| Сохранение в `localStorage` | Pinia + persisted state или `useCookie` |

Pinia в Nuxt тоже создаёт отдельный store на запрос и передаёт состояние через payload — см. [Pinia в Nuxt](<09. Как использовать Pinia в Nuxt.md>).

## Что ещё может утечь

- Синглтон-клиент с токеном пользователя на уровне модуля.
- Кэш в `Map` на уровне модуля, ключи которого не учитывают пользователя.
- Мутация общих констант (`DEFAULTS.user = ...`).

На сервере безопасно хранить в модуле только то, что одинаково для всех: конфигурацию, пулы соединений, кэш публичных данных.

## Частые ошибки

- `ref` на уровне модуля в composable.
- Хранить в `useState` функции и экземпляры классов.
- Одинаковые ключи для разных данных.
- Хранить в `useState` секреты — они попадут в HTML.

## Что важно помнить

- `useState` = `ref` + изоляция по запросу + передача через payload.
- Утечка состояния между запросами — проблема безопасности, а не только корректности.
- Всё в `useState` видно в исходном коде страницы.

## Мини-шпаргалка

- `useState<T>(key, () => init)`.
- Никаких `ref` на уровне модуля.
- Только сериализуемые значения.
- `clearNuxtState(key)` — сброс.
- Сложное — Pinia.
