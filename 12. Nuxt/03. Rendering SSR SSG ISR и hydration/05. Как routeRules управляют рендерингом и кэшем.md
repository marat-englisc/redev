# Как routeRules управляют рендерингом и кэшем

> [!NOTE]
> `routeRules` — карта «шаблон пути → правила» в `nuxt.config.ts`, на которой построен **гибридный рендеринг**. Для каждого маршрута (страницы или API) можно задать: `prerender`, `ssr: false`, `swr` (кэш с фоновым обновлением в хранилище Nitro), `isr` (кэш CDN на Vercel/Netlify), `cache` (тонкая настройка), `redirect`, `headers`, `cors`, `proxy`, `noScripts`, `appMiddleware`. Правила применяет Nitro, и часть из них превращается в настройки платформы при деплое.

## Вопрос

Как работают `routeRules` и какие правила можно задавать?

## Пример

```ts
export default defineNuxtConfig({
  routeRules: {
    // рендеринг
    "/": { prerender: true },
    "/blog/**": { swr: 3600 },
    "/products/**": { isr: 600 },
    "/admin/**": { ssr: false },

    // HTTP
    "/old-blog/**": { redirect: { to: "/blog/**", statusCode: 301 } },
    "/_nuxt/**": { headers: { "cache-control": "public, max-age=31536000, immutable" } },
    "/api/public/**": { cors: true, cache: { maxAge: 60 } },
    "/api/legacy/**": { proxy: "https://legacy.example.com/**" },

    // прочее
    "/terms": { prerender: true, noScripts: true },     // статичный HTML без JS
  },
});
```

## Справочник правил

| Правило | Что делает |
| --- | --- |
| `prerender: true` | Сгенерировать при сборке |
| `ssr: false` | Рендерить в браузере (SPA) |
| `swr: number \| true` | Кэшировать ответ на N секунд, по истечении отдавать устаревший и обновлять в фоне |
| `isr: number \| true` | Кэш на CDN платформы (Vercel, Netlify); без поддержки платформы используйте `swr` |
| `cache: { maxAge, swr, varies, ... }` | Детальная настройка серверного кэша |
| `redirect` | Редирект (по умолчанию 307) |
| `headers` | Добавить заголовки ответа |
| `cors: true` | CORS-заголовки для API |
| `proxy` | Проксировать запрос на другой адрес |
| `noScripts: true` | Не подключать JS Nuxt — чистый HTML |
| `appMiddleware` | Включить или выключить route middleware для пути |
| `robots: false` | С модулем Nuxt Robots: `noindex` для раздела |

## Как сопоставляются пути

- `**` — любая вложенность, `*` — один сегмент.
- Более специфичное правило перекрывает общее; правила для одного пути сливаются.

```ts
routeRules: {
  "/blog/**": { swr: 3600 },
  "/blog/drafts/**": { swr: false, robots: false },
}
```

## Где хранится кэш swr

По умолчанию — в памяти процесса Nitro: при нескольких экземплярах у каждого свой кэш, и он сбрасывается при перезапуске. Для production подключают общее хранилище:

```ts
export default defineNuxtConfig({
  nitro: {
    storage: {
      cache: { driver: "redis", url: process.env.REDIS_URL },
    },
  },
});
```

## Опасный пример

```ts
routeRules: {
  "/account/**": { swr: 3600 },   // ✗ HTML первого пользователя увидят все
}
```

Кэшируемый HTML не должен зависеть от cookie и сессии. Если часть страницы персональная — загружайте её на клиенте, а каркас кэшируйте.

## Частые ошибки

- Кэшировать персональные страницы.
- Ставить `isr` на хостинге без его поддержки и считать, что кэш работает.
- Забывать, что in-memory кэш не общий для реплик.
- Перекрывать правила неочевидно — проверяйте итог в Nuxt DevTools.

## Что важно помнить

- `routeRules` — единая точка управления рендерингом, кэшем и HTTP-поведением маршрутов.
- Правила работают и для страниц, и для `server/api`.
- Сравнение стратегий — в уроке [SSR, CSR, SSG, ISR и SWR](<02. Чем отличаются SSR, CSR, SSG, ISR и SWR.md>), серверный кэш — в [кэшировании Nitro](<../05. Server API Nitro и deployment/07. Как работает caching в Nitro.md>).

## Мини-шпаргалка

- `prerender`, `ssr: false`, `swr`, `isr` — рендеринг.
- `redirect`, `headers`, `cors`, `proxy` — HTTP.
- `**` — любая глубина, специфичное правило важнее.
- Кэш swr — в памяти, для реплик — Redis.
- Персональное не кэшировать.
