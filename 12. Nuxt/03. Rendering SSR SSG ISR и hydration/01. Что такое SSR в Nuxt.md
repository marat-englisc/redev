# Что такое SSR в Nuxt

> [!NOTE]
> **SSR (Server-Side Rendering)** — сервер на каждый запрос выполняет `setup` страницы, загружает данные, рендерит Vue-компоненты в HTML и отправляет готовую разметку вместе с **payload** (сериализованным состоянием). Браузер сразу показывает контент, затем загружает JS и выполняет **гидрацию** — Vue «оживляет» существующий DOM, не перерисовывая его. В Nuxt SSR включён по умолчанию (`ssr: true`). Плюсы — SEO, быстрый первый контент, данные и секреты на сервере; цена — нагрузка на сервер, TTFB и требование SSR-safe кода.

## Вопрос

Что такое SSR в Nuxt и как он работает?

## Как проходит запрос

```text
GET /products
  │
  ├─ сервер: плагины → route middleware → setup страницы
  │          → await useFetch('/api/products') (вызов обработчика напрямую, без HTTP)
  │          → renderToString → HTML + payload
  ▼
браузер: показывает HTML (FCP, LCP)
  │
  ├─ загружает JS-чанки
  ├─ плагины → middleware → setup (useFetch берёт данные из payload, запроса нет)
  └─ гидрация: обработчики событий привязаны → страница интерактивна
  ▼
дальнейшие переходы — клиентские, как в SPA
```

## Пример

```vue
<script setup lang="ts">
const { data: products } = await useFetch("/api/products");
</script>

<template>
  <ul>
    <li v-for="p in products" :key="p.id">{{ p.title }}</li>
  </ul>
</template>
```

В ответе сервера уже есть `<li>` с названиями товаров — поисковик и пользователь видят контент до загрузки JS.

## Плюсы и минусы

| Плюсы | Минусы |
| --- | --- |
| Контент в HTML — SEO и превью в соцсетях | Нужен сервер (Node, serverless, edge) |
| Быстрый первый контент на слабых устройствах | Рендер на каждый запрос увеличивает TTFB |
| Запросы к API идут из дата-центра, а не из браузера | Код должен работать без `window` и `document` |
| Секреты и токены остаются на сервере | Риск hydration mismatch |
| Работает без JS для чтения контента | Страница видна, но не интерактивна до гидрации |

## Что выполняется на сервере

На сервере выполняются: `setup`, `useFetch`/`useAsyncData`, плагины, route middleware, `onServerPrefetch`. **Не** выполняются: `onMounted`, `onUpdated`, `onBeforeUnmount`, обработчики событий. Поэтому работа с DOM переносится в `onMounted`.

## Оптимизация SSR

- Кэшировать рендер публичных страниц через `routeRules` (`swr`, `isr`, `prerender`).
- Загружать данные параллельно (`Promise.all` или несколько `useFetch` без последовательных `await`).
- Не блокировать рендер второстепенными данными: `lazy: true` или загрузка на клиенте с `server: false`.
- Откладывать гидрацию тяжёлых компонентов (`hydrate-on-visible`).

## Частые ошибки

- Обращаться к `window`, `localStorage` в `setup`.
- Загружать данные в `onMounted` — их нет в HTML, SEO-эффект SSR теряется.
- Последовательные `await useFetch` для независимых данных — растёт TTFB.
- Отключать SSR целиком из-за одной браузерной библиотеки.

## Что важно помнить

- SSR в Nuxt — только первый запрос; навигация дальше идёт на клиенте.
- Гидрация не перерисовывает DOM, а сверяет его с виртуальным деревом — поэтому HTML сервера и первый рендер клиента должны совпадать.
- Время до интерактивности определяется размером JS и стоимостью гидрации, а не только скоростью сервера.

## Мини-шпаргалка

- Сервер: setup → данные → HTML + payload.
- Клиент: HTML → JS → гидрация.
- `onMounted` — только клиент.
- Кэш рендера — `routeRules`.
- Независимые запросы — параллельно.
