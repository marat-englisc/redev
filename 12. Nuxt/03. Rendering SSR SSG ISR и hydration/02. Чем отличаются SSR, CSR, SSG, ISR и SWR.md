# Чем отличаются SSR, CSR, SSG, ISR и SWR

> [!NOTE]
> Это стратегии того, **когда и где** формируется HTML. **SSR** — на сервере на каждый запрос: свежо, но дорого. **CSR** — в браузере: дёшево для сервера, но пустой первый HTML. **SSG/prerender** — один раз при сборке: максимально быстро и дёшево, но данные устаревают до следующей сборки. **SWR** — кэш отрендеренного ответа: отдаём сохранённую версию сразу и обновляем её в фоне. **ISR** — то же на уровне CDN платформы (Vercel, Netlify). В Nuxt их смешивают по маршрутам через `routeRules`.

## Вопрос

Чем отличаются SSR, CSR, SSG, ISR и SWR и как выбрать стратегию?

## Простыми словами

| Стратегия | Аналогия |
| --- | --- |
| SSR | Повар готовит блюдо под каждый заказ |
| SSG | Блюда приготовлены заранее утром и ждут на витрине |
| SWR / ISR | Блюдо с витрины отдают сразу, а повар тем временем готовит свежее для следующего гостя |
| CSR | Гостю выдают продукты и рецепт — готовит сам |

## Как работает каждая

```text
SSR:   запрос → рендер на сервере → ответ                       (всегда свежо)
CSR:   запрос → пустой HTML → JS → данные → рендер в браузере
SSG:   сборка → HTML-файлы на CDN → запрос → готовый файл       (свежо на момент сборки)
SWR:   запрос → кэш есть? → отдать кэш, в фоне перерендерить     (свежо с задержкой ≤ TTL)
ISR:   то же, но кэш хранит CDN платформы, переживает деплой
```

## Настройка в Nuxt

```ts
export default defineNuxtConfig({
  routeRules: {
    "/": { prerender: true },              // SSG
    "/blog/**": { isr: 3600 },             // ISR (Vercel, Netlify)
    "/products/**": { swr: 600 },          // SWR: кэш на 10 минут
    "/account/**": { ssr: true },          // SSR (по умолчанию)
    "/admin/**": { ssr: false },           // CSR
  },
});
```

## Сравнение

| | SSR | CSR | SSG | SWR | ISR |
| --- | --- | --- | --- | --- | --- |
| Где рендер | Сервер, каждый запрос | Браузер | Сборка | Сервер, раз в TTL | Сервер, раз в TTL |
| Свежесть | Полная | Полная | До сборки | ≤ TTL | ≤ TTL |
| TTFB | Средний/высокий | Низкий | Минимальный | Низкий | Минимальный |
| SEO | Да | Слабо | Да | Да | Да |
| Нагрузка на сервер | Высокая | Нет | Нет | Низкая | Минимальная |
| Персонализация | Да | Да | Нет | Нет | Нет |
| Нужен сервер | Да | Нет | Нет | Да | Платформа |

## Как выбрать

| Тип страницы | Стратегия |
| --- | --- |
| Лендинг, «О компании», документация | SSG |
| Статьи блога, карточки товаров | SWR или ISR, либо SSG + пересборка по вебхуку CMS |
| Поиск, фильтры с query-параметрами | SSR |
| Личный кабинет, корзина | SSR без кэша или CSR |
| Админка, дашборд за логином | CSR |

## Главное ограничение кэша

SWR, ISR и SSG отдают **один и тот же HTML всем пользователям**. Если страница зависит от cookie, сессии или геолокации, её нельзя кэшировать общим кэшем — иначе пользователь увидит чужие данные. Персональные части страницы загружают на клиенте (`useFetch` с `server: false`) или делают страницу SSR без кэша.

## Частые ошибки

- Включить `swr` для `/account/**`.
- Использовать SSG для тысяч товаров с ценами, меняющимися каждый час.
- Выбирать CSR для публичных страниц, которым нужно SEO.
- Ожидать, что `isr` будет работать на любом хостинге так же, как на Vercel.

## Что важно помнить

- Выбор — компромисс между свежестью, скоростью, стоимостью и персонализацией.
- Гидрация происходит при любой стратегии, кроме CSR: HTML от сервера или CDN всё равно «оживляется» JS.
- Детали настройки — в уроке про [routeRules](<05. Как routeRules управляют рендерингом и кэшем.md>).

## Мини-шпаргалка

- SSR — на запрос, CSR — в браузере, SSG — при сборке.
- SWR — кэш + фоновое обновление, ISR — то же на CDN.
- Кэш общий для всех — не для персональных страниц.
- Всё смешивается через `routeRules`.
