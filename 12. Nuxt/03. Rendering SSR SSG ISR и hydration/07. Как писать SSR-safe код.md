# Как писать SSR-safe код

> [!NOTE]
> SSR-safe код не предполагает, что выполняется в браузере, и не хранит состояние запроса глобально. На сервере нет `window`, `document`, `localStorage`, `navigator`, поэтому браузерный код переносят в `onMounted`, в проверку `import.meta.client`, в компоненты `.client.vue` / `<ClientOnly>` или в плагины `*.client.ts`. Первый рендер должен быть детерминированным, а общее состояние — создаваться через `useState`/Pinia, а не переменной модуля, иначе данные одного пользователя утекут другому.

## Вопрос

Как писать код, который корректно работает при SSR в Nuxt?

## Правило 1: браузерные API — только на клиенте

```ts
// ✗ упадёт на сервере: window is not defined
const width = window.innerWidth;
```

```ts
// ✓ хук жизненного цикла, который на сервере не вызывается
const width = ref(0);
onMounted(() => {
  width.value = window.innerWidth;
});

// ✓ проверка окружения
if (import.meta.client) {
  localStorage.setItem("visited", "1");
}
```

Для типичных задач есть готовые SSR-safe composables из VueUse (`useWindowSize`, `useMediaQuery`, `useLocalStorage`) — они безопасно возвращают значения по умолчанию на сервере.

## Правило 2: изолировать браузерные компоненты и библиотеки

```vue
<ClientOnly>
  <RichTextEditor v-model="text" />
  <template #fallback><EditorSkeleton /></template>
</ClientOnly>
```

```text
app/components/Map.client.vue      → только в браузере
app/plugins/chart-lib.client.ts    → библиотека, которая трогает window при импорте
```

Если библиотека обращается к `window` прямо при импорте, импортируйте её динамически внутри `onMounted`:

```ts
onMounted(async () => {
  const { default: Chart } = await import("chart.js/auto");
  new Chart(canvas.value!, config);
});
```

## Правило 3: детерминированный первый рендер

- Без `Date.now()`, `Math.random()` в шаблоне — `useState` или `useId()`.
- Тема, язык, авторизация — в cookie (`useCookie`), а не в `localStorage`: сервер их видит.
- Явный часовой пояс при форматировании дат.

## Правило 4: никакого состояния на уровне модуля

```ts
// ✗ app/composables/useUser.ts
const user = ref<User | null>(null);      // создаётся ОДИН раз на процесс сервера
export const useUser = () => user;          // все запросы делят одного пользователя
```

```ts
// ✓
export const useUser = () => useState<User | null>("user", () => null);
```

Переменная модуля на сервере живёт между запросами — классическая утечка данных между пользователями (cross-request state pollution). Подробнее — в [уроке про useState](<../04. Data fetching state и runtime config/05. Как использовать useState и не допустить утечки состояния.md>).

## Правило 5: данные — через SSR-aware API

Загрузку данных для первого рендера делают через `useFetch`/`useAsyncData`, а не через `$fetch` в `setup` или в `onMounted`: иначе двойной запрос или пустой HTML.

## Только сервер

```ts
if (import.meta.server) {
  const headers = useRequestHeaders(["cookie", "accept-language"]);
}
```

Код в `server/` и компоненты `.server.vue` вообще не попадают в браузер.

## Частые ошибки

- Отключать SSR из-за одной библиотеки вместо `<ClientOnly>`.
- Использовать `process.client` (устаревшее) вместо `import.meta.client`.
- Синглтон-клиент с данными пользователя на уровне модуля.
- `v-if="isMobile"` по `window.innerWidth` при SSR — mismatch; лучше CSS media queries.

## Что важно помнить

- Каждый `setup` выполняется дважды: на сервере и в браузере — пишите код для обоих.
- Адаптивность решайте CSS, а не JS, где это возможно.
- Глобальное состояние на сервере — уязвимость, а не просто баг.

## Мини-шпаргалка

- `onMounted`, `import.meta.client` — браузерный код.
- `<ClientOnly>`, `.client.vue`, `*.client.ts`.
- Динамический `import()` для библиотек с `window`.
- `useState`/Pinia вместо переменных модуля.
- `useCookie` вместо `localStorage` для SSR-важных значений.
