# Как обрабатывать ошибки в server routes

> [!NOTE]
> В обработчиках Nitro ошибку **бросают** через `throw createError({ statusCode, statusMessage, data })`: клиент получит JSON с кодом и сообщением, а `useFetch` положит его в `error` (`error.value.statusCode`, `error.value.data`). Необработанное исключение превращается в 500 без деталей в production. Бизнес-ошибки возвращают с правильным HTTP-статусом (400, 401, 403, 404, 409, 422), а не `200 { ok: false }`. Ошибки валидации из `readValidatedBody` дают 400 автоматически. Логирование и отправку в Sentry делают в хуке `error`.

## Вопрос

Как правильно обрабатывать и возвращать ошибки в серверных маршрутах Nuxt?

## Бросить ошибку

```ts
// server/api/products/[id].get.ts
export default defineEventHandler(async (event) => {
  const id = Number(getRouterParam(event, "id"));
  const product = await findProduct(id);

  if (!product) {
    throw createError({ statusCode: 404, statusMessage: "Product not found" });
  }
  return product;
});
```

```ts
// бизнес-ошибка с деталями
throw createError({
  statusCode: 409,
  statusMessage: "Conflict",
  data: { code: "OUT_OF_STOCK", available: 0 },
});
```

## Ответ клиенту

```json
{
  "statusCode": 409,
  "statusMessage": "Conflict",
  "message": "Conflict",
  "data": { "code": "OUT_OF_STOCK", "available": 0 }
}
```

## Обработка на клиенте

```ts
const { data, error } = await useFetch(() => `/api/products/${id.value}`);

if (error.value?.statusCode === 404) {
  throw createError({ statusCode: 404, fatal: true }); // показать страницу 404
}
```

```ts
try {
  await $fetch("/api/cart", { method: "POST", body: { productId } });
} catch (err) {
  const e = err as FetchError<{ data: { code: string } }>;
  if (e.data?.data?.code === "OUT_OF_STOCK") toast.error("Товар закончился");
  else throw err;
}
```

## Коды ответов

| Код | Когда |
| --- | --- |
| 400 | Невалидный запрос, ошибка схемы |
| 401 | Нет аутентификации |
| 403 | Аутентифицирован, но нет прав |
| 404 | Ресурс не найден |
| 409 | Конфликт состояния |
| 422 | Данные корректны по формату, но нарушают бизнес-правила |
| 429 | Превышен лимит запросов |
| 500 | Непредвиденная ошибка сервера |

## Ошибки валидации

```ts
const body = await readValidatedBody(event, schema.parse);
// при ошибке: 400 + детали ZodError в data
```

Если детали ошибок валидации нужны в особом формате (например, `{ field: message }` для формы), используйте `schema.safeParse` и бросайте `createError` с нужным `data`.

## Непредвиденные ошибки

```ts
export default defineEventHandler(async () => {
  await db.query("..."); // упало соединение → 500
});
```

В production клиент получит общий `500 Server Error` без стека. Логируйте централизованно:

```ts
// server/plugins/errors.ts
export default defineNitroPlugin((nitroApp) => {
  nitroApp.hooks.hook("error", (error, { event }) => {
    logger.error({ err: error, path: event?.path, requestId: event?.context.requestId });
  });
});
```

## Частые ошибки

- `return { ok: false, error: "..." }` со статусом 200.
- Отдавать клиенту текст исключения БД или стек.
- Путать 401 и 403.
- Ловить все ошибки `try/catch` и возвращать 200, теряя мониторинг.

## Что важно помнить

- `createError` — единый способ ошибок и на сервере, и в Vue-приложении.
- Машиночитаемый код (`data.code`) удобнее для UI, чем разбор текста сообщения.
- Ошибки страниц (`error.vue`) — отдельная тема: см. [обработку ошибок страниц](<../02. Структура проекта и роутинг/11. Как обрабатывать ошибки страниц - error.vue, createError и NuxtErrorBoundary.md>).

## Мини-шпаргалка

- `throw createError({ statusCode, statusMessage, data })`.
- Клиент: `error.value.statusCode`, `error.value.data`.
- Правильные статусы, не `200 { ok: false }`.
- Валидация → 400 автоматически.
- Логи — хук `error` в Nitro plugin.
