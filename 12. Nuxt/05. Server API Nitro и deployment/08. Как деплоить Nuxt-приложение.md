# Как деплоить Nuxt-приложение

> [!NOTE]
> `nuxt build` собирает самодостаточный каталог `.output/`: `public/` — статика, `server/` — Nitro-сервер со всеми зависимостями (на сервере не нужен `node_modules` проекта). Запуск на Node.js — `node .output/server/index.mjs` с переменными `PORT`, `HOST` и `NUXT_*`. Под конкретную платформу сборку адаптирует **Nitro preset** (`vercel`, `netlify`, `cloudflare_pages`, `node-server`, `bun`...) — на CI популярных платформ он выбирается автоматически. Полностью статический сайт — `nuxt generate` и любой CDN, но без `server/api`.

## Вопрос

Как собрать и задеплоить Nuxt-приложение?

## Варианты деплоя

| Вариант | Команда | Где | Server API |
| --- | --- | --- | --- |
| Node.js-сервер | `nuxt build` | VPS, Docker, Render, Fly.io | Да |
| Serverless | `nuxt build` + preset | Vercel, Netlify, AWS Lambda | Да |
| Edge | `nuxt build` + preset | Cloudflare Workers/Pages | Да, с ограничениями edge |
| Статика | `nuxt generate` | GitHub Pages, S3 + CDN | Нет |

## Node.js

```bash
npm run build
PORT=3000 NUXT_API_SECRET=... node .output/server/index.mjs
```

```text
.output/
├── public/        # _nuxt/*.js, картинки, prerender-страницы
├── server/
│   ├── index.mjs  # точка входа
│   └── node_modules/  # только нужные серверу зависимости (трассировка)
└── nitro.json
```

Перед Node.js обычно ставят reverse proxy (Nginx, Caddy) для HTTPS, сжатия и раздачи `public/` напрямую.

## Docker

```dockerfile
FROM node:24-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:24-alpine
WORKDIR /app
ENV NODE_ENV=production HOST=0.0.0.0 PORT=3000
COPY --from=build --chown=node:node /app/.output ./.output
USER node
EXPOSE 3000
CMD ["node", ".output/server/index.mjs"]
```

Финальный образ содержит только `.output` — зависимости уже внутри. Подробнее о Docker — в разделе [Docker](<../../13. Docker/06. Frontend Backend и базы в Docker/01. Как упаковать Node.js-приложение в Docker.md>).

## Платформы и presets

```ts
export default defineNuxtConfig({
  nitro: {
    preset: "cloudflare_pages", // обычно не нужно: определяется по переменным окружения CI
  },
});
```

```bash
NITRO_PRESET=netlify nuxt build
```

На Vercel и Netlify `routeRules` (`isr`, `swr`, `redirect`, `headers`) превращаются в настройки CDN платформы.

## Чек-лист перед деплоем

- Переменные `NUXT_*` заданы в окружении (`.env` в production не читается).
- Секреты не в `runtimeConfig.public`.
- `routeRules` не кэшируют персональные страницы.
- Хранилище кэша и сессий общее для реплик (Redis), если экземпляров несколько.
- Для edge-preset в `server/` нет Node-специфичного кода (`fs`, нативные модули).
- `nuxt preview` и Lighthouse локально прошли без ошибок.
- Healthcheck-эндпоинт (`/api/health`) для балансировщика.

## Частые ошибки

- Копировать на сервер весь проект и `node_modules` вместо `.output`.
- Ожидать работы `server/api` после `nuxt generate`.
- Запускать production через `nuxt dev` или `nuxt preview`.
- Не задать `HOST=0.0.0.0` в контейнере.

## Что важно помнить

- `.output/` — артефакт сборки, его и деплоят.
- Preset определяет формат сервера; код приложения при этом не меняется.
- Гибрид работает везде, но `isr` раскрывается полностью на платформах с поддержкой.

## Мини-шпаргалка

- `nuxt build` → `.output/`, запуск `node .output/server/index.mjs`.
- `nuxt generate` → статика без API.
- `nitro.preset` / `NITRO_PRESET`.
- `PORT`, `HOST`, `NUXT_*` — при запуске.
