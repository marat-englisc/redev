# Как сделать авторизацию и передавать cookies при SSR

> [!NOTE]
> В Nuxt сессию хранят в **cookie** (лучше httpOnly), а не в `localStorage`: при SSR сервер должен знать пользователя, чтобы отрендерить правильный HTML. Типичная схема — **BFF**: `server/api/auth/login` проверяет логин, ставит зашифрованную httpOnly-cookie сессии (модуль `nuxt-auth-utils` или Better Auth), защищённые API читают её через `requireUserSession(event)`, а UI — через `useUserSession()`. Главная ловушка SSR: `$fetch` на сервере **не передаёт cookies браузера** во внешний API — для этого нужны `useRequestFetch()` или `useRequestHeaders(["cookie"])`; `useFetch` к собственным `/api` делает это сам.

## Вопрос

Как реализовать авторизацию в Nuxt и почему при SSR «теряются» cookies?

## Схема BFF с httpOnly-cookie

```text
браузер ──POST /api/auth/login──▶ Nitro: проверка пароля → Set-Cookie: nuxt-session (httpOnly, secure)
браузер ──GET /account (cookie)──▶ SSR: сессия из cookie → HTML для этого пользователя
браузер ──GET /api/orders (cookie)──▶ requireUserSession → данные пользователя
```

Токен никогда не доступен JavaScript в браузере — XSS не сможет его украсть.

## nuxt-auth-utils

```bash
npx nuxt module add auth-utils
```

```env
NUXT_SESSION_PASSWORD=минимум-32-символа-случайной-строки
```

```ts
// server/api/auth/login.post.ts
import { z } from "zod";

export default defineEventHandler(async (event) => {
  const { email, password } = await readValidatedBody(
    event,
    z.object({ email: z.string().email(), password: z.string().min(8) }).parse,
  );

  const user = await db.query.users.findFirst({ where: eq(users.email, email) });
  if (!user || !(await verifyPassword(user.passwordHash, password))) {
    throw createError({ statusCode: 401, statusMessage: "Неверный email или пароль" });
  }

  await setUserSession(event, { user: { id: user.id, name: user.name, role: user.role } });
  return { ok: true };
});
```

```ts
// server/api/orders.get.ts
export default defineEventHandler(async (event) => {
  const { user } = await requireUserSession(event); // 401, если сессии нет
  return db.query.orders.findMany({ where: eq(orders.userId, user.id) });
});
```

```vue
<script setup lang="ts">
const { loggedIn, user, clear, fetch: refreshSession } = useUserSession();

async function login(form: { email: string; password: string }) {
  await $fetch("/api/auth/login", { method: "POST", body: form });
  await refreshSession();
  await navigateTo("/account");
}
</script>
```

Альтернативы: Better Auth (сессии, OAuth, 2FA в одном пакете), Sidebase Nuxt Auth, собственная реализация на `useSession` из h3.

## Проблема cookies при SSR

```text
браузер ──(cookie)──▶ Nuxt SSR ──$fetch("https://api.example.com/me")──▶ внешний API
                                   ^ cookie браузера сюда НЕ попадает
```

Сервер Nuxt — отдельный HTTP-клиент; передавать cookies пользователя в произвольные запросы автоматически было бы небезопасно (SSRF, утечка сессии). Поэтому:

```ts
// 1. useFetch к СВОИМ маршрутам /api/* сам пробрасывает cookie и заголовки
const { data: me } = await useFetch("/api/me");

// 2. $fetch внутри useAsyncData — через useRequestFetch
const requestFetch = useRequestFetch();
const { data } = await useAsyncData("me", () => requestFetch("/api/me"));

// 3. внешний API — передать заголовки явно
const headers = useRequestHeaders(["cookie"]);
const { data: profile } = await useFetch("https://api.example.com/me", { headers });
```

И в обратную сторону: если внешний API на SSR вернул `Set-Cookie`, он не дойдёт до браузера сам — его нужно переслать вручную (`appendResponseHeader(event, "set-cookie", ...)`). Поэтому логин и обновление токена удобнее делать через собственный `server/api`.

## Защита на трёх уровнях

| Уровень | Как |
| --- | --- |
| Страницы | Route middleware: `if (!loggedIn.value) return navigateTo("/login")` |
| API | `requireUserSession(event)` в каждом защищённом обработчике или server middleware |
| Данные | Проверка владельца: `where userId = session.user.id` |

Route middleware — только UX. Без проверки на сервере данные доступны прямым запросом.

## CSRF

Cookie отправляется браузером автоматически, поэтому мутирующие запросы нужно защищать: `sameSite: "lax"`/`"strict"`, проверка заголовка `Origin`, CSRF-токен (модуль `nuxt-csurf` или Nuxt Security). `nuxt-auth-utils` по умолчанию ставит `sameSite: "lax"`.

## Частые ошибки

- Токен в `localStorage` — SSR рендерит гостевую версию, клиент перерисовывает (mismatch, мерцание).
- `$fetch` к внешнему API на сервере без проброса cookie — пользователь «разлогинен» в HTML.
- Защищать только страницы, а не API.
- Хранить в сессии лишнее: cookie ограничена ~4 КБ и отправляется с каждым запросом.
- Кэшировать (`swr`) страницы, зависящие от сессии.

## Что важно помнить

- Для SSR авторизация живёт в cookie — это единственное, что сервер получает с первым запросом.
- `useFetch("/api/...")` пробрасывает cookie сам, остальным запросам нужен `useRequestFetch`/`useRequestHeaders`.
- Проверка прав всегда на сервере, middleware страниц — дополнение.

## Мини-шпаргалка

- httpOnly-cookie + BFF.
- `nuxt-auth-utils`: `setUserSession`, `requireUserSession`, `useUserSession`.
- `useRequestFetch()`, `useRequestHeaders(["cookie"])`.
- Страницы — middleware, API — `requireUserSession`, данные — фильтр по владельцу.
- CSRF: `sameSite`, `Origin`, токен.
