# Git: понятный конспект и шпаргалка

Git — распределённая система контроля версий. Она хранит историю проекта, помогает безопасно экспериментировать в ветках и позволяет нескольким разработчикам работать над одним кодом.

> [!NOTE]
> Git не сохраняет каждое изменение автоматически. Коммит создаётся только из тех изменений, которые разработчик предварительно добавил в staging area.

## Маршрут изучения

1. Разобраться с четырьмя состояниями проекта.
2. Научиться выполнять цикл `status → add → commit`.
3. Освоить ветки и слияние.
4. Подключить удалённый репозиторий.
5. Научиться безопасно отменять изменения.
6. Разобраться с конфликтами, `merge` и `rebase`.

## Как Git видит проект

```text
Рабочая папка ── git add ──> Staging area ── git commit ──> Локальный репозиторий
      ↑                         │                                  │
      └──── git restore ────────┘                                  └── git push ──> Удалённый репозиторий
```

| Область | Что в ней находится |
| --- | --- |
| Рабочая папка | Файлы, которые сейчас открыты и изменяются |
| Staging area, или index | Изменения, выбранные для следующего коммита |
| Локальный репозиторий | История коммитов внутри папки `.git` |
| Удалённый репозиторий | Общая копия проекта на GitHub, GitLab или другом сервере |

### Состояния файла

| Состояние | Значение |
| --- | --- |
| `untracked` | Git ещё не отслеживает новый файл |
| `modified` | Отслеживаемый файл изменён |
| `staged` | Изменения добавлены в staging area |
| `committed` | Изменения сохранены в локальной истории |

## Первоначальная настройка

Настрой имя и почту, которые будут записываться в коммиты:

```bash
git config --global user.name "Marat"
git config --global user.email "example@gmail.com"
git config --global init.defaultBranch main
```

Проверить настройки:

```bash
git config --list
git config user.name
git config user.email
```

Флаг `--global` применяет настройку ко всем репозиториям пользователя. Без него команда меняет конфигурацию только текущего репозитория.

## Создание и получение репозитория

### Новый локальный репозиторий

```bash
git init
git status
```

`git init` создаёт скрытую папку `.git`. Выполнять эту команду повторно при каждом запуске проекта не нужно.

### Клонирование существующего проекта

```bash
git clone https://github.com/user/project.git
cd project
```

`git clone` скачивает файлы, историю, ветки и автоматически добавляет удалённый репозиторий с именем `origin`.

## Первый коммит

```bash
git status
git add README.md
git diff --staged
git commit -m "docs: add project description"
```

Что произошло:

1. `git status` показал состояние файлов.
2. `git add` выбрал изменение для следующего коммита.
3. `git diff --staged` показал содержимое будущего коммита.
4. `git commit` создал снимок в локальной истории.

> [!TIP]
> Коммит должен содержать одно логически завершённое изменение. Небольшие тематические коммиты проще проверять, отменять и переносить между ветками.

## Ежедневный цикл работы

```bash
git status
git diff
git add -p
git diff --staged
git commit -m "feat: add profile form"
git push
```

`git add -p` позволяет просмотреть изменения частями и выбрать только нужные фрагменты. Это помогает не добавлять в коммит отладочный код и случайные правки.

### Перед коммитом проверь

- относятся ли все изменения к одной задаче;
- не попали ли в diff пароли, токены и файлы `.env`;
- проходят ли линтер, тесты и сборка;
- понятно ли сообщение коммита без дополнительного контекста.

## Работа со staging area

| Команда | Что делает |
| --- | --- |
| `git add file.js` | Добавляет конкретный файл |
| `git add src/` | Добавляет изменения внутри папки `src` |
| `git add .` | Добавляет изменения из текущей папки и её вложенных папок |
| `git add -A` | Добавляет все новые, изменённые и удалённые файлы репозитория |
| `git add -u` | Добавляет изменения и удаления отслеживаемых файлов, но не новые файлы |
| `git add -p` | Позволяет выбирать отдельные фрагменты изменений |
| `git restore --staged file.js` | Убирает файл из staging area, не удаляя правки |

> [!WARNING]
> Перед `git add .` или `git add -A` всегда выполняй `git status`. Команда может добавить временные файлы, сборку или секреты, если они не исключены через `.gitignore`.

## Просмотр изменений и истории

```bash
git status
git diff
git diff --staged
git log --oneline --graph --decorate --all
git show <commit>
```

| Команда | Результат |
| --- | --- |
| `git diff` | Неиндексированные изменения в рабочей папке |
| `git diff --staged` | Изменения, подготовленные к коммиту |
| `git diff main...feature/profile` | Разница между общей точкой ветвления и feature-веткой |
| `git show <commit>` | Содержимое и метаданные выбранного коммита |
| `git blame file.js` | Автор и коммит для каждой строки файла |

`HEAD` — указатель на текущий коммит. Обычно он указывает на последний коммит активной ветки.

## Ветки

Ветка — подвижный указатель на цепочку коммитов. Она позволяет разрабатывать функцию или исправление отдельно от `main`.

### Основные команды

```bash
git branch
git switch -c feature/profile
git switch main
git branch -d feature/profile
```

| Команда | Что делает |
| --- | --- |
| `git branch` | Показывает локальные ветки |
| `git branch --all` | Показывает локальные и remote-tracking ветки |
| `git switch <branch>` | Переключает на существующую ветку |
| `git switch -c <branch>` | Создаёт ветку и переключает на неё |
| `git branch -m <new-name>` | Переименовывает текущую ветку |
| `git branch -d <branch>` | Безопасно удаляет уже слитую ветку |
| `git branch -D <branch>` | Принудительно удаляет локальную ветку |

В старых материалах часто встречается `git checkout -b feature/profile`. Современный и более понятный аналог — `git switch -c feature/profile`. Команда `checkout` всё ещё работает, но одновременно решает несколько разных задач.

### Имена веток

```text
feature/user-profile
fix/login-validation
refactor/api-client
docs/git-guide
```

Используй короткое имя без пробелов, которое объясняет назначение ветки.

## Слияние веток

Чтобы влить `feature/profile` в `main`:

```bash
git switch main
git merge feature/profile
```

Git может выполнить:

- **fast-forward** — просто передвинуть указатель `main`, если ветки не расходились;
- **merge commit** — создать отдельный коммит слияния, если обе ветки развивались независимо;
- **conflict** — остановить слияние, если одни строки были несовместимо изменены с двух сторон.

Отменить незавершённое слияние:

```bash
git merge --abort
```

## Удалённый репозиторий

Проверить подключённые серверы:

```bash
git remote -v
```

Подключить GitHub-репозиторий к существующему локальному проекту:

```bash
git remote add origin https://github.com/user/project.git
git push -u origin main
```

Первая отправка новой ветки:

```bash
git push -u origin feature/profile
```

Флаг `-u` связывает локальную ветку с удалённой. После этого достаточно выполнять `git push` и `git pull` без указания имён.

### `fetch`, `pull` и `push`

| Команда | Что делает |
| --- | --- |
| `git fetch origin` | Загружает сведения о новых коммитах, но не меняет рабочую ветку |
| `git pull` | Выполняет `fetch`, затем интегрирует изменения в текущую ветку |
| `git pull --ff-only` | Обновляет ветку только без создания merge-коммита |
| `git pull --rebase` | Переносит локальные коммиты поверх обновлённой удалённой ветки |
| `git push` | Отправляет локальные коммиты в связанную удалённую ветку |

`git fetch` безопасно использовать для проверки состояния сервера: он не изменяет рабочие файлы.

## Типовой сценарий работы над задачей

### 1. Получить свежую основную ветку

```bash
git switch main
git pull --ff-only
```

### 2. Создать отдельную ветку

```bash
git switch -c feature/user-profile
```

### 3. Сделать и проверить коммиты

```bash
git status
git add -p
git diff --staged
git commit -m "feat: add user profile"
```

### 4. Отправить ветку и создать pull request

```bash
git push -u origin feature/user-profile
```

После ревью ветка сливается в `main` через интерфейс GitHub или GitLab. Локальную ветку затем можно удалить:

```bash
git switch main
git pull --ff-only
git branch -d feature/user-profile
```

## Merge и rebase

Обе команды интегрируют изменения, но делают это по-разному.

| Критерий | `merge` | `rebase` |
| --- | --- | --- |
| История | Сохраняет реальное разветвление | Делает историю линейной |
| Коммиты | Может создать merge-коммит | Пересоздаёт коммиты с новыми hash |
| Безопасность | Подходит для общих веток | Подходит прежде всего для локальных коммитов |
| Конфликты | Обычно решаются один раз | Могут возникать при переносе каждого коммита |

Обновить feature-ветку через rebase:

```bash
git switch feature/user-profile
git fetch origin
git rebase origin/main
```

Продолжить или отменить rebase:

```bash
git rebase --continue
git rebase --abort
```

> [!WARNING]
> Не выполняй rebase коммитов, которыми уже пользуются другие разработчики. Rebase переписывает историю. После rebase собственной опубликованной ветки используй `git push --force-with-lease`, а не `git push --force`.

## Разрешение конфликтов

При конфликте Git отмечает проблемный участок:

```text
<<<<<<< HEAD
текущая версия
=======
версия из другой ветки
>>>>>>> feature/profile
```

Порядок действий:

1. Выполни `git status` и найди конфликтующие файлы.
2. Выбери правильный вариант или объедини изменения вручную.
3. Удали маркеры `<<<<<<<`, `=======` и `>>>>>>>`.
4. Проверь код и выполни `git add <file>`.
5. Заверши операцию через `git commit` или `git rebase --continue`.

> [!TIP]
> Не выбирай автоматически «текущую» или «входящую» версию, пока не понял обе стороны конфликта. Синтаксически корректный результат может нарушить бизнес-логику.

## Отмена изменений

Сначала выполни `git status` и определи, где находится изменение: в рабочей папке, staging area, локальном коммите или уже на сервере.

| Ситуация | Команда | Результат |
| --- | --- | --- |
| Убрать файл из staging area | `git restore --staged file.js` | Правки остаются в файле |
| Отменить незакоммиченные правки | `git restore file.js` | Файл возвращается к состоянию последнего коммита |
| Исправить последний локальный коммит | `git commit --amend` | Последний коммит пересоздаётся |
| Безопасно отменить опубликованный коммит | `git revert <commit>` | Создаётся новый обратный коммит |
| Перенести отдельный коммит в текущую ветку | `git cherry-pick <commit>` | Создаётся копия выбранного изменения |

> [!WARNING]
> `git restore file.js` безвозвратно удаляет незакоммиченные изменения этого файла. Перед выполнением проверь путь и при необходимости используй `git stash`.

### Варианты `git reset`

`reset` обычно используют только для локальной, ещё не опубликованной истории.

| Команда | HEAD | Staging | Рабочие файлы |
| --- | --- | --- | --- |
| `git reset --soft HEAD~1` | Перемещает | Сохраняет | Сохраняет |
| `git reset HEAD~1` | Перемещает | Очищает | Сохраняет |
| `git reset --hard HEAD~1` | Перемещает | Очищает | Удаляет изменения |

> [!DANGER]
> `git reset --hard`, `git clean` и принудительный push могут удалить работу. Не копируй такие команды вслепую и не применяй их к общей ветке.

## Временное сохранение через stash

Stash полезен, когда нужно временно убрать незавершённые изменения и переключиться на другую задачу.

```bash
git stash push -m "WIP: profile form"
git stash list
git stash pop
```

Дополнительные команды:

| Команда | Что делает |
| --- | --- |
| `git stash apply stash@{0}` | Применяет stash, но сохраняет его в списке |
| `git stash pop` | Применяет последний stash и удаляет его из списка |
| `git stash drop stash@{0}` | Удаляет выбранный stash |
| `git stash push -u` | Сохраняет также новые неотслеживаемые файлы |

Stash не заменяет коммиты и не предназначен для долговременного хранения важной работы.

## `.gitignore` и секреты

Пример для frontend- и Node.js-проекта:

```gitignore
node_modules/
dist/
coverage/
.env
.env.*
!.env.example
.DS_Store
*.log
```

`.gitignore` действует только на неотслеживаемые файлы. Если файл уже добавлен в Git, убери его из index, не удаляя локальную копию:

```bash
git rm --cached .env
```

> [!WARNING]
> Если секрет уже попал в коммит или был отправлен на сервер, одного удаления файла недостаточно. Считай секрет скомпрометированным и немедленно отзови или замени его.

## Сообщения коммитов

Хорошее сообщение кратко отвечает на вопрос: «Что изменится после применения этого коммита?»

```text
feat: add profile editing
fix: prevent duplicate form submission
refactor: extract API client
test: cover token refresh
docs: explain Git workflow
chore: update dependencies
```

Часто используемые типы Conventional Commits:

| Тип | Назначение |
| --- | --- |
| `feat` | Новая возможность |
| `fix` | Исправление ошибки |
| `refactor` | Изменение структуры без новой функциональности |
| `test` | Добавление или изменение тестов |
| `docs` | Документация |
| `chore` | Служебные изменения |

Формат Conventional Commits полезен, но применять его нужно только если команда договорилась о таком стандарте.

## Частые вопросы на собеседовании

| Вопрос | Короткий ответ |
| --- | --- |
| Чем Git отличается от GitHub? | Git хранит версии локально; GitHub размещает удалённые репозитории и инструменты совместной работы |
| Что такое staging area? | Промежуточная область, из которой формируется следующий коммит |
| Чем `fetch` отличается от `pull`? | `fetch` только загружает данные, `pull` сразу интегрирует их в текущую ветку |
| Чем `merge` отличается от `rebase`? | `merge` сохраняет ветвление, `rebase` переносит и пересоздаёт коммиты |
| Чем `revert` отличается от `reset`? | `revert` добавляет обратный коммит, `reset` перемещает указатель и может переписать историю |
| Что такое `HEAD`? | Указатель на текущий коммит или активную ветку |
| Почему `.gitignore` не скрывает файл? | Git уже отслеживает файл, поэтому его нужно убрать из index |
| Что такое detached HEAD? | Состояние, когда `HEAD` указывает прямо на коммит, а не на ветку |
| Когда нужен `cherry-pick`? | Когда требуется перенести отдельный коммит без слияния всей ветки |
| Почему опасен force push? | Он может переписать удалённую историю и удалить чужие коммиты |

## Практическое упражнение

1. Создай пустую папку и выполни `git init`.
2. Создай `README.md`, добавь его через `git add` и сделай первый коммит.
3. Создай ветку `feature/about`, измени файл и сделай второй коммит.
4. Вернись в `main` и выполни `git merge feature/about`.
5. Посмотри историю через `git log --oneline --graph --decorate --all`.
6. Создай ещё одно изменение, добавь его в staging и верни через `git restore --staged`.
7. Спрячь незавершённую работу через `git stash`, затем восстанови через `git stash pop`.

После упражнения попробуй объяснить вслух, в какой области находились изменения после каждого шага.
