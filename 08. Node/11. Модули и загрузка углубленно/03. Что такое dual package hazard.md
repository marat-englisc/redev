# Что такое dual package hazard?

> [!NOTE]
> Dual package hazard - проблема пакетов, которые одновременно отдают CommonJS и ES Module версии. Если обе версии загружаются в одном приложении, могут появиться два разных экземпляра одного и того же состояния.

## Вопрос

Что такое dual package hazard и как его избежать?

## Проблема

Пакет экспортирует две версии:

```json
{
  "exports": {
    ".": {
      "import": "./index.js",
      "require": "./index.cjs"
    }
  }
}
```

ESM-код загружает `index.js`, а CJS-код загружает `index.cjs`.

Если внутри есть состояние:

```js
let count = 0;

export function increment() {
  count += 1;
  return count;
}
```

то ESM и CJS могут работать с разными копиями.

## Почему это опасно?

Особенно неприятно, если пакет хранит:

- singleton;
- кэш;
- connection pool;
- DI container;
- глобальные настройки.

## Как снижать риск?

Подходы:

- иметь один общий implementation-файл;
- делать CJS-обертку вокруг ESM или наоборот;
- избегать изменяемого глобального состояния;
- тестировать смешанное использование `import` и `require`.

## Собеседовательный ответ

Проблема не в том, что CJS и ESM нельзя смешивать. Проблема в том, что разные entry points могут привести к разным экземплярам пакета.

## Что важно помнить

- Если пакет отдает отдельные ESM- и CJS-сборки, в приложении могут загрузиться две копии с разным состоянием.
- Проявления: два singleton-а, `instanceof` перестает работать между копиями.
- Решения: ESM-обертка над CJS-реализацией, хранение состояния в одном модуле или выпуск только ESM.
- Поддержка `require(esm)` в современных Node.js уменьшает необходимость в двойных сборках.

## Мини-шпаргалка

- Dual package - пакет с ESM и CJS entry points.
- Hazard - риск двух независимых экземпляров состояния.
- Особенно опасно для singleton и кэшей.
- Решение - общий implementation и аккуратные wrappers.
- В приложениях проще придерживаться одного module system.
