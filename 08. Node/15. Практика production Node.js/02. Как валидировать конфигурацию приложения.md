# Как валидировать конфигурацию приложения?

> [!NOTE]
> Конфигурацию Node.js-приложения лучше собирать в одном модуле и валидировать при старте. Это позволяет упасть сразу с понятной ошибкой, а не получить странный runtime-баг под нагрузкой.

## Вопрос

Как валидировать конфигурацию приложения при запуске?

## Плохой подход

```js
const dbUrl = process.env.DATABASE_URL;
```

Если переменная отсутствует, ошибка может проявиться позже и в другом месте.

## Хороший подход

```js
function getRequiredEnv(name) {
  const value = process.env[name];

  if (!value) {
    throw new Error(`Missing environment variable: ${name}`);
  }

  return value;
}

export const config = {
  port: Number(process.env.PORT || 3000),
  databaseUrl: getRequiredEnv('DATABASE_URL'),
  jwtSecret: getRequiredEnv('JWT_SECRET'),
};
```

## Что проверять?

| Тип | Проверка |
|---|---|
| number | число и допустимый диапазон |
| url | валидный URL |
| enum | одно из разрешенных значений |
| secret | не пустой |
| boolean | явный парсинг строки |

## Библиотеки

В проектах часто используют `zod`, `joi`, `envalid` или похожие инструменты, чтобы описать схему конфига.

## Что важно помнить

- Проверяйте конфигурацию один раз при старте и падайте сразу (fail fast).
- Описывайте схему через Zod, Valibot или envalid — получите и проверку, и типы.
- Остальной код импортирует готовый типизированный объект `config`, а не `process.env`.
- Не печатайте значения секретов в сообщениях об ошибках.

## Мини-шпаргалка

- Конфиг лучше держать в одном модуле.
- Env значения являются строками.
- Ошибки конфига нужно ловить при старте.
- Секреты проверяй на наличие, но не печатай в лог.
- Для крупных проектов удобно использовать schema validation.
