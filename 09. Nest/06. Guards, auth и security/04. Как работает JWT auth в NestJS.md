# Как работает JWT auth в NestJS

> [!NOTE]
> **JWT (JSON Web Token)** — подписанный токен `header.payload.signature`, внутри которого лежат утверждения (claims): `sub` (id пользователя), `exp` (срок действия), роли и т. д. Сервер проверяет подпись и срок **без похода в базу**, поэтому JWT удобен для stateless API и микросервисов. Payload **не шифруется**, а лишь кодируется base64url — секретов в нём быть не должно. Стандартная схема: короткоживущий **access token** (5–15 минут) в заголовке `Authorization: Bearer`, и долгоживущий **refresh token** (дни–недели), который хранится в `httpOnly`-cookie, лежит в БД в виде хеша и **ротируется** при каждом обновлении (повторное использование старого refresh-токена — признак кражи → отозвать всю цепочку). В NestJS токены выпускает и проверяет `JwtService` из `@nestjs/jwt`, а защищает маршруты guard (свой или Passport `jwt`).

## Вопрос

Как реализовать JWT-аутентификацию в NestJS?

## Выпуск токенов

```ts
@Injectable()
export class TokenService {
  constructor(private readonly jwt: JwtService, private readonly config: ConfigService, private readonly prisma: PrismaService) {}

  async issue(user: { id: string; role: Role }) {
    const accessToken = await this.jwt.signAsync(
      { sub: user.id, role: user.role },
      { secret: this.config.getOrThrow('JWT_ACCESS_SECRET'), expiresIn: '15m' },
    );

    const refreshToken = randomBytes(48).toString('base64url');          // непрозрачный refresh
    await this.prisma.refreshToken.create({
      data: { userId: user.id, tokenHash: sha256(refreshToken), expiresAt: addDays(new Date(), 30) },
    });

    return { accessToken, refreshToken };
  }

  verifyAccess(token: string) {
    return this.jwt.verifyAsync<{ sub: string; role: Role }>(token, {
      secret: this.config.getOrThrow('JWT_ACCESS_SECRET'),
      algorithms: ['HS256'],
    });
  }
}
```

## Guard

```ts
@Injectable()
export class JwtAuthGuard implements CanActivate {
  constructor(private readonly tokens: TokenService, private readonly reflector: Reflector) {}

  async canActivate(ctx: ExecutionContext) {
    if (this.reflector.getAllAndOverride(Public, [ctx.getHandler(), ctx.getClass()])) return true;

    const req = ctx.switchToHttp().getRequest();
    const [type, token] = (req.headers.authorization ?? '').split(' ');
    if (type !== 'Bearer' || !token) throw new UnauthorizedException();

    try {
      const payload = await this.tokens.verifyAccess(token);
      req.user = { id: payload.sub, role: payload.role };
      return true;
    } catch {
      throw new UnauthorizedException('Invalid or expired token');
    }
  }
}
```

## Ротация refresh-токена

```ts
async refresh(rawRefresh: string) {
  const stored = await this.prisma.refreshToken.findUnique({ where: { tokenHash: sha256(rawRefresh) } });
  if (!stored || stored.expiresAt < new Date()) throw new UnauthorizedException();

  if (stored.revokedAt) {
    // повторное использование уже использованного токена → вероятная кража
    await this.prisma.refreshToken.updateMany({ where: { userId: stored.userId }, data: { revokedAt: new Date() } });
    throw new UnauthorizedException();
  }

  await this.prisma.refreshToken.update({ where: { id: stored.id }, data: { revokedAt: new Date() } });
  const user = await this.users.findById(stored.userId);
  return this.issue(user);
}
```

## Поток

```text
POST /auth/login    → { accessToken } + Set-Cookie: refresh_token (httpOnly, path=/auth)
GET  /api/orders    Authorization: Bearer <access>  → 200
...access истёк     → 401
POST /auth/refresh  (cookie)  → новый access + новый refresh (старый отозван)
POST /auth/logout   → refresh отозван, cookie очищена
```

## Что класть в payload

| Да | Нет |
| --- | --- |
| `sub`, `role`, `tenantId`, `sessionId` | Пароли, хеши, персональные данные |
| Минимум для авторизации без БД | Часто меняющиеся данные (баланс, тариф) |

## Отзыв доступа

Access-токен нельзя «отозвать» до истечения `exp` — поэтому он короткий. Если нужна немедленная блокировка (бан, смена пароля): хранить `tokenVersion` пользователя и сверять, или проверять `sessionId` в кеше/БД, или использовать сессии вместо JWT.

## JWT или сессии

| JWT | Серверные сессии |
| --- | --- |
| Stateless, удобно для микросервисов и мобильных клиентов | Простой мгновенный отзыв |
| Сложнее отзыв, нужен refresh-механизм | Нужен общий store (Redis/БД) |
| Риск больших токенов в каждом запросе | Cookie маленькая, данные на сервере |

## Частые ошибки

- Долгоживущий access-токен (дни) без refresh-механизма.
- Хранить access/refresh в `localStorage` — доступны любому XSS-скрипту.
- Один секрет для разных типов токенов; слабый секрет.
- Не ограничивать `algorithms` и не проверять `exp`.
- Хранить refresh-токен в БД в открытом виде.

## Что важно помнить

- JWT подписан, но не зашифрован.
- Короткий access + ротируемый refresh в `httpOnly`-cookie.
- Отзыв — через короткий срок, версии токенов или сессии.

## Мини-шпаргалка

- `JwtModule.register({})`, `jwt.signAsync(payload, { secret, expiresIn })`.
- `jwt.verifyAsync(token, { secret, algorithms })`.
- `Authorization: Bearer <token>` → 401 при ошибке.
- Refresh: хеш в БД, ротация, детект повторного использования.
