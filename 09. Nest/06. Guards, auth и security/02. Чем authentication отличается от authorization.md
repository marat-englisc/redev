# Чем authentication отличается от authorization

> [!NOTE]
> **Authentication (аутентификация)** отвечает на вопрос **«кто ты?»**: проверка учётных данных или токена/сессии и установление личности пользователя. Ошибка — **401 Unauthorized** (несмотря на название, это именно «не аутентифицирован»). **Authorization (авторизация)** отвечает на вопрос **«что тебе можно?»**: проверка прав уже известного пользователя на действие или ресурс. Ошибка — **403 Forbidden** (или 404, чтобы не раскрывать существование чужого ресурса). В NestJS аутентификацию обычно делает первый guard (JWT, сессия, API-ключ, Better Auth), кладущий пользователя в `request.user`; авторизацию — следующие guards (роли, права) и **сервисы** (проверка владельца ресурса, бизнес-правила). Модели авторизации: **RBAC** (роли), **ABAC/PBAC** (атрибуты и политики, например CASL), **ReBAC** (отношения: «участник проекта»).

## Вопрос

Чем аутентификация отличается от авторизации и как они реализуются в NestJS?

## Сравнение

| | Authentication | Authorization |
| --- | --- | --- |
| Вопрос | Кто ты? | Что тебе можно? |
| Вход | Пароль, токен, сессия, ключ | Пользователь + действие + ресурс |
| Ошибка | 401 | 403 (или 404) |
| В NestJS | `AuthGuard`, Passport-стратегии, Better Auth | `RolesGuard`, `PoliciesGuard`, проверки в сервисе |
| Порядок | Первой | После аутентификации |

## Цепочка в NestJS

```ts
@Controller('projects')
@UseGuards(JwtAuthGuard, RolesGuard)          // 1. кто ты  2. есть ли роль
export class ProjectsController {
  constructor(private readonly projects: ProjectsService) {}

  @Roles(['member', 'admin'])
  @Patch(':id')
  update(@Param('id') id: string, @Body() dto: UpdateProjectDto, @CurrentUser() user: AuthUser) {
    return this.projects.update(id, dto, user);   // 3. владеешь ли этим проектом — в сервисе
  }
}

@Injectable()
export class ProjectsService {
  async update(id: string, dto: UpdateProjectDto, user: AuthUser) {
    const project = await this.repo.findById(id);
    if (!project || (project.ownerId !== user.id && user.role !== 'admin')) {
      throw new NotFoundException();               // не раскрываем чужие проекты
    }
    return this.repo.update(id, dto);
  }
}
```

## Модели авторизации

| Модель | Идея | Пример |
| --- | --- | --- |
| RBAC | Права по ролям | `admin`, `editor`, `viewer` |
| ABAC / PBAC | Политики по атрибутам пользователя, ресурса, контекста | «Редактировать можно свои статьи в статусе draft» |
| ReBAC | Права через отношения | «Участник организации видит её проекты» |

```ts
// CASL — политики в коде
const ability = defineAbilityFor(user);
if (ability.cannot('update', subject('Article', article))) throw new ForbiddenException();
```

## Где проверять владельца

- В guard — если ресурс легко получить по параметру и проверка единообразна (`OrderOwnerGuard`).
- В сервисе — если нужно загрузить ресурс всё равно, а правила зависят от его состояния (чаще всего).
- В запросе к БД — фильтр `where: { id, ownerId: user.id }` защищает и от ошибок в коде.

## IDOR

**Insecure Direct Object Reference** — классическая уязвимость: аутентифицированный пользователь меняет `id` в URL и получает чужие данные, потому что проверена только аутентификация. Защита — авторизация **каждого** доступа к ресурсу, а не только наличия токена.

## Частые ошибки

- Считать, что `JwtAuthGuard` = авторизация.
- 403 при отсутствии токена (должно быть 401).
- Проверять права только на фронтенде.
- Роли зашиты строками по всему коду без единого справочника.

## Что важно помнить

- Аутентификация — личность (401), авторизация — права (403/404).
- Сначала аутентификация, затем роли и политики, затем проверка владельца.
- Каждый доступ к ресурсу должен быть авторизован (защита от IDOR).

## Мини-шпаргалка

- `JwtAuthGuard` → `request.user`.
- `RolesGuard` + `@Roles(...)`.
- Владелец — в сервисе или в `where`.
- RBAC / ABAC (CASL) / ReBAC.
