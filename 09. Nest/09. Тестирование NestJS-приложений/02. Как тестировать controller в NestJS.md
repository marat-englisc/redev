# Как тестировать controller в NestJS

> [!NOTE]
> Тонкий контроллер содержит мало логики, поэтому unit-тест контроллера проверяет немногое: что метод вызывает нужный метод сервиса с правильными аргументами (включая `@CurrentUser`, параметры и DTO) и возвращает его результат, а исключения сервиса пробрасываются. Такой тест создаёт контроллер через `Test.createTestingModule({ controllers: [X], providers: [{ provide: Service, useValue: mock }] })` и вызывает методы **напрямую** — без HTTP, поэтому guards, pipes, interceptors и filters **не выполняются**. Валидацию DTO, статусы, сериализацию, guards и формат ошибок проверяют **e2e-тестами** через HTTP (supertest). Хорошая стратегия: много unit-тестов сервисов, немного unit-тестов контроллеров (или вовсе без них) и e2e-тесты ключевых сценариев.

## Вопрос

Как тестировать контроллеры в NestJS?

## Unit-тест контроллера

```ts
describe('OrdersController', () => {
  let controller: OrdersController;
  const orders = { create: vi.fn(), findOne: vi.fn() };
  const user: AuthUser = { id: 'u1', email: 'a@x.com', roles: [Role.User] };

  beforeEach(async () => {
    vi.resetAllMocks();
    const moduleRef = await Test.createTestingModule({
      controllers: [OrdersController],
      providers: [{ provide: OrdersService, useValue: orders }],
    }).compile();
    controller = moduleRef.get(OrdersController);
  });

  it('создаёт заказ от имени текущего пользователя', async () => {
    const dto: CreateOrderDto = { items: [{ productId: 'p1', qty: 2 }] };
    orders.create.mockResolvedValue({ id: 'o1' });

    await expect(controller.create(dto, user)).resolves.toEqual({ id: 'o1' });
    expect(orders.create).toHaveBeenCalledWith('u1', dto);
  });

  it('пробрасывает NotFoundException', async () => {
    orders.findOne.mockRejectedValue(new NotFoundException());
    await expect(controller.findOne('o404', user)).rejects.toBeInstanceOf(NotFoundException);
  });
});
```

## Guards в unit-тесте контроллера

Если контроллер использует `@UseGuards(JwtAuthGuard)`, Nest при компиляции модуля попытается создать guard и его зависимости. Варианты:

```ts
await Test.createTestingModule({ controllers: [OrdersController], providers: [...] })
  .overrideGuard(JwtAuthGuard).useValue({ canActivate: () => true })
  .compile();
```

## Что проверить в контроллере, а что — в e2e

| Unit-тест контроллера | E2E-тест |
| --- | --- |
| Вызов сервиса с аргументами | Маршрут и HTTP-метод существуют |
| Передача текущего пользователя | Guards: 401 без токена, 403 без роли |
| Преобразование ответа в контроллере (если есть) | Валидация DTO: 400 и формат ошибок |
| | Статусы 201/204, заголовки, cookies |
| | Сериализация: нет `passwordHash` в ответе |

## Пример e2e-проверки того же контроллера

```ts
it('POST /orders → 400 при пустом списке товаров', () =>
  request(app.getHttpServer())
    .post('/orders')
    .set('Authorization', `Bearer ${token}`)
    .send({ items: [] })
    .expect(400));
```

## Частые ошибки

- Ожидать, что unit-тест контроллера проверит валидацию DTO — pipes не выполняются.
- Дублировать в тестах контроллера логику тестов сервиса.
- Не подменить guard — тест падает на зависимостях guard.
- Тестировать контроллер с реальным сервисом и БД под видом unit-теста.

## Что важно помнить

- Unit-тест контроллера — вызов метода напрямую, без HTTP-конвейера.
- Guards, pipes, filters, статусы — в e2e.
- Тонкие контроллеры часто достаточно покрыть e2e-тестами.

## Мини-шпаргалка

- `Test.createTestingModule({ controllers: [C], providers: [{ provide: S, useValue: mock }] })`.
- `controller.method(args)` — без HTTP.
- `.overrideGuard(G).useValue({ canActivate: () => true })`.
- HTTP-поведение — supertest.
