# Как тестировать с реальной базой данных

> [!NOTE]
> Моки репозиториев не проверяют главное в слое данных: корректность SQL/ORM-запросов, миграций, ограничений (`UNIQUE`, `FOREIGN KEY`), транзакций и индексов. Поэтому репозитории и e2e-сценарии тестируют **с настоящей СУБД той же версии, что в проде** — не SQLite вместо PostgreSQL. Удобный способ — **Testcontainers**: тест сам запускает PostgreSQL в Docker-контейнере (`new PostgreSqlContainer('postgres:18').start()`), применяет миграции и передаёт URL приложению; в CI тот же код работает без отдельной настройки. Альтернатива — сервис `postgres` в `docker compose` или в CI (`services:` в GitHub Actions). Ключевая задача — **изоляция данных** между тестами: очистка таблиц (`TRUNCATE ... RESTART IDENTITY CASCADE`), транзакция с откатом на каждый тест или отдельная база/схема на каждый параллельный воркер.

## Вопрос

Как тестировать NestJS-приложение с реальной базой данных?

## Testcontainers + Prisma

```bash
npm i -D @testcontainers/postgresql
```

```ts
// test/setup/db.ts
import { PostgreSqlContainer, StartedPostgreSqlContainer } from '@testcontainers/postgresql';
import { execSync } from 'node:child_process';

let container: StartedPostgreSqlContainer;

export async function startDb() {
  container = await new PostgreSqlContainer('postgres:18-alpine').start();
  const url = container.getConnectionUri();
  process.env.DATABASE_URL = url;
  execSync('npx prisma migrate deploy', { env: { ...process.env, DATABASE_URL: url }, stdio: 'inherit' });
  return url;
}

export async function stopDb() {
  await container?.stop();
}
```

```ts
// vitest.config.e2e.ts
export default defineConfig({
  test: {
    include: ['test/**/*.e2e-spec.ts'],
    globalSetup: ['test/setup/global.ts'],     // startDb() один раз на прогон
    pool: 'forks',
    fileParallelism: false,                    // или база на воркер
  },
});
```

## Очистка между тестами

```ts
export async function resetDb(prisma: PrismaService) {
  const tables = await prisma.$queryRaw<{ tablename: string }[]>`
    SELECT tablename FROM pg_tables WHERE schemaname = 'public' AND tablename <> '_prisma_migrations'`;
  const list = tables.map((t) => `"public"."${t.tablename}"`).join(', ');
  if (list) await prisma.$executeRawUnsafe(`TRUNCATE ${list} RESTART IDENTITY CASCADE`);
}

beforeEach(() => resetDb(app.get(PrismaService)));
```

`$executeRawUnsafe` здесь допустим: имена таблиц берутся из системного каталога, а не от пользователя.

## Тест репозитория

```ts
describe('OrdersRepository (integration)', () => {
  let moduleRef: TestingModule;
  let repo: OrdersRepository;
  let prisma: PrismaService;

  beforeAll(async () => {
    moduleRef = await Test.createTestingModule({ imports: [PrismaModule], providers: [OrdersRepository] }).compile();
    await moduleRef.init();
    repo = moduleRef.get(OrdersRepository);
    prisma = moduleRef.get(PrismaService);
  });

  beforeEach(() => resetDb(prisma));
  afterAll(() => moduleRef.close());

  it('не возвращает чужой заказ', async () => {
    const [anna, ivan] = await Promise.all([
      prisma.user.create({ data: { email: 'a@x.com', name: 'Anna' } }),
      prisma.user.create({ data: { email: 'i@x.com', name: 'Ivan' } }),
    ]);
    const order = await prisma.order.create({ data: { userId: anna.id, total: 100 } });

    await expect(repo.findByIdForUser(order.id, ivan.id)).resolves.toBeNull();
  });

  it('уникальность email обеспечивается базой', async () => {
    await prisma.user.create({ data: { email: 'a@x.com', name: 'A' } });
    await expect(prisma.user.create({ data: { email: 'a@x.com', name: 'B' } }))
      .rejects.toMatchObject({ code: 'P2002' });
  });
});
```

## Фабрики данных

```ts
export const buildUser = (over: Partial<Prisma.UserCreateInput> = {}): Prisma.UserCreateInput => ({
  email: `user-${randomUUID()}@test.local`,
  name: 'Test User',
  ...over,
});

await prisma.user.create({ data: buildUser({ role: 'ADMIN' }) });
```

Фабрики делают тесты короче и избавляют от конфликтов уникальных полей.

## CI без Testcontainers

```yaml
# .github/workflows/test.yml (фрагмент)
services:
  postgres:
    image: postgres:18-alpine
    env: { POSTGRES_PASSWORD: postgres, POSTGRES_DB: test }
    ports: ['5432:5432']
    options: >-
      --health-cmd "pg_isready -U postgres" --health-interval 5s --health-retries 10
```

## Частые ошибки

- SQLite в тестах вместо PostgreSQL — другие типы, ограничения и SQL.
- Тесты зависят от данных, оставшихся от предыдущих тестов.
- `prisma db push` вместо миграций — тесты не проверяют сами миграции.
- Параллельные воркеры пишут в одну базу без изоляции.
- Не закрывать соединения и контейнер — зависающий процесс тестов.

## Что важно помнить

- Слой данных проверяется на реальной СУБД той же версии.
- Testcontainers — база в Docker прямо из теста; в CI — `services`.
- Изоляция данных и фабрики — основа стабильных тестов.

## Мини-шпаргалка

- `new PostgreSqlContainer('postgres:18-alpine').start()`.
- `prisma migrate deploy` перед тестами.
- `TRUNCATE ... RESTART IDENTITY CASCADE` в `beforeEach`.
- `buildUser()` — фабрики с уникальными значениями.
