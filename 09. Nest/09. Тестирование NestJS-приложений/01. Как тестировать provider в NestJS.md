# Как тестировать provider в NestJS

> [!NOTE]
> Unit-тест провайдера (сервиса) проверяет его **бизнес-логику изолированно**: зависимости (репозитории, клиенты внешних API, очереди) заменяются **моками**, а сам сервис создаётся через `Test.createTestingModule({ providers: [...] }).compile()` — так тест использует настоящий DI Nest и ловит ошибки регистрации. Альтернатива для простых сервисов — создать класс напрямую `new UsersService(repoMock)`, без контейнера. В NestJS 12 новые проекты используют **Vitest** (`vi.fn()`, `vi.spyOn`), в старых — Jest (`jest.fn()`); API почти совпадает. Хороший unit-тест: проверяет поведение (результат, выброшенные исключения, вызовы зависимостей с правильными аргументами), покрывает граничные случаи и ошибки, не зависит от БД и сети. `useMocker` автоматически подставляет заглушки для всех недостающих зависимостей.

## Вопрос

Как писать unit-тесты для сервисов в NestJS?

## Сервис

```ts
@Injectable()
export class UsersService {
  constructor(private readonly repo: UsersRepository, private readonly hasher: PasswordHasher) {}

  async register(dto: CreateUserDto) {
    if (await this.repo.findByEmail(dto.email)) throw new ConflictException('Email already registered');
    const passwordHash = await this.hasher.hash(dto.password);
    return this.repo.create({ email: dto.email, name: dto.name, passwordHash });
  }
}
```

## Тест

```ts
import { Test } from '@nestjs/testing';
import { describe, it, expect, beforeEach, vi } from 'vitest';

describe('UsersService', () => {
  let service: UsersService;
  const repo = { findByEmail: vi.fn(), create: vi.fn() };
  const hasher = { hash: vi.fn() };

  beforeEach(async () => {
    vi.resetAllMocks();
    const moduleRef = await Test.createTestingModule({
      providers: [
        UsersService,
        { provide: UsersRepository, useValue: repo },
        { provide: PasswordHasher, useValue: hasher },
      ],
    }).compile();

    service = moduleRef.get(UsersService);
  });

  it('создаёт пользователя с хешем пароля', async () => {
    repo.findByEmail.mockResolvedValue(null);
    hasher.hash.mockResolvedValue('hashed');
    repo.create.mockResolvedValue({ id: 'u1', email: 'a@x.com', name: 'Ann' });

    const user = await service.register({ email: 'a@x.com', name: 'Ann', password: 'secret123' });

    expect(user.id).toBe('u1');
    expect(repo.create).toHaveBeenCalledWith({ email: 'a@x.com', name: 'Ann', passwordHash: 'hashed' });
  });

  it('бросает ConflictException для занятого email', async () => {
    repo.findByEmail.mockResolvedValue({ id: 'u0' });

    await expect(service.register({ email: 'a@x.com', name: 'Ann', password: 'x' }))
      .rejects.toBeInstanceOf(ConflictException);
    expect(repo.create).not.toHaveBeenCalled();
  });
});
```

## useMocker

```ts
const moduleRef = await Test.createTestingModule({ providers: [OrdersService] })
  .useMocker((token) => {
    if (token === PaymentsGateway) return { charge: vi.fn().mockResolvedValue({ id: 'ch_1' }) };
    if (typeof token === 'function') return createMock(token);   // например, из @golevelup/ts-vitest
  })
  .compile();
```

## Без контейнера

```ts
const service = new PricingService(configMock as unknown as ConfigService);
```

Быстрее и проще, но не проверяет регистрацию провайдеров и инъекцию по токенам.

## Время и случайность

```ts
vi.useFakeTimers();
vi.setSystemTime(new Date('2026-10-24T10:00:00Z'));
// ...
vi.useRealTimers();
```

Для id и времени удобно внедрять `Clock`/`IdGenerator` как провайдеры, чтобы подменять их в тестах.

## Что тестировать

| Да | Нет |
| --- | --- |
| Ветвления бизнес-логики | Что фреймворк вызывает конструктор |
| Исключения и граничные значения | Внутреннюю реализацию (порядок приватных вызовов) |
| Вызовы зависимостей с правильными аргументами | ORM-запросы как строки |
| Преобразование данных | Тривиальные геттеры |

Запросы к БД проверяют интеграционными тестами с реальной базой — см. [тестирование с БД](<06. Как тестировать с реальной базой данных.md>).

## Частые ошибки

- Мок без сброса между тестами — тесты влияют друг на друга.
- Тестировать мок, а не сервис (проверять только, что мок вернул то, что ему сказали).
- Мокать Prisma цепочками `prisma.user.findUnique` в каждом тесте вместо репозитория-абстракции.
- Пропускать негативные сценарии.

## Что важно помнить

- Unit-тест сервиса: реальный класс + моки зависимостей.
- `Test.createTestingModule` проверяет и DI; `useMocker` — авто-заглушки.
- В NestJS 12 по умолчанию Vitest.

## Мини-шпаргалка

- `Test.createTestingModule({ providers: [S, { provide: Dep, useValue: mock }] }).compile()`.
- `moduleRef.get(S)`.
- `vi.fn().mockResolvedValue(x)`, `expect(...).rejects.toBeInstanceOf(E)`.
- `vi.resetAllMocks()` в `beforeEach`.
