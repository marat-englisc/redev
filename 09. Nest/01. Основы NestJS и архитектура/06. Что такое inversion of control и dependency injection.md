# Что такое inversion of control и dependency injection

> [!NOTE]
> **Inversion of Control (IoC)** — принцип, при котором объект не создаёт свои зависимости и не управляет их жизненным циклом сам: это делает внешний код — **контейнер**. **Dependency Injection (DI)** — конкретный способ реализовать IoC: зависимости **передаются** объекту снаружи, обычно через конструктор. В NestJS класс помечается `@Injectable()` и регистрируется в `providers` модуля; когда кому-то нужен экземпляр, контейнер находит провайдер по токену (классу), создаёт его (рекурсивно разрешая его собственные зависимости), кеширует как синглтон и внедряет. Выгоды: слабая связанность, подмена реализаций (в тестах — моков, в проде — разных адаптеров), централизованное управление временем жизни. Обратная сторона — «магия»: ошибки разрешения зависимостей видны только при старте приложения.

## Вопрос

Что такое IoC и DI и как они работают в NestJS?

## Без DI

```ts
export class OrdersService {
  private readonly mailer = new SmtpMailer('smtp://...');   // жёсткая связь
  private readonly repo = new OrdersRepository(new Pool()); // создаёт подключение сам

  async create(dto: CreateOrderDto) { ... }
}
```

Проблемы: нельзя подменить почту в тестах, у каждого сервиса свой пул соединений, конфигурация зашита в код.

## С DI

```ts
@Injectable()
export class OrdersService {
  constructor(
    private readonly repo: OrdersRepository,
    private readonly mailer: MailService,
  ) {}
}

@Module({
  providers: [OrdersService, OrdersRepository, MailService],
})
export class OrdersModule {}
```

`OrdersService` объявляет, **что** ему нужно, а **как** это создать, решает контейнер.

## Как контейнер разрешает зависимости

```text
1. Nest сканирует модули и регистрирует провайдеры по токенам (класс = токен)
2. Нужен OrdersService → смотрит design:paramtypes: [OrdersRepository, MailService]
3. Рекурсивно создаёт OrdersRepository (ему нужен PrismaService) и MailService
4. Кладёт экземпляры в кеш модуля (singleton) и внедряет
```

## Подмена в тестах

```ts
const moduleRef = await Test.createTestingModule({
  providers: [
    OrdersService,
    { provide: OrdersRepository, useValue: { create: vi.fn() } },
    { provide: MailService, useValue: { send: vi.fn() } },
  ],
}).compile();

const service = moduleRef.get(OrdersService);
```

## Подмена реализаций

```ts
{
  provide: MailService,
  useClass: process.env.NODE_ENV === 'production' ? SmtpMailService : ConsoleMailService,
}
```

## DI, Service Locator и new

| Подход | Плюсы | Минусы |
| --- | --- | --- |
| `new` внутри класса | Просто | Жёсткая связь, нет подмены |
| Service Locator (`container.get(X)` внутри методов) | Гибко | Скрытые зависимости |
| Constructor DI | Зависимости видны в конструкторе, легко тестировать | Нужен контейнер |

## Частые ошибки

- `new SomeService()` вручную внутри провайдера — обход контейнера, потеря синглтона и подмены.
- Слишком много зависимостей в конструкторе (10+) — сервис делает слишком много.
- Внедрять интерфейс без токена.
- Ожидать, что DI проверяется на этапе компиляции — ошибки появятся только при старте.

## Что важно помнить

- IoC — принцип, DI — способ его реализации.
- Nest разрешает зависимости по токенам и типам конструктора.
- Главный практический выигрыш — тестируемость и подмена реализаций.

## Мини-шпаргалка

- `@Injectable()` + `providers: [...]`.
- Внедрение через конструктор.
- `Test.createTestingModule` + `useValue` — моки.
- По умолчанию провайдеры — синглтоны.
