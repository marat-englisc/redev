# Что такое модульная архитектура NestJS

> [!NOTE]
> Приложение NestJS — это **граф модулей** с корнем в `AppModule`. Модуль (`@Module`) объединяет код одной области: контроллеры, провайдеры, импорты других модулей и экспорты. Провайдеры модуля **инкапсулированы**: другие модули видят только то, что явно перечислено в `exports`, и только если импортировали модуль. Это даёт явные границы между фичами и делает зависимости видимыми прямо в коде. Типичное деление: **feature-модули** по доменным областям (`UsersModule`, `OrdersModule`), **инфраструктурные** (`DatabaseModule`, `MailModule`), **общие** (`CommonModule` с утилитами) и конфигурация в корне. Хорошая модульная структура позволяет развиваться как **модульный монолит** и при необходимости выделять модуль в отдельный сервис.

## Вопрос

Что такое модульная архитектура NestJS и как делить приложение на модули?

## Граф модулей

```text
AppModule
├── ConfigModule (global)
├── DatabaseModule ──► exports PrismaService
├── UsersModule    ──► imports DatabaseModule, exports UsersService
├── OrdersModule   ──► imports DatabaseModule, UsersModule
└── AuthModule     ──► imports UsersModule
```

## Пример

```ts
@Module({
  imports: [DatabaseModule],
  controllers: [UsersController],
  providers: [UsersService, UsersRepository],
  exports: [UsersService],               // UsersRepository остаётся внутренним
})
export class UsersModule {}

@Module({
  imports: [DatabaseModule, UsersModule],
  controllers: [OrdersController],
  providers: [OrdersService],
})
export class OrdersModule {}

@Module({
  imports: [ConfigModule.forRoot({ isGlobal: true }), UsersModule, OrdersModule, AuthModule],
})
export class AppModule {}
```

`OrdersService` может внедрить `UsersService`, но не `UsersRepository` — он не экспортирован.

## Виды модулей

| Вид | Пример | Особенность |
| --- | --- | --- |
| Корневой | `AppModule` | Собирает приложение |
| Feature | `UsersModule`, `OrdersModule` | Доменная область, свои контроллеры |
| Инфраструктурный | `DatabaseModule`, `RedisModule` | Экспортирует клиенты и адаптеры |
| Shared | `CommonModule` | Переиспользуемые провайдеры |
| Динамический | `ConfigModule.forRoot()` | Настраивается при импорте ([dynamic module](<../03. Модули, провайдеры и Dependency Injection/07. Что такое dynamic module.md>)) |
| Глобальный | `@Global()` | Экспорты доступны без импорта — использовать умеренно |

## Как делить на модули

- По **доменным областям**, а не по техническим слоям (`UsersModule`, а не `ControllersModule`).
- Модуль экспортирует **минимальный публичный API** (сервис-фасад), скрывая репозитории и детали.
- Зависимости направлены в одну сторону; циклы (`Users ↔ Orders`) — сигнал выделить общий модуль или использовать события.
- Инфраструктура (БД, кеш, почта) — отдельные модули, которые импортируют фичи.

## Модули — синглтоны

Модуль создаётся один раз, и его провайдеры по умолчанию — синглтоны. Если `DatabaseModule` импортирован в десять фич, `PrismaService` всё равно один.

## Частые ошибки

- Один гигантский `AppModule` со всеми провайдерами.
- Экспортировать всё подряд — границы модулей теряют смысл.
- Объявлять один и тот же провайдер в `providers` нескольких модулей — появляются разные экземпляры.
- Делать всё `@Global()`, чтобы «не мучиться с импортами».

## Что важно помнить

- Приложение — граф модулей, корень — `AppModule`.
- Провайдеры видны снаружи только через `exports` + `imports`.
- Делите по доменам, экспортируйте минимум.

## Мини-шпаргалка

- `@Module({ imports, controllers, providers, exports })`.
- Экспорт провайдера → доступен импортирующим модулям.
- Повторно экспортировать модуль: `exports: [DatabaseModule]`.
- Циклы — признак неудачных границ.
