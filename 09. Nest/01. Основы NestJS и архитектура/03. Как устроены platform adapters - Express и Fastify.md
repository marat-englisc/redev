# Как устроены platform adapters - Express и Fastify

> [!NOTE]
> NestJS не реализует HTTP-сервер сам — он работает через **platform adapter**, обёртку над конкретным HTTP-фреймворком. По умолчанию используется `@nestjs/platform-express` (Express 5 в актуальных версиях); альтернатива — `@nestjs/platform-fastify`, который заметно быстрее на «голом» HTTP и даёт встроенную схему сериализации, но несовместим с Express-middleware и библиотеками, завязанными на `req`/`res` Express. Код контроллеров, сервисов, guards и pipes одинаков для обоих адаптеров, если не обращаться к платформенным объектам напрямую (`@Req()`, `@Res()`, `app.use`). Поэтому платформенно-зависимый код держат в минимуме и изолируют.

## Вопрос

Что такое platform adapter и чем отличаются Express и Fastify в NestJS?

## Express (по умолчанию)

```ts
import { NestFactory } from '@nestjs/core';
import { NestExpressApplication } from '@nestjs/platform-express';

const app = await NestFactory.create<NestExpressApplication>(AppModule);
app.set('trust proxy', 1);          // Express-специфичная настройка
await app.listen(3000);
```

## Fastify

```bash
npm install @nestjs/platform-fastify
```

```ts
import { FastifyAdapter, NestFastifyApplication } from '@nestjs/platform-fastify';

const app = await NestFactory.create<NestFastifyApplication>(
  AppModule,
  new FastifyAdapter({ logger: false, trustProxy: true }),
);
await app.register(import('@fastify/helmet'));    // плагины Fastify вместо Express middleware
await app.listen(3000, '0.0.0.0');                // по умолчанию Fastify слушает только localhost
```

## Сравнение

| | Express | Fastify |
| --- | --- | --- |
| Пакет | `@nestjs/platform-express` | `@nestjs/platform-fastify` |
| Производительность | Достаточная для большинства API | Выше на простых запросах |
| Экосистема middleware | Огромная (`helmet`, `cookie-parser`, `multer`) | Свои плагины (`@fastify/helmet`, `@fastify/cookie`, `@fastify/multipart`) |
| Загрузка файлов в Nest | `FileInterceptor` из коробки | Нужен `@fastify/multipart` и своя обвязка |
| `listen` в Docker | `0.0.0.0` по умолчанию | Нужно явно `'0.0.0.0'` |
| Совместимость сторонних Nest-библиотек | Почти всегда | Иногда ограничена |

## Платформенно-независимый код

```ts
// ✓ работает на обоих адаптерах
@Get(':id')
findOne(@Param('id', ParseIntPipe) id: number) {
  return this.usersService.findOne(id);
}

// ✗ привязано к Express
@Get()
legacy(@Req() req: express.Request, @Res() res: express.Response) {
  res.json(...);
}
```

Если нужен доступ к адаптеру, используют `HttpAdapterHost`:

```ts
constructor(private readonly adapterHost: HttpAdapterHost) {}
// this.adapterHost.httpAdapter.reply(response, body, status)
```

Так пишут, например, глобальный exception filter, работающий с любой платформой.

## Когда переходить на Fastify

- Профилирование показывает, что узкое место — HTTP-слой, а не база.
- Проект новый и не зависит от Express-middleware.
- Команда готова использовать плагины Fastify.

В типичном CRUD-API выигрыш от Fastify меньше, чем от индексов и кеша.

## Частые ошибки

- Переключиться на Fastify и получить сломанные Express-middleware.
- Забыть `'0.0.0.0'` в контейнере с Fastify — сервис недоступен извне.
- Использовать `@Res()` и Express-типы в коде, который должен быть переносимым.

## Что важно помнить

- Адаптер — мост между Nest и HTTP-фреймворком.
- Express — по умолчанию и максимально совместим, Fastify — быстрее, но со своей экосистемой.
- Бизнес-код не должен зависеть от платформы.

## Мини-шпаргалка

- `NestFactory.create<NestExpressApplication>(AppModule)`.
- `new FastifyAdapter()` + `NestFastifyApplication`.
- `HttpAdapterHost` — платформенно-независимый доступ.
- Fastify: `app.listen(port, '0.0.0.0')`.
