# Как NestJS использует TypeScript и decorators

> [!NOTE]
> NestJS построен на **декораторах** TypeScript: `@Module`, `@Controller`, `@Get`, `@Injectable`, `@Body` не выполняют логику сами, а **записывают метаданные** в классы, методы и параметры (через `reflect-metadata`). При старте Nest читает эти метаданные и строит граф модулей, роутинг и DI. Ключевой механизм DI — опция компилятора `emitDecoratorMetadata`: TypeScript сохраняет **типы параметров конструктора** (`design:paramtypes`), и Nest по ним понимает, что внедрить. Поэтому внедрять можно только то, что существует в рантайме: **классы**; интерфейсы и type-алиасы стираются при компиляции, и для них нужны **токены** (`@Inject(TOKEN)`). Nest использует «legacy» (experimental) декораторы TypeScript, а не декораторы стандарта TC39, — `experimentalDecorators` должен быть включён.

## Вопрос

Как NestJS использует TypeScript и декораторы?

## Нужные настройки tsconfig

```json
{
  "compilerOptions": {
    "experimentalDecorators": true,
    "emitDecoratorMetadata": true,
    "strict": true,
    "target": "ES2023"
  }
}
```

Проект, созданный через `nest new`, уже содержит эти опции.

## Что делает декоратор

```ts
@Controller('users')                   // метаданные: префикс пути
export class UsersController {
  constructor(private readonly usersService: UsersService) {}
  //                               ↑ design:paramtypes = [UsersService]

  @Get(':id')                          // метаданные: метод GET, путь ':id'
  findOne(@Param('id') id: string) {   // метаданные параметра: брать из params.id
    return this.usersService.findOne(id);
  }
}
```

Скомпилированный код содержит примерно:

```js
Reflect.metadata('design:paramtypes', [UsersService])
```

## Интерфейсы не внедряются

```ts
interface Mailer { send(to: string, text: string): Promise<void> }

// ✗ в рантайме интерфейса нет → Nest видит Object
constructor(private readonly mailer: Mailer) {}

// ✓ токен
export const MAILER = Symbol('MAILER');
constructor(@Inject(MAILER) private readonly mailer: Mailer) {}
```

Подробнее — [injection token](<../03. Модули, провайдеры и Dependency Injection/06. Что такое injection token.md>).

## Ловушка с `import type`

```ts
import type { UsersService } from './users.service';   // ✗ стирается — DI не найдёт класс
import { UsersService } from './users.service';        // ✓
```

То же с `isolatedModules`/SWC-сборкой: типы, используемые для DI, должны импортироваться как значения.

## Свои метаданные

```ts
export const Roles = Reflector.createDecorator<string[]>();

@Roles(['admin'])
@Delete(':id')
remove() {}

// в guard
const roles = this.reflector.get(Roles, context.getHandler());
```

Подробнее — [metadata и Reflector](<../06. Guards, auth и security/08. Что такое metadata и Reflector.md>).

## Порядок применения

Декораторы применяются снизу вверх, но для Nest-метаданных порядок в основном не важен; он важен для композиции (`applyDecorators`) и для `@UseGuards`/`@UseInterceptors` с несколькими элементами (выполняются слева направо).

## Частые ошибки

- Внедрять интерфейс без токена.
- `import type` для класса, который нужен DI.
- Отключить `emitDecoratorMetadata` — DI перестаёт работать.
- Ожидать, что декоратор выполняет проверку сам (например, `@Roles` без guard ничего не защищает).

## Что важно помнить

- Декораторы Nest — это метаданные, а не логика.
- DI опирается на `design:paramtypes` из `emitDecoratorMetadata`.
- Интерфейсы стираются — нужны токены.

## Мини-шпаргалка

- `experimentalDecorators`, `emitDecoratorMetadata`.
- Внедряются классы или токены.
- `@Inject(TOKEN)` для интерфейсов и значений.
- `Reflector.createDecorator()` — свои метаданные.
