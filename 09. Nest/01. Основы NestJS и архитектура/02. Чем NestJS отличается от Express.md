# Чем NestJS отличается от Express

> [!NOTE]
> **Express** — минималистичная библиотека: роутинг, middleware и объекты `req`/`res`; структуру проекта, валидацию, DI и обработку ошибок команда придумывает сама. **NestJS** — фреймворк поверх Express (или Fastify), который даёт готовую **архитектуру**: модули, DI-контейнер, контроллеры с декораторами, конвейер запроса (guards → interceptors → pipes → handler → filters), типизированную конфигурацию и интеграции. В Express обработчик сам читает `req` и пишет в `res`; в Nest метод контроллера **возвращает значение**, а фреймворк сериализует его и выставляет статус. Выбор — компромисс между свободой и единообразием: Express проще для маленьких сервисов, Nest окупается в больших кодовых базах и командах.

## Вопрос

Чем NestJS отличается от Express и когда что выбрать?

## Один эндпоинт

```ts
// Express
app.post('/users', express.json(), async (req, res, next) => {
  try {
    if (!req.body.email) return res.status(400).json({ message: 'email required' });
    const user = await usersService.create(req.body);
    res.status(201).json(user);
  } catch (e) {
    next(e);
  }
});
```

```ts
// NestJS
@Controller('users')
export class UsersController {
  constructor(private readonly usersService: UsersService) {}

  @Post()                                   // 201 по умолчанию для POST
  create(@Body() dto: CreateUserDto) {       // валидация — ValidationPipe по DTO
    return this.usersService.create(dto);    // ошибки — exception filters
  }
}
```

## Сравнение

| | Express | NestJS |
| --- | --- | --- |
| Тип | Библиотека | Фреймворк |
| Структура проекта | Своя в каждом проекте | Модули, контроллеры, провайдеры |
| DI | Нет (вручную или сторонние контейнеры) | Встроенный контейнер |
| Валидация | Сторонние middleware | Pipes + DTO / Zod |
| Ошибки | `next(err)` + error middleware | `HttpException` + exception filters |
| Авторизация | Middleware | Guards + metadata |
| Ответ | `res.json()` | `return` значения |
| TypeScript | Опционально | По умолчанию |
| Тестирование | Вручную собирать зависимости | `Test.createTestingModule` + подмена провайдеров |
| Порог входа | Низкий | Выше (декораторы, DI, жизненный цикл) |

## Express внутри Nest

Nest не прячет платформу полностью:

```ts
app.use(cookieParser());                     // обычный Express middleware
@Get() handler(@Req() req: Request) {}       // доступ к Express-объектам
```

Но использование `@Res()` отключает стандартную обработку ответа — подробнее в уроке [когда использовать @Req и @Res](<../04. Controllers, роутинг и DTO/06. Когда использовать @Req и @Res.md>).

## Когда что

| Express (или Fastify, Hono) | NestJS |
| --- | --- |
| Маленький сервис, BFF, прокси | Доменный API с десятками сущностей |
| Нужен полный контроль и минимум абстракций | Нужны соглашения для команды |
| Serverless с быстрым холодным стартом | Монолит или модульный монолит, микросервисы |

## Частые ошибки

- Считать, что Nest медленнее «в разы» — накладные расходы фреймворка малы по сравнению с запросами к БД; при необходимости есть Fastify-адаптер.
- Использовать `@Res()` везде «как в Express» и терять interceptors.
- Тащить Express-паттерны (`req.user` везде, логика в middleware) вместо guards и pipes.

## Что важно помнить

- Nest работает поверх Express/Fastify, а не вместо них.
- Главное отличие — архитектура и DI, а не роутинг.
- Контроллер возвращает значение, ответ формирует фреймворк.

## Мини-шпаргалка

- Express: `req`, `res`, `next`, middleware.
- Nest: модули, DI, декораторы, конвейер запроса.
- Express middleware можно подключить через `app.use`.
- `@Res()` — только когда действительно нужен.
