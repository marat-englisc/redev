# Как работать с миграциями Prisma

> [!NOTE]
> **Prisma Migrate** создаёт SQL-миграции из разницы между `schema.prisma` и состоянием базы. В разработке используют **`prisma migrate dev --name <описание>`**: команда сравнивает схему с БД (через shadow database), создаёт папку `prisma/migrations/<timestamp>_<name>/migration.sql`, применяет её и обновляет таблицу `_prisma_migrations`. В Prisma 7 `migrate dev` **больше не запускает** `prisma generate` и seed — их вызывают явно. В CI/CD и проде применяют только **`prisma migrate deploy`** — он выполняет ещё не применённые миграции из репозитория и ничего не генерирует. Сгенерированный SQL обязательно **проверяют** (переименование поля может превратиться в `DROP` + `ADD`), а при необходимости правят вручную или создают пустую миграцию `--create-only` для своих операций (частичные индексы, `CREATE INDEX CONCURRENTLY`, перенос данных). `prisma db push` синхронизирует схему без миграций — только для прототипов.

## Вопрос

Как работать с миграциями в Prisma?

## Разработка

```bash
npx prisma migrate dev --name add_orders_status
npx prisma generate                 # Prisma 7: отдельно
npx prisma db seed                  # если нужно
```

```text
prisma/migrations/
├── 20261020100000_init/migration.sql
├── 20261024120000_add_orders_status/migration.sql
└── migration_lock.toml
```

## Проверка и ручная правка

```bash
npx prisma migrate dev --create-only --name rename_user_name   # создать, не применяя
```

```sql
-- было сгенерировано (потеря данных!):
-- ALTER TABLE "users" DROP COLUMN "name";
-- ALTER TABLE "users" ADD COLUMN "full_name" TEXT NOT NULL;

-- исправлено вручную:
ALTER TABLE "users" RENAME COLUMN "name" TO "full_name";
```

Для безопасных изменений больших таблиц в той же манере добавляют `CREATE INDEX CONCURRENTLY`, ограничения `NOT VALID` + `VALIDATE` — см. [изменение большой таблицы](<../../10. SQL/11. Практика Backend и собеседования/04. Как безопасно изменить большую таблицу.md>). Миграция с `CONCURRENTLY` не должна выполняться в транзакции — такие операции выносят в отдельную миграцию.

## Продакшен и CI

```bash
npx prisma migrate deploy           # применить новые миграции, без генерации и интерактива
npx prisma migrate status           # что применено, что нет
```

```yaml
# фрагмент CI/CD
- run: npm ci
- run: npx prisma generate
- run: npm run build
- run: npx prisma migrate deploy    # шаг деплоя до запуска новой версии приложения
```

Миграции должны быть **обратно совместимы** со старой версией кода, которая ещё работает во время rolling deploy (expand → migrate → contract).

## Seed

```ts
// prisma/seed.ts
const prisma = new PrismaClient({ adapter: new PrismaPg({ connectionString: process.env.DATABASE_URL }) });

async function main() {
  await prisma.role.createMany({ data: [{ code: 'admin' }, { code: 'user' }], skipDuplicates: true });
}
main().finally(() => prisma.$disconnect());
```

```ts
// prisma.config.ts
migrations: { path: 'prisma/migrations', seed: 'tsx prisma/seed.ts' }
```

Seed идемпотентен (`skipDuplicates`, `upsert`) — его можно запускать повторно.

## Разрешение проблем

```bash
npx prisma migrate resolve --applied 20261024120000_add_orders_status   # отметить применённой вручную
npx prisma migrate resolve --rolled-back 20261024120000_add_orders_status
npx prisma migrate reset            # пересоздать dev-базу (удаляет данные!)
npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script   # SQL разницы
```

## Команды

| Команда | Где | Что делает |
| --- | --- | --- |
| `migrate dev` | Локально | Создаёт и применяет миграцию |
| `migrate dev --create-only` | Локально | Только создаёт файл для правки |
| `migrate deploy` | CI / прод | Применяет неприменённые миграции |
| `migrate status` | Везде | Статус |
| `migrate reset` | Локально | Сброс базы и повторное применение |
| `db push` | Прототипы | Синхронизация без миграций |
| `generate` | Везде | Генерация клиента |

## Частые ошибки

- `migrate dev` на продакшене.
- Править уже применённую миграцию вместо создания новой.
- Не просматривать SQL — переименование превращается в удаление столбца.
- Ожидать, что `migrate dev` в Prisma 7 сгенерирует клиент.
- Разработчики создают миграции в разных ветках с конфликтующими изменениями и не перегенерируют после merge.

## Что важно помнить

- `migrate dev` — локально, `migrate deploy` — CI/прод.
- SQL миграций проверяется и при необходимости правится (`--create-only`).
- Prisma 7: `generate` и `db seed` вызываются явно.

## Мини-шпаргалка

- `prisma migrate dev --name x` → `prisma generate`.
- `prisma migrate deploy` в пайплайне деплоя.
- `--create-only` + ручная правка.
- `migrate status`, `migrate resolve`.
