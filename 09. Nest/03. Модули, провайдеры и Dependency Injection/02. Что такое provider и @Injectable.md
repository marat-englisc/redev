# Что такое provider и @Injectable

> [!NOTE]
> **Провайдер** — всё, что DI-контейнер Nest умеет создать и внедрить: чаще всего класс-сервис, но также значение, фабрика или псевдоним, зарегистрированные под **токеном**. Декоратор `@Injectable()` помечает класс как участника DI и заставляет TypeScript сохранить метаданные о типах параметров конструктора, чтобы контейнер мог внедрить зависимости. Чтобы провайдер можно было использовать, его нужно **зарегистрировать** в `providers` модуля; запись `providers: [UsersService]` — сокращение для `{ provide: UsersService, useClass: UsersService }`. По умолчанию провайдер — **синглтон** в рамках приложения. Провайдерами оформляют сервисы бизнес-логики, репозитории, клиенты внешних API, адаптеры (почта, хранилище файлов), а также guards, pipes и interceptors, когда им нужны зависимости.

## Вопрос

Что такое провайдер в NestJS и зачем нужен `@Injectable()`?

## Класс-провайдер

```ts
@Injectable()
export class PricingService {
  constructor(private readonly config: ConfigService) {}

  withVat(amount: number) {
    return amount * (1 + this.config.get<number>('VAT_RATE', 0.2));
  }
}

@Module({
  providers: [PricingService],   // ≡ { provide: PricingService, useClass: PricingService }
  exports: [PricingService],
})
export class PricingModule {}
```

## Когда @Injectable обязателен

| Класс | Нужен `@Injectable()` |
| --- | --- |
| Сервис с зависимостями в конструкторе | Да — иначе нет метаданных `design:paramtypes` |
| Сервис без зависимостей | Технически работает и без него, но принято ставить всегда |
| Guard, pipe, interceptor с зависимостями | Да |
| Контроллер | Нет — `@Controller()` уже даёт метаданные |
| DTO, entity | Нет — это не провайдеры |

## Виды провайдеров

```ts
providers: [
  UsersService,                                                    // класс
  { provide: 'APP_NAME', useValue: 'shop-api' },                   // значение
  { provide: MailService, useClass: SmtpMailService },             // подмена класса
  { provide: 'REDIS', useFactory: (c: ConfigService) => new Redis(c.getOrThrow('REDIS_URL')), inject: [ConfigService] },
  { provide: 'Mailer', useExisting: MailService },                 // псевдоним
]
```

Подробнее — [custom provider](<05. Что такое custom provider.md>).

## Что делать провайдером, а что нет

| Провайдер | Не провайдер |
| --- | --- |
| Сервисы бизнес-логики | DTO и типы |
| Репозитории, клиенты БД, Redis, HTTP-клиенты | Чистые утилиты без состояния (`slugify`) — можно просто функцией |
| Адаптеры внешних систем | Константы, не зависящие от окружения |
| Guards / pipes / interceptors с зависимостями | Entity-классы |

## Синглтон и состояние

```ts
@Injectable()
export class CartService {
  private items: Item[] = [];   // ✗ общий массив для ВСЕХ пользователей
}
```

Провайдер-синглтон не должен хранить данные конкретного запроса или пользователя в полях. Для этого — параметры методов, база, кеш или [request scope](<09. Какие бывают injection scopes.md>).

## Частые ошибки

- Забыть добавить сервис в `providers` — `UnknownDependenciesException`.
- Хранить состояние пользователя в поле синглтона.
- Создавать сервис вручную через `new` вместо внедрения.
- Делать провайдером всё подряд, включая чистые функции.

## Что важно помнить

- Провайдер — то, что контейнер создаёт и внедряет по токену.
- `@Injectable()` + регистрация в `providers`.
- По умолчанию — синглтон без состояния запроса.

## Мини-шпаргалка

- `@Injectable() export class X {}`.
- `providers: [X]` = `{ provide: X, useClass: X }`.
- `useValue`, `useClass`, `useFactory`, `useExisting`.
- Синглтон — без пользовательского состояния в полях.
