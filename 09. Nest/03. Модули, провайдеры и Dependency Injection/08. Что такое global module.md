# Что такое global module

> [!NOTE]
> **Глобальный модуль** (`@Global()` или `global: true` в dynamic module, например `ConfigModule.forRoot({ isGlobal: true })`) делает свои **экспорты доступными во всех модулях без импорта**. Его достаточно один раз подключить в `AppModule`. Это удобно для действительно сквозной инфраструктуры, которая нужна почти везде: конфигурация, логгер, клиент БД, CLS-контекст запроса. Обратная сторона — **неявные зависимости**: из `@Module` фичи уже не видно, что она зависит от `PrismaService`, модуль сложнее вынести в отдельный пакет или протестировать изолированно. Поэтому официальная рекомендация — использовать глобальные модули **умеренно**, а по умолчанию явно импортировать то, что нужно.

## Вопрос

Что такое глобальный модуль и когда его стоит использовать?

## @Global

```ts
@Global()
@Module({
  providers: [PrismaService],
  exports: [PrismaService],
})
export class PrismaModule {}

@Module({
  imports: [PrismaModule],          // один раз в корне
})
export class AppModule {}

@Module({
  providers: [UsersService],        // PrismaModule импортировать не нужно
})
export class UsersModule {}

@Injectable()
export class UsersService {
  constructor(private readonly prisma: PrismaService) {}   // ✓
}
```

## Глобальный dynamic module

```ts
ConfigModule.forRoot({ isGlobal: true });

// свой
static forRoot(options: Options): DynamicModule {
  return { module: AuditModule, global: true, providers: [...], exports: [AuditService] };
}
```

## Когда глобальный уместен

| Хорошо | Плохо |
| --- | --- |
| `ConfigModule` | Доменные сервисы (`UsersService`, `OrdersService`) |
| Логгер, CLS-контекст | Модули, которые нужны двум-трём фичам |
| Клиент БД (иногда) | Всё подряд, «чтобы не писать imports» |

## Минусы

- Зависимости не видны в `imports` — сложнее понять граф приложения.
- Тесты фичи требуют вручную подставить глобальные провайдеры.
- Глобальный модуль нельзя сделать «приватным» для части приложения.
- Модуль с `@Global()` всё равно нужно один раз импортировать — сам по себе он не подключается.

## Тесты

```ts
// в тесте UsersModule глобального PrismaModule нет — его нужно подключить или замокать
await Test.createTestingModule({
  imports: [UsersModule],
  providers: [{ provide: PrismaService, useValue: prismaMock }],   // не сработает: провайдер нужен в области видимости UsersModule
}).compile();

// ✓ подключить глобальный модуль и подменить провайдер
await Test.createTestingModule({ imports: [PrismaModule, UsersModule] })
  .overrideProvider(PrismaService).useValue(prismaMock)
  .compile();
```

## Частые ошибки

- Пометить `@Global()`, но не импортировать модуль ни разу.
- Делать глобальными доменные модули.
- Объявлять один и тот же глобальный модуль несколько раз с разной конфигурацией.

## Что важно помнить

- Глобальный модуль экспортирует провайдеры во все модули без импорта.
- Подключается один раз в корне.
- Используйте только для сквозной инфраструктуры.

## Мини-шпаргалка

- `@Global() @Module({ providers, exports })`.
- `ConfigModule.forRoot({ isGlobal: true })`.
- Dynamic: `{ global: true }`.
- В тестах — импорт + `overrideProvider`.
