# Какие бывают injection scopes

> [!NOTE]
> **Injection scope** определяет время жизни экземпляра провайдера. **`DEFAULT`** (singleton) — один экземпляр на всё приложение, создаётся при старте; это рекомендуемый вариант почти для всего. **`REQUEST`** — новый экземпляр на **каждый входящий запрос**, удаляется после ответа; даёт доступ к объекту запроса через `@Inject(REQUEST)`. **`TRANSIENT`** — новый экземпляр для **каждого потребителя**, который его внедряет (например, логгер со своим контекстом). Важно: request scope **«всплывает» по цепочке** — если сервис зависит от request-scoped провайдера, он тоже становится request-scoped, вместе с контроллером, что увеличивает нагрузку. Для передачи контекста запроса (userId, tenantId, correlation id) вместо request scope обычно используют **AsyncLocalStorage** — например, библиотеку `nestjs-cls`.

## Вопрос

Какие бывают injection scopes и когда их использовать?

## Три скоупа

```ts
@Injectable()                                   // DEFAULT — singleton
export class PricingService {}

@Injectable({ scope: Scope.REQUEST })
export class RequestContextService {
  constructor(@Inject(REQUEST) private readonly req: Request) {}
  get userId() { return (this.req as any).user?.id; }
}

@Injectable({ scope: Scope.TRANSIENT })
export class ContextLogger {
  private context = 'App';
  setContext(ctx: string) { this.context = ctx; }
}
```

| Скоуп | Экземпляр | Применение |
| --- | --- | --- |
| `DEFAULT` | Один на приложение | Почти всё |
| `REQUEST` | Один на запрос | Мультиарендность с подключением на tenant, доступ к `REQUEST` |
| `TRANSIENT` | Один на каждого потребителя | Логгер с контекстом, объекты с внутренним состоянием |

## Всплытие request scope

```text
UsersController  ──►  UsersService  ──►  RequestContextService (REQUEST)
     ↑ становится REQUEST    ↑ становится REQUEST
```

На каждый запрос Nest создаёт заново всю цепочку. Под нагрузкой это заметно: аллокации, отсутствие кеширования в полях, сложнее отладка. Также request-scoped провайдеры недоступны в обычных cron-задачах и `onModuleInit`.

## Альтернатива: AsyncLocalStorage (nestjs-cls)

```ts
// app.module.ts
@Module({
  imports: [
    ClsModule.forRoot({
      global: true,
      middleware: {
        mount: true,
        setup: (cls, req) => {
          cls.set('requestId', req.headers['x-request-id'] ?? randomUUID());
        },
      },
    }),
  ],
})
export class AppModule {}

// в guard после аутентификации
this.cls.set('userId', user.id);

// в любом синглтоне
@Injectable()
export class AuditService {
  constructor(private readonly cls: ClsService) {}
  log(action: string) {
    return this.prisma.audit.create({ data: { action, userId: this.cls.get('userId'), requestId: this.cls.get('requestId') } });
  }
}
```

Сервисы остаются синглтонами, а контекст «следует» за асинхронной цепочкой вызовов запроса.

## Durable providers

Для мультиарендности, где на каждый tenant нужен свой экземпляр (например, своё подключение), Nest поддерживает **durable** request-scoped провайдеры с `ContextIdStrategy`: экземпляры кешируются по tenant, а не создаются на каждый запрос.

## Частые ошибки

- Сделать `REQUEST`-scope «на всякий случай» и получить падение производительности.
- Хранить данные пользователя в полях синглтона.
- Ожидать, что request-scoped провайдер доступен в `onModuleInit` или cron.
- Использовать `TRANSIENT`, рассчитывая на «новый экземпляр на каждый вызов метода» — он создаётся на каждое внедрение, а не на вызов.

## Что важно помнить

- По умолчанию — синглтон, и это правильно.
- Request scope всплывает по цепочке зависимостей.
- Контекст запроса — через AsyncLocalStorage (`nestjs-cls`).

## Мини-шпаргалка

- `@Injectable({ scope: Scope.REQUEST | Scope.TRANSIENT })`.
- `@Inject(REQUEST)` — объект запроса.
- `@Inject(INQUIRER)` — кто внедряет (для transient).
- `nestjs-cls`: `ClsModule.forRoot`, `cls.set/get`.
