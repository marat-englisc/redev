# Как проходит запрос по файлам - от main.ts до service

> [!NOTE]
> Связка файлов в NestJS: `main.ts` создаёт приложение из `AppModule`; `AppModule` импортирует feature-модули; `UsersModule` регистрирует `UsersController` и `UsersService`; контроллер получает сервис через DI. Запрос `POST /api/users` проходит так: HTTP-сервер (Express/Fastify) → **middleware** → роутер Nest находит метод контроллера по метаданным `@Controller('users')` + `@Post()` → **guards** (можно ли) → **interceptors** (до) → **pipes** (валидация `CreateUserDto`) → **метод контроллера** → **сервис** (бизнес-логика) → **репозиторий/ORM** → база → результат возвращается через interceptors (после) → сериализуется в JSON со статусом 201. Ошибка на любом шаге перехватывается **exception filters** и превращается в HTTP-ответ.

## Вопрос

Как связаны `main.ts`, модули, контроллер и сервис и как запрос проходит по файлам?

## Связка файлов

```text
main.ts ──NestFactory.create──► AppModule
                                  └─ imports: UsersModule
                                                ├─ controllers: UsersController
                                                └─ providers: UsersService, UsersRepository
UsersController ──constructor DI──► UsersService ──► UsersRepository ──► PrismaService
```

## Код по шагам

```ts
// main.ts
const app = await NestFactory.create(AppModule);
app.setGlobalPrefix('api');
app.useGlobalPipes(new ValidationPipe({ whitelist: true, transform: true }));
await app.listen(3000);
```

```ts
// app.module.ts
@Module({ imports: [ConfigModule.forRoot({ isGlobal: true }), PrismaModule, UsersModule] })
export class AppModule {}
```

```ts
// users/users.module.ts
@Module({
  controllers: [UsersController],
  providers: [UsersService, UsersRepository],
  exports: [UsersService],
})
export class UsersModule {}
```

```ts
// users/dto/create-user.dto.ts
export class CreateUserDto {
  @IsEmail() email: string;
  @IsString() @Length(2, 100) name: string;
}
```

```ts
// users/users.controller.ts
@Controller('users')
export class UsersController {
  constructor(private readonly usersService: UsersService) {}

  @Post()
  @UseGuards(JwtAuthGuard)
  create(@Body() dto: CreateUserDto) {
    return this.usersService.create(dto);
  }
}
```

```ts
// users/users.service.ts
@Injectable()
export class UsersService {
  constructor(private readonly repo: UsersRepository) {}

  async create(dto: CreateUserDto) {
    const exists = await this.repo.findByEmail(dto.email);
    if (exists) throw new ConflictException('Email already registered');
    return this.repo.create(dto);
  }
}
```

```ts
// users/users.repository.ts
@Injectable()
export class UsersRepository {
  constructor(private readonly prisma: PrismaService) {}
  findByEmail(email: string) { return this.prisma.user.findUnique({ where: { email } }); }
  create(data: CreateUserDto) { return this.prisma.user.create({ data, select: { id: true, email: true, name: true } }); }
}
```

## Путь запроса POST /api/users

| # | Шаг | Файл / механизм | Что может пойти не так |
| --- | --- | --- | --- |
| 1 | HTTP-сервер принимает запрос, парсит JSON | Express/Fastify | Невалидный JSON → 400 |
| 2 | Middleware | `app.use(...)`, `MiddlewareConsumer` | — |
| 3 | Роутинг | `@Controller('users')` + `@Post()` + prefix | Нет маршрута → 404 |
| 4 | Guard | `JwtAuthGuard` | Нет токена → 401/403 |
| 5 | Interceptor (до) | `LoggingInterceptor` | — |
| 6 | Pipe | `ValidationPipe` + `CreateUserDto` | Невалидные данные → 400 |
| 7 | Контроллер | `UsersController.create` | — |
| 8 | Сервис | `UsersService.create` | `ConflictException` → 409 |
| 9 | Репозиторий / ORM | `UsersRepository` → Prisma | Ошибка БД → 500 (или своя обработка) |
| 10 | Interceptor (после) | Трансформация ответа | — |
| 11 | Ответ | Сериализация в JSON, статус 201 | — |
| ✗ | Exception filter | Встроенный или свой | Форматирует любую ошибку |

Подробнее о порядке — [request lifecycle](<../07. Middleware, interceptors и request lifecycle/01. Как устроен request lifecycle в NestJS.md>).

## Ответственность слоёв

| Слой | Делает | Не делает |
| --- | --- | --- |
| Controller | HTTP: маршрут, DTO, статус, вызов сервиса | Бизнес-правила, запросы к БД |
| Service | Бизнес-сценарий, проверки, транзакции | Знание о `req`/`res` |
| Repository | Запросы к данным | Решения бизнес-логики |

## Частые ошибки

- Модуль не импортирован в `AppModule` — маршруты фичи не регистрируются (404).
- Сервис не в `providers` модуля — ошибка DI при старте.
- Валидация в контроллере вручную вместо pipe.
- Prisma-запросы прямо в контроллере.

## Что важно помнить

- `main.ts` → `AppModule` → feature-модуль → контроллер → сервис → репозиторий.
- Запрос: middleware → guards → interceptors → pipes → handler → interceptors → ответ; ошибки — в filters.
- Каждый слой отвечает за своё.

## Мини-шпаргалка

- 404 — модуль/маршрут не зарегистрирован.
- 401/403 — guard.
- 400 — pipe.
- 409/404/422 — исключения сервиса.
- 500 — необработанная ошибка.
