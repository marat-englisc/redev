# Как устроена структура NestJS-проекта и где что лежит

> [!NOTE]
> Стартовый проект содержит `src/main.ts` (точку входа), `src/app.module.ts` (корневой модуль), пример контроллера и сервиса, а также `test/` для e2e-тестов. По мере роста код организуют **по фичам**: у каждой доменной области своя папка с модулем, контроллером, сервисом, DTO, сущностями/репозиторием и тестами рядом с кодом (`*.spec.ts`). Общая инфраструктура (guards, interceptors, filters, декораторы, pipes) — в `common/` или `core/`, конфигурация — в `config/`, подключение к БД — в `database/` или `prisma/`, авторизация — в `auth/`. Правило: **код, который меняется вместе, лежит вместе**, а папка фичи — это её публичная граница через модуль.

## Вопрос

Как устроена структура NestJS-проекта и где хранить DTO, сущности, репозитории, guards и стратегии?

## Стартовая структура

```text
my-api/
├── src/
│   ├── app.controller.ts
│   ├── app.controller.spec.ts
│   ├── app.module.ts
│   ├── app.service.ts
│   └── main.ts
├── test/
│   └── app.e2e-spec.ts
├── nest-cli.json
├── tsconfig.json
├── tsconfig.build.json
└── package.json
```

## Что где лежит

| Что | Где | Почему |
| --- | --- | --- |
| DTO запроса и ответа | `feature/dto/` | Контракт API этой фичи |
| Entity (TypeORM) / доменная модель | `feature/entities/` | Модель данных фичи |
| Repository | `feature/feature.repository.ts` | Доступ к данным фичи, внедряется в сервис |
| Guard, специфичный для фичи | `feature/guards/` | Например, `OrderOwnerGuard` |
| Общий guard / interceptor / filter | `common/` | Используется во многих модулях |
| Passport-стратегии | `auth/strategies/` | Часть модуля авторизации |
| Конфигурация | `config/` | Namespaced-конфиги и схема env |
| Клиент БД | `database/` или `prisma/` | Инфраструктурный модуль |
| Prisma-схема и миграции | `prisma/` в корне проекта | Так ожидает Prisma CLI |
| Unit-тесты | Рядом с кодом: `*.spec.ts` | Видно, что покрыто |
| E2E-тесты | `test/*.e2e-spec.ts` | Тестируют приложение целиком |

## Соглашения об именах

```text
users.module.ts        UsersModule
users.controller.ts    UsersController
users.service.ts       UsersService
create-user.dto.ts     CreateUserDto
roles.guard.ts         RolesGuard
logging.interceptor.ts LoggingInterceptor
```

Kebab-case в файлах, PascalCase в классах, суффикс типа блока в обоих.

## Как читать незнакомый проект

1. `main.ts` — глобальные pipes, filters, prefix, CORS, Swagger.
2. `app.module.ts` — список модулей и глобальная конфигурация.
3. Модуль нужной фичи — что он импортирует и экспортирует.
4. Контроллер — эндпоинты и DTO; затем сервис — бизнес-логика.
5. `common/` — что применяется глобально (guards, interceptors).

## Частые ошибки

- Папки по техническим слоям (`controllers/`, `services/`, `dtos/`) для всего приложения — изменения одной фичи разбросаны по проекту.
- Общий guard внутри папки одной фичи, импортируемый из десяти мест.
- DTO и сущности одной фичи используются как общие типы по всему проекту.
- Тесты в отдельном дереве, далёком от кода.

## Что важно помнить

- Структура по фичам: модуль + контроллер + сервис + DTO + данные + тесты.
- Общая инфраструктура — в `common/`, конфиг — в `config/`.
- Модуль — публичная граница папки фичи.

## Мини-шпаргалка

- `src/main.ts`, `src/app.module.ts`.
- `src/<feature>/{module,controller,service,repository}.ts`, `dto/`, `entities/`.
- `src/common/{guards,interceptors,filters,decorators,pipes}`.
- `test/*.e2e-spec.ts`.
