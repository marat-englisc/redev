# Чем send отличается от emit в ClientProxy

> [!NOTE]
> `ClientProxy.send(pattern, data)` — **request-response**: отправляет сообщение обработчику `@MessagePattern(pattern)` и возвращает **холодный `Observable`** с ответом; сообщение не уйдёт, пока на `Observable` никто не подписался (`firstValueFrom`, `subscribe`, `return` из обработчика Nest). `emit(pattern, data)` — **событие**: публикуется для обработчиков `@EventPattern(pattern)`, ответа не ждёт (fire-and-forget) и возвращает **горячий** `Observable`, который отправляет сообщение сразу. `send` подходит, когда вызывающему нужен результат (резерв товара, проверка лимита) — и обязательно с **таймаутом**; `emit` — для оповещения о факте («заказ создан»), когда подписчиков может быть несколько или ни одного, и вызывающий не должен зависеть от их работы. С `emit` нужно обеспечить надёжность: брокер с персистентностью, подтверждения, идемпотентных потребителей и, при необходимости, outbox.

## Вопрос

Чем отличаются `send()` и `emit()` в `ClientProxy`?

## send — запрос-ответ

```ts
@Injectable()
export class CheckoutService {
  constructor(@Inject('BILLING') private readonly billing: ClientProxy) {}

  async charge(orderId: string, amount: number) {
    return firstValueFrom(
      this.billing.send<ChargeResult>('billing.charge', { orderId, amount }).pipe(
        timeout(5_000),
        catchError((err) =>
          throwError(() => (err instanceof TimeoutError ? new GatewayTimeoutException() : err)),
        ),
      ),
    );
  }
}

// billing-service
@MessagePattern('billing.charge')
charge(@Payload() dto: ChargeDto): Promise<ChargeResult> {
  return this.billing.charge(dto);
}
```

## emit — событие

```ts
this.events.emit('order.created', { orderId, userId, total });   // не ждём

// любой сервис может подписаться
@EventPattern('order.created')
async onOrderCreated(@Payload() e: OrderCreatedEvent) {
  await this.analytics.track(e);
}
```

## Сравнение

| | `send` | `emit` |
| --- | --- | --- |
| Обработчик | `@MessagePattern` | `@EventPattern` |
| Ответ | Да | Нет |
| Observable | Холодный — отправка при подписке | Горячий — отправка сразу |
| Получатели | Один обработчик | Ноль, один или много |
| Связанность | Вызывающий зависит от доступности сервиса | Слабая |
| Таймаут | Обязателен | Не применим |
| Пример | `inventory.reserve`, `user.get` | `order.created`, `user.registered` |

## Ловушка холодного Observable

```ts
// ✗ сообщение не отправится — никто не подписался
this.billing.send('billing.charge', dto);

// ✓
await firstValueFrom(this.billing.send('billing.charge', dto));
```

## Именование

- Команды и запросы (`send`) — глагол: `billing.charge`, `user.get`.
- События (`emit`) — факт в прошедшем времени: `order.created`, `payment.failed`.

## Надёжность событий

- Брокер с персистентностью (RabbitMQ durable queues, Kafka, NATS JetStream), а не Redis pub/sub, если потеря недопустима.
- Публикация после `COMMIT` или через outbox, чтобы событие соответствовало данным.
- Потребители идемпотентны: доставка «как минимум один раз».
- Dead letter queue для сообщений, которые не удалось обработать.

## Частые ошибки

- `send()` без подписки — ничего не происходит.
- `send()` без `timeout`.
- Использовать `send` для оповещений и ждать ответа от «подписчика».
- `emit` критичного события через транспорт без персистентности.

## Что важно помнить

- `send` — запрос с ответом, холодный, с таймаутом.
- `emit` — событие без ответа, горячий.
- События требуют надёжного брокера и идемпотентности.

## Мини-шпаргалка

- `firstValueFrom(client.send(p, d).pipe(timeout(ms)))`.
- `client.emit(p, d)`.
- `@MessagePattern` ↔ `send`, `@EventPattern` ↔ `emit`.
- Команды — глаголы, события — прошедшее время.
