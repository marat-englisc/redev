# Как обрабатывать timeout в NestJS microservices

> [!NOTE]
> Межсервисный вызов `send()` может не получить ответ: сервис упал, перегружен, сообщение потерялось, сеть «зависла». Без таймаута запрос ждёт бесконечно, держит ресурсы, и цепочка вызовов «замерзает» каскадом. Поэтому каждый `send()` ограничивают RxJS-оператором **`timeout(ms)`**, а `TimeoutError` превращают в понятную ошибку (`GatewayTimeoutException` 504 / `ServiceUnavailableException` 503 или доменную). Дальнейшие слои устойчивости: **повторы** с экспоненциальной задержкой (`retry({ count, delay })`) только для **идемпотентных** операций, **circuit breaker** (не стучаться в упавший сервис, например `opossum`), **fallback** (кешированный ответ, деградация функции), и **deadline propagation** — суммарный таймаут цепочки должен быть меньше таймаута исходного HTTP-запроса. На стороне обработчика ошибки отдаются через `RpcException`, а у клиента — проверяются и маппятся.

## Вопрос

Как обрабатывать таймауты и ошибки при вызовах между микросервисами?

## Таймаут и маппинг ошибки

```ts
@Injectable()
export class InventoryClient {
  constructor(@Inject('INVENTORY') private readonly client: ClientProxy) {}

  reserve(items: ReserveItem[]) {
    return firstValueFrom(
      this.client.send<Reservation>('inventory.reserve', { items }).pipe(
        timeout({ first: 2_000 }),
        catchError((err) => {
          if (err instanceof TimeoutError) return throwError(() => new GatewayTimeoutException('Inventory timeout'));
          if (err?.code === 'OUT_OF_STOCK') return throwError(() => new UnprocessableEntityException(err.message));
          return throwError(() => new ServiceUnavailableException('Inventory unavailable'));
        }),
      ),
    );
  }
}
```

## Повторы — только для идемпотентного

```ts
this.client.send('catalog.product.get', { id }).pipe(
  timeout(1_000),
  retry({ count: 2, delay: (_err, attempt) => timer(100 * 2 ** attempt + Math.random() * 50) }),
);
```

`inventory.reserve` повторять без ключа идемпотентности нельзя: первый вызов мог успешно выполниться, а потеряться — только ответ. Передавайте `requestId`/`idempotencyKey`, чтобы обработчик распознал повтор.

## Ошибки на стороне обработчика

```ts
@MessagePattern('inventory.reserve')
async reserve(@Payload() dto: ReserveDto) {
  const ok = await this.inventory.tryReserve(dto);
  if (!ok) throw new RpcException({ code: 'OUT_OF_STOCK', message: 'Not enough items' });
  return ok;
}
```

## Circuit breaker

```ts
const breaker = new CircuitBreaker((items: ReserveItem[]) => this.reserveRaw(items), {
  timeout: 2_000,                // таймаут вызова
  errorThresholdPercentage: 50,  // открыть при 50% ошибок
  resetTimeout: 10_000,          // через 10 с попробовать снова (half-open)
});
breaker.fallback(() => { throw new ServiceUnavailableException('Inventory temporarily unavailable'); });

reserve(items: ReserveItem[]) { return breaker.fire(items); }
```

Открытый breaker мгновенно отклоняет вызовы, давая упавшему сервису восстановиться, а пользователю — быстрый ответ вместо ожидания.

## Бюджет времени

```text
HTTP-запрос клиента: таймаут 10 с (балансировщик)
  └─ OrdersService
       ├─ inventory.reserve   2 с
       ├─ billing.charge      5 с
       └─ запас               3 с
```

Если сумма таймаутов вложенных вызовов больше внешнего, клиент получит 504 от балансировщика, а сервисы продолжат работать «впустую».

## Асинхронность вместо ожидания

Если ответ не нужен сразу, вместо `send` + ожидания используют событие или задачу в очереди, а результат сообщают позже (WebSocket, webhook, polling статуса). Это убирает каскадные таймауты из критического пути.

## Частые ошибки

- `send()` без `timeout`.
- Повторы неидемпотентных команд.
- Повторы без задержки и jitter — «шторм» запросов к восстанавливающемуся сервису.
- Таймауты вложенных вызовов больше внешнего.
- Ошибка обработчика как обычный `Error` — клиент получает неинформативный ответ.

## Что важно помнить

- Каждый `send()` — с таймаутом и маппингом ошибок.
- Retry — только для идемпотентных операций, с backoff и jitter.
- Circuit breaker и fallback защищают от каскадных отказов.

## Мини-шпаргалка

- `.pipe(timeout(ms), catchError(...))`.
- `TimeoutError` → `GatewayTimeoutException`.
- `retry({ count, delay })`.
- `throw new RpcException({ code, message })`.
- `opossum` — circuit breaker.
