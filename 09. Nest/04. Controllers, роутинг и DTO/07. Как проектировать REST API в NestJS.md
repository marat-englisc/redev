# Как проектировать REST API в NestJS

> [!NOTE]
> REST API строится вокруг **ресурсов** (существительных во множественном числе: `/users`, `/orders/:id/items`) и стандартной семантики **HTTP-методов**: `GET` — чтение (безопасный и идемпотентный), `POST` — создание или действие, `PUT` — полная замена, `PATCH` — частичное изменение, `DELETE` — удаление (последние три — идемпотентны по смыслу, `POST` — нет). Статусы отражают результат: 200/201/204 — успех, 400 — невалидный вход, 401 — не аутентифицирован, 403 — нет прав, 404 — нет ресурса, 409 — конфликт состояния, 422 — бизнес-правило нарушено, 429 — лимит запросов. В NestJS это выражается контроллером на ресурс, DTO на каждую операцию, pipes для валидации, исключениями для ошибок, единым форматом ответов и ошибок, пагинацией списков и версионированием при ломающих изменениях.

## Вопрос

Как спроектировать REST API в NestJS?

## Ресурсы и маршруты

| Операция | Метод и путь | Статус |
| --- | --- | --- |
| Список | `GET /orders?status=paid&page=2` | 200 |
| Получить | `GET /orders/:id` | 200 / 404 |
| Создать | `POST /orders` | 201 + тело (и `Location`) |
| Заменить | `PUT /orders/:id` | 200 |
| Изменить | `PATCH /orders/:id` | 200 |
| Удалить | `DELETE /orders/:id` | 204 |
| Вложенный ресурс | `GET /orders/:id/items` | 200 |
| Действие | `POST /orders/:id/cancel` | 200 / 409 |

```ts
@Controller('orders')
export class OrdersController {
  @Get()                 findAll(@Query() q: ListOrdersQueryDto, @CurrentUser() u: AuthUser) {}
  @Get(':id')            findOne(@Param('id', ParseUUIDPipe) id: string, @CurrentUser() u: AuthUser) {}
  @Post()                create(@Body() dto: CreateOrderDto, @CurrentUser() u: AuthUser) {}
  @Patch(':id')          update(@Param('id', ParseUUIDPipe) id: string, @Body() dto: UpdateOrderDto) {}
  @Post(':id/cancel')    @HttpCode(200) cancel(@Param('id', ParseUUIDPipe) id: string) {}
  @Delete(':id')         @HttpCode(204) remove(@Param('id', ParseUUIDPipe) id: string) {}
}
```

## Статусы ошибок

```ts
throw new BadRequestException('Invalid date range');         // 400 — некорректный ввод
throw new UnauthorizedException();                            // 401 — нет/невалидная аутентификация
throw new ForbiddenException('Not your order');               // 403 — нет прав
throw new NotFoundException(`Order ${id} not found`);         // 404
throw new ConflictException('Order already paid');            // 409 — конфликт состояния
throw new UnprocessableEntityException('Insufficient stock'); // 422 — бизнес-правило
```

Для чужого ресурса часто отвечают 404, а не 403, чтобы не раскрывать его существование.

## Единый формат

```json
// список
{ "items": [...], "meta": { "page": 2, "limit": 20, "total": 134 } }

// ошибка
{ "statusCode": 400, "error": "Bad Request", "message": "Validation failed",
  "details": [{ "field": "email", "message": "email must be an email" }], "requestId": "a1b2" }
```

## Чек-лист дизайна

- Существительные во множественном числе, kebab-case: `/order-items`.
- Без глаголов в путях, кроме действий над ресурсом (`/cancel`, `/publish`).
- Фильтры, сортировка, пагинация — в query.
- Даты — ISO 8601 в UTC, деньги — в минимальных единицах или строкой-decimal.
- Идентификаторы — непредсказуемые (UUID) для публичных ресурсов.
- Идемпотентность создания платежей — `Idempotency-Key`.
- Ограничения: `limit` максимум, размер тела, rate limiting.
- Документация OpenAPI генерируется из кода.
- Версионирование только для ломающих изменений.

## PUT или PATCH

| `PUT` | `PATCH` |
| --- | --- |
| Клиент присылает ресурс целиком | Только изменяемые поля |
| Отсутствующие поля — сбрасываются | Отсутствующие — не трогаются |
| DTO = `CreateDto` | DTO = `PartialType(...)` |

На практике большинство API используют `PATCH`.

## Частые ошибки

- `POST /getOrders`, `GET /deleteUser?id=1`.
- 200 с `{ success: false }` вместо статуса ошибки.
- 500 на ожидаемые ситуации (нет записи, дубль email).
- Списки без пагинации и лимита.
- Разный формат ответов в разных контроллерах.

## Что важно помнить

- Ресурсы — существительные, действия — HTTP-методы.
- Статус отражает результат, ошибки — исключения.
- Единый формат, пагинация, документация и версии.

## Мини-шпаргалка

- `GET` 200, `POST` 201, `DELETE` 204.
- 400 / 401 / 403 / 404 / 409 / 422 / 429.
- Фильтры в query, тело — DTO.
- `PATCH` + `PartialType`.
