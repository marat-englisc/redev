# Как сделать единый формат ошибок

> [!NOTE]
> Клиенту (фронтенду, мобильному приложению, партнёру) удобно, когда **все** ошибки API имеют одну форму: статус, **машиночитаемый код** (`EMAIL_TAKEN`, `VALIDATION_FAILED`), человекочитаемое сообщение, детали по полям для форм и **requestId** для поиска в логах. В NestJS это собирается из трёх частей: `ValidationPipe` с `exceptionFactory` (единый формат ошибок валидации), доменные или HTTP-исключения с кодом и **глобальный catch-all exception filter**, который приводит к общей форме всё — `HttpException`, ошибки ORM, неизвестные ошибки (как 500 без деталей). Можно ориентироваться на стандарт **RFC 9457 Problem Details** (`application/problem+json` с полями `type`, `title`, `status`, `detail`, `instance`). Формат описывают в OpenAPI, чтобы клиент мог сгенерировать типы.

## Вопрос

Как сделать единый формат ошибок в NestJS-приложении?

## Целевой формат

```json
{
  "statusCode": 400,
  "code": "VALIDATION_FAILED",
  "message": "Validation failed",
  "details": [
    { "field": "email", "message": "email must be an email" },
    { "field": "items.0.quantity", "message": "quantity must not be less than 1" }
  ],
  "requestId": "6c1f9b1e-...",
  "timestamp": "2026-10-24T10:15:00.000Z"
}
```

## Исключение приложения

```ts
export class AppException extends HttpException {
  constructor(status: HttpStatus, public readonly code: string, message: string, public readonly details?: unknown) {
    super({ code, message, details }, status);
  }
}

throw new AppException(HttpStatus.CONFLICT, 'EMAIL_TAKEN', 'Email already registered');
```

## Валидация

```ts
new ValidationPipe({
  whitelist: true,
  transform: true,
  exceptionFactory: (errors) =>
    new AppException(HttpStatus.BAD_REQUEST, 'VALIDATION_FAILED', 'Validation failed', toFieldErrors(errors)),
});
```

## Глобальный filter

```ts
@Catch()
export class GlobalExceptionFilter implements ExceptionFilter {
  private readonly logger = new Logger('Exceptions');

  constructor(private readonly adapterHost: HttpAdapterHost, private readonly cls: ClsService) {}

  catch(exception: unknown, host: ArgumentsHost) {
    const { httpAdapter } = this.adapterHost;
    const ctx = host.switchToHttp();
    const body = this.toBody(exception);

    if (body.statusCode >= 500) {
      this.logger.error({ err: exception, requestId: body.requestId }, 'Unhandled error');
    }
    httpAdapter.reply(ctx.getResponse(), body, body.statusCode);
  }

  private toBody(e: unknown) {
    const base = { requestId: this.cls.getId(), timestamp: new Date().toISOString() };

    if (e instanceof HttpException) {
      const res = e.getResponse();
      const r = typeof res === 'string' ? { message: res } : (res as Record<string, any>);
      return {
        statusCode: e.getStatus(),
        code: r.code ?? HttpStatus[e.getStatus()],
        message: Array.isArray(r.message) ? 'Validation failed' : r.message ?? e.message,
        details: r.details ?? (Array.isArray(r.message) ? r.message : undefined),
        ...base,
      };
    }

    if (e instanceof Prisma.PrismaClientKnownRequestError) {
      if (e.code === 'P2002') return { statusCode: 409, code: 'CONFLICT', message: 'Resource already exists', ...base };
      if (e.code === 'P2025') return { statusCode: 404, code: 'NOT_FOUND', message: 'Resource not found', ...base };
    }

    return { statusCode: 500, code: 'INTERNAL_ERROR', message: 'Internal server error', ...base };
  }
}

// app.module.ts
providers: [{ provide: APP_FILTER, useClass: GlobalExceptionFilter }]
```

## Problem Details (RFC 9457)

```json
{
  "type": "https://api.example.com/errors/insufficient-stock",
  "title": "Insufficient stock",
  "status": 422,
  "detail": "Only 2 items left for product KB-1",
  "instance": "/api/orders",
  "productId": "KB-1"
}
```

Ответ с `Content-Type: application/problem+json`. Стандарт полезен для публичных API и интеграций.

## Правила

- Код ошибки стабилен и документирован; сообщение может меняться и переводиться.
- 4xx — детали для клиента; 5xx — только общий текст и requestId.
- Ошибки по полям — с путём (`items.0.quantity`), чтобы форма подсветила поле.
- Логировать 5xx с контекстом, 4xx — на уровне `warn`/`debug`, без спама.
- Описать формат в Swagger как общий `ErrorResponseDto`.

## Частые ошибки

- Разный формат в разных контроллерах и у ошибок валидации.
- Стек и SQL-ошибки в ответе клиенту.
- Только текст без кода — фронтенд парсит сообщения строками.
- Нет requestId — невозможно найти ошибку в логах по жалобе пользователя.

## Что важно помнить

- Единый формат = `exceptionFactory` + коды исключений + глобальный filter.
- Машиночитаемый `code`, детали по полям, `requestId`.
- 5xx без деталей, с логированием.

## Мини-шпаргалка

- `AppException(status, code, message, details)`.
- `ValidationPipe({ exceptionFactory })`.
- `@Catch()` + `APP_FILTER` + `HttpAdapterHost`.
- RFC 9457 — `application/problem+json`.
