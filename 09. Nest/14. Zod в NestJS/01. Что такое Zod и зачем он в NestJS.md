# Что такое Zod и зачем он в NestJS

> [!NOTE]
> **Zod** — TypeScript-first библиотека схем: схема описывается как **значение** (`z.object({ email: z.email() })`), проверяет данные **во время выполнения** и одновременно даёт **тип TypeScript** через `z.infer<typeof schema>` — один источник правды для валидации и типов. TypeScript-типы исчезают после компиляции, поэтому всё, что приходит извне (тело и параметры запроса, переменные окружения, вебхуки, ответы внешних API, сообщения из очередей), нужно проверять в рантайме. В NestJS традиционно используют DTO-классы с `class-validator`, но Zod — полноценная альтернатива: в **NestJS 12** есть встроенный `StandardSchemaValidationPipe` и опция `@Body({ schema })`, а `ConfigModule` принимает Zod-схему в `validationSchema`. Zod удобен, когда схемы нужно **разделять между фронтендом и бэкендом** (монорепозиторий), когда важна композиция схем (`pick`, `omit`, `extend`, `discriminatedUnion`) и преобразования (`transform`, `coerce`). Актуальная версия — **Zod 4** (форматы как `z.email()`, `z.url()`, `z.uuid()`; `z.stringbool()`, `z.prettifyError()`).

## Вопрос

Что такое Zod и зачем использовать его в NestJS?

## Схема и тип из одного места

```ts
import { z } from 'zod';

export const createUserSchema = z.object({
  email: z.email(),
  name: z.string().trim().min(2).max(100),
  password: z.string().min(10),
  locale: z.enum(['ru', 'en']).default('ru'),
});

export type CreateUserDto = z.infer<typeof createUserSchema>;
// { email: string; name: string; password: string; locale: 'ru' | 'en' }
```

```ts
// NestJS 12
@Post()
create(@Body({ schema: createUserSchema }) dto: CreateUserDto) {
  return this.users.create(dto);
}
```

## Zod и class-validator

| | `class-validator` + DTO-класс | Zod |
| --- | --- | --- |
| Описание | Декораторы на свойствах класса | Схема-значение |
| Тип TypeScript | Сам класс | `z.infer<typeof schema>` |
| Интеграция с Nest | `ValidationPipe` (исторически стандарт) | `StandardSchemaValidationPipe` (NestJS 12) или свой pipe |
| Swagger | Нативно (`@ApiProperty`, CLI-плагин) | Через `z.toJSONSchema()` или `nestjs-zod` |
| Общие схемы с фронтендом | Неудобно (декораторы, классы) | Естественно |
| Преобразования | `@Transform`, `@Type` | `transform`, `coerce`, `pipe` |
| Композиция | Mapped types | `pick`, `omit`, `partial`, `extend`, `merge`, unions |

Выбирают один подход на проект, чтобы не смешивать стили.

## Где Zod полезен в бэкенде

| Граница | Пример |
| --- | --- |
| HTTP-вход | `@Body({ schema })`, `@Query({ schema })` |
| Конфигурация | `ConfigModule.forRoot({ validationSchema: envSchema })` |
| Внешние API | `responseSchema.parse(await res.json())` |
| Вебхуки | Проверка payload от платёжного провайдера |
| Очереди | Проверка данных задачи в воркере |
| Ответы API (контракт) | Схема ответа как документация и тест |

## Ответ внешнего API

```ts
const rateSchema = z.object({ base: z.literal('USD'), rates: z.record(z.string(), z.number().positive()) });

const res = await fetch('https://api.example.com/rates');
const data = rateSchema.parse(await res.json());   // ошибка сразу, а не undefined в глубине кода
```

## Частые ошибки

- Считать, что `z.infer` проверяет данные — тип не выполняется в рантайме, нужен `parse`/pipe.
- Смешивать в одном проекте DTO-классы и Zod без правила, где что.
- `z.any()` на границах — проверка теряет смысл.
- Старый синтаксис Zod 3 (`z.string().email()`) в новых материалах — в Zod 4 предпочтительны `z.email()` и др.

## Что важно помнить

- Zod = рантайм-проверка + вывод типа из одной схемы.
- NestJS 12 поддерживает Zod из коробки через Standard Schema.
- Проверяйте всё, что приходит извне.

## Мини-шпаргалка

- `const s = z.object({...})`, `type T = z.infer<typeof s>`.
- `@Body({ schema: s })` + `StandardSchemaValidationPipe`.
- `s.parse(x)` / `s.safeParse(x)`.
- `ConfigModule.forRoot({ validationSchema: envSchema })`.
