# Чем parse отличается от safeParse

> [!NOTE]
> `schema.parse(input)` проверяет данные и **возвращает результат** (с применёнными `default`, `transform`, `coerce` и без лишних ключей объекта) либо **бросает `ZodError`** со списком проблем (`error.issues`: `path`, `message`, `code`). `schema.safeParse(input)` не бросает исключение, а возвращает **дискриминированный результат** `{ success: true, data } | { success: false, error }` — после проверки `if (!result.success)` TypeScript сужает тип. Для схем с асинхронными проверками (`refine(async ...)`, `transform(async ...)`) нужны `parseAsync` / `safeParseAsync`, иначе Zod бросит ошибку о синхронном вызове. `parse` удобен там, где ошибка — исключительная ситуация (скрипты, конфигурация, ответы внешних API), `safeParse` — там, где ошибку нужно обработать и превратить в ответ (pipes, обработчики вебхуков). Для вывода ошибок есть `z.prettifyError(error)` (читаемый текст), `z.flattenError(error)` (поля → сообщения) и `z.treeifyError(error)` (вложенная структура).

## Вопрос

Чем `parse` отличается от `safeParse` в Zod и когда что использовать?

## parse

```ts
const config = envSchema.parse(process.env);   // при ошибке приложение не стартует — так и нужно

try {
  const dto = createUserSchema.parse(body);
} catch (e) {
  if (e instanceof z.ZodError) {
    console.log(e.issues);
    // [{ code: 'invalid_format', format: 'email', path: ['email'], message: 'Invalid email address' }]
  }
}
```

## safeParse

```ts
const result = createUserSchema.safeParse(body);

if (!result.success) {
  return { status: 400, errors: z.flattenError(result.error).fieldErrors };
  // { email: ['Invalid email address'], name: ['Too small: expected string to have >=2 characters'] }
}

result.data;   // тип CreateUserDto, уже с default/transform
```

## Async-проверки

```ts
const signupSchema = z.object({
  email: z.email().refine(async (email) => !(await isDisposableDomain(email)), 'Disposable emails are not allowed'),
});

await signupSchema.parseAsync(body);
const res = await signupSchema.safeParseAsync(body);
signupSchema.parse(body);   // ✗ ошибка: схема содержит async-проверку
```

## Форматирование ошибок

```ts
const r = schema.safeParse(input);
if (!r.success) {
  z.prettifyError(r.error);
  // ✖ Invalid email address
  //   → at email
  // ✖ Too small: expected array to have >=1 items
  //   → at items

  z.flattenError(r.error);   // { formErrors: [], fieldErrors: { email: [...], items: [...] } }
  z.treeifyError(r.error);   // вложенная структура для вложенных объектов
}
```

## Что использовать

| Ситуация | Метод |
| --- | --- |
| Env и конфигурация при старте | `parse` — упасть сразу |
| Ответ внешнего API | `parse` (или `safeParse` + логирование и fallback) |
| Pipe / обработчик запроса | `safeParse` → `BadRequestException` с деталями |
| Вебхук | `safeParse` → 400 и лог |
| Схема с async `refine` | `parseAsync` / `safeParseAsync` |

## Частые ошибки

- Использовать исходный `input` вместо `result.data` — теряются `default`, `transform` и удаление лишних ключей.
- `parse` в обработчике без `try/catch` — клиент получит 500 вместо 400.
- Синхронный `parse` для схемы с async-проверкой.
- Отдавать клиенту сырой `error` со всем содержимым вместо отформатированных полей.

## Что важно помнить

- `parse` — бросает `ZodError`, `safeParse` — возвращает `{ success, data | error }`.
- Используйте `data` из результата, а не исходный объект.
- Async-проверки — `parseAsync`/`safeParseAsync`.

## Мини-шпаргалка

- `schema.parse(x)` → данные или `ZodError`.
- `schema.safeParse(x)` → `{ success, data, error }`.
- `z.prettifyError`, `z.flattenError`, `z.treeifyError`.
- `parseAsync`, `safeParseAsync`.
