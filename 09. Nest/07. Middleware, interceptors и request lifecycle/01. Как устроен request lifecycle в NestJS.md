# Как устроен request lifecycle в NestJS

> [!NOTE]
> Каждый HTTP-запрос в NestJS проходит фиксированный конвейер: **middleware** (глобальные, затем модульные) → **guards** (глобальные → контроллера → метода) → **interceptors до** вызова (в том же порядке) → **pipes** (глобальные → контроллера → метода → параметра) → **обработчик** контроллера и сервисы → **interceptors после** (в обратном порядке, через RxJS-поток ответа) → отправка ответа. Если на любом шаге выброшено исключение, его перехватывают **exception filters** — от уровня метода к глобальному, первый подходящий формирует ответ. Понимание порядка объясняет практические вещи: почему guard не видит провалидированный DTO (pipes ещё не выполнились), почему interceptor измеряет время вместе с pipes, почему middleware не знает, какой обработчик будет вызван, и где подключать каждую сквозную задачу.

## Вопрос

Как устроен жизненный цикл запроса в NestJS и как отвечать на этот вопрос на собеседовании?

## Схема

```text
Request
  │
  ├─ Middleware            global (app.use) → module (MiddlewareConsumer)
  ├─ Guards                global → controller → route
  ├─ Interceptors (before) global → controller → route
  ├─ Pipes                 global → controller → route → param
  ├─ Controller handler  → Service → Repository
  ├─ Interceptors (after)  route → controller → global   (обратный порядок)
  ├─ Exception filters     route → controller → global   (только при ошибке)
  ▼
Response
```

## Что для чего

| Этап | Знает обработчик | Типичные задачи |
| --- | --- | --- |
| Middleware | Нет | Логирование запроса, request id, `cookie-parser`, `helmet`, CORS |
| Guard | Да (`ExecutionContext`, метаданные) | Аутентификация, роли, API-ключи, feature flags |
| Interceptor | Да | Время выполнения, трансформация ответа, кеш, таймауты, ретраи, сериализация |
| Pipe | Да (параметр и его тип) | Валидация, преобразование типов |
| Filter | Да | Формат ошибок, логирование, перевод доменных ошибок в HTTP |

## Пример: что выполнится

```ts
@Controller('orders')
@UseGuards(JwtAuthGuard)
@UseInterceptors(LoggingInterceptor)
export class OrdersController {
  @Post()
  @UseGuards(RolesGuard)
  @Roles(['customer'])
  @UseInterceptors(TimeoutInterceptor)
  create(@Body() dto: CreateOrderDto) {}   // ValidationPipe глобально
}
```

```text
RequestIdMiddleware
→ ThrottlerGuard (global) → JwtAuthGuard → RolesGuard
→ LoggingInterceptor (до) → TimeoutInterceptor (до)
→ ValidationPipe(CreateOrderDto)
→ create()
→ TimeoutInterceptor (после) → LoggingInterceptor (после)
```

Если `JwtAuthGuard` бросит 401 — interceptors, pipes и обработчик не выполнятся; ответ сформирует filter.

## Как ответить на собеседовании

1. Назвать порядок: middleware → guards → interceptors → pipes → handler → interceptors → response; ошибки — в filters.
2. Объяснить разницу middleware и guard: guard знает обработчик и метаданные.
3. Сказать про уровни: глобальный → контроллер → метод (→ параметр для pipes) и обратный порядок interceptors на выходе.
4. Привести пример, куда положить логирование, auth, валидацию и формат ошибок.
5. Упомянуть, что для WebSocket и микросервисов работают guards/interceptors/pipes/filters, но не HTTP-middleware.

## Частые ошибки

- Проверять DTO в guard — он ещё не провалидирован.
- Делать авторизацию в middleware — нет доступа к `@Roles`.
- Ожидать, что interceptor перехватит исключение, выброшенное в guard (guards выполняются раньше).
- Форматировать ошибки interceptor-ом вместо filter.

## Что важно помнить

- Middleware → Guards → Interceptors → Pipes → Handler → Interceptors → Response.
- Ошибки на любом этапе — в exception filters.
- Каждая сквозная задача — на своём этапе.

## Мини-шпаргалка

- Логи запроса, request id → middleware.
- Auth, роли → guards.
- Время, трансформация ответа, кеш → interceptors.
- Валидация → pipes.
- Формат ошибок → filters.
