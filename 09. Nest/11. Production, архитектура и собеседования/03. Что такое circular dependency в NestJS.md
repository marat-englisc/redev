# Что такое circular dependency в NestJS

> [!NOTE]
> **Циклическая зависимость** возникает, когда A зависит от B, а B — от A (напрямую или через цепочку). В NestJS бывает два уровня: **между провайдерами** (`UsersService` ↔ `AuthService`) и **между модулями** (`UsersModule` импортирует `OrdersModule` и наоборот), а также цикл **импортов файлов**, из-за которого в момент чтения метаданных класс ещё `undefined` (в ошибке — `?` или `undefined` вместо имени). Технический обход — **`forwardRef(() => X)`** с обеих сторон: в `imports` модулей и в `@Inject(forwardRef(() => Service))` у провайдеров; есть и `ModuleRef.get()` для ленивого получения. Но цикл почти всегда — **симптом неудачных границ**: правильнее выделить общую логику в третий модуль/сервис, развернуть зависимость через интерфейс-порт или заменить прямой вызов **событием**. `forwardRef` оставляют как временное решение.

## Вопрос

Что такое циклическая зависимость в NestJS и как её устранить?

## Пример цикла

```ts
@Injectable()
export class UsersService {
  constructor(private readonly orders: OrdersService) {}       // при удалении пользователя отменить заказы
}

@Injectable()
export class OrdersService {
  constructor(private readonly users: UsersService) {}         // при заказе проверить пользователя
}
```

```text
Nest cannot create the UsersModule instance.
The module at index [0] of the UsersModule "imports" array is undefined.
Potential causes: A circular dependency between modules. Use forwardRef() to avoid it.
```

## Обход: forwardRef

```ts
@Module({ imports: [forwardRef(() => OrdersModule)], providers: [UsersService], exports: [UsersService] })
export class UsersModule {}

@Module({ imports: [forwardRef(() => UsersModule)], providers: [OrdersService], exports: [OrdersService] })
export class OrdersModule {}

@Injectable()
export class UsersService {
  constructor(@Inject(forwardRef(() => OrdersService)) private readonly orders: OrdersService) {}
}
```

Ограничения: порядок создания не гарантирован, использовать зависимость в конструкторе нельзя, не работает с request-scoped провайдерами в цикле.

## Исправление 1: события

```ts
// users публикует факт, orders подписывается — users больше не зависит от orders
this.events.emit('user.deleted', new UserDeletedEvent(userId));

@OnEvent('user.deleted')
cancelOrders(e: UserDeletedEvent) { return this.orders.cancelAllForUser(e.userId); }
```

## Исправление 2: выделить общее

```text
до:  UsersModule ↔ OrdersModule
после: UsersModule → AccountsModule ← OrdersModule
       (AccountsModule содержит то, что нужно обоим, например проверку статуса аккаунта)
```

## Исправление 3: инвертировать зависимость

```ts
// orders определяет, что ему нужно знать о пользователе
export abstract class CustomerLookup {
  abstract isActive(userId: string): Promise<boolean>;
}

// users реализует порт и экспортирует под этим токеном
@Module({
  providers: [UsersService, { provide: CustomerLookup, useExisting: UsersService }],
  exports: [CustomerLookup],
})
export class UsersModule {}
```

## Цикл импортов файлов

```ts
// a.ts
import { B } from './b';        // b.ts импортирует a.ts → в момент декорирования один из классов undefined
```

Признак — ошибка с `?`. Решение: разнести типы и константы в отдельные файлы, избегать «barrel»-файлов `index.ts`, которые реэкспортируют всё подряд, проверить `npx madge --circular src`.

## Частые ошибки

- Ставить `forwardRef` только с одной стороны.
- Использовать `forwardRef` как постоянную архитектуру.
- Barrel-файлы, создающие скрытые циклы импортов.
- Вызов зависимости из `forwardRef` в конструкторе.

## Что важно помнить

- Цикл — сигнал о неудачных границах модулей.
- `forwardRef` — обход, а не решение.
- Исправления: события, выделение общего модуля, инверсия через порт.

## Мини-шпаргалка

- `imports: [forwardRef(() => XModule)]`.
- `@Inject(forwardRef(() => XService))`.
- `?` в ошибке → цикл файлов, `madge --circular`.
- Вместо цикла — `emit` + `@OnEvent`.
