# Как структурировать NestJS проект

> [!NOTE]
> Для большинства продуктов на NestJS подходит **модульный монолит**: один деплой, одна кодовая база, но код разделён на **модули по доменным областям** (`users`, `catalog`, `orders`, `billing`) с явными публичными API (экспортируемыми сервисами-фасадами) и инфраструктурными модулями (`database`, `cache`, `queue`, `mail`). Внутри модуля код организуют **слоями**: транспорт (контроллеры, resolvers, gateways, обработчики очередей) → прикладные сервисы / use cases → доменная логика → доступ к данным (репозитории). Зависимости направлены внутрь: домен не знает об HTTP и ORM. Связь между модулями — через экспортированные сервисы или **события**; прямой доступ к чужим репозиториям и таблицам запрещён. Для больших систем используют идеи DDD и hexagonal architecture (порты и адаптеры), CQRS (`@nestjs/cqrs`) — там, где разделение команд и запросов действительно упрощает модель. Монорепозиторий (Nest workspace, Nx, Turborepo) нужен, когда приложений несколько.

## Вопрос

Как структурировать NestJS-проект, чтобы он хорошо масштабировался?

## Модульный монолит

```text
src/
├── main.ts
├── app.module.ts
├── config/                     # env-схема, namespace-конфиги
├── infrastructure/
│   ├── database/               # PrismaModule
│   ├── cache/                  # CacheModule (Redis)
│   ├── queue/                  # BullModule.forRoot
│   └── mail/                   # MailModule (адаптер SMTP/Resend)
├── common/                     # guards, filters, interceptors, decorators — без бизнес-логики
└── modules/
    ├── users/
    ├── catalog/
    ├── orders/
    │   ├── orders.module.ts
    │   ├── api/                # controllers, DTO
    │   ├── application/        # use cases / services
    │   ├── domain/             # сущности, правила, доменные ошибки и события
    │   └── infrastructure/     # репозитории, внешние клиенты
    └── billing/
```

Для небольших модулей достаточно плоской структуры (`controller`, `service`, `repository`, `dto/`) — слои вводят, когда модуль растёт.

## Правила зависимостей

```text
api ──► application ──► domain
              │
              └──► infrastructure ──► ORM / внешние API
```

- Домен не импортирует Nest, ORM и HTTP-исключения.
- Модуль `orders` использует `UsersService` (экспорт), но не `prisma.user` напрямую.
- Общий код в `common` — технический, не доменный.
- Циклы между модулями устраняются событиями или выделением общего модуля.

## Порты и адаптеры

```ts
// domain/application: порт
export abstract class PaymentsPort {
  abstract charge(orderId: string, amountCents: number): Promise<{ paymentId: string }>;
}

// infrastructure: адаптер
@Injectable()
export class StripePaymentsAdapter extends PaymentsPort { ... }

// модуль связывает
providers: [{ provide: PaymentsPort, useClass: StripePaymentsAdapter }]
```

## Связь модулей через события

```ts
// orders публикует факт
this.events.emit('order.paid', new OrderPaidEvent(order.id, order.userId));

// loyalty, notifications, analytics реагируют, не будучи зависимостями orders
```

## CQRS — когда уместен

```ts
@CommandHandler(PlaceOrderCommand)
export class PlaceOrderHandler implements ICommandHandler<PlaceOrderCommand> {
  async execute(cmd: PlaceOrderCommand) { ... }
}

await this.commandBus.execute(new PlaceOrderCommand(userId, items));
```

Полезен, когда модель записи и чтения сильно различаются или нужны доменные события и саги. Для CRUD — лишняя сложность.

## Монолит → сервисы

Чёткие границы модулей (свой API, свои таблицы, связь через события) позволяют позже выделить модуль в отдельный сервис, заменив вызовы сервиса на `ClientProxy`, а EventEmitter — на брокер.

## Частые ошибки

- Структура по техническим слоям на всё приложение (`controllers/`, `services/`).
- «Свалка» в `common`/`shared` с бизнес-логикой.
- Модули, читающие таблицы друг друга напрямую.
- DDD и CQRS «по учебнику» для простого CRUD.
- Микросервисы с первого дня без необходимости.

## Что важно помнить

- Модульный монолит с доменными модулями — хороший дефолт.
- Внутри модуля — слои, зависимости внутрь.
- Связь модулей — через публичные сервисы и события.

## Мини-шпаргалка

- `modules/<domain>`, `infrastructure/`, `common/`, `config/`.
- `api → application → domain`, `infrastructure` — адаптеры.
- Абстрактный класс-порт + `useClass` адаптера.
- `@nestjs/cqrs` — только по необходимости.
