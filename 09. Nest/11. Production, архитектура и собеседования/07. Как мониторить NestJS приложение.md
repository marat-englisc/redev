# Как мониторить NestJS приложение

> [!NOTE]
> Наблюдаемость (observability) строится на трёх сигналах. **Метрики** — числа во времени: RPS, задержки (p50/p95/p99), доля ошибок, использование CPU/памяти, event loop lag, размер пула БД, длина очередей; обычно Prometheus-формат (`prom-client`, `/metrics`) и дашборды Grafana. **Логи** — структурированные события с requestId. **Трейсы** — путь запроса через сервисы, БД и внешние API с длительностью каждого шага; стандарт — **OpenTelemetry** с автоинструментированием HTTP, `pg`, Redis, и экспортом в Jaeger/Tempo/Datadog. Плюс **health checks** через `@nestjs/terminus`: liveness (процесс жив) и readiness (готов принимать трафик: БД, Redis доступны); в NestJS 12 свои индикаторы пишутся через `HealthIndicatorService`. Алерты настраивают на симптомы, видимые пользователю (рост ошибок и задержек — «golden signals»), а не на каждую метрику.

## Вопрос

Как мониторить NestJS-приложение в продакшене?

## Health checks (Terminus)

```bash
npm install @nestjs/terminus
```

```ts
@Controller('health')
export class HealthController {
  constructor(
    private readonly health: HealthCheckService,
    private readonly prismaHealth: PrismaHealthIndicator,
    private readonly memory: MemoryHealthIndicator,
    private readonly redisHealth: RedisHealthIndicator,
    private readonly prisma: PrismaService,
  ) {}

  @Get('live')
  @HealthCheck()
  live() {
    return this.health.check([() => this.memory.checkHeap('heap', 512 * 1024 * 1024)]);
  }

  @Get('ready')
  @HealthCheck()
  ready() {
    return this.health.check([
      () => this.prismaHealth.pingCheck('db', this.prisma),
      () => this.redisHealth.isHealthy('redis'),
    ]);
  }
}
```

## Свой индикатор (NestJS 12)

```ts
@Injectable()
export class RedisHealthIndicator {
  constructor(private readonly indicator: HealthIndicatorService, @Inject(REDIS) private readonly redis: Redis) {}

  async isHealthy(key: string) {
    const check = this.indicator.check(key);
    try {
      await this.redis.ping();
      return check.up();
    } catch (e) {
      return check.down({ message: (e as Error).message });
    }
  }
}
```

Liveness не должен зависеть от внешних систем — иначе при падении БД оркестратор перезапустит все поды, что не поможет.

## Метрики

```ts
// metrics.module.ts — prom-client
const httpDuration = new Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP request duration',
  labelNames: ['method', 'route', 'status'],
  buckets: [0.01, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5],
});

@Injectable()
export class MetricsInterceptor implements NestInterceptor {
  intercept(ctx: ExecutionContext, next: CallHandler) {
    const req = ctx.switchToHttp().getRequest();
    const end = httpDuration.startTimer({ method: req.method });
    return next.handle().pipe(
      finalize(() => end({ route: req.route?.path ?? 'unknown', status: ctx.switchToHttp().getResponse().statusCode })),
    );
  }
}

@Controller('metrics')
export class MetricsController {
  @Get() @Header('Content-Type', register.contentType)
  metrics() { return register.metrics(); }
}
```

Лейбл `route` — шаблон пути (`/orders/:id`), а не реальный URL, иначе кардинальность метрик взорвётся. `collectDefaultMetrics()` добавит память, GC, event loop lag. Эндпоинт `/metrics` не открывают наружу.

## Трейсинг (OpenTelemetry)

```ts
// instrumentation.ts — подключается ДО импорта приложения: node --import ./dist/instrumentation.js dist/main.js
const sdk = new NodeSDK({
  serviceName: 'orders-api',
  traceExporter: new OTLPTraceExporter({ url: process.env.OTEL_EXPORTER_OTLP_ENDPOINT }),
  instrumentations: [getNodeAutoInstrumentations()],     // http, express, pg, ioredis, ...
});
sdk.start();
```

Trace id добавляют в логи — тогда из записи об ошибке можно перейти к трейсу.

## Что мониторить

| Сигнал | Метрика |
| --- | --- |
| Трафик | RPS по маршрутам |
| Ошибки | Доля 5xx, ошибки интеграций |
| Задержки | p95/p99 по маршрутам |
| Насыщение | CPU, память, event loop lag, пул БД, длина очередей BullMQ |
| Бизнес | Заказы в минуту, неуспешные платежи |

## Частые ошибки

- Liveness проверяет БД — каскадные рестарты.
- Метрики с userId или полным URL в лейблах.
- Только логи, без метрик и трейсов.
- Алерты на всё подряд — команда перестаёт их читать.
- Открытые `/metrics` и `/health` с деталями наружу.

## Что важно помнить

- Метрики + логи + трейсы + health checks.
- Terminus: liveness без внешних зависимостей, readiness с ними; NestJS 12 — `HealthIndicatorService`.
- OpenTelemetry для трейсов, Prometheus для метрик, алерты на golden signals.

## Мини-шпаргалка

- `@HealthCheck()` + `health.check([...])`.
- `HealthIndicatorService.check(key).up()/down()`.
- `prom-client`: `Histogram`, `collectDefaultMetrics()`.
- OpenTelemetry `NodeSDK` + auto-instrumentations, `--import`.
