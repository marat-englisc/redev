# Как масштабировать NestJS WebSocket

> [!NOTE]
> WebSocket-соединение долгоживущее и **привязано к конкретному процессу**. При нескольких репликах клиент A подключён к инстансу 1, клиент B — к инстансу 2, и `server.to(room).emit()` на инстансе 1 не дойдёт до B. Решение для Socket.IO — **Redis adapter** (`@socket.io/redis-adapter` или streams-адаптер): каждое событие публикуется в Redis и рассылается всем инстансам, которые доставляют его своим клиентам; комнаты и `server.emit` начинают работать на весь кластер. Второе требование — **sticky sessions** на балансировщике, если Socket.IO может начинать с HTTP long-polling (handshake из нескольких запросов должен попасть на один инстанс); при `transports: ['websocket']` без polling sticky не обязательны. Также учитывают: аутентификацию при подключении, лимиты соединений на процесс и файловых дескрипторов, таймауты idle на прокси (ping/pong), graceful shutdown с переподключением клиентов на другие инстансы и состояние (кто онлайн) — в Redis, а не в памяти.

## Вопрос

Как масштабировать WebSocket в NestJS на несколько инстансов?

## Проблема

```text
Клиент A ──► Instance 1   server.to('room:42').emit('msg')  → доходит только до клиентов Instance 1
Клиент B ──► Instance 2                                       → B ничего не получает
```

## Redis adapter

```bash
npm install @socket.io/redis-adapter redis
```

```ts
export class RedisIoAdapter extends IoAdapter {
  private adapterConstructor: ReturnType<typeof createAdapter>;

  async connectToRedis(url: string) {
    const pubClient = createClient({ url });
    const subClient = pubClient.duplicate();
    await Promise.all([pubClient.connect(), subClient.connect()]);
    this.adapterConstructor = createAdapter(pubClient, subClient);
  }

  createIOServer(port: number, options?: ServerOptions) {
    const server = super.createIOServer(port, options);
    server.adapter(this.adapterConstructor);
    return server;
  }
}

// main.ts
const redisIoAdapter = new RedisIoAdapter(app);
await redisIoAdapter.connectToRedis(config.getOrThrow('REDIS_URL'));
app.useWebSocketAdapter(redisIoAdapter);
```

```text
Instance 1: emit('room:42') → Redis pub/sub → Instance 1, 2, 3 → их клиенты в room:42
```

## Sticky sessions

```ts
// клиент без long-polling — sticky не нужны
io(url, { transports: ['websocket'], auth: { token } });
```

```nginx
# nginx с polling — привязка по IP или cookie
upstream ws_backend {
  ip_hash;
  server api-1:3000;
  server api-2:3000;
}
location /socket.io/ {
  proxy_pass http://ws_backend;
  proxy_http_version 1.1;
  proxy_set_header Upgrade $http_upgrade;
  proxy_set_header Connection "upgrade";
  proxy_read_timeout 120s;
}
```

## Отправка из любого места

С Redis adapter событие можно отправить из HTTP-обработчика или воркера на любом инстансе. Если отправитель — отдельный процесс без Socket.IO-сервера (например, BullMQ-воркер), используют `@socket.io/redis-emitter`:

```ts
const emitter = new Emitter(redisClient);
emitter.to(`user:${userId}`).emit('export:ready', { url });
```

## Состояние кластера

| Данные | Где хранить |
| --- | --- |
| Комнаты и рассылка | Redis adapter |
| Онлайн-статус, присутствие | Redis (set/hash с TTL) |
| История сообщений | БД |
| Rate limit событий | Redis |

## Остановка и переподключение

При деплое инстанс закрывает соединения, клиенты переподключаются к другим инстансам. Нужны: экспоненциальная задержка переподключения на клиенте (Socket.IO делает сам), дозапрос пропущенных событий по последнему id, `connectionStateRecovery` для коротких разрывов.

## Ёмкость

- Лимит открытых файлов (`ulimit -n`) и памяти на соединение.
- Ping/pong интервалы короче idle-таймаута прокси и балансировщика.
- Метрики: число соединений на инстанс, события в секунду, задержка доставки.
- Для очень больших нагрузок — выделенные realtime-сервисы или управляемые решения (Ably, Pusher, Centrifugo).

## Частые ошибки

- Несколько реплик без адаптера — «пропадающие» сообщения.
- Polling + балансировщик без sticky — ошибки `Session ID unknown`.
- Онлайн-статусы в памяти инстанса.
- Нет `Upgrade`/`Connection` заголовков в прокси.

## Что важно помнить

- WebSocket привязан к процессу; рассылка в кластере — через Redis adapter.
- Sticky sessions нужны при long-polling.
- Состояние — в Redis/БД, клиенты должны уметь переподключаться.

## Мини-шпаргалка

- `createAdapter(pub, sub)` + свой `IoAdapter` + `app.useWebSocketAdapter()`.
- `transports: ['websocket']` — без sticky.
- `@socket.io/redis-emitter` — отправка из воркеров.
- nginx: `Upgrade`, `Connection: upgrade`, `proxy_read_timeout`.
