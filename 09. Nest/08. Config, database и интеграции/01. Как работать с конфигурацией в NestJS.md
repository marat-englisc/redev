# Как работать с конфигурацией в NestJS

> [!NOTE]
> Конфигурация (порты, URL баз, ключи, лимиты, флаги) приходит из **переменных окружения** — по принципу twelve-factor она отделена от кода и различается между окружениями. В NestJS её читают через `@nestjs/config`: `ConfigModule.forRoot()` загружает `.env` (через dotenv) и `process.env`, валидирует их при старте (`validationSchema` или `validate`), а `ConfigService` внедряется в провайдеры. Удобные возможности: `isGlobal: true` (не импортировать в каждом модуле), **`registerAs('database', () => ({...}))`** — типизированные namespace-конфиги, которые внедряются через `@Inject(databaseConfig.KEY)` с типом `ConfigType<typeof databaseConfig>`; `getOrThrow()` — падать, если значения нет; `get(key, { infer: true })` — типизация по интерфейсу; `cache: true` — ускорение; `envFilePath` — несколько файлов (первый имеет приоритет); `expandVariables` — ссылки `${VAR}` внутри `.env`. В коде за пределами конфиг-модуля `process.env` не читают.

## Вопрос

Как организовать конфигурацию NestJS-приложения?

## Подключение

```ts
@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal: true,
      cache: true,
      envFilePath: ['.env.local', '.env'],            // .env.local важнее
      load: [appConfig, databaseConfig, authConfig],  // namespace-конфиги
      validationSchema: envSchema,                    // Zod / Joi / любая Standard Schema
    }),
  ],
})
export class AppModule {}
```

## Namespace-конфиги

```ts
// config/database.config.ts
export const databaseConfig = registerAs('database', () => ({
  url: process.env.DATABASE_URL!,
  poolSize: Number(process.env.DB_POOL_SIZE ?? 10),
  ssl: process.env.DB_SSL === 'true',
}));

// использование — типизированно
@Injectable()
export class DbHealth {
  constructor(@Inject(databaseConfig.KEY) private readonly db: ConfigType<typeof databaseConfig>) {}
  info() { return { pool: this.db.poolSize, ssl: this.db.ssl }; }
}

// или через ConfigService по ключу
this.config.get<number>('database.poolSize');
```

## ConfigService

```ts
@Injectable()
export class MailService {
  private readonly from: string;

  constructor(private readonly config: ConfigService<EnvVars, true>) {
    this.from = this.config.getOrThrow('MAIL_FROM');                 // string, без undefined
    const port = this.config.get('SMTP_PORT', { infer: true });       // тип из EnvVars
  }
}
```

## Feature-конфиг и async-модули

```ts
@Module({
  imports: [ConfigModule.forFeature(authConfig)],     // конфиг только для модуля
})
export class AuthModule {}

JwtModule.registerAsync({
  inject: [authConfig.KEY],
  useFactory: (auth: ConfigType<typeof authConfig>) => ({ secret: auth.accessSecret, signOptions: { expiresIn: '15m' } }),
});
```

## Файлы окружения

```text
.env.example     ← в git: список переменных без значений секретов
.env             ← локально, в .gitignore
.env.test        ← для тестов
```

В проде `.env` обычно не используется: переменные задаёт платформа (Kubernetes Secrets, Docker Compose `env_file`, Vercel, Railway), а секреты — secret manager. Чтобы `ConfigModule` не искал файл, есть `ignoreEnvFile: true`.

## Частые ошибки

- `process.env.X` в сервисах — нет валидации, типов и единого места.
- Секреты в git или в Docker-образе.
- Нет валидации — приложение стартует и падает позже на первом запросе.
- `ConfigModule.forRoot()` без `isGlobal` и ошибки DI в модулях.
- `Number(process.env.PORT)` без проверки — `NaN`.

## Что важно помнить

- Конфигурация — из окружения, через `@nestjs/config`.
- `registerAs` + `ConfigType` — типизированные namespace-конфиги.
- Валидация при старте и `getOrThrow` для обязательных значений.

## Мини-шпаргалка

- `ConfigModule.forRoot({ isGlobal, load, validationSchema, envFilePath })`.
- `registerAs('ns', () => ({...}))` → `@Inject(cfg.KEY) c: ConfigType<typeof cfg>`.
- `config.getOrThrow('KEY')`, `get('KEY', { infer: true })`.
- `.env.example` в git, `.env` — нет.
