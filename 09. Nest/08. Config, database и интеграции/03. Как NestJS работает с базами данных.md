# Как NestJS работает с базами данных

> [!NOTE]
> NestJS не содержит собственного слоя работы с БД и не навязывает ORM: база подключается через **провайдер** — экземпляр клиента, зарегистрированный в инфраструктурном модуле и внедряемый в репозитории и сервисы. Популярные варианты: **Prisma** (schema-first, сгенерированный типизированный клиент, свои миграции — рецепт есть в документации Nest), **TypeORM** (официальный пакет `@nestjs/typeorm`, entity-классы с декораторами, репозитории), **MikroORM** (Unit of Work, Identity Map), **Drizzle** и **Kysely** (типизированный SQL-подобный API), **Mongoose** (`@nestjs/mongoose` для MongoDB) и «сырой» драйвер (`pg`). Общие правила: **один клиент/пул на приложение** (синглтон-провайдер), подключение и закрытие — в lifecycle hooks, конфигурация — из `ConfigService`, транзакционные границы — в сервисах, миграции — отдельным шагом деплоя, а не `synchronize` в проде.

## Вопрос

Как NestJS работает с базами данных и какой инструмент выбрать?

## Общая схема

```text
Controller → Service → Repository → DB-провайдер (PrismaService / DataSource / Pool) → PostgreSQL
                                 ↑
                    DatabaseModule (global или импортируемый)
```

## Сырой драйвер как провайдер

```ts
export const PG_POOL = Symbol('PG_POOL');

@Module({
  providers: [
    {
      provide: PG_POOL,
      inject: [ConfigService],
      useFactory: (config: ConfigService) => new Pool({ connectionString: config.getOrThrow('DATABASE_URL'), max: 10 }),
    },
  ],
  exports: [PG_POOL],
})
export class DatabaseModule implements OnApplicationShutdown {
  constructor(@Inject(PG_POOL) private readonly pool: Pool) {}
  onApplicationShutdown() { return this.pool.end(); }
}
```

## Правила

- Клиент — синглтон; пул соединений рассчитан под число инстансов (`инстансы × pool ≤ max_connections`).
- `onModuleInit` — подключение и проверка доступности; `onApplicationShutdown` — закрытие (+ `app.enableShutdownHooks()`).
- Контроллер не обращается к БД напрямую.
- Транзакции — в сервисах; внешние HTTP-вызовы внутри транзакции не делают.
- Миграции применяются шагом CI/CD (`prisma migrate deploy`, `typeorm migration:run`) до запуска новой версии.
- `synchronize: true` / `prisma db push` — только для прототипов.
- Индексы и запросы проверяются `EXPLAIN` — ORM не отменяет SQL-мышления.

## Несколько баз

```ts
TypeOrmModule.forRootAsync({ name: 'analytics', useFactory: ... });
@InjectRepository(Event, 'analytics') private readonly events: Repository<Event>;
```

Для Prisma — несколько схем и сгенерированных клиентов с разными `output`, каждый в своём провайдере.

## Частые ошибки

- `new PrismaClient()` в каждом сервисе — множество пулов и исчерпание соединений.
- `synchronize: true` в проде — потеря данных при изменении entity.
- Нет закрытия соединений при остановке.
- N+1 из-за ленивых связей ORM.

## Что важно помнить

- БД в Nest — это провайдер в инфраструктурном модуле.
- Выбор ORM — по задачам команды; Prisma и TypeORM — самые распространённые.
- Один пул, lifecycle hooks, миграции отдельным шагом.

## Мини-шпаргалка

- `DatabaseModule` экспортирует клиент.
- `onModuleInit` → connect, `onApplicationShutdown` → close.
- Миграции в CI/CD, не `synchronize`.
- Транзакции — в сервисах.
