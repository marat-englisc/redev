# Как использовать sudo, su и минимальные привилегии

> [!NOTE]
> `sudo` запускает разрешённую политикой команду от другого пользователя, обычно root; `su` переключает пользователя и shell по своим правилам аутентификации. Root имеет UID 0 и широкие полномочия. Рабочая привычка — использовать обычного пользователя, а повышать права для конкретной административной операции. Политику sudoers редактируют через `visudo`.

## Вопрос

Чем sudo отличается от su? Почему права на запуск одного редактора через sudo могут фактически дать полный root-доступ?

## Основные сценарии

```bash
sudo -l
sudo -u nobody id
sudo -k
```

`sudo -l` показывает разрешения, `-u` выбирает пользователя, `-k` сбрасывает кеш аутентификации. Доступность команды от `nobody` зависит от политики; этот пример не создаёт служебную учётную запись.

`sudo -i` открывает login shell с административными правами. Это полезно для некоторых задач, но увеличивает область случайной ошибки. Заверши такую сессию `exit`, когда она больше не нужна.

## Разница с su

`su - имя` запускает login shell выбранного пользователя. В обычной локальной конфигурации su просит пароль целевого пользователя, а sudo — пароль вызывающего; конкретное поведение задают PAM и политика. У root пароль может быть заблокирован, а администрирование работать через sudo.

## Почему «одна команда» иногда означает всё

Редактор с запуском shell-команд, интерпретатор Python, shell, пакетный менеджер или программа, способная записать произвольный системный файл, могут позволить обойти намерение узкого разрешения. Строка sudoers должна учитывать аргументы, доступные файлы и возможности самой программы.

Не добавляй `NOPASSWD: ALL` ради удобства одного скрипта. `sudo visudo` проверяет синтаксис, но не доказывает безопасность политики.

## Типичная ошибка перенаправления

```text
sudo printf ... > /etc/example.conf
```

Файл открывает родительский shell, у которого нет повышенных прав. Для ручной правки применяют `sudoedit`, для записи потока — тщательно выбранный `sudo tee`.

## Практика

Изучи `sudo -l` в своей VM. Выполни `id` обычным пользователем и `sudo id`, сравни UID. Не меняй политику: задача — понять разницу контекстов, а не расширить свои полномочия.
