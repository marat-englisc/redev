# Как понимать память, page cache, swap и OOM

> [!NOTE]
> Linux использует свободную RAM для кеша файлов, поэтому низкий показатель free сам по себе не означает нехватку памяти. Available оценивает память, доступную приложениям без существенной необходимости swapping. Swap — дополнительное место для вытеснения некоторых страниц, а не быстрая замена RAM. OOM может возникнуть как на уровне хоста, так и из-за лимита cgroup.

## Вопрос

Почему сервер с большим cached не обязательно перегружен? Как подтвердить, что процесс завершил именно OOM killer?

## Начальные наблюдения

```bash
free -h
grep -E 'MemAvailable|Cached|SwapTotal|SwapFree' /proc/meminfo
vmstat 1 5
ps -eo pid,rss,vsz,comm --sort=-rss | head -n 12
```

`RSS` — резидентная память процесса; общие страницы могут учитываться у нескольких процессов. `VSZ` — виртуальное адресное пространство, не объём реально занятой RAM. Сумма RSS не является точной оценкой уникально занятой памяти всех приложений.

## Page cache

После чтения файла его страницы могут остаться в RAM для ускорения повторных чтений. Значительную часть чистого файлового кеша ядро может освободить под приложения. Записанные, но ещё не сброшенные на диск страницы требуют другого обращения.

Не запускай очистку cache «для здоровья сервера»: она способна ухудшить задержки и не устраняет утечку памяти приложения.

## Swap и давление

Сам факт занятого swap не доказывает текущую проблему: там могут оставаться давно неиспользуемые страницы. Важны динамика, latency и `si/so` в последующих строках `vmstat`. Постоянный активный обмен со swap при недостаточной RAM может резко замедлять приложение.

## OOM

```bash
sudo journalctl -k -b --since '1 hour ago' --no-pager
```

Ищи сообщения о нехватке памяти и выбранном процессе, сопоставляй время. Для cgroup v2 полезен `memory.events` нужной группы: счётчики `oom` и `oom_kill` помогают подтвердить ограничение. Отдельный userspace-менеджер, например systemd-oomd, также способен завершать процессы при давлении памяти.

Контейнер может получить OOM при свободной RAM хоста, если достиг `memory.max`. Код 137 — подсказка о SIGKILL в типичном shell, но не самостоятельное доказательство OOM.

## Практика

Сравни free и available, найди три крупнейших процесса по RSS. Ничего не выделяй до исчерпания памяти: цель — интерпретация наблюдений, а не авария VM.
