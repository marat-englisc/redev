# Как обрабатывается CSS в сборке

> [!NOTE]
> При сборке CSS проходит свой конвейер: **препроцессор** (Sass, Less) компилирует расширенный синтаксис, **PostCSS** с плагинами (Autoprefixer, Tailwind, postcss-preset-env) или **Lightning CSS** добавляет вендорные префиксы и понижает новые возможности под браузеры, **CSS Modules** делают имена классов локальными, а в production стили **извлекаются** в отдельные `.css`-файлы, **минифицируются** и получают хеш в имени. В dev CSS обычно вставляется через JS, чтобы работал HMR.

## Вопрос

Как CSS обрабатывается в сборке фронтенд-проекта? Что делают PostCSS и Autoprefixer, как работают CSS Modules и почему в production CSS извлекается в отдельные файлы?

## Конвейер

```text
*.scss → Sass → CSS → PostCSS (Tailwind, Autoprefixer, nesting) → CSS Modules (хеш классов)
       → dev: <style> через JS + HMR
       → prod: извлечение в *.css, минификация, хеш в имени, code splitting стилей
```

## PostCSS и Autoprefixer

```javascript
// postcss.config.js
export default {
  plugins: {
    "@tailwindcss/postcss": {},       // Tailwind v4
    autoprefixer: {},                 // префиксы по browserslist
  },
};
```

```css
/* до */
.card { user-select: none; }

/* после Autoprefixer (для старых Safari) */
.card { -webkit-user-select: none; user-select: none; }
```

Vite подхватывает `postcss.config.js` автоматически. Альтернатива — **Lightning CSS** (Rust): префиксы, вложенность, минификация в одном быстром инструменте (`css.transformer: "lightningcss"` в Vite).

## CSS Modules

```css
/* Button.module.css */
.button { padding: 8px 16px; }
.primary { background: var(--color-accent); }
```

```tsx
import styles from "./Button.module.css";

<button className={`${styles.button} ${styles.primary}`}>OK</button>
// в DOM: class="_button_x7a1q_1 _primary_x7a1q_5"
```

Сборщик генерирует уникальные имена, поэтому классы разных компонентов не конфликтуют. Файлы без `.module` остаются глобальными.

## Извлечение CSS в production

| | Dev | Prod |
| --- | --- | --- |
| Как подключается | `<style>` через JS | `<link rel="stylesheet">` к отдельному файлу |
| Зачем | HMR без перезагрузки | CSS грузится параллельно с JS, кешируется, не ждет выполнения JS |
| Инструмент | Vite по умолчанию, `style-loader` | Vite по умолчанию, `MiniCssExtractPlugin` |

CSS ленивых чанков подгружается вместе с ними.

## Критический CSS и производительность

- CSS блокирует рендеринг: держите стили первого экрана небольшими;
- инлайн критического CSS в `<head>` и отложенная загрузка остального (фреймворки и плагины вроде `critters`/`beasties`);
- удаление неиспользуемых стилей: Tailwind генерирует только использованные классы, для обычного CSS — PurgeCSS с осторожностью;
- шрифты: `font-display: swap`, preload основного шрифта.

## Что важно помнить

- Autoprefixer и postcss-preset-env берут целевые браузеры из `browserslist`.
- CSS Modules дают изоляцию на этапе сборки без рантайма, в отличие от runtime CSS-in-JS.
- В production CSS всегда отдельным файлом с хешем; inline-стили через JS только в dev.
- Порядок подключения CSS-файлов влияет на каскад — при code splitting следите за специфичностью или используйте `@layer`.

## Мини-шпаргалка

Sass → PostCSS (Tailwind, Autoprefixer) или Lightning CSS → CSS Modules (`*.module.css`, хеш классов) → dev: `<style>` + HMR, prod: отдельные `.css` с хешем, минификация, CSS по чанкам. Префиксы — по browserslist. Критический CSS — inline.
