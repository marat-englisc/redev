# Зачем нужна сборка и что делает бандлер

> [!NOTE]
> **Сборка** превращает исходный код проекта (TypeScript, JSX, SCSS, импорты npm-пакетов, изображения) в оптимизированные файлы, которые браузер умеет загрузить быстро и без ошибок. **Бандлер** (Vite, webpack, Rspack, Turbopack, esbuild, Rollup) строит граф модулей и выполняет основные шаги: **разрешение импортов**, **транспиляцию**, **объединение модулей в чанки**, **tree shaking**, **минификацию**, **хеширование имен файлов** и обработку ассетов. В разработке инструмент дополнительно дает **dev-сервер с HMR**.

## Вопрос

Зачем фронтенду нужна сборка, если браузеры поддерживают ES-модули? Что делает бандлер и из каких этапов состоит сборка?

## Почему нельзя просто отдать исходники

| Проблема | Что делает сборка |
| --- | --- |
| Браузер не понимает TypeScript, JSX, SCSS | транспиляция в JS и CSS |
| `import React from "react"` — «голый» импорт npm-пакета | разрешение пути в `node_modules` |
| Сотни модулей = сотни запросов и водопад загрузки | объединение в чанки |
| Неиспользуемый код библиотек | tree shaking |
| Пробелы, длинные имена, комментарии | минификация |
| Кеширование новых версий | хеш в имени файла (`app.3f9a1c.js`) |
| Старые браузеры | понижение синтаксиса, полифилы |
| Картинки, шрифты, SVG | копирование, оптимизация, инлайнинг маленьких файлов |
| Переменные окружения | подстановка `import.meta.env.*` на этапе сборки |

## Этапы сборки

```text
entry (index.html, src/main.tsx)
  → resolve: найти каждый импортированный модуль
  → transform: TS/JSX → JS, SCSS → CSS, плагины
  → граф зависимостей
  → tree shaking: убрать неиспользуемые экспорты
  → chunking: разбить на чанки (entry, vendor, ленивые маршруты)
  → minify: JS (esbuild/terser/SWC), CSS (lightningcss/cssnano)
  → emit: dist/ с хешами в именах + манифест + source maps
```

## Режимы: разработка и production

| | Development | Production |
| --- | --- | --- |
| Цель | быстрый старт и мгновенные изменения | маленький и быстрый результат |
| Бандлинг | Vite не бандлит код приложения, отдает ESM по запросу | полный бандлинг |
| Минификация | нет | да |
| Source maps | подробные | скрытые или загружаемые в Sentry |
| HMR | да | нет |
| Проверки React | dev-предупреждения | отключены |

## Пример результата сборки

```text
dist/
  index.html
  assets/
    index-B3f9a1cD.js          ← код приложения
    vendor-react-Ck29xQ.js     ← библиотеки (кешируются дольше)
    Settings-D7h2kL.js         ← ленивый маршрут
    index-Fa81zq.css
    logo-9cX1aa.svg
```

## Что важно помнить

- Нативные ES-модули в браузере есть, но без сборки остаются проблемы голых импортов, водопада запросов, TypeScript/JSX и оптимизаций.
- Бандлер работает на этапе сборки: в браузер попадает только результат.
- Переменные окружения встраиваются в бандл при сборке — секреты туда класть нельзя.
- Сборка — источник производительности: размер бандла напрямую влияет на LCP и INP.
- Связанные темы: [tree shaking](<../../04. JavaScript/09. Производительность в JS/06. Что такое “tree shaking”.md>), [code splitting](<../../04. JavaScript/09. Производительность в JS/13. Code splitting и динамический import().md>), [минификация](<../../04. JavaScript/09. Производительность в JS/11. Минимизация HTTP-запросов и минификация.md>).

## Мини-шпаргалка

Сборка: resolve → transform (TS, JSX, SCSS) → граф модулей → tree shaking → чанки → минификация → файлы с хешами. Dev — быстрый сервер и HMR, prod — оптимизированный бандл. Бандлеры: Vite, webpack, Rspack, Turbopack, esbuild, Rollup.
