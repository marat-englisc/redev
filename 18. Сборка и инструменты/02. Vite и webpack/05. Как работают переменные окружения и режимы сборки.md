# Как работают переменные окружения и режимы сборки

> [!NOTE]
> Во фронтенде переменные окружения **подставляются в код на этапе сборки**: `import.meta.env.VITE_API_URL` превращается в строку прямо в бандле. Поэтому всё, что попало в клиентский бандл, **публично**. Чтобы секреты случайно не утекли, инструменты пропускают в клиент только переменные с префиксом: `VITE_*` в Vite, `NEXT_PUBLIC_*` в Next.js, `REACT_APP_*` в Create React App. Значения берутся из `.env`-файлов по **режиму** (`development`, `production`, `staging`) и из окружения CI.

## Вопрос

Как работают переменные окружения во фронтенд-сборке? Почему секреты нельзя класть в `VITE_*`, как задать разные настройки для окружений и как сделать один образ на несколько окружений?

## .env-файлы в Vite

```text
.env                    всегда
.env.local              всегда, не коммитится
.env.[mode]             только для режима: .env.production, .env.staging
.env.[mode].local       режим, не коммитится
```

```bash
# .env.production
VITE_API_URL=https://api.example.com
VITE_SENTRY_DSN=https://abc@o1.ingest.sentry.io/1
DATABASE_URL=postgres://...      # без префикса — в клиент НЕ попадет
```

```typescript
const api = import.meta.env.VITE_API_URL;      // заменится строкой при сборке
import.meta.env.MODE;                           // "development" | "production" | "staging"
import.meta.env.DEV;                            // true в dev
import.meta.env.PROD;                           // true в production-сборке
```

```bash
vite build --mode staging     # загрузит .env.staging
```

Типизация:

```typescript
// src/vite-env.d.ts
interface ImportMetaEnv {
  readonly VITE_API_URL: string;
  readonly VITE_SENTRY_DSN?: string;
}
interface ImportMeta {
  readonly env: ImportMetaEnv;
}
```

## Префиксы в инструментах

| Инструмент | Доступ в клиенте | Префикс |
| --- | --- | --- |
| Vite | `import.meta.env.X` | `VITE_` |
| Next.js | `process.env.X` | `NEXT_PUBLIC_` (остальные — только на сервере) |
| Create React App | `process.env.X` | `REACT_APP_` |
| webpack | `process.env.X` | что передадите в `DefinePlugin` / `EnvironmentPlugin` |

## Почему секреты нельзя в клиент

```javascript
// в собранном бандле
const t = "https://api.example.com", n = "sk_live_..."; // любой увидит в DevTools → Sources
```

Ключи платежных систем, токены API, пароли БД используются только на сервере (BFF, Route Handlers, Server Actions). В клиенте — только публичные значения: адрес API, публичный ключ аналитики, DSN Sentry.

## Один образ на много окружений

Так как значения встраиваются при сборке, для каждого окружения нужна своя сборка. Если хочется собрать **один Docker-образ** для staging и production, используют **runtime-конфиг**:

```html
<!-- index.html -->
<script src="/config.js"></script>
```

```javascript
// config.js генерируется при старте контейнера из переменных окружения
window.__APP_CONFIG__ = { apiUrl: "https://api.staging.example.com" };
```

```typescript
export const config = window.__APP_CONFIG__;
```

## Что важно помнить

- Всё с префиксом `VITE_`/`NEXT_PUBLIC_` — публично; секреты — только на сервере.
- Значения — строки: `"false"` истинно в `if`; приводите типы и валидируйте схемой (Zod) при старте.
- `.env.local` и `.env.*.local` добавляйте в `.gitignore`, коммитьте `.env.example` с именами переменных.
- После изменения `.env` перезапустите dev-сервер.
- Связанные темы: [env и секреты в Node.js](<../../08. Node/07. Процессы, переменные окружения и CLI/03. Переменные окружения, .env и безопасное хранение секретов.md>), [Docker для фронтендера](<../../01. Web технологии/07. Доставка и инфраструктура/03. Что нужно знать фронтендеру о Docker.md>).

## Мини-шпаргалка

Env во фронтенде встраивается при сборке → всё публично. Префиксы: `VITE_`, `NEXT_PUBLIC_`, `REACT_APP_`. Файлы: `.env`, `.env.local`, `.env.[mode]`. `import.meta.env.MODE/DEV/PROD`, `--mode staging`. Типизация `ImportMetaEnv`. Один образ — runtime `config.js`.
