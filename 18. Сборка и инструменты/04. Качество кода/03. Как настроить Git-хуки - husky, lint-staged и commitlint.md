# Как настроить Git-хуки: husky, lint-staged и commitlint

> [!NOTE]
> **Git-хуки** — скрипты, которые Git запускает при событиях: перед коммитом (`pre-commit`), при проверке сообщения коммита (`commit-msg`), перед push (`pre-push`). **husky** упрощает их установку для всей команды через `package.json`. **lint-staged** запускает линтер и форматтер **только для файлов в индексе** — быстро даже в большом проекте. **commitlint** проверяет, что сообщение коммита соответствует соглашению **Conventional Commits** (`feat:`, `fix:`, `chore:`), — это позволяет автоматически генерировать changelog и версии.

## Вопрос

Что такое Git-хуки и зачем нужны husky и lint-staged? Как проверять сообщения коммитов через commitlint и почему хуки не заменяют CI?

## Установка husky и lint-staged

```bash
npm install --save-dev husky lint-staged
npx husky init
```

`husky init` создает папку `.husky/` и добавляет скрипт `"prepare": "husky"` — хуки устанавливаются у каждого разработчика после `npm install`.

```bash
# .husky/pre-commit
npx lint-staged
```

```json
// package.json
{
  "lint-staged": {
    "*.{ts,tsx,js,jsx}": ["eslint --fix --max-warnings=0", "prettier --write"],
    "*.{css,scss,md,json,yml}": "prettier --write"
  }
}
```

lint-staged берет только застейдженные файлы, запускает команды и добавляет исправления обратно в коммит. Если ESLint нашел ошибку — коммит отменяется.

## commitlint и Conventional Commits

```bash
npm install --save-dev @commitlint/cli @commitlint/config-conventional
```

```javascript
// commitlint.config.js
export default { extends: ["@commitlint/config-conventional"] };
```

```bash
# .husky/commit-msg
npx --no -- commitlint --edit "$1"
```

Формат сообщений:

```text
<type>(<scope>): <описание>

feat(cart): добавить промокоды
fix(auth): исправить редирект после логина
refactor: вынести api-клиент в отдельный модуль
chore(deps): обновить react до 19.2
feat!: удалить старый API профиля       ← ! или BREAKING CHANGE — мажорная версия
```

| Тип | Значение | Версия при semantic-release |
| --- | --- | --- |
| `feat` | новая функциональность | minor |
| `fix` | исправление | patch |
| `docs`, `style`, `refactor`, `test`, `chore`, `ci`, `perf` | прочее | без релиза (кроме `perf` в некоторых настройках) |
| `!` / `BREAKING CHANGE:` | несовместимое изменение | major |

## pre-push

```bash
# .husky/pre-push
npm run typecheck && npm test -- --run
```

Тяжелые проверки лучше оставлять CI, чтобы push не занимал минуты.

## Что важно помнить

- Хуки можно обойти (`git commit --no-verify`) — они ускоряют обратную связь, но **не заменяют CI**.
- pre-commit должен быть быстрым: только измененные файлы и только быстрые проверки.
- Проверку типов `tsc` нельзя ограничить измененными файлами — ее запускают целиком в pre-push или CI.
- Conventional Commits нужны для автоматики: Changesets, semantic-release, генерация changelog.
- Альтернативы husky: `simple-git-hooks`, `lefthook` (быстрый, на Go).

## Мини-шпаргалка

husky — установка Git-хуков для команды (`npx husky init`, `.husky/pre-commit`). lint-staged — ESLint и Prettier только по застейдженным файлам. commitlint + config-conventional в `commit-msg` — формат `type(scope): описание`. `feat` → minor, `fix` → patch, `!` → major. Хуки не заменяют CI.
