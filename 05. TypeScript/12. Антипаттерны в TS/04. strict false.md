# strict false

> [!NOTE]
> `strict: false` отключает набор строгих проверок TypeScript. Проект компилируется легче, но теряет значительную часть защиты от ошибок.

## Вопрос

Почему `strict: false` считают антипаттерном?

## Что такое strict

В `tsconfig.json` опция `strict` включает набор строгих проверок.

```json
{
  "compilerOptions": {
    "strict": true
  }
}
```

Сюда входят важные правила вроде `strictNullChecks`, `noImplicitAny`, `strictFunctionTypes` и другие.

## Что ломается при strict false

Например, без строгой проверки `null` код может выглядеть безопасным.

```typescript
function upper(value: string | null) {
  return value.toUpperCase();
}
```

При строгих настройках TypeScript заставит обработать `null`.

## Почему это опасно

Проект получает ложное ощущение типобезопасности: файлы написаны на TypeScript, но компилятор пропускает много рискованных мест.

## Как включать strict постепенно

Если проект большой, строгий режим можно включать по частям: сначала убрать явные `any`, затем разобраться с `null`, потом включать более жесткие флаги.

```json
{
  "compilerOptions": {
    "strict": true,
    "skipLibCheck": true
  }
}
```

`skipLibCheck` можно временно оставить, чтобы не чинить типы зависимостей.

## Что важно помнить

- Без `strict` TypeScript пропускает неявный `any`, ошибки с `null` и небезопасные функции.
- Включить `strict` в большом проекте можно постепенно: по одному флагу или через `// @ts-strict` плагины и отдельные tsconfig для папок.
- Сверх `strict` полезны `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`.
- Новые проекты стоит сразу начинать со `strict: true`.

## Мини-шпаргалка

- `strict: false` ослабляет TypeScript.
- Главные риски: `any`, `null`, небезопасные функции.
- Для нового проекта лучше `strict: true`.
- В старом проекте включай строгость постепенно.
