# Типизация ради типизации

> [!NOTE]
> Типизация ради типизации - это чрезмерно сложные типы, которые не дают реальной пользы: не защищают бизнес-логику, ухудшают читаемость и усложняют поддержку.

## Вопрос

Почему типизация ради типизации считается антипаттерном?

## Как это выглядит

```typescript
type DeepMagic<T> = T extends object
  ? { [K in keyof T]: DeepMagic<T[K]> }
  : T;
```

Сам по себе сложный тип не плох. Проблема начинается, когда команда не понимает, зачем он нужен и какие ошибки он предотвращает.

## Признаки лишней типизации

- Тип сложнее данных, которые он описывает.
- Ошибка TypeScript непонятнее возможной runtime-ошибки.
- Для простого объекта написано несколько слоев generic.
- При любом изменении бизнес-логики приходится чинить хитрые utility-типы.

## Лучше проще

```typescript
type UserCardProps = {
  name: string;
  avatarUrl?: string;
  onClick: () => void;
};
```

Явный простой тип часто лучше, чем универсальный helper, который пытается предугадать все случаи.

## Хороший критерий

Тип полезен, если он ловит реальную ошибку, документирует важный контракт или уменьшает дублирование. Если он только демонстрирует знание advanced TypeScript, это слабый сигнал.

## Баланс

```typescript
type ApiResponse<T> = {
  data: T;
  error: string | null;
};
```

Такой generic простой и полезный: он повторяет реальную структуру API.

## Что важно помнить

- Не дублируйте типы, которые TypeScript выводит сам: `const count: number = 0` избыточно.
- Сложные generic-конструкции оправданы в библиотеках, но в прикладном коде мешают читать.
- Выводите типы из одного источника: схемы Zod, OpenAPI, `typeof`, `ReturnType`, чтобы они не расходились.
- Цель типов — ловить ошибки и документировать контракты, а не покрыть аннотациями каждую строку.

## Мини-шпаргалка

- Типы должны помогать читать и менять код.
- Не усложняй модель без практической выгоды.
- Выноси generic только при реальном повторении.
- Сложные utility-типы стоит документировать примером.
