# Тип any: что делает, когда допустим и чем опасен

> [!NOTE]
> `any` отключает проверку типов для значения: ему можно присвоить что угодно, его можно присвоить куда угодно, у него можно вызвать любой метод. `any` «заражает» код — результаты операций с ним тоже становятся `any`, и ошибки незаметно уходят в runtime. Допустим он в редких случаях: постепенная миграция с JavaScript, временный обход неверных типов библиотеки, прототипирование. В остальных случаях используют `unknown`, дженерики или точные типы.

## Вопрос

Что делает тип `any`? Когда использовать `any` допустимо и чем он опасен в проекте?

## Как работает

```typescript
let value: any = "текст";
value = 42;
value = { a: 1 };

value.foo.bar();          // компилируется
const n: number = value;  // компилируется
value();                  // компилируется
```

TypeScript «верит на слово» и не проверяет ничего.

## Неявный any

```typescript
function format(item) {  // при noImplicitAny: Parameter 'item' implicitly has an 'any' type
  return item.title;
}
```

Флаг `noImplicitAny` (входит в `strict`) запрещает неявный `any` — его нужно написать явно или указать тип.

## Почему any опасен

```typescript
function getTotal(order: any) {
  return order.items.reduce((sum: number, i: any) => sum + i.price, 0);
}

getTotal({ itms: [] }); // опечатка — компилятор молчит, в runtime TypeError
```

- **ошибки уходят в runtime** — пропадает главная польза TypeScript;
- **заражение**: `const total = order.total * 2` — тоже `any`, и дальше по цепочке;
- **ложная уверенность**: код выглядит типизированным, но не проверяется;
- **ломает рефакторинг**: переименование поля не подсветит места с `any`;
- **скрывает баги библиотек** вместо того, чтобы их явно описать.

## Когда any допустим

| Ситуация | Почему |
| --- | --- |
| Постепенная миграция JS → TS | временно, с планом замены |
| Обход ошибочных типов сторонней библиотеки | точечно, с комментарием и `@ts-expect-error` или локальной декларацией |
| Быстрый прототип | код, который выбросят |
| Сложные generic-реализации внутри библиотеки | снаружи типы остаются строгими |

## Чем заменить

```typescript
// неизвестные данные
function parse(input: unknown) {}

// универсальная функция — дженерик сохраняет тип
function first<T>(items: T[]): T | undefined {
  return items[0];
}

// объект с произвольными ключами
const map: Record<string, number> = {};

// любой объект
function logKeys(obj: object) {}

// функция с любыми аргументами
type AnyFn = (...args: never[]) => unknown;
```

## Контроль в проекте

```json
{
  "rules": {
    "@typescript-eslint/no-explicit-any": "error",
    "@typescript-eslint/no-unsafe-assignment": "error",
    "@typescript-eslint/no-unsafe-member-access": "error"
  }
}
```

Правила `no-unsafe-*` ловят использование `any`, пришедшего из библиотек и `JSON.parse`.

## Что важно помнить

- `JSON.parse`, `response.json()` и некоторые старые типы библиотек возвращают `any` — это главный источник «невидимого» any.
- `as any` — тот же `any`, только точечно.
- `any[]` и `Function` — тоже слабые типы, их стоит уточнять.
- На собеседовании хороший ответ: «any отключает проверку, вместо него — unknown с сужением или дженерики».

## Мини-шпаргалка

- `any` отключает проверку типов полностью.
- Заражает: операции с `any` дают `any`.
- `noImplicitAny` запрещает неявный `any`.
- Допустим для миграции и точечного обхода багов типов.
- Замены: `unknown`, дженерики, `Record`, `object`.
