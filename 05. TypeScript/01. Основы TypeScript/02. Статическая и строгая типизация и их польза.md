# Статическая и строгая типизация и в чем их польза

> [!NOTE]
> **Статическая типизация** — типы проверяются до выполнения программы, на этапе компиляции. **Динамическая** (как в JavaScript) — ошибки типов обнаруживаются только при запуске. **Строгая (сильная) типизация** — язык не приводит типы неявно; **слабая** — приводит (`"5" * 2 === 10` в JS). TypeScript добавляет к JavaScript статическую проверку, а режим `strict` делает ее строже: запрещает неявный `any`, требует обработки `null` и `undefined`.

## Вопрос

Что означает статическая типизация? Что означает строгая типизация? Какая польза от статической и строгой типизации?

## Две независимые оси

| | Статическая | Динамическая |
| --- | --- | --- |
| **Строгая** | TypeScript (`strict`), Java, Rust, C# | Python, Ruby |
| **Слабая** | C | JavaScript, PHP |

Это разные характеристики: «статическая» отвечает на вопрос **когда** проверяются типы, «строгая» — **насколько** язык допускает неявные преобразования.

## Статическая типизация

```typescript
function getLength(value: string): number {
  return value.length;
}

getLength(42); // ошибка видна в редакторе до запуска
```

В JavaScript та же ошибка проявится только при выполнении — возможно, у пользователя в production.

## Строгость в TypeScript

TypeScript наследует слабую типизацию JS в runtime, но проверка типов не дает смешивать типы без явного намерения:

```typescript
const total: number = "100" * 2;  // ошибка: арифметика со строкой
const label: string = 42;         // ошибка: number не string
```

Флаг `strict: true` включает группу проверок:

| Флаг | Что делает |
| --- | --- |
| `noImplicitAny` | запрещает неявный `any` |
| `strictNullChecks` | `null` и `undefined` — отдельные типы, их нужно обрабатывать |
| `strictFunctionTypes` | строгая проверка параметров функций |
| `strictPropertyInitialization` | поля класса должны быть инициализированы |
| `useUnknownInCatchVariables` | ошибка в `catch` имеет тип `unknown` |
| `noImplicitThis`, `alwaysStrict` и др. | прочие проверки |

```typescript
function greet(user: { name: string } | null) {
  return user.name; // ошибка при strictNullChecks: 'user' is possibly 'null'
}
```

## Польза

- **Раннее обнаружение ошибок**: опечатки, неверные аргументы, забытые `null`-проверки.
- **Надежный рефакторинг**: изменение типа подсвечивает все места, которые нужно поправить.
- **Документация**: сигнатура функции объясняет, что она принимает и возвращает.
- **Инструменты**: автодополнение, переход к определению, поиск использований.
- **Командная работа**: контракт между модулями явный, меньше договоренностей «на словах».

## Цена

- нужно писать и поддерживать типы;
- сложные дженерики иногда труднее понять, чем сам код;
- сборка и проверка занимают время;
- ложное чувство безопасности, если злоупотреблять `any` и `as`.

## Что важно помнить

- В новых проектах включайте `strict: true` с самого начала — включить его в большом проекте позже дорого.
- Статическая проверка не видит данные, пришедшие в runtime: API, `localStorage`, ввод пользователя.
- Дополнительные строгие флаги вне `strict`: `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`.
- На собеседовании полезно разделять «статическая vs динамическая» и «строгая vs слабая» — их часто путают.

## Мини-шпаргалка

- Статическая — проверка до запуска, динамическая — во время.
- Строгая — без неявных приведений, слабая — с ними.
- JS — динамический и слабый; TS добавляет статическую проверку.
- `strict: true` — `noImplicitAny`, `strictNullChecks` и другие.
- Польза: ранние ошибки, рефакторинг, документация, инструменты.
