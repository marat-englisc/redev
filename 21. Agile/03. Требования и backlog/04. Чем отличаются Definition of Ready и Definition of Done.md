# Чем отличаются Definition of Ready и Definition of Done

> [!NOTE]
> **Definition of Ready, DoR** — необязательная договоренность команды о достаточной подготовке задачи к работе. **Definition of Done, DoD** — обязательное в Scrum общее описание качества готового инкремента. **Acceptance criteria** задают поведение конкретной задачи. DoR помогает начать с понятным контекстом, критерии — проверить нужный сценарий, DoD — убедиться, что результат действительно готов.

## Вопрос

Чем DoR отличается от DoD и критериев приемки? Можно ли считать задачу готовой, если код написан, но не прошел проверки?

## Сравнение

| Понятие | К чему относится | Пример |
| --- | --- | --- |
| DoR | К подготовке элемента backlog | Понятны цель, основные состояния и зависимость от API |
| Acceptance criteria | К поведению конкретного изменения | При неверном коде пользователь видит ошибку и может повторить ввод |
| DoD | К качеству инкремента продукта | Изменения интегрированы и прошли обязательные проверки |

DoR не входит в обязательные элементы Scrum. Ее полезно применять как помощь обсуждению, а не как формальное разрешение начать любую работу.

## Пример DoR для frontend-задачи

- Понятны пользовательская цель и границы первого варианта.
- Есть критерии приемки основных сценариев.
- Согласованы значимые состояния UI и требования доступности.
- Понятен контракт API или явно описан риск его изменения.
- Известны зависимости, ограничения и способ проверки.
- Размер позволяет завершить работу в выбранном цикле.

Пункты — пример для команды. Для небольшого исправления текста не нужен полный пакет макетов, а для платежного сценария подготовки может потребоваться больше.

## Пример DoD для web-продукта

```text
- поведение соответствует согласованным критериям;
- код прошел ревью и интегрирован в общую версию;
- проходят обязательные автоматические проверки;
- нужные пользовательские сценарии проверены с реальным API;
- проверены согласованные браузеры, адаптивность и доступность;
- выполнены применимые требования безопасности;
- обновлены необходимые контракты и документация;
- результат пригоден к выпуску, известны способ наблюдения и ограничения.
```

Это иллюстрация, а не универсальный стандарт. Команда определяет подходящий DoD с учетом продукта и минимальных требований организации. Несколько Scrum-команд одного продукта должны согласовать и соблюдать общее определение готовности.

## Почему важен общий стандарт

Если «готово» у одного разработчика означает «написан компонент», а у другого — «проверен сценарий на стенде», состояние продукта непрозрачно.

Общий DoD помогает при планировании: интеграция, тесты и другие обязательные шаги входят в работу сразу. Их нельзя незаметно вынести в следующий спринт, продолжая считать исходный результат Done.

DoD может улучшаться по мере развития команды. Его не следует ослаблять в конце спринта ради красивой статистики.

## Если часть работы не завершена

| Ситуация | Честное состояние |
| --- | --- |
| UI работает на моках, интеграция не проверена | Разработка продолжается |
| Найдена ошибка в обязательном сценарии | Требуется исправление |
| Проверки завершены, запуск аудитории запланирован позднее | Возможно Done, если выполнен DoD |
| Фича скрыта флагом, но не выполнены обязательные проверки | Флаг не превращает работу в Done |

Удобно различать статус задачи в трекере и реальную готовность продукта. Если трекер не показывает важную незавершенную работу, правила статусов стоит изменить.

## Гибкость без потери качества

Новые подробности могут появляться во время работы. DoR не должен требовать отсутствия любой неопределенности: иногда полезно начать с ограниченного исследования.

При нехватке времени пересматривают объем и порядок работы. Например, откладывают дополнительный способ сортировки, сохраняя проверки основного сценария.

## Частые ошибки

- Называть DoR обязательным правилом Scrum.
- Путать готовый PR с готовым инкрементом.
- Делать DoD недостижимым списком пожеланий, который никто не соблюдает.
- Менять определение готовности отдельно для каждой неудобной задачи.

## Мини-шпаргалка

DoR — достаточно ли понятно, чтобы начать. Acceptance criteria — нужное ли поведение получили. DoD — соблюден ли общий стандарт готовности. Качество учитывают в оценке и планировании, а статус отражает реальное состояние.
