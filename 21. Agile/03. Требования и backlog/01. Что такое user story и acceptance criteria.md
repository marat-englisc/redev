# Что такое user story и acceptance criteria

> [!NOTE]
> **User story** описывает небольшую потребность пользователя и ее ценность, а **acceptance criteria**, или критерии приемки, уточняют проверяемое поведение конкретной задачи. История — повод для обсуждения, а не замена всем требованиям. Для frontend важно согласовать успешный сценарий, ошибки, состояния и ограничения. User stories удобны, но не обязательны в Scrum: технические задачи и исследования можно описывать напрямую.

## Вопрос

Как написать хорошую user story? Чем критерии приемки отличаются от технических подзадач и Definition of Done?

## История, задача и подзадача

| Понятие | Назначение | Пример |
| --- | --- | --- |
| Epic | Крупная область работы, требующая декомпозиции | Управление подпиской |
| User story | Небольшая пользовательская потребность | Пользователь видит дату следующего списания |
| Task | Конкретная работа; значение зависит от команды | Обновить клиент платежного API |
| Subtask | Часть реализации выбранной работы | Добавить обработку ошибки запроса |

Epic, story и task — распространенные термины инструментов и практик, а не обязательная иерархия Scrum.

## Шаблон user story

```text
Как пользователь с активной подпиской,
я хочу видеть дату и сумму следующего списания,
чтобы заранее решить, продолжать ли подписку.
```

Шаблон помогает обсудить **для кого**, **что** и **зачем**. Если всем понятнее короткое обычное описание, строгая формула не нужна.

Плохой вариант: «Как пользователь, я хочу React-компонент, чтобы использовать React». Здесь технический способ реализации выдается за потребность.

## Признаки хорошей истории: INVEST

| Буква | Смысл | Проверочный вопрос |
| --- | --- | --- |
| I — Independent | По возможности независимая | Можно ли выполнить ее без длинной цепочки других историй? |
| N — Negotiable | Допускает обсуждение | Можно ли вместе выбрать способ решения? |
| V — Valuable | Имеет ценность | Кому и в чем станет лучше? |
| E — Estimable | Поддается оценке | Достаточно ли понимания, чтобы обсудить размер? |
| S — Small | Небольшая | Реально ли закончить в рабочем цикле команды? |
| T — Testable | Проверяемая | Как убедиться, что ожидаемое поведение работает? |

Полная независимость не всегда достижима. Важно обнаруживать зависимости, а не скрывать их ради формального соответствия шаблону.

## Критерии приемки

Для истории о подписке команда может согласовать:

- активный пользователь видит сумму, валюту и дату следующего списания;
- дата отображается по согласованному правилу часового пояса;
- во время запроса показано состояние загрузки;
- при ошибке есть понятное сообщение и повторная попытка;
- пользователь без подписки видит согласованный пустой сценарий;
- данные другого пользователя недоступны.

Последний пункт требует проверки серверной авторизации: скрыть элемент на клиенте недостаточно.

## Given / When / Then

Критерий удобно записать через условия, действие и результат:

```text
Given: у пользователя активная подписка, запрос статуса завершился ошибкой
When: пользователь нажимает «Повторить»
Then: выполняется новый запрос, а после успеха отображаются данные подписки
```

Это один из способов формулировки. Не каждый критерий обязательно превращать в отдельный E2E-тест: уровень автоматизации выбирают по риску и стоимости проверки.

## Критерии приемки и DoD

**Acceptance criteria** описывают особенности конкретной работы: какие данные и поведение нужны в сценарии подписки.

**Definition of Done** задает общую планку качества результата: например, изменения проверены, интегрированы и прошли обязательные тесты.

Выполнить все критерии истории, но пропустить обязательное ревью — недостаточно для Done. Пройти линтер, но показывать неверную дату списания — недостаточно для приемки истории.

## Частые ошибки

- Описывать только реализацию: «создать компонент и хук».
- Считать заголовок тикета полным описанием поведения.
- Оставлять ошибки и пустые состояния «на усмотрение разработчика» без обсуждения.
- Переписывать техническую задачу в искусственную историю от лица пользователя.

## Мини-шпаргалка

Story: кто → потребность → ценность. Критерии: наблюдаемое поведение и границы. INVEST помогает проверить размер и понятность. Acceptance criteria относятся к задаче, DoD — к общему качеству инкремента.
