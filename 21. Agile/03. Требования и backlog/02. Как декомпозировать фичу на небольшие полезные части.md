# Как декомпозировать фичу на небольшие полезные части

> [!NOTE]
> Хорошая декомпозиция позволяет рано получить небольшой проверяемый результат и уменьшить риск. **Вертикальный срез** проходит через нужные слои системы и дает законченный сценарий; **горизонтальное разбиение** делит работу по техническим частям. Технические подзадачи нужны, но «сначала весь backend, потом весь frontend» часто откладывает обратную связь. При сокращении объема сохраняют качество выбранного сценария.

## Вопрос

Как разделить большую frontend-фичу на истории и подзадачи? Что такое вертикальный срез и почему он полезен?

## Два способа разбиения

Допустим, нужно сделать страницу заказов с фильтрами, деталями и повторной покупкой.

| Способ | Части работы | Когда увидим пользовательский результат |
| --- | --- | --- |
| По слоям | Весь API → вся верстка → вся интеграция → все тесты | После завершения большинства частей |
| По сценариям | Просмотр последних заказов → фильтр по статусу → детали → повтор покупки | После первого законченного среза |

Внутри среза «просмотр последних заказов» все равно есть API, UI, тесты и проверки. Вертикальное разбиение меняет единицу результата, а не отменяет технические шаги.

## Варианты разбиения

| По чему делить | Пример |
| --- | --- |
| По пользовательскому сценарию | Просмотреть заказ отдельно от повторной покупки |
| По бизнес-правилу | Один тип скидки до поддержки нескольких правил |
| По источнику данных | Один согласованный источник до подключения остальных |
| По способу взаимодействия | Выбор из списка до добавления сложного поиска |
| По возможностям | Чтение данных до редактирования |
| По аудитории выпуска | Ограниченный пилот при полной готовности выбранного сценария |

Разбиение по аудитории уменьшает риск выпуска, но само по себе не делает реализацию меньше. Если код одинаково сложен для десяти и тысячи пользователей, это прежде всего стратегия rollout.

## Алгоритм декомпозиции

1. Назвать пользовательскую проблему и ожидаемый результат.
2. Выделить самый узкий сценарий, который имеет самостоятельный смысл.
3. Проверить, какие слои и зависимости нужны для его завершения.
4. Убрать второстепенные возможности и явно записать границы.
5. Согласовать критерии приемки и обязательные проверки.
6. Остальные сценарии оформить отдельно и упорядочить.

Если часть нельзя независимо проверить или использовать, возможно, это подзадача реализации, а не отдельная история.

## Пример первого среза

```text
Большая фича: сложная таблица заказов.

Первый срез:
- показать последние 20 заказов текущего пользователя;
- отобразить номер, дату, статус и сумму;
- обработать загрузку, пустой ответ и ошибку;
- проверить права доступа и критичный сценарий чтения.

Позже:
- добавить фильтр по статусу;
- поддержать следующий набор заказов;
- добавить детали и повтор покупки.
```

Ограничение первыми 20 заказами нужно согласовать. Если без доступа к старым заказам сценарий бесполезен для целевой аудитории, пагинация должна войти раньше.

## Что нельзя просто вынести «на потом»

- обязательные проверки безопасности;
- целостность данных;
- обработку ошибок, без которой выбранный сценарий ломается;
- согласованный уровень доступности;
- минимальные проверки регрессий и наблюдение за критичным выпуском.

Можно временно отказаться от экспорта CSV. Нельзя считать экспорт готовым, если он иногда содержит чужие данные.

## Технические и исследовательские задачи

Не вся работа обязана немедленно давать отдельную пользовательскую функцию. Обновление библиотеки, настройка окружения или исследование API могут быть необходимы для следующего результата.

Для такой задачи полезны ясная причина, ограниченный объем и критерий завершения. Для исследования — вопрос, ограничение времени и ожидаемый вывод, а не обещание готовой production-фичи.

## Частые ошибки

- Делить только по файлам и компонентам.
- Делать одну историю на весь месяц, а затем отмечать ее готовность в процентах.
- Убирать тестирование и интеграцию из оценки первого среза.
- Называть любой незаконченный прототип минимально полезным продуктом.

## Мини-шпаргалка

Небольшой сценарий → нужные слои → интеграция и качество → проверяемый результат. Технические подзадачи описывают способ работы; вертикальные срезы помогают раньше проверить ценность и зависимости.
