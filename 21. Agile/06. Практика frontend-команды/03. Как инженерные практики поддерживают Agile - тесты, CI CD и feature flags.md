# Как инженерные практики поддерживают Agile - тесты, CI CD и feature flags

> [!NOTE]
> Часто менять продукт безопасно помогают **автоматические проверки, небольшие изменения, ревью, рефакторинг и частая интеграция**. CI быстро обнаруживает проблемы общей версии; Continuous Delivery поддерживает готовность к развертыванию, Continuous Deployment автоматически разворачивает прошедшие проверки изменения в production. Feature flags отделяют доставку кода от включения возможности. Сами встречи Agile не заменяют инженерную способность регулярно поставлять качественный результат.

## Вопрос

Как связаны Agile, автотесты и CI/CD? Зачем нужны небольшие PR и feature flags?

## Почему размер изменения важен

Большой PR на тысячи строк дольше проверяют, сложнее интегрируют и труднее разбирают при регрессии. Небольшое логически связное изменение быстрее получает обратную связь.

Размер оценивают по понятности и риску, а не только по строкам. Механическое деление одной несовместимой правки на несколько зависимых PR не всегда упрощает работу.

| Практика | Как помогает циклу обратной связи |
| --- | --- |
| Ревью | Проверить решение и распространить знания |
| Автотесты | Быстро обнаружить нарушение известного поведения |
| Типизация и статический анализ | Рано найти часть ошибок и несогласованностей |
| Рефакторинг | Снизить стоимость следующих изменений |
| Парная работа | Быстрее разобраться с рискованной частью и передать контекст |

## Тестирование и TDD

Полезны проверки на подходящих уровнях: чистая логика, поведение компонента, работа с API и критичные пользовательские пути.

**TDD** — короткий цикл: падающий тест ожидаемого поведения → минимальная реализация → улучшение кода при зеленых тестах. Его можно применять там, где он помогает понять контракт и быстро проверить решение.

Не требуется превращать каждое визуальное изменение в большое количество хрупких тестов. Важны риски и полезность проверок; высокий процент coverage не доказывает правильность продукта.

## CI, Continuous Integration

CI означает частое объединение небольших изменений в общую версию с автоматической проверкой результата. Проблему интеграции обнаруживают близко к моменту появления.

```text
Небольшое изменение → интеграция → сборка и проверки → быстрая обратная связь
```

Pipeline только в PR не гарантирует CI, если ветки живут месяцами и редко объединяются. Сломанная общая сборка требует быстрого внимания: иначе остальные теряют надежную основу работы.

## Два значения CD

| Подход | Что обеспечивается | Как попадает в production |
| --- | --- | --- |
| Continuous Delivery | Изменения проверены и поддерживаются в готовности к развертыванию | Решение о развертывании может быть ручным |
| Continuous Deployment | Прошедшие необходимые проверки изменения разворачиваются автоматически | Через автоматический процесс |

Конкретный набор проверок зависит от риска продукта. В обоих случаях важно уметь обнаружить проблему после развертывания и восстановить работоспособность. Включение возможности пользователям может отдельно управляться флагом.

## Feature flags

Флаг позволяет доставить код и включить возможность позже, ограниченной аудитории или постепенно. Это помогает разнести техническую доставку и продуктовый запуск.

```text
Код интегрирован → версия доставлена → флаг включен пилоту
                 → проверка результата → расширение доступа
```

Флаг требует дисциплины:

- проверить нужные включенное и выключенное состояния;
- определить владельца и условие удаления;
- учитывать совместимость API и данных;
- понимать, что произойдет при отключении;
- удалить временную ветку поведения после завершения выпуска.

Клиентский флаг не является проверкой прав доступа. Защищенные операции и данные должны проверяться сервером.

## Связь с Definition of Done

Обязательные проверки и интеграция должны входить в понятный процесс готовности. Скрытый незавершенный код может быть технически доставлен, но не становится готовым пользовательским инкрементом автоматически.

Команда может часто интегрировать заготовки, сохраняя честное различие между состоянием кода и готовностью целого сценария.

## Частые ошибки

- Называть CI любой установленный сервис запуска тестов.
- Держать изменения отдельно до последнего дня спринта.
- Считать флаг заменой тестам и серверной авторизации.
- Навсегда оставлять временные флаги без владельца.

## Мини-шпаргалка

Короткие циклы поддерживаются технически: маленькие изменения, полезные проверки, частая интеграция и безопасный выпуск. Delivery — готовность к развертыванию, Deployment — автоматическое развертывание. Флаги управляют доступностью возможности и тоже требуют проверки и удаления.
