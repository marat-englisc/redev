# Как работать с продактом, дизайном, backend и QA

> [!NOTE]
> Кросс-функциональная работа помогает совместно получить законченный сценарий, а не последовательно передавать недоделанные части между ролями. Middle frontend заранее уточняет цель, UX-состояния, контракт API и способ проверки, делает зависимости видимыми и сохраняет договоренности. Асинхронное общение подходит для многих вопросов; сложную неоднозначность полезно быстро обсудить нужным составом и записать решение.

## Вопрос

Как организовать взаимодействие frontend с другими участниками Agile-команды? Что делать, если макет или API еще не готовы?

## О чем договариваться

| Участник | Что уточнить | Что дать со своей стороны |
| --- | --- | --- |
| Продакт / PO | Проблема, ценность, границы, порядок | Варианты объема, стоимость и технические риски |
| Дизайнер | Сценарии, состояния, адаптивность и доступность | Ограничения платформы, существующие компоненты, примеры |
| Backend | Схема данных, ошибки, права и совместимость | Потребности экрана, пограничные случаи, пример запроса |
| QA | Риски, данные и способ проверки | Критерии, ограничения, воспроизведение и изменения |
| Другая команда | Результат зависимости, владелец, срок проверки | Контекст и влияние задержки |

Не каждый вопрос требует общей встречи. Нужен минимальный состав, который может принять нужное решение.

## Если макет неполный

Разработчик замечает, что показан только идеальный список. До оценки или начала реализации стоит собрать конкретные вопросы: пустое состояние, длинный текст, ошибка запроса, мобильный вариант, клавиатурный фокус.

Можно предложить решение из дизайн-системы и попросить подтвердить его. Это помогает сдвинуть работу, сохраняя видимость принятого допущения.

Если обнаружена проблема доступности, полезно объяснить нарушенный сценарий: например, пользователь с клавиатурой не может закрыть диалог. Так разговор связывается с поведением продукта.

## Если API еще в работе

```text
Договориться заранее:
- запросы, ответы и коды ошибок;
- ограничения и права доступа;
- примеры для успеха, пустых данных и отказа;
- источник схемы и порядок изменения контракта;
- кто и когда проверяет реальную интеграцию.
```

После этого frontend может использовать моки, а backend — развивать сервис параллельно. Если обе стороны независимо придумали разные ответы, параллельность только отложит обнаружение конфликта.

Типы, сгенерированные из схемы, помогают находить расхождения, но не доказывают правильность бизнес-логики и авторизации.

## Как работать с QA раньше

QA полезен не только после написания кода. На уточнении требований он может помочь найти пропущенные переходы, проблемные данные и сценарии отказов.

Например, для формы приглашения важны повторная отправка, уже существующий участник, истекшее приглашение и отсутствие права приглашать. Обсудить их заранее дешевле, чем менять готовую модель состояния.

Разработчики при этом сохраняют ответственность за качество: ручная проверка QA не заменяет собственную проверку и обязательные автотесты.

## Асинхронные договоренности

Хорошее сообщение включает контекст, наблюдение, варианты и нужное решение.

```text
Для таблицы заказов API возвращает только customerId.
Экран должен показывать имя; отдельный запрос на каждую строку
создаст много обращений к сервису.

Варианты: вернуть имя вместе с заказом или добавить пакетный запрос.
Нужен выбор до интеграции в четверг. Примеры ответа приложены к задаче.
```

После разговора стоит обновить задачу или контракт, чтобы остальные не искали решение в длинной переписке.

## Как управлять внешней зависимостью

1. Назвать нужный результат и дату его проверки.
2. Найти участника, который может помочь с решением.
3. Описать влияние на цель и возможные альтернативы.
4. Проверять состояние достаточно рано.
5. При риске пересмотреть план вместе с ответственными участниками.

Не следует обещать дату чужой команды от ее имени. Можно объяснить зависимость и обозначить условие собственного прогноза.

## Частые ошибки

- Передавать задачу дальше без общего понимания сценария.
- Продолжать работу на выдуманном контракте без фиксации допущения.
- Считать тестирование исключительной ответственностью QA.
- Оставлять решение только в личной переписке.

## Мини-шпаргалка

Рано обсудить цель, состояния, контракт и проверки. Моки ускоряют параллельную работу при общем контракте. Зависимость должна иметь понятный результат, владельца взаимодействия и следующий шаг.
