# Зачем нужен Daily Scrum и как говорить о блокерах

> [!NOTE]
> **Daily Scrum** — ежедневное 15-минутное событие Developers, на котором проверяют продвижение к Sprint Goal и согласуют ближайшую работу. Это не отчет руководителю и не обязательный опрос по трем вопросам. Полезный результат — понятный план: что закончить, кому нужна помощь и как снять препятствия. О критичном блокере сообщают сразу, не дожидаясь следующего Daily.

## Вопрос

Зачем нужен Daily Scrum? Как сообщить статус задачи и что делать, если вас заблокировал API или код-ревью?

## Что нужно получить от Daily

| Вопрос команды | Возможное решение |
| --- | --- |
| Продвигаемся ли мы к цели? | Сначала закончить интеграцию основного сценария |
| Где работа остановилась? | Найти владельца решения по API |
| Что стоит изменить сегодня? | Помочь с ревью вместо начала новой задачи |
| Какой риск появился? | Обсудить объем с PO после встречи |

Если все перечислили вчерашние действия, но никто не понял, что делать с застрявшей фичей, полезность встречи низкая.

## Как сообщить статус

**Мало информации:** «Вчера делал форму, сегодня продолжаю, есть вопросы к API».

**Полезнее:** «Ввод и клиентская валидация готовы. Сохранение блокирует отсутствие поля `phoneVerified` в ответе API. Без него не проверим основной сценарий. Нужен ответ бэкенда до обеда; пока могу дописать обработку ошибки, затем потребуется помощь с интеграцией».

В сообщении есть результат, остаток работы, влияние препятствия и следующий шаг. Проценты вроде «готово на 90%» без описания оставшегося мало помогают планированию.

## Что такое блокер

Блокер — препятствие, из-за которого работа не может продвигаться в нужном направлении. Его полезно отличать от обычного вопроса и риска будущей задержки.

| Ситуация | Действие |
| --- | --- |
| Непонятна реализация хука | Исследовать, ограничить время поиска, обратиться за помощью |
| Нет доступа к обязательному стенду | Обозначить блокировку, запросить доступ и владельца решения |
| API будет готов позднее плана | Сразу обсудить риск для цели и порядок интеграции |
| PR второй день ждет проверки | Договориться о ревью, проверить очередь всей команды |

Важен не ярлык, а понимание: что именно нельзя закончить, кто может помочь и когда нужен ответ.

## Алгоритм работы с препятствием

```text
Обнаружить → сделать видимым → описать влияние
          → предложить варианты → договориться о действии и сроке
          → проверить, снята ли блокировка
```

1. Обновить задачу: причина, оставшаяся работа и зависимость.
2. Сообщить нужному участнику с контекстом, примером или воспроизведением.
3. Найти полезный параллельный шаг, если он не скрывает риск.
4. При угрозе цели подключить команду и PO для пересмотра плана.
5. Если препятствие организационное или повторяется, привлечь Scrum Master.

Моки помогут продолжить разработку UI, но не доказывают работоспособность реального API. Статус интеграции должен оставаться видимым.

## Формат встречи

Developers выбирают формат сами. Можно пройти по доске справа налево: что почти завершено, где очередь и чем помочь. Можно обсудить цель и ближайшие совместные шаги.

Три вопроса «вчера / сегодня / препятствия» допустимы как техника, если помогают плану. Они не обязательны по Scrum Guide.

Детальное обсуждение race condition или нового API лучше продолжить после Daily с нужными людьми. Остальным не требуется присутствовать при всей отладке.

## Частые ошибки

- Ждать Daily, хотя критичная блокировка появилась утром предыдущего дня.
- Подменять продвижение количеством написанного кода.
- Использовать встречу для оценки личной продуктивности.
- Начинать следующую задачу, оставляя очередь ревью без внимания.
- Сообщать о проблеме без контекста и запроса на действие.

## Мини-шпаргалка

Daily: цель → состояние работы → препятствия → план на день. Блокер: причина, влияние, нужная помощь, срок следующей проверки. Срочные проблемы обсуждаются сразу; подробная отладка — отдельным составом.
