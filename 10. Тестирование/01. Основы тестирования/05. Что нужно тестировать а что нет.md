# Что тестировать, а что нет

> [!NOTE]
> Тестируют поведение, которое видит пользователь или потребитель кода: бизнес-логику, критичные сценарии, граничные случаи и исправленные баги. Не тестируют детали реализации, сторонние библиотеки и тривиальный код.

## Вопрос

Как решить, что покрывать тестами? Что значит «не тестировать детали реализации»?

## Основная идея

У кода есть два потребителя: **пользователь**, который видит интерфейс, и **разработчик**, который вызывает функцию или передаёт props. Тест должен работать так же, как они. Пользователь не знает про `useState`, название CSS-класса или количество рендеров — он видит текст, кнопки и результат действий.

**Детали реализации** — всё, что можно изменить без изменения поведения: внутренний state компонента, имена приватных функций, структура DOM-обёрток, вызов конкретного хука. Тест, завязанный на них, падает при безопасном рефакторинге (ложная тревога) и может не упасть при реальной поломке (ложная уверенность).

Приоритеты стоит выбирать по риску: что сломается чаще всего и что обойдётся дороже всего. Оплата и авторизация важнее цвета кнопки.

## Пример

```tsx
// Плохо: тест знает про внутренний state и реализацию
expect(wrapper.state('isOpen')).toBe(true);
expect(container.querySelector('.dropdown__menu--open')).not.toBeNull();

// Хорошо: тест проверяет то, что видит пользователь
await user.click(screen.getByRole('button', { name: 'Меню' }));
expect(screen.getByRole('menu')).toBeVisible();
```

Если заменить `useState` на `useReducer` или поменять класс на `data-state="open"`, второй тест продолжит проходить.

## Что тестировать

| Стоит | Почему |
| --- | --- |
| Бизнес-логику: расчёты, валидацию, форматирование | ошибки дорогие, тесты дешёвые |
| Пользовательские сценарии: формы, фильтры, корзину | основная ценность продукта |
| Граничные случаи: пустой список, ошибка сети, `0`, длинный текст | там живут баги |
| Состояния loading / error / empty | их часто забывают |
| Исправленный баг | чтобы он не вернулся (регрессионный тест) |
| Кастомные хуки и утилиты, используемые во многих местах | широкий радиус поломки |

| Не стоит | Почему |
| --- | --- |
| Сторонние библиотеки (React, роутер, lodash) | их тестируют авторы |
| Тривиальный код без логики | тест повторяет код |
| Внутренний state, приватные функции | детали реализации |
| Точную вёрстку и стили в jsdom | jsdom не считает layout |
| Константы и конфиги | нет поведения |

## Что важно помнить

- Чем больше тест похож на использование софта, тем больше уверенности он даёт (принцип Testing Library).
- Регрессионный тест пишется до исправления бага: сначала он падает, после фикса проходит.
- Визуальную корректность проверяют скриншотными тестами или вручную, а не через проверку классов.
- Если тест трудно написать, это часто сигнал о плохой архитектуре: слишком много связей.

## Мини-шпаргалка

Тестируй поведение, а не реализацию. Приоритет — по риску. Баг → сначала тест. Чужие библиотеки и тривиальный код не тестируем.
