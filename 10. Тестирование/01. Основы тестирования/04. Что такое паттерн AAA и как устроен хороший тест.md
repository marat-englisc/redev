# Паттерн AAA и устройство хорошего теста

> [!NOTE]
> AAA (Arrange — Act — Assert) делит тест на три шага: подготовить данные, выполнить действие и проверить результат. Хороший тест проверяет одно поведение, понятно назван, независим и детерминирован.

## Вопрос

Как структурировать тест? Какими свойствами обладает хороший тест?

## Основная идея

**Arrange** — подготовка: создать данные, отрендерить компонент, настроить моки. **Act** — одно действие, поведение которого проверяется: вызов функции, клик, отправка формы. **Assert** — проверка результата: что вернулось, что появилось на экране, какой запрос ушёл.

Такая структура делает тест читаемым: сразу видно, что подготовлено, что сделано и что ожидается. Если в одном тесте несколько чередующихся Act и Assert, он, скорее всего, проверяет несколько поведений и его стоит разделить. Исключение — e2e-сценарии, где цепочка шагов и есть проверяемое поведение.

Качества хорошего теста часто описывают акронимом **FIRST**:

| Буква | Свойство | Смысл |
| --- | --- | --- |
| F | Fast | быстро выполняется, его не лень запускать |
| I | Independent | не зависит от порядка и других тестов |
| R | Repeatable | даёт одинаковый результат на любой машине |
| S | Self-validating | сам говорит «прошёл/упал», без ручного анализа |
| T | Timely | пишется вместе с кодом, а не через полгода |

Название теста должно описывать поведение и условие: «показывает ошибку, если email пустой», а не «test1» или «проверка handleSubmit». Удобный шаблон: «делает X, когда Y».

## Пример

```tsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { LoginForm } from './LoginForm';

it('показывает ошибку, если email пустой', async () => {
  // Arrange
  const user = userEvent.setup();
  const onSubmit = vi.fn();
  render(<LoginForm onSubmit={onSubmit} />);

  // Act
  await user.click(screen.getByRole('button', { name: 'Войти' }));

  // Assert
  expect(screen.getByRole('alert')).toHaveTextContent('Введите email');
  expect(onSubmit).not.toHaveBeenCalled();
});
```

Два `expect` здесь допустимы: они проверяют одно поведение — «форма не отправляется и объясняет почему».

## Что важно помнить

- Один тест — одна причина упасть. Тогда по названию упавшего теста понятно, что сломалось.
- Не используйте логику в тестах: `if`, циклы и вычисления ожидаемого значения той же формулой, что и в коде.
- Ожидаемое значение пишите явно: `toBe(250)`, а не `toBe(price * qty)`.
- Общую подготовку выносите в helper-функции или `beforeEach`, но без потери читаемости.
- Иногда используют синоним Given — When — Then (BDD-стиль).

## Мини-шпаргалка

Arrange → Act → Assert. Одно поведение на тест. Название: «делает X, когда Y». FIRST: быстрый, независимый, повторяемый.
