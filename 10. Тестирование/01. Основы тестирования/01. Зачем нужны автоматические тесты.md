# Зачем нужны автоматические тесты

> [!NOTE]
> Автоматические тесты — код, который проверяет поведение приложения без ручных действий. Они дают уверенность при изменениях, ловят регрессии до production и служат исполняемой документацией.

## Вопрос

Зачем писать тесты, если можно проверить всё руками в браузере?

## Основная идея

Ручная проверка работает, пока приложение маленькое. Когда в корзине есть промокоды, скидки, разные способы доставки и авторизация, после каждого изменения нужно заново прокликать десятки сценариев. Человек устаёт и пропускает шаги, а тест выполняет одно и то же одинаково каждый раз.

Главная ценность тестов — **защита от регрессий**. Регрессия — ситуация, когда новое изменение ломает то, что раньше работало. Например, разработчик поправил округление цены в одном компоненте, а итоговая сумма заказа стала неверной в другом. Тест на расчёт суммы упадёт сразу, а не после жалобы пользователя.

Вторая ценность — **безопасный рефакторинг**. Если тесты проверяют поведение, а не внутреннюю реализацию, можно переписать компонент с классов на хуки или заменить state manager и убедиться, что пользователь видит то же самое.

Третья — **документация**. Название теста «не даёт оформить заказ с пустой корзиной» объясняет правило бизнеса точнее, чем комментарий, и не устаревает: если правило изменится, тест упадёт.

Тесты не доказывают отсутствие ошибок. Они проверяют только те сценарии, которые кто-то описал. Поэтому важно тестировать важное, а не всё подряд.

## Пример

```ts
// cart.ts
export function getTotal(items: { price: number; qty: number }[]) {
  return items.reduce((sum, item) => sum + item.price * item.qty, 0);
}

// cart.test.ts
import { describe, it, expect } from 'vitest';
import { getTotal } from './cart';

describe('getTotal', () => {
  it('суммирует цену с учётом количества', () => {
    expect(getTotal([{ price: 100, qty: 2 }, { price: 50, qty: 1 }])).toBe(250);
  });

  it('возвращает 0 для пустой корзины', () => {
    expect(getTotal([])).toBe(0);
  });
});
```

Если кто-то поменяет `reduce` и забудет начальное значение `0`, второй тест упадёт: `reduce` пустого массива без начального значения бросает `TypeError`.

## Что важно помнить

- Тесты — инструмент снижения риска, а не цель сами по себе.
- Тест полезен, если падает при реальной поломке и не падает при безопасном рефакторинге.
- Медленные и нестабильные тесты перестают запускать — их ценность падает до нуля.
- Тесты в CI блокируют слияние сломанного кода, поэтому важны вместе с pipeline.
- Ручное и исследовательское тестирование тестами не заменяется полностью.

## Мини-шпаргалка

Регрессии → ловим автоматически. Рефакторинг → без страха. Название теста → документация правила. Тесты проверяют поведение, а не реализацию.
