# userEvent и fireEvent

> [!NOTE]
> `fireEvent` отправляет одно DOM-событие. `userEvent` симулирует действие пользователя целиком: при вводе текста — фокус, `keydown`, `keypress`, `input`, `keyup` для каждого символа, учёт `disabled` и `readonly`. Для тестов поведения рекомендуется `userEvent`.

## Вопрос

Чем `userEvent` отличается от `fireEvent`? Почему методы `userEvent` асинхронные?

## Основная идея

Когда пользователь кликает по кнопке, браузер генерирует цепочку: `pointerdown`, `mousedown`, `focus`, `pointerup`, `mouseup`, `click`. `fireEvent.click(button)` создаёт только событие `click`. Если компонент реагирует на `onMouseDown` или `onFocus`, `fireEvent` этого не заметит.

С вводом разница ещё заметнее. `fireEvent.change(input, { target: { value: 'Анна' } })` сразу подставляет значение. Не будет событий клавиатуры, не сработает `maxLength`, ограничение по маске и валидация на каждый символ. А `user.type(input, 'Анна')` вводит символы по одному, как человек.

`userEvent` также проверяет, можно ли взаимодействовать с элементом. Клик по `disabled`-кнопке не вызовет обработчик. Клик по элементу с `pointer-events: none` выбросит ошибку.

В версии 14 API стал асинхронным: каждый метод возвращает Promise, потому что между событиями могут быть задержки. Рекомендуемый способ — создать экземпляр через `userEvent.setup()` в начале теста.

| Метод | Что делает |
| --- | --- |
| `user.click(el)` / `dblClick` / `tripleClick` | клики |
| `user.type(el, text)` | клик по полю и ввод текста |
| `user.clear(el)` | очистка поля |
| `user.keyboard('{Enter}')` | нажатие клавиш |
| `user.tab()` | переход фокуса по Tab |
| `user.selectOptions(select, 'value')` | выбор в `<select>` |
| `user.upload(input, file)` | загрузка файла |
| `user.hover(el)` / `unhover` | наведение |
| `user.paste('текст')` | вставка из буфера |

## Пример

```tsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

it('ограничивает длину названия задачи', async () => {
  const user = userEvent.setup();
  render(<TodoInput maxLength={10} />);
  const input = screen.getByRole('textbox', { name: 'Задача' });

  await user.type(input, 'Очень длинная задача');

  expect(input).toHaveValue('Очень длин');
});

it('отправляет форму по Enter', async () => {
  const user = userEvent.setup();
  const onSubmit = vi.fn();
  render(<SearchForm onSubmit={onSubmit} />);

  await user.type(screen.getByRole('searchbox'), 'чайник{Enter}');

  expect(onSubmit).toHaveBeenCalledWith('чайник');
});

it('позволяет пройти форму с клавиатуры', async () => {
  const user = userEvent.setup();
  render(<LoginForm />);

  await user.tab();
  expect(screen.getByLabelText('Email')).toHaveFocus();
  await user.tab();
  expect(screen.getByLabelText('Пароль')).toHaveFocus();
});
```

С `fireEvent` первый тест прошёл бы с полным значением или повёл бы себя иначе: `maxLength` браузер применяет только при вводе с клавиатуры.

## Что важно помнить

- Не забывайте `await` перед каждым методом `user.*`.
- `userEvent.setup()` вызывают до `render` или сразу после, но в каждом тесте — экземпляры не переиспользуют между тестами.
- `fireEvent` подходит для событий, которые user-event не симулирует: `scroll`, `resize`, кастомные события.
- С fake timers: `userEvent.setup({ advanceTimers: vi.advanceTimersByTime })`.
- user-event работает поверх jsdom: layout и реальные координаты по-прежнему недоступны.

## Мини-шпаргалка

`fireEvent` — одно событие. `userEvent` — полная цепочка, как у человека, с учётом `disabled`. `const user = userEvent.setup()` и `await user.click(...)`.
