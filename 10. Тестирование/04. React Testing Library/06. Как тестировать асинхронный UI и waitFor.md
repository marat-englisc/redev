# Асинхронный UI, waitFor и act

> [!NOTE]
> Для ожидания появления элемента используют `findBy*`, для ожидания произвольного условия — `waitFor`. Оба повторяют проверку, пока она не пройдёт или не истечёт таймаут. Предупреждение «not wrapped in act(...)» обычно означает, что тест закончился раньше асинхронного обновления.

## Вопрос

Как тестировать компонент, который обновляется после запроса или таймера? Что значит предупреждение про `act`?

## Основная идея

После клика компонент может отправить запрос, дождаться ответа и только потом обновить состояние. В момент синхронной проверки результата ещё нет. Testing Library даёт утилиты ожидания:

| Утилита | Для чего |
| --- | --- |
| `await screen.findBy...` | дождаться появления элемента |
| `await waitFor(() => expect(...))` | дождаться выполнения любой проверки |
| `await waitForElementToBeRemoved(() => queryBy...)` | дождаться исчезновения |

`waitFor` вызывает колбэк каждые 50 мс (по умолчанию) и при изменениях DOM, пока он не перестанет бросать ошибку. Через 1000 мс тест падает с последней ошибкой.

Правила для `waitFor`:

- внутри — только проверка, **без побочных эффектов**: кликов, вызовов функций. Колбэк выполняется много раз;
- одна проверка на `waitFor`: тогда понятно, чего ждём, и падение быстрее;
- не пустой колбэк: `await waitFor(() => {})` ничего не ждёт осмысленно.

**`act`** — функция React, которая гарантирует, что все обновления состояния и эффекты применены перед проверкой. `render`, `user.*`, `findBy` и `waitFor` уже обёрнуты в `act`. Предупреждение `An update to X inside a test was not wrapped in act(...)` значит: состояние изменилось, когда тест этого не ждал. Обычно это промис, завершившийся после последней проверки. Решение — дождаться результата через `findBy`/`waitFor`, а не оборачивать всё в `act` вручную.

## Пример

```tsx
import { render, screen, waitFor } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { http, HttpResponse } from 'msw';
import { server } from '@/test/server';

it('сохраняет профиль и показывает уведомление', async () => {
  const user = userEvent.setup();
  render(<ProfileForm />);

  await user.type(screen.getByLabelText('Имя'), 'Анна');
  await user.click(screen.getByRole('button', { name: 'Сохранить' }));

  // кнопка блокируется на время запроса
  expect(screen.getByRole('button', { name: 'Сохранение...' })).toBeDisabled();

  // ждём результат
  expect(await screen.findByRole('status')).toHaveTextContent('Профиль сохранён');
  expect(screen.getByRole('button', { name: 'Сохранить' })).toBeEnabled();
});

it('вызывает аналитику после сохранения', async () => {
  const track = vi.fn();
  const user = userEvent.setup();
  render(<ProfileForm onSaved={track} />);

  await user.click(screen.getByRole('button', { name: 'Сохранить' }));

  await waitFor(() => expect(track).toHaveBeenCalledWith('profile_saved'));
});
```

Плохие варианты:

```tsx
// побочный эффект внутри waitFor — клик повторится много раз
await waitFor(() => {
  fireEvent.click(button);
  expect(screen.getByText('Готово')).toBeInTheDocument();
});

// waitFor + getBy вместо findBy
await waitFor(() => screen.getByText('Готово'));

// ручное ожидание
await new Promise((r) => setTimeout(r, 500));
```

## Что важно помнить

- Сеть в тестах мокается (MSW), поэтому ответы приходят быстро и таймауты по умолчанию достаточны.
- `act` вручную нужен редко: продвижение fake timers, вызов функций из `renderHook`, прямое обновление внешнего store.
- Проверка промежуточного состояния (loading) делается синхронно сразу после действия.
- Если `findBy` падает по таймауту, проверьте `screen.debug()` — возможно, запрос упал с ошибкой.

## Мини-шпаргалка

Появится → `await findBy`. Условие → `await waitFor(() => expect(...))` без побочных эффектов. Исчезнет → `waitForElementToBeRemoved`. Act-warning → дождись асинхронного результата.
