# MSW: мок сети на уровне запросов

> [!NOTE]
> MSW (Mock Service Worker) перехватывает HTTP-запросы на сетевом уровне и отвечает по описанным обработчикам. Код приложения — `fetch`, axios, TanStack Query — работает без изменений. Одни и те же обработчики используются в тестах (Node), в браузере при разработке и в Storybook.

## Вопрос

Что такое MSW? Чем он лучше мока `fetch` или модуля API через `vi.mock`?

## Основная идея

Если замокать модуль `api`, тест не проверит, какой URL, метод, заголовки и тело реально отправляются, и как разбирается ответ. Если замокать `fetch` через `vi.fn`, придётся повторять логику ответа (`ok`, `status`, `json()`), а переход с `fetch` на axios сломает все тесты.

MSW работает на границе сети. В Node он перехватывает запросы на уровне модулей `http` и глобального `fetch`, в браузере — через Service Worker. Приложение «думает», что общается с настоящим сервером. Обработчики описываются похоже на маршруты бэкенда: метод, путь, функция, возвращающая ответ.

Типичная организация:

- `handlers.ts` — обработчики «счастливого пути» по умолчанию;
- `server.ts` — `setupServer(...handlers)` для тестов;
- setup-файл — `listen` перед всеми тестами, `resetHandlers` после каждого, `close` в конце;
- в конкретном тесте `server.use(...)` переопределяет ответ: ошибка, пустой список, задержка.

Опция `onUnhandledRequest: 'error'` роняет тест, если приложение сделало запрос, для которого нет обработчика. Это защищает от случайных реальных запросов.

## Пример

```ts
// src/test/handlers.ts
import { http, HttpResponse } from 'msw';

export const handlers = [
  http.get('/api/todos', () =>
    HttpResponse.json([
      { id: '1', title: 'Купить хлеб', done: false },
      { id: '2', title: 'Позвонить маме', done: true },
    ]),
  ),
  http.post('/api/todos', async ({ request }) => {
    const body = (await request.json()) as { title: string };
    return HttpResponse.json({ id: '3', title: body.title, done: false }, { status: 201 });
  }),
];
```

```ts
// src/test/server.ts
import { setupServer } from 'msw/node';
import { handlers } from './handlers';

export const server = setupServer(...handlers);
```

```ts
// src/test/setup.ts
import '@testing-library/jest-dom/vitest';
import { server } from './server';

beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));
afterEach(() => server.resetHandlers());
afterAll(() => server.close());
```

```tsx
// TodoPage.test.tsx
import { http, HttpResponse } from 'msw';
import { server } from '@/test/server';

it('показывает ошибку, если сервер недоступен', async () => {
  server.use(http.get('/api/todos', () => new HttpResponse(null, { status: 500 })));

  renderWithProviders(<TodoPage />);

  expect(await screen.findByRole('alert')).toHaveTextContent('Не удалось загрузить задачи');
});
```

## Что важно помнить

- Глобальный `fetch` в Node не разбирает относительные URL (`fetch('/api/todos')` бросит `TypeError`). Задайте базовый адрес API через env, например `http://localhost/api`, и используйте его же в handlers. Axios в jsdom работает через XHR и резолвит относительный URL от `location`.
- `HttpResponse.error()` имитирует сетевую ошибку (запрос не дошёл), а статус 500 — ошибку сервера. Это разные сценарии.
- Задержку ответа задаёт `await delay(ms)` из `msw` — так проверяют состояние loading.
- Проверить тело запроса можно внутри обработчика, сохранив его в переменную теста.
- Тот же набор handlers через `setupWorker` даёт работающий фронтенд без бэкенда.

## Мини-шпаргалка

MSW = мок на границе сети, код приложения не меняется. `http.get(path, () => HttpResponse.json(...))`. `listen` → `resetHandlers` → `close`. Особый случай → `server.use(...)`. `onUnhandledRequest: 'error'`.
