# Тесты в CI

> [!NOTE]
> CI (Continuous Integration) автоматически запускает проверки на каждый push и pull request: установку зависимостей, линтер, проверку типов, unit/integration-тесты, сборку и e2e. Если проверка падает, слияние блокируется. Тесты, которые не запускаются в CI, быстро перестают поддерживаться.

## Вопрос

Как организовать запуск тестов в CI? В каком порядке выполнять проверки?

## Основная идея

Локально разработчик может забыть запустить тесты. CI делает это всегда и в одинаковом окружении. Результат виден прямо в pull request, а правило защиты ветки (branch protection) не даёт слить код с красными проверками.

Порядок шагов строят от быстрых к медленным — так ошибка находится раньше и дешевле:

1. `npm ci` — точная установка по lock-файлу;
2. lint — секунды;
3. typecheck (`tsc --noEmit`) — секунды или минута;
4. unit и integration (`vitest run`) — минуты;
5. сборка (`npm run build`);
6. e2e на собранном приложении — самое долгое.

Независимые шаги запускают параллельными job-ами. Долгие e2e-наборы делят на части (**sharding**): Playwright поддерживает `--shard=1/4`. Зависимости и браузеры кешируют.

После падения нужны артефакты: HTML-отчёт Playwright, trace, скриншоты, отчёт покрытия. Их загружают как artifacts, чтобы не воспроизводить ошибку вслепую.

## Пример

```yaml
# .github/workflows/ci.yml
name: CI
on:
  pull_request:
  push:
    branches: [main]

jobs:
  checks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npx vitest run --coverage

  e2e:
    needs: checks
    runs-on: ubuntu-latest
    strategy:
      matrix:
        shard: [1, 2]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npx playwright install --with-deps chromium
      - run: npx playwright test --shard=${{ matrix.shard }}/2
      - uses: actions/upload-artifact@v4
        if: ${{ !cancelled() }}
        with:
          name: playwright-report-${{ matrix.shard }}
          path: playwright-report/
          retention-days: 7
```

Локально полезно запускать быстрые проверки до коммита через husky и lint-staged: линтер и тесты только для изменённых файлов (`vitest related --run`).

## Что важно помнить

- `npm ci`, а не `npm install`: он не меняет lock-файл и падает при расхождении с `package.json`.
- В CI тесты запускают без watch-режима: `vitest run`.
- Переменная `CI=true` включает в Playwright `retries` и запрещает `.only` (`forbidOnly`), если это настроено в конфиге.
- Секреты (тестовые пароли, токены) хранятся в secrets CI, а не в репозитории.
- Медленный CI — проблема продукта: разработчики начинают обходить проверки. Следите за временем прогона.

## Мини-шпаргалка

push/PR → `npm ci` → lint → typecheck → `vitest run` → build → e2e. От быстрого к медленному. Параллельные job-ы, шардирование, кеш, артефакты отчётов. Красный CI блокирует merge.
