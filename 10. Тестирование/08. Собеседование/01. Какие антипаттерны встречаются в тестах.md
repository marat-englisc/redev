# Антипаттерны в тестах

> [!NOTE]
> Плохой тест либо не ловит поломки (ложная уверенность), либо падает без поломок (ложная тревога). Основные причины: проверка деталей реализации, отсутствие `await` и assertions, избыточные моки, общие данные, паузы вместо ожиданий и гигантские снапшоты.

## Вопрос

Какие ошибки чаще всего допускают при написании тестов? Как отличить хороший тест от плохого?

## Основная идея

Хороший тест отвечает на два вопроса «да»: **упадёт ли он, если сломать поведение?** и **выживет ли он при рефакторинге без изменения поведения?** Большинство антипаттернов нарушают одно из этих условий.

| Антипаттерн | Почему плохо | Как лучше |
| --- | --- | --- |
| Проверка state, классов, внутренних функций | ломается при рефакторинге | проверять видимый результат |
| Тест без `expect` («рендерится без ошибок») | проверяет только отсутствие исключения | проверить конкретный текст или роль |
| Забытый `await` перед `findBy`, `user.*`, `rejects` | ложнозелёный тест | правило `no-floating-promises`, внимательность |
| `container.querySelector('.btn')` | привязка к вёрстке, нет проверки a11y | `getByRole` с `name` |
| `getBy` для проверки отсутствия | падает не там, где нужно | `queryBy` + `not.toBeInTheDocument()` |
| Мок всего подряд | тест проверяет моки | мокать только границы (MSW) |
| `setTimeout`/`waitForTimeout` вместо ожидания | медленно и нестабильно | `findBy`, `waitFor`, web-first assertions |
| Побочные эффекты внутри `waitFor` | действие повторяется много раз | действие до `waitFor`, внутри только проверка |
| Общие изменяемые данные между тестами | зависимость от порядка | свежие данные в каждом тесте |
| Логика в тесте (`if`, циклы, формулы) | тест дублирует баг кода | явные ожидаемые значения, `it.each` |
| Огромные снапшоты | никто не читает diff | точечные проверки, inline-снапшоты |
| Один тест на десять поведений | непонятно, что сломалось | один тест — одно поведение |
| Неинформативные названия | отчёт ничего не говорит | «делает X, когда Y» |
| `.only` и `.skip` в репозитории | часть тестов не выполняется | правило линтера |
| Тест ради покрытия | цифра растёт, уверенность — нет | тестировать риски |

## Пример

```tsx
// Плохо: сразу несколько антипаттернов
it('test form', () => {
  const { container } = render(<LoginForm />);
  fireEvent.change(container.querySelector('input[name="email"]')!, { target: { value: 'a' } });
  fireEvent.click(container.querySelector('.submit-btn')!);
  setTimeout(() => {
    expect(container.querySelector('.error')).toBeTruthy();
  }, 500);
});
```

Проблемы: непонятное название, поиск по CSS, `fireEvent.change` вместо ввода, проверка в `setTimeout`, которая выполнится после завершения теста, проверка класса вместо текста.

```tsx
// Хорошо
it('показывает ошибку при некорректном email', async () => {
  const user = userEvent.setup();
  render(<LoginForm />);

  await user.type(screen.getByLabelText('Email'), 'a');
  await user.click(screen.getByRole('button', { name: 'Войти' }));

  expect(await screen.findByRole('alert')).toHaveTextContent('Введите корректный email');
});
```

## Что важно помнить

- Проверка теста: временно сломайте код — тест должен упасть.
- `eslint-plugin-testing-library` и `eslint-plugin-vitest` / `eslint-plugin-jest` автоматически ловят большую часть этих ошибок.
- Тесты — production-код: их ревьюят, рефакторят и удаляют, если они больше не полезны.
- DRY в тестах менее важен, чем читаемость: немного повторения лучше запутанных абстракций.

## Мини-шпаргалка

Хороший тест падает при поломке и выживает при рефакторинге. Главные враги: детали реализации, забытый `await`, лишние моки, паузы, общие данные, гигантские снапшоты.
