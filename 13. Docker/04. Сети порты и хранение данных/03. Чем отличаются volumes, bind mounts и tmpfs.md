# Чем отличаются volumes, bind mounts и tmpfs

> [!NOTE]
> Записываемый слой контейнера пропадает вместе с ним, поэтому данные выносят наружу. **Volume** — хранилище, которым управляет Docker (`/var/lib/docker/volumes`): переживает удаление контейнера, подходит для данных БД. **Bind mount** — конкретный каталог или файл хоста, смонтированный в контейнер: удобен для кода в разработке и конфигов. **tmpfs** — каталог в оперативной памяти, исчезает при остановке: для временных и чувствительных файлов.

## Вопрос

Чем отличаются volumes, bind mounts и tmpfs и когда что использовать?

## Volume

```bash
docker volume create pgdata
docker run -d -v pgdata:/var/lib/postgresql postgres:18
# или подробный синтаксис
docker run -d --mount type=volume,source=pgdata,target=/var/lib/postgresql postgres:18
```

- Создаётся и хранится Docker'ом, не зависит от структуры каталогов хоста.
- Переживает `docker rm`; удаляется только явно.
- Быстрее записываемого слоя и bind mount на macOS/Windows.
- Если volume пустой, Docker при первом монтировании копирует в него содержимое каталога из образа.

**Анонимный volume** — без имени (`-v /app/node_modules` или `VOLUME` в Dockerfile). Получает случайный ID, его легко потерять.

## Bind mount

```bash
docker run -d -v "$(pwd)":/app -w /app node:24-alpine npm run dev
docker run -d -v ./nginx.conf:/etc/nginx/conf.d/default.conf:ro nginx:1.29-alpine
```

- Монтирует путь хоста как есть — изменения видны сразу с обеих сторон.
- Перекрывает содержимое образа в целевом каталоге.
- Зависит от хоста: путей, прав (UID/GID), производительности файловой системы.
- `:ro` — только для чтения; используйте для конфигов.

## tmpfs

```bash
docker run -d --tmpfs /tmp:size=64m my-api
```

Хранится в RAM, на диск не пишется, при остановке исчезает. Подходит для кэша, временных файлов и в паре с `--read-only`, когда приложению всё же нужен каталог для записи.

## Пример в Compose

```yaml
services:
  api:
    build: .
    volumes:
      - .:/app                  # bind mount: код для hot reload
      - /app/node_modules       # анонимный volume: не затирать зависимости контейнера
    tmpfs:
      - /tmp
  db:
    image: postgres:18
    volumes:
      - pgdata:/var/lib/postgresql   # named volume для данных

volumes:
  pgdata:
```

Строка `/app/node_modules` нужна потому, что bind mount `.:/app` перекрыл бы `node_modules`, установленные в образе, содержимым хоста (или пустотой).

## Что выбрать

| Задача | Решение |
| --- | --- |
| Данные PostgreSQL, Redis | Named volume |
| Код при разработке | Bind mount или `compose watch` |
| Конфиг Nginx | Bind mount `:ro` или `COPY` в образ |
| `node_modules` в dev | Анонимный или named volume |
| Временные файлы, секреты в памяти | tmpfs |
| Файлы пользователей в production | Объектное хранилище (S3) |

## Резервная копия volume

```bash
docker run --rm -v pgdata:/data -v "$(pwd)":/backup alpine \
  tar czf /backup/pgdata.tar.gz -C /data .
```

Для баз данных надёжнее логический дамп (`pg_dump`) — копия файлов работающей БД может оказаться несогласованной.

## Частые ошибки

- Хранить данные БД в записываемом слое.
- Затирать `node_modules` bind mount'ом проекта.
- Использовать bind mount для production-данных — привязка к конкретному серверу.
- Монтировать volume не в тот путь (например, `/var/lib/postgresql/data` для postgres 18+) — данные уходят в анонимный volume.
- Чистить `volume prune` без проверки.

## Что важно помнить

- Volume переживает контейнер, но не `docker volume rm` и не `compose down -v`.
- Bind mount перекрывает содержимое образа, пустой volume — наоборот, наполняется из образа.
- Volume — не бэкап: он лежит на том же диске, что и сервер.

## Мини-шпаргалка

- Volume — управляет Docker, для данных.
- Bind mount — путь хоста, для кода и конфигов.
- tmpfs — RAM, для временного.
- `-v name:/path`, `-v ./dir:/path:ro`, `--tmpfs /tmp`.
