# Как хранить данные базы данных в Docker

> [!NOTE]
> Данные БД всегда выносят за пределы контейнера — в **named volume** (локально и на небольших серверах) или в **управляемую базу** (RDS, Cloud SQL, Neon) в production. Путь монтирования зависит от образа: для **PostgreSQL 18+** — `/var/lib/postgresql`, для 17 и ниже — `/var/lib/postgresql/data`. `docker compose down` volumes сохраняет, `down -v` — удаляет. Volume не бэкап: нужен регулярный `pg_dump` с проверкой восстановления.

## Вопрос

Как правильно хранить данные базы данных в Docker и делать резервные копии?

## Почему не в контейнере

Контейнер одноразовый: `docker rm db` или пересоздание при обновлении образа уничтожает записываемый слой, а с ним и базу. Кроме того, запись в overlay медленнее, чем в volume.

## PostgreSQL с named volume

```yaml
services:
  db:
    image: postgres:18
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql
    ports:
      - "127.0.0.1:5432:5432"   # для GUI-клиента на своей машине
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  pgdata:
```

## Ловушка с путём в PostgreSQL 18

В образе `postgres:18` данные хранятся в `/var/lib/postgresql/18/docker`, а объявленный `VOLUME` — `/var/lib/postgresql`. Если по старой привычке смонтировать volume в `/var/lib/postgresql/data`, база будет писать в **анонимный** volume на `/var/lib/postgresql`, а ваш named volume останется пустым. После пересоздания контейнера данные «пропадут». Если же в старом пути уже лежит база от предыдущей версии, entrypoint образа остановится с ошибкой и подскажет поменять точку монтирования. Новая структура каталогов нужна для удобного обновления мажорной версии через `pg_upgrade`.

| Образ | Куда монтировать |
| --- | --- |
| `postgres:18` и новее | `/var/lib/postgresql` |
| `postgres:17` и старше | `/var/lib/postgresql/data` |
| `mysql` | `/var/lib/mysql` |
| `mongo` | `/data/db` |
| `redis` | `/data` |

Всегда сверяйтесь с описанием образа на Docker Hub.

## Начальная инициализация

```yaml
volumes:
  - pgdata:/var/lib/postgresql
  - ./db/init:/docker-entrypoint-initdb.d:ro
```

Скрипты `*.sql` и `*.sh` из `/docker-entrypoint-initdb.d` выполняются **только при первом запуске**, когда каталог данных пуст. Если volume уже существует, изменения в скриптах не применятся — для этого нужны миграции.

## Что сохраняет и что удаляет Compose

```bash
docker compose down        # контейнеры и сеть удалены, pgdata сохранён
docker compose up -d       # данные на месте
docker compose down -v     # удалены и volumes проекта — база потеряна
```

## Бэкап и восстановление

```bash
# дамп
docker compose exec -T db pg_dump -U app -Fc app > backup.dump

# восстановление
docker compose exec -T db pg_restore -U app -d app --clean < backup.dump
```

Флаг `-T` отключает TTY, иначе бинарный дамп повредится. Бэкап хранят вне сервера и регулярно проверяют восстановление — непроверенный бэкап считается отсутствующим.

## Обновление мажорной версии

Нельзя просто поменять `postgres:17` на `postgres:18` с тем же volume: формат данных разный, контейнер не стартует. Варианты: `pg_dump` из старой версии и восстановление в новую или `pg_upgrade`.

## Dev и production

| | Локально | Production |
| --- | --- | --- |
| Где БД | Контейнер + named volume | Управляемая БД или выделенный сервер |
| Порт | `127.0.0.1:5432` | Не публикуется наружу |
| Пароль | В `.env` | В secret manager |
| Бэкап | По желанию | Автоматический, с проверкой восстановления |

## Частые ошибки

- Запускать БД без volume.
- Монтировать volume в старый путь для postgres 18.
- Ждать, что изменённые init-скрипты применятся к существующей базе.
- Делать `down -v` «для чистоты» и терять локальные данные.
- Считать volume резервной копией.
- Менять мажорную версию образа без миграции данных.

## Что важно помнить

- Путь данных — часть контракта образа; при смене версии его перепроверяют.
- Init-скрипты срабатывают один раз — на пустом каталоге данных.
- В production stateful-сервисы чаще выносят из Docker на управляемые платформы.

## Мини-шпаргалка

- Данные → named volume.
- postgres 18+ → `/var/lib/postgresql`.
- `down` сохраняет, `down -v` удаляет.
- Бэкап: `pg_dump -Fc`, восстановление: `pg_restore`.
- Мажорное обновление — через dump/restore или `pg_upgrade`.
