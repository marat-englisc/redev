# Как работают сети Docker и DNS между контейнерами

> [!NOTE]
> Сеть Docker — виртуальная сеть, к которой подключаются контейнеры. В **пользовательской bridge-сети** (её автоматически создаёт Compose) работает встроенный DNS: контейнеры находят друг друга по имени контейнера или сервиса, например `db:5432`. В сети `bridge` по умолчанию DNS по именам **нет** — только IP. Кроме bridge есть `host` (контейнер использует сеть хоста), `none` (без сети) и overlay для кластеров.

## Вопрос

Как контейнеры общаются между собой и как работает DNS внутри Docker?

## Основная идея

```text
сеть app-net (172.20.0.0/16), DNS 127.0.0.11
├── api  172.20.0.2   → обращается к db:5432
└── db   172.20.0.3
```

IP контейнеров меняются при пересоздании, поэтому ходят по именам. Встроенный DNS-сервер Docker (`127.0.0.11` внутри контейнера) превращает имя в текущий IP.

## Пример с Docker CLI

```bash
docker network create app-net

docker run -d --name db --network app-net \
  -e POSTGRES_PASSWORD=secret postgres:18

docker run -d --name api --network app-net \
  -e DATABASE_URL=postgres://postgres:secret@db:5432/postgres \
  my-api
```

`api` видит `db` по имени. Если запустить их без `--network`, оба попадут в сеть `bridge` по умолчанию, где имя `db` не резолвится.

## Пример с Compose

```yaml
services:
  api:
    build: .
    environment:
      DATABASE_URL: postgres://app:secret@db:5432/app
  db:
    image: postgres:18
```

Compose создаёт сеть `<проект>_default` и подключает к ней все сервисы. Имя сервиса становится DNS-именем; дополнительные имена задаются через `aliases`.

## Почему не localhost

```text
postgres://localhost:5432/app   ✗ ищет Postgres внутри контейнера api
postgres://db:5432/app          ✓ контейнер db через DNS
```

## Драйверы сетей

| Драйвер | Когда используют |
| --- | --- |
| `bridge` (пользовательская) | Основной вариант на одном хосте, есть DNS |
| `bridge` (по умолчанию) | Устаревший режим без DNS по именам |
| `host` | Контейнер делит сеть с хостом: нет NAT, нет изоляции портов (полноценно — на Linux) |
| `none` | Сеть отключена — для задач, которым она не нужна |
| `overlay` | Сеть между хостами в Swarm |

## Разделение сетей

```yaml
services:
  proxy:
    image: nginx:1.29-alpine
    ports: ["80:80"]
    networks: [public, internal]
  api:
    build: .
    networks: [internal]
  db:
    image: postgres:18
    networks: [internal]

networks:
  public:
  internal:
    internal: true        # без выхода в интернет
```

Прокси видит API, API видит базу, но база недоступна из публичной сети и не может сама выходить наружу.

## Диагностика

```bash
docker network ls
docker network inspect app-net                       # кто подключён и с какими IP
docker exec api getent hosts db                      # резолвится ли имя
docker run --rm --network app-net nicolaka/netshoot nc -zv db 5432
```

Образ `netshoot` содержит `dig`, `curl`, `nc`, `tcpdump` — удобно, когда в рабочем образе нет утилит.

## Частые ошибки

- Использовать `localhost` для обращения к другому контейнеру.
- Запускать контейнеры через CLI без общей пользовательской сети.
- Публиковать порты только ради общения контейнеров.
- Хардкодить IP контейнера.

## Что важно помнить

- DNS по именам работает только в пользовательских сетях, Compose создаёт такую автоматически.
- Контейнер может быть подключён к нескольким сетям одновременно.
- Внутри сети используется внутренний порт контейнера, а не опубликованный.

## Мини-шпаргалка

- `docker network create`, `--network`.
- Имя сервиса = DNS-имя.
- `localhost` — сам контейнер.
- `internal: true` — сеть без выхода наружу.
- `getent hosts db` — проверить DNS.
