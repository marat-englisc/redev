# Как упаковать Next.js-приложение в Docker

> [!NOTE]
> Next.js с SSR, Route Handlers и Server Actions — это **Node.js-сервер**, а не статика. Для Docker включают `output: "standalone"`: `next build` кладёт в `.next/standalone` минимальный `server.js` и только нужные модули. В финальный stage копируют `.next/standalone`, `.next/static` и `public`, задают `HOSTNAME=0.0.0.0` и запускают `node server.js`. Переменные `NEXT_PUBLIC_*` вшиваются в клиентский бандл при сборке; серверные переменные читаются при запуске.

## Вопрос

Как упаковать Next.js-приложение в Docker?

## next.config.ts

```ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  output: "standalone",
};

export default nextConfig;
```

Next.js трассирует импорты и копирует в `.next/standalone` только используемые файлы из `node_modules`. Образ получается в несколько раз меньше, чем при копировании всех зависимостей.

## Production Dockerfile

```dockerfile
# syntax=docker/dockerfile:1
FROM node:24-alpine AS base
WORKDIR /app

FROM base AS deps
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci

FROM base AS build
COPY --from=deps /app/node_modules ./node_modules
COPY . .
ARG NEXT_PUBLIC_SITE_URL
ENV NEXT_PUBLIC_SITE_URL=${NEXT_PUBLIC_SITE_URL}
ENV NEXT_TELEMETRY_DISABLED=1
RUN npm run build

FROM base AS runner
ENV NODE_ENV=production \
    NEXT_TELEMETRY_DISABLED=1 \
    PORT=3000 \
    HOSTNAME=0.0.0.0
COPY --from=build --chown=node:node /app/public ./public
COPY --from=build --chown=node:node /app/.next/standalone ./
COPY --from=build --chown=node:node /app/.next/static ./.next/static
USER node
EXPOSE 3000
CMD ["node", "server.js"]
```

`public` и `.next/static` в standalone не включаются — их копируют отдельно (или раздают через CDN).

## Build-time и runtime переменные

| Переменная | Когда читается | Где видна |
| --- | --- | --- |
| `NEXT_PUBLIC_*` | При `next build`, вшивается в JS | В браузере — публично |
| Остальные (`DATABASE_URL`, `AUTH_SECRET`) | При запуске сервера | Только на сервере |

```bash
docker build --build-arg NEXT_PUBLIC_SITE_URL=https://shop.example.com -t web .
docker run -e DATABASE_URL=postgres://... -e AUTH_SECRET=... -p 3000:3000 web
```

Нюанс: страницы, статически отрендеренные при сборке, тоже «запекают» прочитанные в момент сборки значения. Если конфигурация должна меняться без пересборки, делайте такие страницы динамическими или читайте её в рантайме.

## Кэш и несколько реплик

Next.js хранит кэш данных и ISR в файловой системе контейнера (`.next/cache`). При нескольких репликах у каждой свой кэш, и `revalidatePath` в одной не очищает остальные. Для горизонтального масштабирования настраивают общий cache handler (например, на Redis) или используют платформу с поддержкой Next.js.

## Изображения

`next/image` оптимизирует картинки на сервере через `sharp` — он ставится автоматически, но на Alpine иногда требует проверки. Оптимизированные изображения кэшируются в `.next/cache/images`; чтобы кэш переживал пересоздание, этот каталог можно вынести во volume.

## Compose

```yaml
services:
  web:
    build:
      context: .
      args:
        NEXT_PUBLIC_SITE_URL: http://localhost:3000
    ports: ["3000:3000"]
    environment:
      DATABASE_URL: postgres://app:secret@db:5432/app
    depends_on:
      db:
        condition: service_healthy
  db:
    image: postgres:18
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      retries: 10
volumes:
  pgdata:
```

Если `next build` обращается к БД (статическая генерация с данными), база должна быть доступна во время сборки — это частая причина падений в CI. Обычно такие страницы делают динамическими или передают адрес БД на этапе сборки отдельно.

## Частые ошибки

- Раздавать SSR-приложение как статику через Nginx.
- Забыть скопировать `.next/static` или `public` — стили и картинки 404.
- Не задать `HOSTNAME=0.0.0.0` — сервер недоступен снаружи.
- Положить секреты в `NEXT_PUBLIC_*`.
- Ждать, что `-e NEXT_PUBLIC_*` изменит клиентский код без пересборки.

## Что важно помнить

- `output: "standalone"` — стандартный способ получить компактный образ.
- Чисто статический сайт (`output: "export"`) упаковывают как Vite-приложение — в Nginx.
- При нескольких репликах кэш Next.js нужно делать общим.

## Мини-шпаргалка

- `output: "standalone"`.
- Копировать `.next/standalone`, `.next/static`, `public`.
- `HOSTNAME=0.0.0.0`, `CMD ["node", "server.js"]`.
- `NEXT_PUBLIC_*` — build-time, публичны; остальные — runtime.
