# Как передавать переменные окружения из Compose в приложение

> [!NOTE]
> В Compose есть два разных механизма. **Подстановка (interpolation)**: `${VAR}` в YAML заменяется значением из shell или файла `.env` рядом с `compose.yaml` — это настройка самого файла. **Передача в контейнер**: поля `environment` и `env_file` создают переменные окружения процесса, которые приложение читает через `process.env`. Значение в `.env` само по себе в контейнер **не попадает**. Для frontend-переменных (`VITE_*`, `NEXT_PUBLIC_*`) есть третий этап — сборка: они вшиваются в бандл и публичны.

## Вопрос

Как Compose передаёт переменные окружения в контейнер и чем `.env` отличается от `env_file`?

## Три уровня

```text
.env рядом с compose.yaml ──подстановка──▶ ${VAR} в YAML
environment / env_file    ──────────────▶ process.env в контейнере
build.args                ──────────────▶ ARG при сборке (VITE_*, NEXT_PUBLIC_*)
```

## Подстановка в YAML

```env
# .env
TAG=1.4.0
DB_PASSWORD=dev-password
```

```yaml
services:
  api:
    image: ghcr.io/team/api:${TAG:-latest}
    environment:
      DATABASE_URL: postgres://app:${DB_PASSWORD}@db:5432/app
```

| Синтаксис | Значение |
| --- | --- |
| `${VAR}` | Значение или пустая строка |
| `${VAR:-default}` | По умолчанию, если не задано или пусто |
| `${VAR:?message}` | Ошибка с сообщением, если не задано |
| `$$` | Литеральный `$` |

## Передача в контейнер

```yaml
services:
  api:
    env_file:
      - .env.api              # все переменные файла попадут в контейнер
    environment:
      NODE_ENV: production    # приоритет выше, чем у env_file
      PORT: 3000
      LOG_LEVEL:              # без значения — взять из окружения shell
```

Приоритет (от высшего): `docker compose run -e` → `environment` → `env_file` → `ENV` в Dockerfile.

## Как проверить

```bash
docker compose config                    # YAML после подстановки
docker compose exec api printenv | sort  # что реально видит процесс
```

Переменные применяются при **создании** контейнера. После изменения `.env` нужен `docker compose up -d` — Compose пересоздаст изменённые сервисы. `restart` контейнер не пересоздаёт и новые значения не подхватит.

## Валидация на старте

```ts
import { z } from "zod";

const env = z
  .object({
    DATABASE_URL: z.string().url(),
    PORT: z.coerce.number().default(3000),
    JWT_SECRET: z.string().min(32),
  })
  .parse(process.env);
```

Приложение должно падать сразу с понятной ошибкой, если переменной нет, а не через час на первом запросе.

## Frontend-переменные

```yaml
services:
  web:
    build:
      context: ./web
      args:
        VITE_API_URL: /api         # попадёт в бандл при сборке
```

`environment` для собранного SPA бесполезен: код уже в браузере. Всё, что передано в `VITE_*` или `NEXT_PUBLIC_*`, видно пользователю.

## Секреты

`environment` удобен для конфигурации, но значения видны в `docker inspect` и могут попасть в логи. Для паролей в production используют Compose `secrets`, secret manager платформы или как минимум файл, который не попадает в git, — см. [урок про секреты](<../07. Production безопасность и отладка/03. Как безопасно передавать секреты при сборке и запуске.md>).

## Частые ошибки

- Ждать, что переменная из `.env` сама появится в контейнере.
- Путать `.env` (подстановка) и `env_file` (передача).
- Делать `restart` вместо `up -d` после изменения переменных.
- Коммитить `.env` с реальными паролями вместо `.env.example`.
- Класть секреты во frontend-переменные.

## Что важно помнить

- `.env` настраивает Compose, `environment`/`env_file` настраивают приложение.
- `docker compose config` и `printenv` — два шага проверки.
- Frontend-переменные — build-time и публичны.

## Мини-шпаргалка

- `${VAR:-default}`, `${VAR:?error}`.
- `environment` > `env_file` > `ENV`.
- Изменил переменные → `docker compose up -d`.
- Проверка: `config`, `exec printenv`.
- В git — `.env.example`.
