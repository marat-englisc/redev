# Как работать с образами - pull, build, tag, push

> [!NOTE]
> Жизненный цикл образа: `docker pull` — скачать из registry, `docker build` — собрать из `Dockerfile`, `docker tag` — дать образу ещё одно имя, `docker push` — отправить в registry. Имя образа — `registry/namespace/repo:tag`. Тег изменяемый: `latest` и даже `1.2` могут указывать на разные образы в разное время. Неизменяемая ссылка — **digest** `@sha256:…`.

## Вопрос

Как скачивать, собирать, тегировать и публиковать образы?

## Скачать

```bash
docker pull node:24-alpine
docker pull postgres:18
docker pull --platform linux/amd64 node:24-alpine
```

Без тега Docker подставляет `latest`.

## Собрать

```bash
docker build -t my-api:1.0.0 .
docker build -f docker/Dockerfile -t my-api:1.0.0 .
docker build --target runner -t my-api:1.0.0 .
docker build --build-arg NODE_VERSION=24 -t my-api .
```

- `-t` — имя и тег (можно указать несколько `-t`);
- `.` — build context, каталог с файлами для сборки;
- `-f` — путь к Dockerfile, если он не в корне context;
- `--target` — собрать до определённого stage multi-stage-сборки.

## Посмотреть

```bash
docker image ls
docker image history my-api:1.0.0   # слои и их размер
docker image inspect my-api:1.0.0   # метаданные: CMD, ENV, архитектура, digest
```

## Тегировать и опубликовать

```bash
docker login ghcr.io
docker tag my-api:1.0.0 ghcr.io/team/my-api:1.0.0
docker tag my-api:1.0.0 ghcr.io/team/my-api:latest
docker push ghcr.io/team/my-api:1.0.0
docker push ghcr.io/team/my-api:latest
```

`docker tag` ничего не копирует: это ещё одно имя для того же image ID. Без префикса registry `push` уйдёт в Docker Hub.

## Тег, latest и digest

```text
my-api:latest                → «то, что последним запушили с этим тегом»
my-api:1.14.3                → конкретный релиз, но тег можно перезаписать
my-api@sha256:4f3c...e91a    → ровно этот образ, навсегда
```

| Ссылка | Когда использовать |
| --- | --- |
| `latest` | Локальные эксперименты |
| `1.14.3`, `git-sha` | Деплой и CI |
| Digest | Максимальная воспроизводимость: базовый образ в `FROM`, production-манифесты |

Типичная схема тегов в CI: SHA коммита (`api:9f2c1ab`) плюс semver релиза (`api:1.14.3`).

## Сохранить без registry

```bash
docker save my-api:1.0.0 -o my-api.tar
docker load -i my-api.tar
```

Пригодится для изолированных серверов без доступа к registry.

## Частые ошибки

- Считать `latest` «последней стабильной версией» — это просто тег по умолчанию.
- Пушить без префикса registry.
- Думать, что `docker tag` пересобирает образ.
- Собирать с огромным build context без `.dockerignore`.

## Что важно помнить

- Тег — изменяемый указатель, digest — неизменяемый идентификатор содержимого.
- Один образ может иметь сколько угодно тегов, и все они указывают на один image ID.
- Мультиархитектурный образ — это манифест-список с вариантами под `amd64` и `arm64` под одним тегом.

## Мини-шпаргалка

- `pull image:tag` — скачать.
- `build -t name:tag .` — собрать.
- `tag src dst` — новое имя.
- `push registry/name:tag` — опубликовать.
- `image history` — слои.
- В production — версии или digest, не `latest`.
