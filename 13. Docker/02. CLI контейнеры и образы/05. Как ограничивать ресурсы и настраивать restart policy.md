# Как ограничивать ресурсы и настраивать restart policy

> [!NOTE]
> По умолчанию контейнер может использовать **всю** память и CPU хоста. Лимиты задают флагами `--memory`, `--cpus`, `--pids-limit` (в Compose — `mem_limit`, `cpus` или `deploy.resources`). При превышении лимита памяти ядро убивает процесс — **OOM kill, exit code 137**. **Restart policy** (`no`, `on-failure`, `always`, `unless-stopped`) определяет, перезапустит ли Docker контейнер после падения или перезагрузки хоста.

## Вопрос

Как ограничить ресурсы контейнера и настроить автоматический перезапуск?

## Лимиты ресурсов

```bash
docker run -d \
  --memory=512m \
  --memory-reservation=256m \
  --cpus=1.5 \
  --pids-limit=200 \
  my-api
```

| Флаг | Смысл |
| --- | --- |
| `--memory` | Жёсткий лимит; превышение → OOM kill |
| `--memory-reservation` | Мягкий лимит, учитывается при нехватке памяти на хосте |
| `--cpus` | Доля процессорного времени (1.5 = полтора ядра) |
| `--cpu-shares` | Относительный вес при конкуренции за CPU |
| `--pids-limit` | Максимум процессов, защита от fork-бомбы |

В Compose:

```yaml
services:
  api:
    image: my-api:1.4.0
    mem_limit: 512m
    cpus: 1.5
    pids_limit: 200
```

## Node.js и лимит памяти

Node.js учитывает лимит cgroup при выборе размера кучи, но запас на буферы, стек и native-память нужен всё равно. Надёжнее задать размер кучи явно — примерно 70–80% лимита контейнера:

```dockerfile
ENV NODE_OPTIONS="--max-old-space-size=384"
```

Тогда при утечке приложение упадёт с понятной ошибкой `JavaScript heap out of memory`, а не будет молча убито ядром.

## Как распознать OOM

```bash
docker inspect -f '{{.State.OOMKilled}} {{.State.ExitCode}}' api
# true 137
```

Exit code 137 = 128 + 9 (SIGKILL). Если `OOMKilled: true` — лимит слишком мал или есть утечка памяти.

## Restart policy

```bash
docker run -d --restart unless-stopped my-api
docker update --restart on-failure:5 api    # изменить у существующего контейнера
```

| Политика | Поведение |
| --- | --- |
| `no` (по умолчанию) | Не перезапускать |
| `on-failure[:N]` | Перезапускать при ненулевом коде выхода, максимум N раз |
| `always` | Перезапускать всегда, в том числе после рестарта демона |
| `unless-stopped` | Как `always`, но не поднимать, если контейнер остановили вручную |

Docker перезапускает с увеличивающейся задержкой, чтобы падающий контейнер не нагружал хост. Статус `Restarting` в `docker ps` — признак цикла падений: смотри `docker logs`.

## Restart policy — не замена оркестратору

Restart policy работает только на одном хосте. Она не переносит контейнер на другой сервер, не делает rolling update и не балансирует трафик. Для этого нужны Kubernetes, Swarm, Nomad или PaaS (см. [урок про оркестрацию](<../07. Production безопасность и отладка/08. Чем Compose отличается от Kubernetes и что такое оркестрация.md>)).

## Частые ошибки

- Не задавать лимиты в production: утечка в одном сервисе роняет весь хост.
- Ставить `--memory` впритык к потреблению Node.js и получать случайные OOM.
- Использовать `always` для одноразовых задач (миграций) — они будут запускаться бесконечно.
- Не замечать цикл `Restarting` и не смотреть логи.

## Что важно помнить

- Без лимитов контейнер ограничен только ресурсами хоста.
- Exit code 137 и `OOMKilled: true` — классический признак нехватки памяти.
- Для веб-сервисов обычно выбирают `unless-stopped`, для задач — `no` или `on-failure`.

## Мини-шпаргалка

- `--memory 512m --cpus 1 --pids-limit 200`.
- 137 = SIGKILL, проверь `OOMKilled`.
- `NODE_OPTIONS=--max-old-space-size` ниже лимита.
- Restart: `no`, `on-failure`, `always`, `unless-stopped`.
