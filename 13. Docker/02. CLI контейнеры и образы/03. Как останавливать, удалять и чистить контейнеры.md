# Как останавливать, удалять и чистить контейнеры

> [!NOTE]
> `docker stop` отправляет главному процессу **SIGTERM** и через 10 секунд, если он не завершился, — **SIGKILL**. `docker kill` сразу шлёт SIGKILL. `docker rm` удаляет контейнер, `docker rmi` — образ, `docker system prune` чистит неиспользуемое. Volumes обычные команды не трогают, потому что в них лежат данные: их удаляют только явно (`docker volume rm`, `prune --volumes`, `compose down -v`).

## Вопрос

Как останавливать и удалять контейнеры и как освободить место, не потеряв данные?

## Остановка и запуск

```bash
docker stop api               # SIGTERM → ждать 10 с → SIGKILL
docker stop -t 30 api         # дать 30 секунд на graceful shutdown
docker kill api               # сразу SIGKILL
docker start api              # снова запустить существующий контейнер
docker restart api            # stop + start
```

Если контейнер каждый раз останавливается ровно 10 секунд, приложение не обрабатывает SIGTERM — типичная проблема с `CMD npm start` или shell-формой (см. [PID 1 и сигналы](<../07. Production безопасность и отладка/06. Как работают PID 1, сигналы и graceful shutdown.md>)).

## Удаление контейнеров

```bash
docker rm api                 # только остановленный
docker rm -f api              # остановить (SIGKILL) и удалить
docker container prune        # удалить все остановленные
```

## Удаление образов

```bash
docker rmi my-api:1.0.0
docker image prune            # dangling-образы (<none>:<none>), оставшиеся после пересборок
docker image prune -a         # все образы без контейнеров
```

Образ нельзя удалить, пока от него есть контейнеры — даже остановленные. Если у образа несколько тегов, `rmi` по тегу удаляет только этот тег.

## Общая очистка

```bash
docker system df              # сколько места занимают образы, контейнеры, volumes, кэш
docker system prune           # остановленные контейнеры, неиспользуемые сети, dangling-образы, кэш сборки
docker system prune -a        # + все неиспользуемые образы
docker builder prune          # только кэш BuildKit
```

`docker system df` стоит запускать первым: часто больше всего места занимает кэш сборки, а не образы.

## Volumes — осторожно

```bash
docker volume ls
docker volume rm pgdata                 # явное удаление
docker volume prune                     # анонимные volumes без контейнеров
docker system prune --volumes           # + volumes; данные будут потеряны
```

С Docker 23 `volume prune` по умолчанию удаляет только **анонимные** volumes; чтобы удалить и именованные, нужен флаг `-a`. Перед любой такой командой проверь, что в volume нет единственной копии базы.

## Частые ошибки

- Путать `stop` (остановить) и `rm` (удалить).
- Запускать `system prune -a --volumes` «чтобы починить» и терять локальную базу.
- Не понимать, почему образ не удаляется: от него остались остановленные контейнеры.
- Использовать `kill` по умолчанию и лишать приложение шанса корректно завершиться.

## Что важно помнить

- `stop` даёт приложению время на graceful shutdown, `kill` — нет.
- Образ, контейнер и volume — независимые сущности со своим жизненным циклом.
- Данные удаляются только явными командами для volumes — в этом их смысл.

## Мини-шпаргалка

- `stop` → SIGTERM, 10 с, SIGKILL; `kill` → SIGKILL.
- `rm` — контейнер, `rmi` — образ, `volume rm` — данные.
- `system df` — посмотреть, `system prune` — почистить.
- `--volumes` и `down -v` — опасно для данных.
