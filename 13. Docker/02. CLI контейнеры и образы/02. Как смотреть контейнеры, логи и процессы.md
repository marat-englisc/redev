# Как смотреть контейнеры, логи и процессы

> [!NOTE]
> Основной набор диагностики: `docker ps -a` — какие контейнеры есть и в каком статусе, `docker logs` — что процесс написал в stdout/stderr, `docker inspect` — полная конфигурация (порты, env, mounts, сети, health), `docker exec` — команда внутри работающего контейнера, `docker stats` и `docker top` — ресурсы и процессы. Приложение в контейнере должно логировать в stdout/stderr, иначе `docker logs` ничего не покажет.

## Вопрос

Как посмотреть список контейнеров, их логи и что происходит внутри?

## Список контейнеров

```bash
docker ps        # только запущенные
docker ps -a     # все, включая остановленные (Exited)
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
```

Колонка `STATUS` подсказывает причину проблемы: `Exited (1)` — приложение упало, `Exited (137)` — убито (OOM или `kill`), `Restarting` — цикл падений, `(unhealthy)` — не проходит healthcheck.

## Логи

```bash
docker logs api                 # всё, что было
docker logs -f api              # следить в реальном времени
docker logs --tail 100 api      # последние 100 строк
docker logs --since 10m api     # за последние 10 минут
docker logs -t api              # с временными метками
```

Docker собирает то, что процесс пишет в `stdout` и `stderr`. Если приложение пишет в файл внутри контейнера, логов в `docker logs` не будет — поэтому в контейнерах логируют в консоль. Официальный образ Nginx, например, делает `access.log` симлинком на `/dev/stdout`.

## Команда внутри контейнера

```bash
docker exec -it api sh          # оболочка (в alpine нет bash)
docker exec api printenv        # переменные окружения
docker exec -u root -it api sh  # от root, если процесс работает от node
```

`exec` запускает **новый** процесс в работающем контейнере. В остановленный контейнер «войти» нельзя.

`docker attach` — другое: он подключает терминал к главному процессу (PID 1). Нажатие `Ctrl+C` в attach может остановить контейнер, поэтому для отладки используют `exec`.

## Конфигурация

```bash
docker inspect api
docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}}' api
docker inspect -f '{{json .NetworkSettings.Ports}}' api
docker port api
```

В `inspect` есть всё: команда, env, mounts, сети и IP, restart policy, статус healthcheck, причина остановки.

## Ресурсы и процессы

```bash
docker stats                    # CPU, память, сеть, диск в реальном времени
docker stats --no-stream api    # один снимок
docker top api                  # процессы контейнера
```

## Копирование файлов

```bash
docker cp api:/app/logs/error.log ./error.log
docker cp ./config.json api:/app/config.json
```

Работает и с остановленными контейнерами — удобно, чтобы забрать артефакт после падения.

## Быстрый сценарий

```bash
docker ps -a                   # статус и код выхода
docker logs --tail 100 api     # причина падения
docker inspect api             # порты, env, mounts
docker exec -it api sh         # если контейнер работает
```

## Частые ошибки

- Смотреть только `docker ps` и не замечать упавшие контейнеры.
- Пытаться выполнить `exec` в остановленный контейнер.
- Писать логи в файл внутри контейнера.
- Использовать `attach` вместо `exec` и случайно останавливать процесс.

## Что важно помнить

- Код выхода в `docker ps -a` — первая подсказка: `1` — ошибка приложения, `137` — SIGKILL, часто OOM.
- Логи контейнера по умолчанию хранятся в json-файлах на хосте и без ротации могут занять весь диск — настраивают `max-size`.
- `docker cp` и `docker logs` работают и после остановки контейнера, `exec` — нет.

## Мини-шпаргалка

- `ps -a` — все контейнеры.
- `logs -f --tail 100` — логи.
- `exec -it ... sh` — внутрь.
- `inspect` — конфигурация.
- `stats`, `top` — ресурсы и процессы.
- `cp` — файлы туда и обратно.
