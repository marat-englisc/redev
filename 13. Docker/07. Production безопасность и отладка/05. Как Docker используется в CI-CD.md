# Как Docker используется в CI-CD

> [!NOTE]
> В CI/CD Docker даёт **один артефакт для всех окружений**: pipeline собирает образ, запускает в нём тесты и сканирование, публикует в registry с тегом по SHA коммита и semver, а деплой скачивает **тот же самый** образ в staging и production — различаются только переменные и секреты. Чтобы сборка была быстрой, кэш BuildKit сохраняют во внешнее хранилище (`type=gha`, `type=registry`), потому что раннер CI каждый раз чистый.

## Вопрос

Как Docker используется в CI/CD?

## Типичный pipeline

```text
checkout ─▶ lint + unit-тесты ─▶ docker build ─▶ integration/e2e в контейнерах
        ─▶ сканирование (Trivy/Scout) ─▶ push в registry ─▶ миграции ─▶ deploy
```

## GitHub Actions

```yaml
name: build
on:
  push:
    branches: [main]

jobs:
  image:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: |
            ghcr.io/${{ github.repository }}:${{ github.sha }}
            ghcr.io/${{ github.repository }}:main
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

## Теги

| Тег | Назначение |
| --- | --- |
| `api:9f2c1ab` (SHA) | Неизменяемая ссылка на коммит, основной для деплоя |
| `api:1.14.3` | Релиз |
| `api:main`, `api:staging` | Плавающий указатель на последнюю сборку ветки |
| `api:latest` | Удобство, но не для деплоя |

Деплоят по SHA или digest — тогда понятно, что именно работает, и откат сводится к деплою предыдущего тега.

## Build once, deploy many

```text
сборка ─▶ api:9f2c1ab ─▶ staging (env: staging) ─▶ production (env: prod)
```

Если пересобирать образ для production, можно получить другие версии зависимостей и базового образа, и протестированный в staging артефакт окажется не тем, что задеплоено. Поэтому конфигурацию окружения передают в рантайме, а не при сборке. Исключение — frontend с build-time переменными: их стараются заменить относительными адресами или runtime-конфигом.

## Тесты в контейнерах

```bash
docker compose -f compose.yaml -f compose.test.yaml up --build \
  --abort-on-container-exit --exit-code-from tests
```

Поднимаются API, база и сервис `tests`; код выхода pipeline берётся из сервиса тестов. Альтернатива для unit и integration-тестов — Testcontainers, где база поднимается прямо из кода теста.

## Безопасность pipeline

- Секреты — в хранилище CI, в сборку — через `--secret`, не через `--build-arg`.
- Сканирование образа с порогом блокировки (например, критические CVE).
- Короткоживущие токены (OIDC) вместо постоянных ключей облака.
- Подпись образа и provenance (`cosign`, `--provenance`) для проверки происхождения.

## Частые ошибки

- Деплоить `latest`.
- Пересобирать образ для каждого окружения.
- Передавать токены через `--build-arg`.
- Не кэшировать слои — каждая сборка с нуля.
- Не сканировать образы.

## Что важно помнить

- Артефакт CI — образ, а не каталог с кодом.
- Тег по SHA связывает работающий контейнер с коммитом.
- Кэш между запусками CI нужно сохранять явно.

## Мини-шпаргалка

- build → test → scan → push → migrate → deploy.
- Теги: SHA + semver.
- `cache-from`/`cache-to: type=gha`.
- Один образ для всех окружений.
- Секреты — `--secret`.
