# Как ограничить привилегии контейнера

> [!NOTE]
> Контейнер делит ядро с хостом, поэтому при взломе приложения важно, **что ещё может сделать атакующий**. Принцип минимальных привилегий: процесс работает **не от root** (`USER node`), файловая система **только для чтения** (`--read-only` + tmpfs для временных файлов), лишние **capabilities сброшены** (`--cap-drop ALL`), повышение привилегий запрещено (`no-new-privileges`), **никаких `--privileged` и `docker.sock`** внутри контейнера. Дополнительно — rootless Docker или user namespaces.

## Вопрос

Как ограничить привилегии контейнера и почему запуск от root опасен?

## Почему root в контейнере — проблема

По умолчанию процесс в контейнере работает от root (UID 0) — того же UID, что root на хосте. Namespaces и урезанный набор capabilities ограничивают его, но при уязвимости в ядре, неудачном монтировании или лишних правах побег из контейнера даёт root на хосте. Непривилегированный пользователь резко сужает последствия.

## USER

```dockerfile
FROM node:24-alpine
WORKDIR /app
COPY --chown=node:node . .
USER node                       # в образах node пользователь уже есть (UID 1000)
CMD ["node", "dist/main.js"]
```

Для образов без готового пользователя:

```dockerfile
RUN addgroup -S app && adduser -S app -G app
USER app
```

Порты ниже 1024 непривилегированный пользователь занять не может — приложение слушает 3000 или 8080, а наружу публикуется любой порт (`-p 80:8080`). Для Nginx есть образ `nginxinc/nginx-unprivileged`.

## Read-only файловая система

```bash
docker run --read-only --tmpfs /tmp my-api
```

```yaml
services:
  api:
    read_only: true
    tmpfs:
      - /tmp
```

Атакующий не сможет записать вредоносный файл или изменить код приложения. Каталоги, куда приложению нужно писать, выделяют явно: tmpfs или volume.

## Capabilities

Root в Linux — набор отдельных привилегий (capabilities): `NET_BIND_SERVICE`, `CHOWN`, `SYS_ADMIN` и другие. Docker по умолчанию оставляет часть из них. Обычному веб-приложению не нужна ни одна:

```yaml
services:
  api:
    cap_drop: [ALL]
    # cap_add: [NET_BIND_SERVICE]   # только если нужно занимать порт < 1024
    security_opt:
      - no-new-privileges:true      # запрет setuid-бинарникам повышать права
```

## Что никогда не делать без крайней необходимости

| Опасная настройка | Чем грозит |
| --- | --- |
| `--privileged` | Почти все capabilities и доступ к устройствам хоста — фактически root на хосте |
| `-v /var/run/docker.sock:/var/run/docker.sock` | Контейнер может запустить любой контейнер с монтированием `/` хоста |
| `--network host` | Нет сетевой изоляции, доступ ко всем сервисам хоста на localhost |
| `--pid host` | Видит и может сигналить процессам хоста |
| Монтирование `/` или `/etc` хоста | Чтение и изменение системных файлов |

Если CI или инструменту нужен Docker внутри контейнера, предпочтительнее rootless-сборщики (BuildKit rootless, Kaniko) или отдельный изолированный демон.

## Rootless и user namespaces

- **Rootless Docker** — сам демон работает от обычного пользователя, и даже root в контейнере соответствует непривилегированному UID на хосте.
- **userns-remap** — демон отображает UID 0 контейнера на диапазон непривилегированных UID хоста.
- **Podman** по умолчанию работает без root.

## Другие уровни защиты

- Seccomp-профиль по умолчанию блокирует опасные системные вызовы — не отключайте его (`seccomp=unconfined`).
- AppArmor и SELinux добавляют обязательный контроль доступа.
- Лимиты ресурсов (`mem_limit`, `pids_limit`) защищают от DoS соседей.
- В Kubernetes те же идеи задаются в `securityContext`: `runAsNonRoot`, `readOnlyRootFilesystem`, `allowPrivilegeEscalation: false`.

## Частые ошибки

- Не указывать `USER` и работать от root.
- `USER node` без `--chown` — приложение не может писать в свои каталоги.
- Монтировать `docker.sock` в контейнер ради удобства.
- Использовать `--privileged`, чтобы «починить» ошибку прав.

## Что важно помнить

- Изоляция контейнера — не граница безопасности уровня VM; минимальные привилегии компенсируют это.
- `docker.sock` в контейнере равен root-доступу к хосту.
- Набор «не root + read-only + cap_drop ALL + no-new-privileges» подходит большинству веб-сервисов.

## Мини-шпаргалка

- `USER node`, `COPY --chown`.
- `read_only: true` + `tmpfs: [/tmp]`.
- `cap_drop: [ALL]`, `no-new-privileges:true`.
- Без `--privileged` и `docker.sock`.
- Rootless Docker / userns-remap.
