# Чем Compose отличается от Kubernetes и что такое оркестрация

> [!NOTE]
> **Оркестратор** управляет контейнерами на **кластере** серверов: сам размещает их по узлам, поддерживает нужное число реплик, перезапускает и переносит упавшие, делает rolling update и откат, балансирует трафик, хранит секреты и конфигурацию. **Docker Compose** описывает и запускает контейнеры на **одном хосте** — для разработки, тестов и небольшого production. **Kubernetes** — стандарт оркестрации в индустрии; Docker Swarm и Nomad — более простые альтернативы, а PaaS (Fly.io, Render, Cloud Run, ECS) скрывают оркестрацию за удобным интерфейсом.

## Вопрос

Чем Docker Compose отличается от Kubernetes и что такое оркестрация контейнеров?

## Что умеет оркестратор

| Возможность | Compose | Kubernetes |
| --- | --- | --- |
| Количество хостов | Один | Кластер |
| Реплики | `--scale`, без распределения по серверам | Deployment с автоматическим размещением |
| Самовосстановление | Restart policy на одном хосте | Перезапуск и перенос подов на здоровые узлы |
| Обновление без простоя | Нет из коробки | Rolling update, откат |
| Автомасштабирование | Нет | HPA по CPU, памяти, метрикам |
| Балансировка и DNS | DNS внутри проекта | Service, Ingress, Gateway |
| Секреты и конфиги | Файлы и переменные | Secret, ConfigMap |
| Проверки здоровья | Healthcheck | Liveness, readiness, startup probes |
| Сложность | Низкая | Высокая |

## Соответствие понятий

| Docker / Compose | Kubernetes |
| --- | --- |
| Контейнер | Контейнер внутри **Pod** |
| Сервис в `compose.yaml` | **Deployment** + **Service** |
| `ports` наружу | **Ingress** / **Gateway** / Service `LoadBalancer` |
| `environment` | **ConfigMap**, переменные в манифесте |
| `secrets` | **Secret** |
| Named volume | **PersistentVolumeClaim** |
| `healthcheck` | `livenessProbe`, `readinessProbe` |
| Одноразовый сервис `migrate` | **Job** |

## Пример манифеста Kubernetes

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 3
  selector:
    matchLabels: { app: api }
  template:
    metadata:
      labels: { app: api }
    spec:
      containers:
        - name: api
          image: ghcr.io/team/api:9f2c1ab
          ports: [{ containerPort: 3000 }]
          readinessProbe:
            httpGet: { path: /health, port: 3000 }
          resources:
            limits: { memory: 512Mi, cpu: "1" }
```

Kubernetes будет держать три реплики, распределит их по узлам, при обновлении тега заменит поды постепенно, направляя трафик только на готовые.

## Что выбрать

| Ситуация | Подходящий вариант |
| --- | --- |
| Локальная разработка, тесты в CI | Compose |
| Pet-проект или внутренний сервис на одном VPS | Compose + restart policy, либо Coolify/Dokku |
| Небольшая команда, нужен деплой без DevOps | PaaS: Render, Fly.io, Railway, Cloud Run, Vercel для Next.js |
| Много сервисов, высокая нагрузка, своя платформа | Kubernetes (часто управляемый: EKS, GKE, AKS) |
| Нужна оркестрация попроще Kubernetes | Docker Swarm, Nomad |

## Зачем это знать frontend-разработчику

Даже если кластером занимается DevOps, решения в приложении зависят от оркестрации:

- несколько реплик → нельзя хранить сессии и кэш Next.js в памяти одного контейнера;
- rolling update → схема БД должна быть совместима со старой и новой версией;
- probes → нужен эндпоинт `/health`, и приложение должно корректно обрабатывать SIGTERM;
- лимиты памяти → `--max-old-space-size` для Node.js.

## Частые ошибки

- Считать Compose полноценным оркестратором.
- Тащить Kubernetes в маленький проект, где хватило бы PaaS.
- Хранить состояние в контейнере, рассчитывая на одну реплику.
- Путать pod и контейнер: под может содержать несколько контейнеров (sidecar).

## Что важно помнить

- Образ один и тот же: Compose, Swarm и Kubernetes запускают одни и те же OCI-образы.
- Kubernetes не использует Docker Engine как runtime — он работает через containerd или CRI-O.
- Требования «stateless, healthcheck, SIGTERM, логи в stdout» одинаковы для всех платформ.

## Мини-шпаргалка

- Compose — один хост, просто.
- Kubernetes — кластер, реплики, rolling update, автомасштабирование.
- Pod, Deployment, Service, Ingress, ConfigMap, Secret, PVC, Job.
- Маленьким проектам — PaaS.
