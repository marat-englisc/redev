# Как уменьшить размер образа и поверхность атаки

> [!NOTE]
> Размер образа и число уязвимостей уменьшают одними и теми же приёмами: **multi-stage** (в финальном образе только runtime и артефакты), **маленький базовый образ** (`slim`, `alpine`, distroless), **только production-зависимости**, **`.dockerignore`**, очистка кэшей в той же инструкции, где они создаются, и отказ от лишних утилит. Результат проверяют через `docker image history`, `dive` и сканеры (`docker scout`, Trivy).

## Вопрос

Как уменьшить размер Docker-образа и снизить число уязвимостей в нём?

## Почему это важно

- Меньше образ — быстрее push и pull, быстрее масштабирование и откат.
- Каждый лишний пакет (`git`, `curl`, `bash`, компиляторы) — потенциальная CVE и инструмент для атакующего, который получил выполнение кода в контейнере.

## Приёмы

**Multi-stage.** Сборка с TypeScript и devDependencies — в отдельном stage, в финальный копируются `dist` и prod-зависимости.

**Базовый образ.**

| Образ | Плюсы | Минусы |
| --- | --- | --- |
| `node:24` | Есть всё для сборки | ~1 ГБ, много CVE |
| `node:24-slim` | glibc, совместимость | Больше alpine |
| `node:24-alpine` | Маленький | musl: проблемы с некоторыми native-модулями |
| distroless | Нет shell и пакетного менеджера | Сложная отладка, нет `sh` для healthcheck |
| Chainguard / Docker Hardened Images | Минимум CVE, частые обновления | Зависимость от поставщика |

**Только нужные зависимости.**

```dockerfile
RUN npm ci --omit=dev && npm cache clean --force
```

**Чистка в той же инструкции.**

```dockerfile
RUN apk add --no-cache --virtual .build-deps python3 make g++ \
  && npm ci --omit=dev \
  && apk del .build-deps
```

Инструменты компиляции native-модулей ставятся и удаляются в одном слое — в образ они не попадают.

**`.dockerignore` или allowlist** — в образ не попадают тесты, документация, `.git`.

**Для Next.js** — `output: "standalone"`, для SPA — Nginx со статикой вместо Node.js.

## Как анализировать

```bash
docker image ls my-api                 # общий размер
docker image history my-api            # какие инструкции создали большие слои
dive my-api                            # интерактивный просмотр слоёв и «мусора»
docker scout quickview my-api          # сводка уязвимостей
docker scout cves my-api               # подробный список CVE
trivy image my-api                     # альтернативный сканер, удобен в CI
```

## Снижение поверхности атаки сверх размера

- Запуск от непривилегированного пользователя (`USER node`).
- Read-only файловая система и сброс capabilities — см. [урок про привилегии](<07. Как ограничить привилегии контейнера.md>).
- Регулярная пересборка, чтобы получать исправления базового образа.
- Сканирование в CI с блокировкой релиза при критических CVE.
- SBOM (`docker buildx build --sbom=true`) — список компонентов образа для аудита.

## Частые ошибки

- Полный `node:24` в production «потому что работает».
- Компиляторы и `git` в финальном образе.
- Удаление кэша отдельным `RUN`.
- Считать Alpine безусловно лучшим выбором и ловить ошибки native-модулей.
- Собрать образ однажды и не пересобирать годами.

## Что важно помнить

- Размер определяется финальным stage — всё остальное остаётся в кэше сборки.
- Удалённый в верхнем слое файл всё равно занимает место в нижнем.
- Сканер находит уязвимости, но исправляет их только обновление базового образа и зависимостей.

## Мини-шпаргалка

- Multi-stage + slim/alpine/distroless.
- `--omit=dev`, cache clean в той же строке.
- `.dockerignore`.
- `history`, `dive`, `scout`, `trivy`.
- Регулярная пересборка.
