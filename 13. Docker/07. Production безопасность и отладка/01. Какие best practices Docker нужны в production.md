# Какие best practices Docker нужны в production

> [!NOTE]
> Production-образ должен быть **воспроизводимым** (зафиксированные версии базового образа и lock-файл), **маленьким** (multi-stage, только runtime), **безопасным** (не root, без секретов, регулярное сканирование) и **предсказуемым в работе**: один процесс на контейнер, логи в stdout, healthcheck, корректная обработка SIGTERM, лимиты ресурсов и конфигурация через окружение. Образ собирают один раз и продвигают без изменений через все окружения.

## Вопрос

Какие практики нужно соблюдать, чтобы Docker-образ был готов к production?

## Чек-лист

| Область | Практика |
| --- | --- |
| Воспроизводимость | Тег с версией (`node:24.11-alpine`) или digest; `npm ci` по lock-файлу |
| Размер | Multi-stage, `--omit=dev`, `.dockerignore`, slim/alpine/distroless |
| Безопасность | `USER node`, нет секретов в образе, сканирование, минимум пакетов |
| Запуск | Exec-форма `CMD`, обработка SIGTERM, `init` при необходимости |
| Наблюдаемость | Логи в stdout/stderr, healthcheck, метки OCI с версией и коммитом |
| Ресурсы | Лимиты памяти и CPU, restart policy |
| Конфигурация | Через переменные окружения и секреты, не через файлы в образе |
| Поставка | Собрать один раз, теги по SHA и semver, продвигать один и тот же образ |

## Фиксация версий

```dockerfile
FROM node:24-alpine                       # мажорная версия — минимум
FROM node:24.11.1-alpine3.22              # точная версия
FROM node:24-alpine@sha256:<digest>       # неизменяемо
```

Digest гарантирует, что сборка через полгода использует тот же базовый образ. Чтобы не застрять на уязвимой версии, обновления digest автоматизируют через Renovate или Dependabot.

## Метаданные образа

```dockerfile
ARG GIT_SHA
LABEL org.opencontainers.image.source="https://github.com/team/api" \
      org.opencontainers.image.revision="${GIT_SHA}"
```

По образу в production сразу видно, из какого коммита он собран.

## Один процесс — один контейнер

Не надо запускать в одном контейнере API, cron, Nginx и Redis через supervisord. Отдельные контейнеры независимо масштабируются, перезапускаются и логируются. Фоновый worker — тот же образ с другой командой:

```yaml
api:
  image: ghcr.io/team/api:1.4.0
worker:
  image: ghcr.io/team/api:1.4.0
  command: ["node", "dist/worker.js"]
```

## Логи

Пишите в stdout в структурированном виде (JSON через pino), без ротации внутри контейнера. Сбор, ротацию и отправку в Loki, ELK или облачный сервис берёт на себя платформа. На хосте с Docker настраивайте ротацию json-логов, иначе они займут диск:

```json
{ "log-driver": "json-file", "log-opts": { "max-size": "10m", "max-file": "3" } }
```

## Stateless-контейнеры

Контейнер можно в любой момент убить и запустить на другом сервере. Поэтому сессии хранят в Redis, файлы — в S3, данные — в БД, а не в файловой системе контейнера.

## Graceful shutdown

При деплое старый контейнер получает SIGTERM. Приложение должно перестать принимать новые запросы, дождаться текущих, закрыть соединения с БД и выйти до SIGKILL — подробно в [уроке про PID 1 и сигналы](<06. Как работают PID 1, сигналы и graceful shutdown.md>).

## Частые ошибки

- `FROM node:latest`.
- devDependencies и исходники в образе.
- Запуск от root.
- `.env` внутри образа.
- Логи в файлы внутри контейнера.
- Пересборка образа для каждого окружения.
- Отсутствие лимитов памяти.

## Что важно помнить

- Образ — неизменяемый артефакт; различия окружений — только в конфигурации.
- Безопасность и размер связаны: меньше пакетов — меньше уязвимостей.
- Детали — в уроках про [размер образа](<02. Как уменьшить размер образа и поверхность атаки.md>), [секреты](<03. Как безопасно передавать секреты при сборке и запуске.md>) и [привилегии](<07. Как ограничить привилегии контейнера.md>).

## Мини-шпаргалка

- Pin версий, multi-stage, `.dockerignore`.
- `USER node`, без секретов, сканирование.
- Exec-форма, SIGTERM, healthcheck.
- stdout, лимиты, stateless.
- Build once, deploy many.
