# Чем CMD отличается от ENTRYPOINT

> [!NOTE]
> `CMD` задаёт **команду или аргументы по умолчанию** — аргументы `docker run image ...` полностью её заменяют. `ENTRYPOINT` задаёт **исполняемый файл** контейнера — аргументы `docker run` дописываются к нему, а заменить его можно только флагом `--entrypoint`. Вместе: `ENTRYPOINT` — программа, `CMD` — её аргументы по умолчанию. Обе инструкции пишут в exec-форме `["..."]`, чтобы процесс получал сигналы.

## Вопрос

Чем `CMD` отличается от `ENTRYPOINT` и как они работают вместе?

## Основная идея

```dockerfile
CMD ["node", "dist/main.js"]
```

```bash
docker run my-api                     # node dist/main.js
docker run my-api node dist/worker.js # node dist/worker.js — CMD заменён
```

```dockerfile
ENTRYPOINT ["node"]
CMD ["dist/main.js"]
```

```bash
docker run my-api                     # node dist/main.js
docker run my-api dist/worker.js      # node dist/worker.js — заменён только CMD
docker run --entrypoint sh my-api     # sh — ENTRYPOINT заменён
```

## Таблица сочетаний

| Dockerfile | `docker run image` | `docker run image x` |
| --- | --- | --- |
| `CMD ["a"]` | `a` | `x` |
| `ENTRYPOINT ["e"]` | `e` | `e x` |
| `ENTRYPOINT ["e"]` + `CMD ["a"]` | `e a` | `e x` |

## Exec-форма и shell-форма

```dockerfile
CMD ["node", "dist/main.js"]   # exec-форма: node — это PID 1
CMD node dist/main.js          # shell-форма: /bin/sh -c "node dist/main.js"
```

В shell-форме PID 1 — оболочка `sh`, которая не пересылает SIGTERM дочернему процессу. В итоге `docker stop` ждёт 10 секунд и убивает контейнер через SIGKILL, а приложение не успевает закрыть соединения. Ещё одна ловушка: `ENTRYPOINT` в shell-форме игнорирует `CMD` и аргументы `docker run`.

Та же проблема с `CMD ["npm", "start"]`: npm запускает Node.js дочерним процессом и пересылает сигналы ненадёжно. В production запускают `node` напрямую.

## Когда что использовать

**Только `CMD`** — для большинства сервисов (API, frontend-сервер, worker). Легко запустить другую команду для отладки или миграции:

```bash
docker run --rm my-api npx prisma migrate deploy
```

**`ENTRYPOINT` + `CMD`** — когда контейнер ведёт себя как утилита:

```dockerfile
ENTRYPOINT ["eslint"]
CMD ["."]
```

```bash
docker run --rm -v "$(pwd)":/src -w /src my-eslint src/
```

**Скрипт-обёртка в `ENTRYPOINT`** — когда перед стартом нужно подготовить окружение. Так устроен официальный образ PostgreSQL:

```dockerfile
COPY docker-entrypoint.sh /usr/local/bin/
ENTRYPOINT ["docker-entrypoint.sh"]
CMD ["node", "dist/main.js"]
```

```sh
#!/bin/sh
set -e
# подготовка: проверить env, дождаться зависимостей...
exec "$@"   # заменить оболочку на CMD — процесс станет PID 1
```

`exec "$@"` критичен: без него приложение будет дочерним процессом оболочки и не получит сигналы.

## Частые ошибки

- Путать `RUN` (сборка) и `CMD` (запуск).
- Использовать shell-форму и получать 10-секундную остановку.
- Писать entrypoint-скрипт без `exec "$@"`.
- Делать `ENTRYPOINT` там, где хватает `CMD`, — потом неудобно запускать другие команды.

## Что важно помнить

- `CMD` заменяется аргументами `docker run`, `ENTRYPOINT` — только `--entrypoint`.
- В Compose им соответствуют поля `command` и `entrypoint`.
- Если `CMD` указан несколько раз, действует последний.

## Мини-шпаргалка

- `CMD` — по умолчанию, легко заменить.
- `ENTRYPOINT` — программа, аргументы дописываются.
- `ENTRYPOINT` + `CMD` = программа + аргументы по умолчанию.
- Exec-форма `["..."]` всегда.
- Скрипт-обёртка заканчивается `exec "$@"`.
