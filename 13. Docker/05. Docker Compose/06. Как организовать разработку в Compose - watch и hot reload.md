# Как организовать разработку в Compose - watch и hot reload

> [!NOTE]
> Для разработки в контейнере нужно, чтобы правки кода сразу попадали внутрь. Классический способ — **bind mount** каталога проекта плюс отдельный volume для `node_modules`. Современный — **`docker compose watch`**: в секции `develop.watch` описывают, какие файлы синхронизировать (`sync`), при изменении каких перезапустить контейнер (`sync+restart`) или пересобрать образ (`rebuild`, например при смене `package.json`). Watch работает быстрее bind mount на macOS и Windows и не смешивает `node_modules` хоста и контейнера.

## Вопрос

Как настроить hot reload и удобную разработку внутри Docker Compose?

## Вариант 1: bind mount

```yaml
services:
  web:
    build:
      context: .
      target: dev              # stage с devDependencies
    command: ["npm", "run", "dev", "--", "--host", "0.0.0.0"]
    ports: ["5173:5173"]
    volumes:
      - .:/app
      - /app/node_modules      # зависимости остаются из образа
```

Плюсы — просто и мгновенно. Минусы — медленная файловая система на macOS и Windows, проблемы с правами, file watcher иногда не видит изменений (тогда нужен polling).

## Вариант 2: compose watch

```yaml
services:
  api:
    build:
      context: .
      target: dev
    command: ["npm", "run", "dev"]
    ports: ["3000:3000"]
    develop:
      watch:
        - action: sync               # копировать изменения в контейнер
          path: ./src
          target: /app/src
          ignore:
            - "**/*.test.ts"
        - action: sync+restart       # скопировать и перезапустить процесс
          path: ./config
          target: /app/config
        - action: rebuild            # пересобрать образ и пересоздать контейнер
          path: package.json
```

```bash
docker compose watch          # или: docker compose up --watch
```

| Действие | Когда |
| --- | --- |
| `sync` | Исходники, если dev-сервер сам делает hot reload (Vite, `tsx watch`, `next dev`) |
| `sync+restart` | Конфиги, которые читаются только при старте |
| `rebuild` | `package.json`, lock-файл, `Dockerfile` — нужна переустановка зависимостей |

Watch не синхронизирует `node_modules` с хоста и учитывает `.dockerignore`. Пользователь в контейнере должен иметь право записи в `target`.

## Dev-stage в Dockerfile

```dockerfile
FROM node:24-alpine AS dev
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
CMD ["npm", "run", "dev"]

FROM dev AS build
RUN npm run build

FROM node:24-alpine AS runner
# ... production
```

Один Dockerfile даёт и dev-образ (`target: dev`), и production.

## Отладка Node.js в контейнере

```yaml
command: ["node", "--inspect=0.0.0.0:9229", "dist/main.js"]
ports: ["9229:9229"]
```

После этого VS Code или Chrome DevTools подключаются к `localhost:9229`. Публикуйте порт отладчика только локально — он даёт выполнение произвольного кода.

## Dev Containers

Если разработчик хочет работать **внутри** контейнера целиком (терминал, расширения, отладчик), используют Dev Containers (`.devcontainer/devcontainer.json`) в VS Code или JetBrains. Это удобно для единого окружения всей команды, но не заменяет Compose для поднятия зависимостей — их часто сочетают.

## Частые ошибки

- Затирать `node_modules` bind mount'ом.
- Запускать dev-сервер на `localhost` внутри контейнера.
- Не пересобирать образ после изменения `package.json`.
- Использовать dev-образ с devDependencies в production.

## Что важно помнить

- Bind mount — проще, watch — быстрее и чище на macOS и Windows.
- `rebuild` на lock-файл избавляет от рассинхронизации зависимостей.
- Dev- и production-образы собираются из одного Dockerfile разными `target`.

## Мини-шпаргалка

- Bind mount: `.:/app` + `/app/node_modules`.
- Watch: `develop.watch` → `sync`, `sync+restart`, `rebuild`.
- Запуск: `docker compose watch`.
- Dev-сервер слушает `0.0.0.0`.
- Отладчик: `--inspect=0.0.0.0:9229`.
