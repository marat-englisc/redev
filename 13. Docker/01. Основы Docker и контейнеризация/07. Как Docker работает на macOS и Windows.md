# Как Docker работает на macOS и Windows

> [!NOTE]
> Linux-контейнерам нужно ядро Linux, поэтому на macOS и Windows Docker запускает **лёгкую Linux-VM**, а контейнеры работают внутри неё. На Windows это обычно **WSL 2**, на macOS — VM через Apple Virtualization Framework. Отсюда главные особенности: bind mount файлов с хоста работает медленнее, чем на Linux; `localhost` контейнера — это не хост; на Apple Silicon образы по умолчанию собираются под `arm64`.

## Вопрос

Как Docker работает на macOS и Windows и какие из этого следуют особенности?

## Основная идея

```text
macOS / Windows
└── Docker Desktop
    └── Linux-VM (WSL 2 / Virtualization.framework)
        └── dockerd
            ├── контейнер api
            └── контейнер db
```

CLI работает на хосте и общается с демоном внутри VM. Docker Desktop прозрачно пробрасывает порты (`-p 3000:3000` доступен на `localhost` хоста) и файлы (bind mounts).

## Производительность bind mounts

На Linux bind mount — просто монтирование каталога, почти без накладных расходов. На macOS и Windows файлы должны пересечь границу VM:

- `npm install` в примонтированную папку проекта может быть в разы медленнее;
- file watchers (Vite, Next.js) иногда не получают события изменений.

Что помогает:

- держать `node_modules` в анонимном или именованном volume, а не на хосте;
- на Windows хранить проект **внутри файловой системы WSL** (`\\wsl$\Ubuntu\home\...`), а не на `C:\`;
- на macOS включить VirtioFS (по умолчанию в новых версиях Docker Desktop) или использовать OrbStack;
- использовать [`docker compose watch`](<../05. Docker Compose/06. Как организовать разработку в Compose - watch и hot reload.md>) вместо bind mount;
- если watcher не видит изменений — включить polling (`CHOKIDAR_USEPOLLING=true`, `server.watch.usePolling` в Vite).

## Доступ к хосту из контейнера

Внутри контейнера `localhost` — сам контейнер. Чтобы обратиться к сервису, запущенному на хосте (например, к локальному API на порту 4000), используют специальное имя:

```bash
curl http://host.docker.internal:4000
```

На macOS и Windows оно работает из коробки, на Linux его добавляют явно:

```yaml
services:
  app:
    extra_hosts:
      - "host.docker.internal:host-gateway"
```

## Архитектура: Apple Silicon

Mac на M-чипах — это `arm64`. Образ, собранный на нём, по умолчанию тоже `arm64`, а большинство серверов — `amd64`:

```text
exec /usr/local/bin/node: exec format error
```

Решение — собирать под нужную платформу (`--platform linux/amd64`) или сразу мультиплатформенно через `buildx` — см. [урок про сборку под разные платформы](<../03. Dockerfile и сборка образов/08. Как собирать образы для разных платформ через buildx.md>).

## Ресурсы VM

VM получает ограниченную память и CPU (настраиваются в Docker Desktop или в `.wslconfig`). Если контейнеры падают с OOM или сборка тормозит, проверь лимиты именно VM, а не только `--memory` контейнера.

## Частые ошибки

- Ждать от bind mount на macOS той же скорости, что на Linux.
- Держать проект на `C:\` при работе через WSL 2.
- Обращаться из контейнера к сервису на хосте через `localhost`.
- Собрать образ на M-чипе и задеплоить на `amd64`-сервер без указания платформы.

## Что важно помнить

- На macOS и Windows всегда есть промежуточная Linux-VM — это объясняет большинство «странностей».
- `host.docker.internal` — способ достучаться до хоста; на Linux нужен `host-gateway`.
- Архитектуру образа нужно контролировать явно, если разработка на `arm64`, а production на `amd64`.

## Мини-шпаргалка

- macOS/Windows: контейнеры живут в Linux-VM.
- Медленные bind mounts → volume для `node_modules`, WSL FS, `compose watch`.
- Хост из контейнера: `host.docker.internal`.
- Apple Silicon: `--platform linux/amd64` или `buildx`.
