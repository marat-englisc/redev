# Что такое контейнер

> [!NOTE]
> **Контейнер** — запущенный экземпляр образа: обычный процесс хоста, который ядро изолирует с помощью **namespaces** (свои PID, сеть, файловая система, hostname) и ограничивает через **cgroups** (CPU, память). Поверх слоёв образа у контейнера есть тонкий **записываемый слой**, который удаляется вместе с контейнером. Контейнер живёт, пока работает его главный процесс (PID 1).

## Вопрос

Что такое контейнер и как он живёт?

## Основная идея

Контейнер удобно представлять так:

```text
процесс + изолированная файловая система + своя сеть + переменные окружения + лимиты ресурсов
```

Например, контейнер с API на Node.js содержит runtime Node.js, `node_modules`, скомпилированный код, переменные окружения и команду `node dist/main.js`. При этом своего ядра ОС в контейнере нет — системные вызовы обслуживает ядро хоста.

## Контейнер живёт, пока жив главный процесс

```dockerfile
CMD ["node", "dist/main.js"]
```

Процесс из `CMD`/`ENTRYPOINT` становится PID 1 внутри контейнера. Если он завершился — неважно, успешно или с ошибкой, — контейнер переходит в статус `Exited`:

```bash
docker ps -a
# CONTAINER ID  IMAGE   STATUS
# 3f2a...       my-api  Exited (1) 5 seconds ago
```

Поэтому команда запуска должна держать процесс на переднем плане: `nginx -g "daemon off;"`, а не запуск демона в фоне.

## Состояния контейнера

```text
created ──start──▶ running ──stop──▶ exited ──rm──▶ (удалён)
                     │  ▲
                pause│  │unpause
                     ▼  │
                   paused
```

`docker stop` останавливает, но не удаляет: контейнер можно снова запустить через `docker start`, его записываемый слой сохранится. `docker rm` удаляет контейнер вместе с этим слоем.

## Контейнеры одноразовые

Хорошая практика — относиться к контейнеру как к disposable: его можно удалить и создать заново из образа без потерь.

```bash
docker rm -f api
docker run -d --name api my-api:1.4.0
```

Всё, что должно пережить пересоздание (данные БД, загруженные файлы), хранят во volume, в базе данных или во внешнем хранилище вроде S3.

## Изоляция не равна безопасности

Контейнеры разделяют ядро хоста. Уязвимость ядра или контейнер, запущенный с `--privileged`, может дать доступ к хосту. Поэтому в production процесс запускают не от root, урезают capabilities и не монтируют `docker.sock` — подробнее в [уроке про ограничение привилегий](<../07. Production безопасность и отладка/07. Как ограничить привилегии контейнера.md>).

## Частые ошибки

- Ожидать, что контейнер продолжит работать после завершения главного процесса.
- Править файлы внутри контейнера вместо изменения `Dockerfile`.
- Путать остановленный и удалённый контейнер.
- Запускать в одном контейнере backend, базу и cron — так теряются изоляция, раздельные логи и независимый перезапуск.

## Что важно помнить

- Контейнер — процесс хоста, изолированный namespaces и ограниченный cgroups, а не мини-ОС.
- Записываемый слой живёт столько же, сколько контейнер: после `rm` изменений нет.
- Один контейнер — один основной процесс; несколько процессов — повод разделить сервисы.
- `exec` работает только с запущенным контейнером; упавший диагностируют через `docker logs`.

## Мини-шпаргалка

- Контейнер = образ + записываемый слой + процесс.
- Статусы: created → running → exited.
- PID 1 завершился — контейнер остановился.
- Важные данные — во volume.
- Войти внутрь: `docker exec -it <name> sh`.
