# Как контейнер устроен внутри - namespaces, cgroups и overlay

> [!NOTE]
> Контейнер собран из трёх механизмов ядра Linux. **Namespaces** ограничивают, что процесс *видит*: свои PID, сеть, точки монтирования, hostname, пользователей. **Cgroups** ограничивают, сколько ресурсов он *потребляет*: CPU, память, число процессов. **Union filesystem** (обычно overlay2) собирает файловую систему из read-only слоёв образа и записываемого слоя контейнера по принципу copy-on-write. Docker лишь удобно настраивает эти механизмы.

## Вопрос

На каких механизмах ядра Linux построены контейнеры?

## Основная идея

```text
docker run ──▶ runc
                ├─ clone() с флагами namespaces   → что процесс видит
                ├─ запись в /sys/fs/cgroup/...    → сколько процесс может потреблять
                ├─ overlay-монтирование слоёв      → какую файловую систему видит
                └─ exec(CMD)                       → процесс становится PID 1
```

## Namespaces — изоляция видимости

| Namespace | Что изолирует | Эффект в контейнере |
| --- | --- | --- |
| PID | Дерево процессов | Приложение видит себя как PID 1, процессов хоста не видит |
| NET | Сетевые интерфейсы, порты, таблицы маршрутизации | Свой `localhost`, свой порт 3000 |
| MNT | Точки монтирования | Своя корневая файловая система |
| UTS | Hostname | `hostname` возвращает ID контейнера |
| IPC | Shared memory, очереди сообщений | Нет общей памяти с другими процессами |
| USER | UID/GID | root в контейнере можно отобразить на непривилегированного пользователя хоста |

Именно NET namespace объясняет, почему `localhost` внутри контейнера — это сам контейнер, а не хост и не соседний контейнер.

```bash
docker run --rm alpine ps aux
# PID   USER     COMMAND
#   1   root     ps aux       ← видит только себя
```

## Cgroups — ограничение ресурсов

```bash
docker run -d --memory=512m --cpus=1.5 --pids-limit=200 my-api
```

- `--memory` — жёсткий лимит; при превышении ядро убивает процесс (OOM kill, exit code 137).
- `--cpus` — квота процессорного времени.
- `--pids-limit` — защита от fork-бомбы.

Без лимитов один контейнер может съесть всю память хоста и уронить соседей.

## Overlay — слоистая файловая система

```text
┌──────────────────────────┐
│ upperdir (записываемый)  │ ← изменения контейнера
├──────────────────────────┤
│ lowerdir: слой 3 (COPY)  │
│ lowerdir: слой 2 (RUN)   │ ← read-only, общие для всех контейнеров
│ lowerdir: слой 1 (FROM)  │
└──────────────────────────┘
          ▼
   merged — то, что видит процесс
```

- Чтение идёт сверху вниз до первого слоя, где есть файл.
- При записи файл копируется наверх (copy-on-write) — первая запись в большой файл медленная.
- Удаление файла из нижнего слоя создаёт «whiteout» наверху — **размер образа от этого не уменьшается**. Поэтому `RUN rm -rf cache` в отдельной инструкции бесполезен для размера.

## Почему это важно на практике

- Понятно, почему контейнер стартует мгновенно: не загружается ОС, просто создаётся процесс.
- Понятно, почему изоляция слабее VM: всё это — настройки одного общего ядра.
- Понятно, откуда exit code 137 и почему Node.js в контейнере стоит ограничивать `--max-old-space-size` ниже лимита памяти.
- Понятно, почему данные БД кладут во volume: он монтируется в обход overlay и работает быстрее.

## Частые ошибки

- Думать, что контейнер — «лёгкая VM» с собственным ядром.
- Не задавать лимиты памяти в production и получать падение всего хоста.
- Удалять файлы отдельным `RUN` и ждать уменьшения образа.

## Что важно помнить

- Namespaces отвечают за «что видно», cgroups — за «сколько можно».
- Слои образа общие и неизменяемые, записываемый слой — свой у каждого контейнера.
- Exit code 137 почти всегда означает OOM kill по лимиту cgroup.
- Docker не изобрёл эти механизмы — он стандартизировал их использование (OCI runtime).

## Мини-шпаргалка

- PID, NET, MNT, UTS, IPC, USER namespaces.
- cgroups: `--memory`, `--cpus`, `--pids-limit`.
- overlay2: lowerdir (образ) + upperdir (контейнер).
- Copy-on-write, whiteout не уменьшает образ.
