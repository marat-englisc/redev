# Чем образ отличается от контейнера

> [!NOTE]
> **Образ (image)** — неизменяемый шаблон: набор read-only слоёв файловой системы плюс метаданные (команда запуска, переменные, порт). **Контейнер** — запущенный экземпляр образа: те же слои, собственный записываемый слой, процесс, сеть и переменные окружения. Из одного образа можно создать сколько угодно контейнеров — как объекты из класса.

## Вопрос

Чем образ отличается от контейнера?

## Основная идея

```text
Образ (read-only)              Контейнер
┌─────────────────┐            ┌─────────────────────┐
│ COPY dist       │            │ записываемый слой   │ ← изменения контейнера
│ RUN npm ci      │            ├─────────────────────┤
│ node:24-alpine  │  ──run──▶  │ слои образа         │ ← общие для всех контейнеров
└─────────────────┘            └─────────────────────┘
```

```bash
docker pull postgres:18          # скачали образ — база ещё не запущена
docker run -d --name db \
  -e POSTGRES_PASSWORD=secret \
  postgres:18                    # появился контейнер с процессом PostgreSQL
```

Аналогия: образ — класс, контейнер — объект. Или: образ — установочный дистрибутив, контейнер — установленная и запущенная программа.

## Почему изменения в контейнере не попадают в образ

Слои образа доступны только для чтения. Когда процесс в контейнере меняет файл, Docker копирует его в записываемый слой контейнера (copy-on-write), а исходный слой остаётся нетронутым.

```bash
docker exec -it app sh -c 'echo debug > /tmp/file'
docker rm -f app
docker run -d --name app my-api   # /tmp/file здесь уже нет
```

Правильный способ изменить окружение — поправить `Dockerfile` и пересобрать образ:

```dockerfile
FROM node:24-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
CMD ["npm", "start"]
```

```bash
docker build -t my-api:1.1.0 .
```

Команда `docker commit` умеет превратить контейнер в образ, но в работе её почти не используют: такой образ невоспроизводим.

## Связь при удалении

| Действие | Что происходит |
| --- | --- |
| `docker rm container` | Удаляется контейнер и его записываемый слой, образ остаётся |
| `docker rmi image` | Не получится, пока есть контейнеры из этого образа (даже остановленные) |
| Пересобрать образ с тем же тегом | Старые контейнеры продолжают работать на старом образе |

## Частые ошибки

- Пытаться «зайти в образ» как в работающую систему — заходят в контейнер.
- Ждать, что ручные правки в контейнере сохранятся после пересоздания.
- Хранить важные данные в записываемом слое вместо volume.

## Что важно помнить

- Образ неизменяем и однозначно идентифицируется digest `sha256:…`; тег — лишь удобное и изменяемое имя.
- Слои образа разделяются между контейнерами, поэтому десять контейнеров не занимают десятикратное место.
- Записываемый слой медленнее volume и пропадает вместе с контейнером — для данных он не подходит.

## Мини-шпаргалка

- Образ — шаблон, контейнер — запущенный экземпляр.
- Один образ → много контейнеров.
- Изменения контейнера → записываемый слой (copy-on-write).
- Изменить окружение → `Dockerfile` + `docker build`.
