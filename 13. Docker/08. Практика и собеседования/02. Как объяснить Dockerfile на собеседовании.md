# Как объяснить Dockerfile на собеседовании

> [!NOTE]
> Объясняй Dockerfile не построчным пересказом, а через **решения и их причины**: почему такой базовый образ, почему lock-файлы копируются отдельно (кэш), зачем multi-stage (размер и уязвимости), почему `npm ci --omit=dev`, `USER node` (привилегии), exec-форма `CMD` и запуск `node` напрямую (сигналы). В конце — что Dockerfile **не** делает: не публикует порт, не хранит секреты и данные.

## Вопрос

Как объяснить Dockerfile на собеседовании, если попросили рассказать о своём или разобрать чужой?

## Пример для разбора

```dockerfile
# syntax=docker/dockerfile:1
FROM node:24-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci

FROM deps AS build
COPY . .
RUN npm run build

FROM node:24-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production
COPY package.json package-lock.json ./
RUN npm ci --omit=dev && npm cache clean --force
COPY --from=build --chown=node:node /app/dist ./dist
USER node
EXPOSE 3000
CMD ["node", "dist/main.js"]
```

## Как рассказывать

1. **Цель.** «Это production-образ API на NestJS. Требования: маленький размер, быстрая пересборка, запуск без root».
2. **Базовый образ.** «`node:24-alpine` — LTS-версия, маленький образ. Если бы были проблемы с native-модулями, взял бы `slim`».
3. **Кэш зависимостей.** «Сначала копирую только `package.json` и lock-файл и делаю `npm ci`. Пока зависимости не меняются, этот слой берётся из кэша, и пересборка после правки кода занимает секунды. Cache mount ускоряет даже установку с нуля».
4. **Сборка.** «Отдельный stage `build` с devDependencies компилирует TypeScript».
5. **Финальный stage.** «Начинаю с чистого образа, ставлю только production-зависимости и копирую `dist`. TypeScript, тесты и исходники в образ не попадают — меньше размер и уязвимостей».
6. **Безопасность.** «`USER node` — процесс без root, `--chown`, чтобы у него были права на свои файлы. Секретов в образе нет — они приходят переменными при запуске».
7. **Запуск.** «Exec-форма и `node` напрямую, чтобы приложение получало SIGTERM и корректно завершалось. `EXPOSE` — только документация, порт публикуется при запуске».

## Как разбирать чужой Dockerfile

```dockerfile
FROM node:latest
COPY . .
RUN npm install
ENV DB_PASSWORD=secret
CMD npm start
```

| Проблема | Почему плохо | Исправление |
| --- | --- | --- |
| `node:latest` | Невоспроизводимо, огромный образ | `node:24-alpine` или digest |
| Нет `WORKDIR` | Файлы в `/`, путаница | `WORKDIR /app` |
| `COPY . .` до установки | Нет кэша, в образ попадают `node_modules`, `.env`, `.git` | Lock-файлы → `npm ci` → код, `.dockerignore` |
| `npm install` | Невоспроизводимые версии | `npm ci` |
| `ENV DB_PASSWORD` | Секрет виден в `docker inspect` | Передавать при запуске |
| Один stage | devDependencies в production | Multi-stage, `--omit=dev` |
| Нет `USER` | Процесс от root | `USER node` |
| `CMD npm start` | Shell-форма + npm: SIGTERM не доходит | `CMD ["node", "dist/main.js"]` |

## Частые ошибки

- Читать инструкции вслух без объяснения «зачем».
- Не упомянуть кэш и multi-stage.
- Сказать, что `EXPOSE` открывает порт наружу.
- Забыть про `.dockerignore` и секреты.

## Что важно помнить

- Структура ответа: цель → кэш → сборка → финальный образ → безопасность → запуск.
- Каждое решение подкрепляй последствием: скорость, размер, безопасность, корректная остановка.
- Умение найти ошибки в плохом Dockerfile ценится не меньше, чем написать хороший.

## Мини-шпаргалка

- Base image и почему.
- Lock-файлы → `npm ci` → код.
- Multi-stage, `--omit=dev`.
- `USER node`, без секретов.
- Exec-форма, `node` напрямую, `EXPOSE` — документация.
