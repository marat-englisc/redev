# Как Docker решает проблему works on my machine

> [!NOTE]
> «У меня работает» возникает из-за различий окружения: версии runtime и пакетного менеджера, системные библиотеки, версии БД, переменные, ручные шаги установки. Docker убирает эти различия, описывая окружение кодом: **Dockerfile** фиксирует runtime, зависимости и команду запуска приложения, **Compose** — внешние сервисы (PostgreSQL, Redis) и связи между ними. Но Docker помогает, только если версии зафиксированы, всё воспроизводится из файлов в git, а не из ручных действий в контейнере.

## Вопрос

Как с помощью Docker решить проблему «у меня работает, а у тебя нет»?

## Откуда берутся различия

```text
разработчик A: Node 24, pnpm 10, PostgreSQL 18, macOS arm64
разработчик B: Node 20, npm 10, PostgreSQL 15, Windows
CI:            Node 22, Ubuntu, без системной libvips
production:    Debian, другой OpenSSL, другие переменные
```

Результат: разные версии зависимостей, ломающиеся native-модули, несовместимый SQL, отсутствующие переменные.

## Что фиксирует Docker

| Источник различий | Чем фиксируется |
| --- | --- |
| Версия Node.js и ОС | `FROM node:24-alpine` (лучше с digest) |
| Версии зависимостей | lock-файл + `npm ci` |
| Системные пакеты | `RUN apk add ...` в Dockerfile |
| Команда запуска | `CMD` |
| БД, Redis, очереди и их версии | `compose.yaml` |
| Переменные | `.env.example` + валидация на старте |
| Схема БД | Миграции, запускаемые одной командой |

## Onboarding одной командой

```bash
git clone git@github.com:team/shop.git
cd shop
cp .env.example .env
docker compose up --build
```

```yaml
services:
  api:
    build: .
    env_file: [.env]
    ports: ["3000:3000"]
    depends_on:
      migrate:
        condition: service_completed_successfully
  migrate:
    build: .
    command: ["npx", "prisma", "migrate", "deploy"]
    env_file: [.env]
    depends_on:
      db:
        condition: service_healthy
  db:
    image: postgres:18
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app
    volumes: [pgdata:/var/lib/postgresql]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      retries: 10
volumes:
  pgdata:
```

Новый разработчик получает работающее окружение с базой нужной версии и применёнными миграциями, не устанавливая ничего, кроме Docker.

## Где Docker не спасает

- `FROM node:latest` или `postgres:latest` — версии всё равно «плывут».
- Шаги, описанные только в README, а не в файлах.
- Ручная установка пакетов внутри запущенного контейнера.
- Различие архитектур (`arm64` у разработчика, `amd64` на сервере) без `--platform`.
- Bind mount `node_modules` с хоста — снова бинарники «с моей машины».
- Различия, вынесенные в конфигурацию: другие переменные и секреты в production.
- Внешние сервисы (платёжный шлюз, S3), которых нет локально, — нужны моки или локальные аналоги (MinIO, Mailpit).

## Дополнительно

- Тот же Compose-файл запускать в CI для интеграционных тестов — тогда «работает в CI» означает «работает у всех».
- Dev Containers переносят в контейнер и сам инструментарий разработчика (линтеры, CLI).
- Версию Node.js для запуска вне Docker фиксируют в `.nvmrc` или `engines`.

## Частые ошибки

- Не коммитить Dockerfile и `compose.yaml`.
- Нет `.env.example` — каждый собирает переменные по памяти.
- Не описаны миграции и seed.
- Сценарий Docker не проверяется в CI и постепенно ломается.

## Что важно помнить

- Docker делает окружение воспроизводимым, но только то, что описано в файлах.
- Конфигурация между окружениями отличается намеренно — её проверяют валидацией при старте.
- Цель — «клонировал и запустил одной командой».

## Мини-шпаргалка

- Dockerfile — runtime и приложение.
- Compose — сервисы и связи.
- Pin версий, lock-файл, `.env.example`.
- Миграции — сервис в Compose.
- Тот же сценарий — в CI.
