# Как объяснить Docker-проект на собеседовании

> [!NOTE]
> Рассказ о Docker в своём проекте строят **от архитектуры к деталям**: какие сервисы и зачем, как собираются образы, как сервисы связаны и где хранятся данные, как передаются конфигурация и секреты, как запускаются миграции, чем dev отличается от production, как устроены CI/CD и деплой. Обязательно добавь **конкретную проблему**, которую ты решил: медленная сборка, падения из-за OOM, потерянные данные, долгая остановка контейнеров.

## Вопрос

Как рассказать на собеседовании о том, как в проекте используется Docker?

## Структура ответа

1. **Контекст.** Что за приложение и почему Docker.
2. **Сервисы.** Какие контейнеры и за что отвечают.
3. **Образы.** Как собираются: multi-stage, базовый образ, размер.
4. **Связи.** Сеть, DNS по именам, что опубликовано наружу.
5. **Данные.** Volumes или управляемые сервисы, бэкапы.
6. **Конфигурация.** Переменные, секреты, разница окружений.
7. **Миграции.** Когда и кем запускаются.
8. **Dev и production.** Hot reload, override, отличия.
9. **CI/CD.** Сборка, теги, сканирование, деплой, откат.
10. **История.** Проблема, которую нашёл и исправил, с результатом.

## Пример ответа

```text
У нас SPA на React, API на NestJS, PostgreSQL и Redis для очередей BullMQ.

Локально всё поднимается через docker compose up: API и фронтенд в dev-режиме
с bind mounts и hot reload, база — postgres:18 с named volume и healthcheck.
Миграции — отдельный одноразовый сервис, API стартует только после
его успешного завершения.

Образы production собираются multi-stage: для фронтенда Node.js собирает
статику, а финальный образ — Nginx на 50 МБ. Для API финальный stage содержит
только dist и production-зависимости, процесс работает от пользователя node.

В CI GitHub Actions собирает образы с кэшем BuildKit, прогоняет интеграционные
тесты в Compose, сканирует Trivy и пушит в GHCR с тегом по SHA. Деплой
обновляет тег в манифестах Kubernetes, миграции выполняются Job'ом перед
rolling update.

Одна из задач, которую я решал: при каждом деплое часть запросов падала с 502.
Оказалось, CMD был ["npm", "start"], SIGTERM не доходил до Node.js, и через
30 секунд под убивали. Перевели запуск на node напрямую, добавили обработку
SIGTERM и закрытие соединений — ошибки при деплое пропали.
```

## Что подчеркнуть

- Docker нужен для воспроизводимости и единого артефакта, а не «потому что модно».
- Контейнеры stateless: состояние в БД, Redis и S3.
- Секреты не попадают в образ.
- Production-образ отличается от dev-окружения.
- Ты понимаешь компромиссы: Alpine или slim, Compose или Kubernetes.

## Уточняющие вопросы, к которым стоит подготовиться

- Почему `db`, а не `localhost`?
- Что будет после `docker compose down -v`?
- Как вы уменьшили размер образа и насколько?
- Как передаёте `VITE_API_URL` в разные окружения?
- Как не запустить миграции из каждой реплики?
- Как откатить неудачный деплой?
- Как отлаживаете контейнер, который сразу падает?

## Частые ошибки

- Начинать с YAML-деталей без общей картины.
- Не знать, как проект поднимается с нуля.
- Рассказывать только про локальную разработку, не зная, как устроен production.
- Приписывать себе всю инфраструктуру — лучше честно разделить «настраивал сам» и «знаю, как устроено».
- Не иметь ни одной истории о проблеме.

## Что важно помнить

- Сначала архитектура, потом детали.
- Одна конкретная история с измеримым результатом убедительнее перечня технологий.
- Будь готов нарисовать схему сервисов и сетей.

## Мини-шпаргалка

- Сервисы → образы → сеть → данные → конфигурация → миграции → dev/prod → CI/CD.
- История: проблема → причина → решение → результат.
- Stateless, секреты вне образа, non-root, graceful shutdown.
