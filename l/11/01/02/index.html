Как строить ответ: фреймворк RADIO

Кратко

RADIO — план ответа на frontend system design интервью из пяти шагов: Requirements (требования и ограничения), Architecture (компоненты и их связи), Data model (данные и состояние на клиенте), Interface (API между клиентом и сервером и между компонентами), Optimizations (производительность, надежность, a11y, безопасность). План помогает не забыть важные части и распределить время.

Вопрос

Как структурировать ответ на задачу frontend system design? Что входит в каждый шаг фреймворка RADIO?

R — Requirements (≈10%)

Уточните, что строим и для кого.

  • Основные сценарии: что пользователь делает в первую очередь?
  • Что вне рамок задачи (out of scope)?
  • Платформы: desktop, mobile web, слабые устройства?
  • Масштаб: сколько элементов, пользователей, как часто обновляются данные?
  • Нефункциональные требования: SEO, офлайн, realtime, i18n, a11y?

Итог шага — короткий список требований на доске.

A — Architecture (≈20%)

Нарисуйте основные части и потоки данных:

Решения этого шага: стратегия рендеринга (CSR, SSR, SSG, streaming), разбиение на компоненты, где живет состояние, есть ли BFF.

D — Data model (≈15%)

  • Какие сущности на клиенте (Post, User, Comment) и их поля?
  • Серверное состояние (кеш запросов) и клиентское (UI-состояние, черновики)?
  • Нормализация: хранить по id или вложенно?
  • Что держать в URL (фильтры, страница), что — в памяти, что — в localStorage?

I — Interface (≈20%)

  • API клиент — сервер: эндпоинты, методы, параметры, формат ответа, пагинация, ошибки.
  • Realtime: polling, SSE или WebSocket?
  • Для задач на компонент — API компонента: props, события, слоты, контролируемый/неконтролируемый режим.

O — Optimizations (≈35%)

Выберите 3–4 самые важные для задачи темы и углубитесь:

ТемаПримеры решений
Производительностьcode splitting, виртуализация, ленивые изображения, prefetch
Сетькеш, дедупликация, debounce, отмена устаревших запросов
UXskeleton, optimistic update, обработка ошибок, retry, пустые состояния
Офлайн и надежностьService Worker, очередь отправки, восстановление соединения
Доступностьклавиатура, ARIA, фокус, объявления скринридеру
i18nIntl, RTL, длина строк
БезопасностьXSS, CSRF, CSP, хранение токенов
НаблюдаемостьRUM-метрики, логирование ошибок, feature flags

Распределение времени

Время ориентировочное: если интервьюер хочет копнуть в API, следуйте за ним.

Что важно помнить

  • Фреймворк — каркас, а не жесткий сценарий: озвучьте план в начале, чтобы интервьюер знал, куда вы идете.
  • На каждом шаге называйте альтернативы и причины выбора.
  • Не тратьте больше 10 минут на требования, но и не пропускайте их.
  • В конце кратко подытожьте решение и назовите, что бы улучшили при большем времени.
  • Для задач на компонент Interface (props, события) обычно важнее, чем серверный API.

Мини-шпаргалка

RADIO: Requirements — сценарии, масштаб, ограничения. Architecture — компоненты, рендеринг, потоки. Data model — сущности, server/client state, нормализация, URL. Interface — API, пагинация, realtime, props компонента. Optimizations — производительность, сеть, UX, офлайн, a11y, безопасность.
