Как обеспечить надежность, обработку ошибок и офлайн

Кратко

Надежный фронтенд продолжает работать, когда что-то идет не так: медленная сеть, ошибка сервера, обрыв соединения, сбой компонента. Основные приемы: явные состояния (загрузка, пусто, ошибка, частичные данные), повторы с экспоненциальной задержкой для временных ошибок, таймауты и отмена запросов, Error Boundary для изоляции сбоев UI, оптимистичные обновления с откатом и офлайн-режим: кеш данных и очередь действий, которые отправятся после восстановления сети.

Вопрос

Как обеспечить надежность фронтенд-приложения? Как обрабатывать ошибки сети и сервера, делать повторы и поддержать работу без интернета?

Состояния экрана

Для каждого блока данных продумайте:

СостояниеЧто показать
Загрузкаskeleton, а не спиннер на весь экран
Пустопонятный текст и действие («Создайте первый пост»)
Ошибкачто случилось + кнопка «Повторить», данные пользователя не теряются
Частичнопоказать то, что загрузилось, остальное — с ошибкой рядом
Офлайнбаннер «Нет соединения», кешированные данные, отложенные действия
Устарелометка «Обновлено 5 мин назад», фоновая синхронизация

Повторы

  • повторяйте только временные ошибки: сеть, таймаут, 5xx, 429;
  • не повторяйте неидемпотентные операции без Idempotency-Key — можно создать дубль;
  • TanStack Query и RTK Query умеют повторы из коробки (retry, retryDelay).

Изоляция сбоев UI

Ошибка в рекомендациях не роняет ленту. Ошибки отправляются в Sentry с контекстом.

Офлайн и очередь действий

  • navigator.onLine и события online/offline — подсказка, но не гарантия: проверяйте реальными запросами;
  • Service Worker отдает оболочку и кешированные данные без сети;
  • конфликты при синхронизации: last-write-wins, версии сущностей или CRDT для совместного редактирования.

Деградация функциональности

  • некритичные сервисы (рекомендации, аналитика, чат поддержки) не блокируют основной сценарий;
  • feature flags позволяют выключить сломанную функцию без деплоя;
  • таймауты на сторонние скрипты и API.

Что важно помнить

  • Каждый асинхронный блок имеет 4 состояния: loading, empty, error, success — назовите их на интервью.
  • Ошибка не должна стирать введенные пользователем данные.
  • Backoff с jitter защищает сервер от «лавины» повторов после сбоя.
  • Оптимистичные обновления требуют отката и понятного сообщения при ошибке.
  • Связанные темы: Error Boundary, optimistic update.

Мини-шпаргалка

Состояния: loading (skeleton), empty, error (+ «Повторить»), partial, offline. Повторы: только временные ошибки, backoff + jitter, idempotency key. Error Boundary по блокам. Офлайн: Service Worker + IndexedDB + очередь действий. Некритичное не блокирует главное, feature flags.

Документация

web.dev: Offline Cookbook, AWS: Exponential Backoff And Jitter, TanStack Query: Query Retries, React: Error boundaries.
