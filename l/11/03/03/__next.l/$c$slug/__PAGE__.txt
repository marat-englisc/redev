<div class="callout-title">Кратко</div>
<div class="callout-body"><p>Надежный фронтенд продолжает работать, когда что-то идет не так: медленная сеть, ошибка сервера, обрыв соединения, сбой компонента. Основные приемы: <strong>явные состояния</strong> (загрузка, пусто, ошибка, частичные данные), <strong>повторы с экспоненциальной задержкой</strong> для временных ошибок, <strong>таймауты и отмена</strong> запросов, <strong>Error Boundary</strong> для изоляции сбоев UI, <strong>оптимистичные обновления с откатом</strong> и <strong>офлайн-режим</strong>: кеш данных и очередь действий, которые отправятся после восстановления сети.</p></div>
</div>
<h2 id="вопрос">Вопрос</h2>
<p>Как обеспечить надежность фронтенд-приложения? Как обрабатывать ошибки сети и сервера, делать повторы и поддержать работу без интернета?</p>

<h2 id="офлайн-и-очередь-действий">Офлайн и очередь действий</h2>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="plaintext" data-theme="mono"><code data-language="plaintext" data-theme="mono" style="display: grid;"><span data-line=""><span>Пользователь отправляет сообщение без сети</span></span>
<span data-line=""><span>  → сообщение сразу в UI со статусом «sending»</span></span>
<span data-line=""><span>  → действие кладется в очередь (IndexedDB)</span></span>
<span data-line=""><span>  → событие online / восстановление WebSocket</span></span>
<span data-line=""><span>  → очередь отправляется по порядку с idempotency key</span></span>
<span data-line=""><span>  → статус «sent» или «failed» + «Повторить»</span></span></code></pre></figure>
<ul>
<li><code>navigator.onLine</code> и события <code>online</code>/<code>offline</code> — подсказка, но не гарантия: проверяйте реальными запросами;</li>
<li>Service Worker отдает оболочку и кешированные данные без сети;</li>
<li>конфликты при синхронизации: last-write-wins, версии сущностей или CRDT для совместного редактирования.</li>
</ul>
<h2 id="деградация-функциональности">Деградация функциональности</h2>
<ul>
<li>некритичные сервисы (рекомендации, аналитика, чат поддержки) не блокируют основной сценарий;</li>
<li>feature flags позволяют выключить сломанную функцию без деплоя;</li>
<li>таймауты на сторонние скрипты и API.</li>
</ul>
<h2 id="что-важно-помнить">Что важно помнить</h2>
<ul>
<li>Каждый асинхронный блок имеет 4 состояния: loading, empty, error, success — назовите их на интервью.</li>
<li>Ошибка не должна стирать введенные пользователем данные.</li>
<li>Backoff с jitter защищает сервер от «лавины» повторов после сбоя.</li>
<li>Оптимистичные обновления требуют отката и понятного сообщения при ошибке.</li>
<li>Связанные темы: <a href="/refront/l/06/11/04/" data-internal="true">Error Boundary</a>, <a href="/refront/l/06/10/07/" data-internal="true">optimistic update</a>.</li>
</ul>
<h2 id="мини-шпаргалка">Мини-шпаргалка</h2>
<p>Состояния: loading (skeleton), empty, error (+ «Повторить»), partial, offline. Повторы: только временные ошибки, backoff + jitter, idempotency key. Error Boundary по блокам. Офлайн: Service Worker + IndexedDB + очередь действий. Некритичное не блокирует главное, feature flags.</p>
