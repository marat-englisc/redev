<div class="callout-title">Кратко</div>
<div class="callout-body"><p>Производительность на system design интервью обсуждают через <strong>метрики</strong> и <strong>приемы</strong>. Метрики — Core Web Vitals: <strong>LCP</strong> (скорость показа главного контента, хорошо ≤ 2,5 с), <strong>INP</strong> (отзывчивость на действия, ≤ 200 мс), <strong>CLS</strong> (стабильность верстки, ≤ 0,1), плюс TTFB и размер JS. Приемы делятся на четыре группы: <strong>загружать меньше</strong> (code splitting, сжатие, оптимизация изображений), <strong>загружать раньше</strong> (preload, prefetch, SSR), <strong>рендерить меньше</strong> (виртуализация, мемоизация, <code>content-visibility</code>) и <strong>не блокировать главный поток</strong> (debounce, workers, transitions).</p></div>
</div>
<h2 id="вопрос">Вопрос</h2>
<p>Как обеспечить производительность фронтенд-приложения на system design интервью? Какие метрики назвать и какие приемы применить?</p>
<h2 id="метрики">Метрики</h2>



































<div class="table-wrap"><table><thead><tr><th>Метрика</th><th>Что измеряет</th><th>Чем улучшают</th></tr></thead><tbody><tr><td>LCP</td><td>когда отрисован главный элемент</td><td>SSR/SSG, preload героя, CDN, оптимизация изображений и шрифтов</td></tr><tr><td>INP</td><td>задержка ответа на взаимодействие</td><td>меньше JS, разбиение долгих задач, transitions, workers</td></tr><tr><td>CLS</td><td>сдвиги верстки</td><td>размеры медиа, резерв места под рекламу и баннеры, <code>font-display</code></td></tr><tr><td>TTFB</td><td>время до первого байта</td><td>кеш, CDN, edge, streaming</td></tr><tr><td>Bundle size</td><td>объем JS</td><td>code splitting, tree shaking, замена тяжелых зависимостей</td></tr></tbody></table></div>
<h2 id="1-загружать-меньше">1. Загружать меньше</h2>
<ul>
<li><strong>code splitting по маршрутам</strong> и ленивые компоненты (<code>React.lazy</code>, <code>next/dynamic</code>) для модалок, редакторов, графиков;</li>
<li>tree shaking, анализ бандла (<code>rollup-plugin-visualizer</code>, <code>@next/bundle-analyzer</code>), бюджет размера в CI;</li>
<li>изображения: AVIF/WebP, <code>srcset</code> и <code>sizes</code>, правильные размеры, <code>loading="lazy"</code> для невидимых, CDN с ресайзом;</li>
<li>шрифты: <code>woff2</code>, subset, <code>font-display: swap</code>, preload основного начертания;</li>
<li>сжатие Brotli/gzip, HTTP/2 или HTTP/3.</li>
</ul>
<h2 id="2-загружать-раньше">2. Загружать раньше</h2>
<ul>
<li>SSR/streaming для первого экрана;</li>
<li><code>&#x3C;link rel="preload"></code> для LCP-изображения и критичного шрифта, <code>fetchpriority="high"</code> для героя;</li>
<li><code>preconnect</code> к CDN и API;</li>
<li>prefetch следующего маршрута при наведении или появлении ссылки в viewport;</li>
<li>кеш: HTTP, CDN, Service Worker, кеш запросов.</li>
</ul>
<h2 id="3-рендерить-меньше">3. Рендерить меньше</h2>
<ul>
<li><strong>виртуализация</strong> длинных списков — в DOM только видимые элементы;</li>
<li>мемоизация тяжелых компонентов (<code>memo</code>) и вычислений, React Compiler;</li>
<li>colocation состояния, чтобы обновление не ререндерило всё дерево;</li>
<li><code>content-visibility: auto</code> для блоков ниже первого экрана;</li>
<li>анимации через <code>transform</code> и <code>opacity</code>, а не <code>top</code>/<code>width</code>.</li>
</ul>
<h2 id="4-не-блокировать-главный-поток">4. Не блокировать главный поток</h2>
<ul>
<li>debounce и throttle для ввода, скролла, ресайза;</li>
<li><code>startTransition</code> и <code>useDeferredValue</code> для тяжелых обновлений UI;</li>
<li>разбиение долгих задач (<code>scheduler.yield()</code>, <code>setTimeout</code>), <code>requestIdleCallback</code> для некритичного;</li>
<li>Web Worker для парсинга, сортировки больших данных, обработки изображений;</li>
<li>откладывание сторонних скриптов (аналитика, чаты поддержки) — <code>defer</code>, загрузка после взаимодействия.</li>
</ul>
<h2 id="пример-ответа">Пример ответа</h2>
<blockquote>
<p>«Главный риск ленты — INP и память при длинном скролле. Виртуализирую список, изображения — с размерами и lazy, первую — с <code>fetchpriority="high"</code>. Композер поста и просмотрщик медиа — отдельные чанки. Лайк — оптимистично, без ожидания сети. Метрики собираю через RUM (<code>web-vitals</code>), бюджет бандла — в CI.»</p>
</blockquote>
<h2 id="что-важно-помнить">Что важно помнить</h2>
<ul>
<li>Сначала измерить: Lighthouse и DevTools Performance — лабораторные данные, RUM (<code>web-vitals</code>, CrUX) — реальные пользователи.</li>
<li>Связывайте прием с метрикой: «виртуализация улучшает INP и память», «размеры изображений — CLS».</li>
<li>Самые дорогие ресурсы на мобильных — JavaScript (парсинг и выполнение), а не картинки того же размера.</li>
<li>Оптимистичные обновления и skeleton улучшают <strong>воспринимаемую</strong> производительность.</li>
<li>Связанные темы: <a href="/refront/l/04/09/01/" data-internal="true">Core Web Vitals</a>, <a href="/refront/l/06/07/04/" data-internal="true">виртуализация</a>.</li>
</ul>
<h2 id="мини-шпаргалка">Мини-шпаргалка</h2>
<p>Метрики: LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1, TTFB, размер JS. Меньше: code splitting, изображения, шрифты. Раньше: SSR, preload, prefetch, кеш. Меньше рендера: виртуализация, memo, colocation. Не блокировать поток: debounce, transitions, workers. Измерять: Lighthouse + RUM.</p>
