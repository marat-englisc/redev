Как защищаться от CSRF и чем помогают SameSite cookies?

Кратко

Защита от CSRF строится слоями: SameSite cookies, CSRF tokens, проверка Origin/Referer, запрет state-changing GET-запросов и дополнительное подтверждение для чувствительных операций. SameSite ограничивает отправку cookies в cross-site контексте, но не должен быть единственным слоем.

Вопрос

Как защитить приложение от CSRF? Как работают значения SameSite=Strict, Lax и None и почему одного SameSite недостаточно?

CSRF token

Server выдает token, а client отправляет его с state-changing request:

Server проверяет, что token валиден для текущей session. Атакующий сайт может заставить browser отправить form, но не должен знать правильный CSRF token: Same-Origin Policy не дает ему прочитать страницу или cookie с токеном.

Double submit cookie

Один из подходов:

Server сравнивает token из cookie и header. Чужой сайт не может прочитать cookie и подставить значение в header. Для более строгой защиты token связывают с session и подписывают.

SameSite cookies

SameSite говорит браузеру, отправлять ли cookie, если запрос инициирован с другого сайта.

ЗначениеПоведениеКогда использовать
Strictcookie только в same-site запросах, даже переход по внешней ссылке придет без неебанкинг, админки
Laxcross-site subrequests (form POST, fetch, img) без cookie, но top-level GET-навигация с cookieпрактичный default для session
Noneотправляется всегда, требует Securefrontend и API на разных сайтах, виджеты, iframe

Современные браузеры трактуют cookie без атрибута SameSite как Lax.

Site ≠ origin. app.example.com и api.example.com — разные origins, но один site (example.com). Поэтому SameSite не защищает от атак с поддомена, который контролирует атакующий.

Почему SameSite не всегда достаточно?

  • старые браузеры и edge cases;
  • Lax пропускает top-level GET — значит, state-changing GET остается уязвим;
  • атаки с поддоменов того же site;
  • сложные cross-site auth flows требуют SameSite=None;
  • XSS обходит любые CSRF-слои, потому что выполняется внутри origin.

Не меняй состояние через GET

Плохо:

Хорошо:

State-changing operations не должны выполняться через safe methods.

Что важно помнить

  • Если auth построена на Authorization: Bearer header из памяти, классический CSRF не работает: браузер не добавляет header автоматически. Риск появляется с cookies.
  • JSON API с Content-Type: application/json требует preflight для cross-origin, что дополнительно мешает CSRF, но полагаться только на это нельзя.
  • Фреймворки часто имеют встроенную защиту: Next.js Server Actions сравнивают Origin и Host, Django и Rails выдают CSRF tokens.
  • Для критичных действий (смена пароля, вывод денег) добавляют повторный ввод пароля или 2FA.

Мини-шпаргалка

  • CSRF tokens — основной слой защиты.
  • SameSite=Lax — хороший default, Strict — строже, None требует Secure.
  • SameSite защищает от cross-site, но не от same-site поддоменов.
  • Проверяй Origin/Referer/Sec-Fetch-Site для state-changing requests.
  • GET не должен менять состояние.
