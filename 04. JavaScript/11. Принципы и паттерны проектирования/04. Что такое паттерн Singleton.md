# Что такое паттерн Singleton

> [!NOTE]
> **Singleton (Одиночка)** — порождающий паттерн, который гарантирует, что у класса есть **только один экземпляр**, и дает к нему глобальную точку доступа. В JavaScript синглтон чаще всего получается сам собой: **ES-модуль выполняется один раз**, и экспортированный объект общий для всего приложения. Паттерн удобен для API-клиента, логгера, конфигурации, но глобальное изменяемое состояние усложняет тесты и SSR.

## Вопрос

Что такое Singleton? Как реализовать его в JavaScript и почему его иногда называют антипаттерном?

## Классическая реализация

```typescript
class Config {
  private static instance: Config | null = null;
  private constructor(readonly apiUrl: string) {}

  static getInstance() {
    if (!Config.instance) {
      Config.instance = new Config(import.meta.env.VITE_API_URL);
    }
    return Config.instance;
  }
}

Config.getInstance() === Config.getInstance(); // true
```

Ленивая инициализация: экземпляр создается при первом обращении.

## Синглтон через модуль (идиоматично для JS)

```typescript
// api.ts
class ApiClient {
  constructor(private baseUrl: string) {}
  get<T>(path: string): Promise<T> {
    return fetch(this.baseUrl + path).then((r) => r.json());
  }
}

export const api = new ApiClient("/api"); // модуль выполнится один раз
```

```typescript
// в любом месте приложения — один и тот же объект
import { api } from "./api";
```

Модульный кеш гарантирует единственность в рамках одного бандла или процесса.

## Где встречается

- клиенты API (`axios.create`), `QueryClient` в TanStack Query;
- логгер, аналитика, конфигурация;
- store менеджеров состояния (Redux store, Zustand store);
- подключение к БД на сервере (пул соединений).

## Почему его критикуют

| Проблема | Почему |
| --- | --- |
| Скрытые зависимости | модуль использует синглтон внутри — по сигнатуре не видно |
| Тестирование | состояние сохраняется между тестами, сложно подменить |
| SSR | один объект на весь Node.js-процесс — данные пользователей могут смешаться |
| Связанность | весь код зависит от конкретной реализации |

```typescript
// SSR-ловушка: store создан на уровне модуля и общий для всех запросов
export const store = createStore();

// правильно: новый экземпляр на запрос, передаваемый через контекст
export const makeStore = () => createStore();
```

Решение — внедрение зависимостей: создавать экземпляр в одном месте и передавать через параметры или контекст.

## Что важно помнить

- В JS модуль уже синглтон — отдельный класс с `getInstance` нужен редко.
- Одни и те же файлы, попавшие в разные бандлы или микрофронтенды, создают **разные** экземпляры.
- В Next.js в режиме разработки HMR может пересоздавать модули — для подключения к БД синглтон кладут в `globalThis`.
- Для SSR store и `QueryClient` создают на запрос, а не на модуль.

## Мини-шпаргалка

Singleton — один экземпляр и глобальный доступ. В JS — `export const instance = new X()`: модуль выполняется один раз. Применение: API-клиент, логгер, конфиг. Минусы: скрытые зависимости, тесты, SSR. Лучше — создать один раз и передать зависимостью.
