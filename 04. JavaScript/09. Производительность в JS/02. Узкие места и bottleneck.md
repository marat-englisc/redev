# Узкие места (bottleneck) и размер входных данных

> [!NOTE]
> **Bottleneck (узкое место)** — часть программы, которая ограничивает скорость всей системы: квадратичный алгоритм, лишние ререндеры, большой бандл, медленный запрос, layout thrashing. Ускорять нужно именно его — оптимизация остального почти не даст эффекта. Важно учитывать **размер входных данных**: алгоритм `O(n²)` незаметен на 10 элементах и «вешает» страницу на 50 000. Узкие места находят профилированием, а не догадками.

## Вопрос

Что такое узкие места в JS-коде и bottleneck в алгоритмах? Как размер входных данных влияет на производительность и как найти узкое место?

## Где обычно узкие места

| Область | Примеры |
| --- | --- |
| Алгоритмы | вложенные циклы, `includes`/`find` внутри цикла, сортировка в рендере |
| DOM | частые изменения по одному элементу, чтение layout после записи |
| Рендер фреймворка | лишние ререндеры, нестабильные пропсы, огромные списки без виртуализации |
| Сеть | водопад запросов, большие ответы, отсутствие кеша |
| Бандл | тяжелые библиотеки, нет code splitting |
| Память | утечки, огромные структуры в state |
| Основной поток | долгие синхронные задачи, `JSON.parse` больших данных |

## Размер входных данных

```javascript
// O(n²): для каждого заказа ищем пользователя перебором
const result = orders.map((order) => ({
  ...order,
  user: users.find((u) => u.id === order.userId),
}));

// O(n): индекс по id через Map
const usersById = new Map(users.map((u) => [u.id, u]));
const result2 = orders.map((order) => ({ ...order, user: usersById.get(order.userId) }));
```

| n | `O(n)` | `O(n log n)` | `O(n²)` |
| --- | --- | --- | --- |
| 100 | 100 | ~700 | 10 000 |
| 10 000 | 10 000 | ~130 000 | 100 000 000 |
| 100 000 | 100 000 | ~1 700 000 | 10 000 000 000 |

На маленьких данных разница не видна, поэтому проблема проявляется только в production на реальных объемах.

## Как найти узкое место

1. **Измерить**, а не угадывать: DevTools Performance, React Profiler, Lighthouse, `performance.now()`.
2. Найти самую долгую часть — «горячую» функцию, долгую задачу, частый ререндер.
3. Оптимизировать только ее и снова измерить.

```javascript
performance.mark("filter-start");
const visible = filterProducts(products, query);
performance.mark("filter-end");
performance.measure("filter", "filter-start", "filter-end");
console.table(performance.getEntriesByType("measure"));
```

## Типичные исправления

- Map/Set вместо поиска по массиву;
- мемоизация тяжелых вычислений (`useMemo`, кеш);
- debounce для поиска и фильтрации на ввод;
- пагинация, виртуализация;
- перенос тяжелой работы в Web Worker;
- батчинг DOM-изменений;
- параллельные запросы вместо последовательных, кеширование ответов.

## Что важно помнить

- «Преждевременная оптимизация — корень всех зол»: сначала понятный код, затем измерение и оптимизация узких мест.
- Микрооптимизации (`for` вместо `forEach`) почти никогда не являются узким местом.
- Узким местом может быть не код, а сервер или сеть — смотрите Network и TTFB.
- Закон Амдала: ускорение части программы ограничено долей времени, которую эта часть занимает.

## Мини-шпаргалка

- Bottleneck — самая медленная часть, ограничивающая всю систему.
- Размер данных решает: `O(n²)` опасен на больших n.
- Сначала профилирование, потом оптимизация.
- Частые исправления: Map, мемоизация, debounce, виртуализация, Worker.
- Оптимизируйте только измеренное узкое место.
