# Минимизация HTTP-запросов и минификация кода

> [!NOTE]
> Каждый запрос стоит времени на соединение и ожидание ответа, поэтому количество и вес ресурсов напрямую влияют на скорость загрузки. **Минимизация запросов** — бандлинг, спрайты и инлайн критичных ресурсов, кеширование, объединение API-запросов. **Минификация** — удаление пробелов, комментариев и сокращение имен в JS и CSS без изменения поведения. Вместе со сжатием (gzip, Brotli) это уменьшает объем передаваемых данных.

## Вопрос

Зачем минимизировать HTTP-запросы и как это делать? Что такое минификация кода и чем она отличается от сжатия?

## Почему запросы дорогие

```text
каждый новый origin: DNS → TCP → TLS → запрос → ожидание → загрузка
```

С HTTP/2 и HTTP/3 много запросов к одному origin идут параллельно по одному соединению, поэтому старое правило «склеить всё в один файл» уже не абсолютно. Но остаются:

- лимиты приоритета и очереди;
- задержка каждого запроса на медленных мобильных сетях;
- водопады зависимостей (CSS → шрифт → картинка);
- дорогие запросы к сторонним доменам.

## Как уменьшить количество запросов

| Прием | Что дает |
| --- | --- |
| Бандлинг (Vite, webpack) | меньше файлов JS и CSS |
| Code splitting по маршрутам | грузится только нужное, но меньшими чанками |
| HTTP-кеширование (`Cache-Control`, hash в имени) | повторные визиты без запросов |
| Service Worker | офлайн и кеш приложения |
| SVG-спрайты, иконочные шрифты или инлайн SVG | одна загрузка на все иконки |
| Inline критичного CSS | первый экран без ожидания CSS |
| `preconnect` к нужным origin | соединение заранее |
| Объединение API-запросов (BFF, GraphQL, batch) | меньше round-trip |
| Отказ от лишних сторонних скриптов | меньше доменов и JS |

## Минификация

```javascript
// исходный код
function calculateTotal(items) {
  // сумма с учетом количества
  return items.reduce((total, item) => total + item.price * item.qty, 0);
}

// после минификации (terser, esbuild)
function c(t){return t.reduce((e,r)=>e+r.price*r.qty,0)}
```

Что делает минификатор:

- удаляет пробелы, переносы, комментарии;
- сокращает имена локальных переменных (mangling);
- упрощает выражения, удаляет мертвый код (`if (false)`);
- для CSS — сокращает цвета и значения, объединяет правила (cssnano, Lightning CSS);
- для HTML — удаляет лишние пробелы и атрибуты по умолчанию.

Сборщики делают это автоматически в production-сборке (`vite build`, `next build`).

## Минификация и сжатие

| | Минификация | Сжатие (gzip, Brotli) |
| --- | --- | --- |
| Где | на этапе сборки | на сервере или CDN при отдаче |
| Результат | валидный, но нечитаемый код | бинарный поток, браузер распаковывает |
| Header | — | `Content-Encoding: br` |
| Эффект | -30–60% | дополнительно -60–80% от минифицированного |

Используют оба: сначала минификация, затем сжатие. Brotli обычно эффективнее gzip для текста.

## Что важно помнить

- Source maps позволяют отлаживать минифицированный код; в production их выкладывают в сервис мониторинга, а не публично.
- Минификация не уменьшает время **выполнения** JS — для этого нужно меньше кода (tree shaking, code splitting).
- Слишком мелкое дробление на чанки тоже вредит: много запросов и хуже сжатие.
- Анализ бандла (`rollup-plugin-visualizer`, `@next/bundle-analyzer`) показывает, что занимает место.

## Мини-шпаргалка

- Меньше запросов: бандлинг, кеш, спрайты, `preconnect`, объединение API.
- HTTP/2 смягчил проблему, но не отменил.
- Минификация — удаление лишнего и сокращение имен на сборке.
- Сжатие — gzip/Brotli при передаче.
- Минификация + сжатие + source maps.
