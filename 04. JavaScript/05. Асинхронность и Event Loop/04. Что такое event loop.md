# Что такое event loop и как в него встроен рендеринг

> [!NOTE]
> **Event loop** — механизм среды выполнения, который решает, когда выполнить следующую задачу. Один шаг цикла: взять **одну** макрозадачу из очереди, выполнить ее до конца, затем выполнить **все** микрозадачи, а затем, если пришло время кадра, дать браузеру **отрисовать** страницу: вызвать колбэки `requestAnimationFrame`, пересчитать стили, layout и paint. После этого цикл повторяется.

## Вопрос

Что такое event loop и зачем он нужен JavaScript? Где в цикле происходит рендеринг и когда выполняется `requestAnimationFrame`?

## Участники

| Часть | Что делает |
| --- | --- |
| Call stack | выполняет текущий синхронный код |
| Web API / Node API | таймеры, сеть, события, I/O вне JS-потока |
| Task queue (макрозадачи) | `setTimeout`, события, сообщения, I/O |
| Microtask queue | `Promise.then`, `await`, `queueMicrotask`, `MutationObserver` |
| Animation frame callbacks | колбэки `requestAnimationFrame` |
| Event loop | переносит задачи в стек в правильном порядке |

## Модель одного «оборота»

```text
┌─► 1. Взять одну макрозадачу и выполнить до конца
│   2. Выполнить ВСЕ микрозадачи (включая новые, добавленные по ходу)
│   3. Если пора рисовать кадр (~16 мс при 60 Гц):
│        • события resize / scroll
│        • колбэки requestAnimationFrame
│        • style → layout → paint → composite
│        • (микрозадачи после каждого rAF-колбэка)
│   4. Если есть свободное время — requestIdleCallback
└── повторить
```

Браузер не обязан рисовать после каждой макрозадачи: если страница не изменилась или кадр еще не наступил, шаг рендеринга пропускается.

## Пример

```javascript
console.log("sync 1");

setTimeout(() => console.log("macrotask"), 0);

requestAnimationFrame(() => console.log("rAF — перед отрисовкой"));

Promise.resolve().then(() => console.log("microtask"));

console.log("sync 2");

// sync 1
// sync 2
// microtask
// затем «macrotask» и «rAF» — их взаимный порядок зависит от того,
// успеет ли наступить кадр до выполнения таймера
```

Точно гарантировано только то, что синхронный код и микрозадачи идут раньше таймера и rAF.

## Почему важен шаг рендеринга

```javascript
box.style.transform = "translateX(0)";
box.style.transform = "translateX(100px)";
// пользователь увидит только конечное состояние: рендер происходит после задачи
```

- Изменения DOM внутри одной задачи объединяются в один кадр.
- Долгая задача или бесконечная цепочка микрозадач **задерживает рендер** — страница «замирает».
- `requestAnimationFrame` вызывается прямо перед отрисовкой — лучшее место для анимаций на JS и чтения/записи layout.

```javascript
function animate(time) {
  box.style.transform = `translateX(${(time / 10) % 300}px)`;
  requestAnimationFrame(animate);
}
requestAnimationFrame(animate);
```

## Важный вывод

Если call stack занят тяжелым синхронным кодом, event loop не может взять задачи из очередей и не может отрисовать кадр. Поэтому таймеры, клики, промисы и анимации ждут.

## Что важно помнить

- Event loop — часть среды (браузер, Node.js), а не языка ECMAScript; спецификация описана в HTML Standard.
- В Node.js цикл устроен иначе: фазы timers → pending → poll → check → close и отдельная очередь `process.nextTick`.
- rAF не вызывается в фоновых вкладках, а таймеры там замедляются до раза в секунду и реже.
- Для разбиения долгой работы используйте `setTimeout`/`scheduler.yield()`, а не цепочку микрозадач — иначе рендер не получит шанса.

## Мини-шпаргалка

- Одна макрозадача → все микрозадачи → (рендер, если пора) → повтор.
- Рендер: rAF → style → layout → paint.
- Изменения DOM в одной задаче — один кадр.
- Занятый стек блокирует и задачи, и отрисовку.
- В Node.js — фазы libuv и `process.nextTick`.
