# Как бандлер строит граф модулей, чанки и хеши

> [!NOTE]
> Бандлер начинает с **точки входа** (entry), рекурсивно проходит по всем `import` и строит **граф зависимостей**. Затем граф делится на **чанки**: основной (entry), **общие** (код, нужный нескольким частям, часто — библиотеки из `node_modules`) и **ленивые** (то, что подключается через динамический `import()`). Каждому файлу дается имя с **хешем содержимого** — если файл не изменился, хеш тот же, и браузер берет его из кеша.

## Вопрос

Как бандлер строит граф модулей? Что такое чанки, как код делится на entry, vendor и ленивые чанки и зачем нужен content hash в имени файла?

## Граф зависимостей

```text
main.tsx
 ├─ App.tsx
 │   ├─ react, react-dom              (node_modules)
 │   ├─ Header.tsx ─ Logo.svg
 │   ├─ routes.tsx
 │   │   ├─ import("./pages/Home")     ← динамический импорт = новый чанк
 │   │   └─ import("./pages/Settings") ← новый чанк
 │   └─ styles.css
 └─ api/client.ts ─ ky
```

## Виды чанков

| Чанк | Что внутри | Как часто меняется |
| --- | --- | --- |
| Entry | код запуска и общий код страниц | часто |
| Vendor / общий | `react`, `react-dom`, роутер | редко → долгий кеш |
| Ленивый (async) | страницы, модалки, тяжелые библиотеки | при изменении конкретной фичи |
| CSS | извлеченные стили | вместе с компонентами |

Ручная настройка в Vite (Rollup):

```typescript
// vite.config.ts
export default defineConfig({
  build: {
    rollupOptions: {
      output: {
        manualChunks: {
          react: ["react", "react-dom", "react-router"],
          charts: ["recharts"],
        },
      },
    },
  },
});
```

В webpack за это отвечает `optimization.splitChunks`.

## Хеши в именах

```text
index-B3f9a1cD.js    хеш содержимого: изменился код → новое имя
```

```http
assets/*.js   Cache-Control: public, max-age=31536000, immutable
index.html    Cache-Control: no-cache
```

- новое имя гарантирует, что пользователь получит новую версию;
- неизмененные чанки (например, vendor) остаются в кеше браузера между релизами;
- поэтому полезно отделять редко меняющиеся библиотеки от часто меняющегося кода приложения.

## Предзагрузка чанков

Сборщик добавляет в `index.html` `<link rel="modulepreload">` для чанков, нужных сразу, чтобы браузер загружал их параллельно, а не по цепочке импортов. Для ленивых маршрутов полезен prefetch при наведении на ссылку.

## Типичные проблемы

| Проблема | Причина | Решение |
| --- | --- | --- |
| Огромный entry-чанк | всё импортировано статически | ленивые маршруты и компоненты |
| Библиотека дублируется в чанках | разные версии в зависимостях | `npm dedupe`, единые версии |
| `ChunkLoadError` после деплоя | старый HTML ссылается на удаленные чанки | хранить старые ассеты, перезагрузка при ошибке |
| Слишком много мелких чанков | агрессивное дробление | объединять связанные модули |

## Что важно помнить

- Граница чанка — это динамический `import()`; статические импорты попадают в тот же чанк.
- Content hash + `immutable` — основа кеширования статики.
- Vendor-чанк выгоден, если библиотеки меняются реже кода приложения.
- После деплоя не удаляйте сразу старые ассеты: у открытых вкладок еще старый HTML.
- Связанные темы: [code splitting](<../../04. JavaScript/09. Производительность в JS/13. Code splitting и динамический import().md>), [React.lazy](<../../06. React/07. Рендеринг и производительность/07. React.lazy и lazy loading компонентов, в том числе при SSR.md>).

## Мини-шпаргалка

Entry → граф импортов → чанки: entry, vendor/общие, ленивые (по `import()`), CSS. Хеш содержимого в имени → долгий кеш + `immutable`, HTML — `no-cache`. `manualChunks` (Vite) / `splitChunks` (webpack). `modulepreload`, prefetch, осторожно со старыми ассетами при деплое.
