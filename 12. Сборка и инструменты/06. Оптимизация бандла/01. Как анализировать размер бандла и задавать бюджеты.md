# Как анализировать размер бандла и задавать бюджеты

> [!NOTE]
> Размер JavaScript напрямую влияет на скорость: его нужно скачать, распарсить и выполнить, и на слабых телефонах это главный тормоз. **Анализ бандла** показывает, из чего состоит каждый чанк (визуализаторы `rollup-plugin-visualizer`, `webpack-bundle-analyzer`, `@next/bundle-analyzer`, source-map-explorer), а **бюджеты производительности** (size-limit, Lighthouse CI, `performance.hints` в webpack) не дают размеру незаметно расти: CI падает, если чанк превысил лимит.

## Вопрос

Как проанализировать, из чего состоит бандл, и найти лишний код? Как настроить бюджеты размера, чтобы бандл не рос незаметно?

## Анализ в Vite

```typescript
// vite.config.ts
import { visualizer } from "rollup-plugin-visualizer";

export default defineConfig({
  plugins: [react(), visualizer({ filename: "stats.html", gzipSize: true, brotliSize: true })],
});
```

После `vite build` откроется карта, где площадь прямоугольника пропорциональна размеру модуля.

Next.js: `@next/bundle-analyzer` (`ANALYZE=true next build`), webpack: `webpack-bundle-analyzer`.

## Что искать

| Находка | Решение |
| --- | --- |
| `moment` с локалями (~300 КБ) | `date-fns`, `dayjs`, `Temporal`/`Intl` |
| весь `lodash` | `lodash-es` с точечным импортом или нативные методы |
| иконки целым набором | импорт отдельных иконок, SVG-спрайт |
| тяжелая библиотека на одной странице (графики, редактор, карта) | `React.lazy` / динамический `import()` |
| две версии одной библиотеки | `npm ls`, `dedupe`, `overrides` |
| полифилы для браузеров, которых нет у аудитории | сузить browserslist |
| код только для админов в общем бандле | отдельный чанк по маршруту |
| CommonJS-библиотека без tree shaking | ESM-альтернатива |

Перед добавлением зависимости — проверьте ее вес на bundlephobia.com или pkg-size.dev.

## Бюджеты

```json
// .size-limit.json
[
  { "path": "dist/assets/index-*.js", "limit": "120 kB" },
  { "path": "dist/assets/*.css", "limit": "30 kB" }
]
```

```json
// package.json
{ "scripts": { "size": "size-limit" } }
```

В CI `size-limit` комментирует PR изменением размера и падает при превышении. Аналоги: `bundlewatch`, `performance.maxEntrypointSize` в webpack, Lighthouse CI с бюджетами метрик.

## Ориентиры

- считайте размер **после сжатия** (gzip/brotli), но помните, что парсинг идет по распакованному коду;
- для первого экрана мобильного приложения ориентир — порядка 100–170 КБ сжатого JS (рекомендации web.dev);
- смотрите в DevTools → Coverage, сколько загруженного кода реально выполнилось.

## Что важно помнить

- Измеряйте до и после: оптимизация «на глаз» часто ничего не дает.
- Главный рычаг — не загружать сразу то, что не нужно для первого экрана (code splitting), а не микрооптимизации.
- Бюджет в CI превращает производительность из разовой акции в постоянное правило.
- Сторонние скрипты (аналитика, виджеты чатов) тоже часть бюджета — загружайте их отложенно.

## Мини-шпаргалка

Анализ: `rollup-plugin-visualizer`, `webpack-bundle-analyzer`, `@next/bundle-analyzer`, DevTools Coverage. Лечение: легкие альтернативы, точечные импорты, lazy-чанки, dedupe, узкий browserslist. Бюджеты: size-limit, bundlewatch, Lighthouse CI в CI. Перед установкой — bundlephobia.
