# Что такое менеджер состояния и зачем централизованный стор

> [!NOTE]
> **Менеджер состояния** — библиотека, которая хранит общее состояние приложения в **централизованных сторах** вне дерева компонентов и задаёт правила его изменения. Плюсы централизованного стора: **единый источник истины** (корзина одна для шапки, каталога и оформления заказа), **предсказуемые изменения** через actions, **devtools** с историей изменений и time-travel, удобная **SSR-сериализация** и гидрация, переиспользование логики (запросы, кеш, вычисления) без prop drilling, простое тестирование бизнес-логики отдельно от UI. Минусы: лишний слой абстракции для простых приложений, соблазн складывать в стор всё подряд (в том числе локальное UI-состояние), риск «God store» с перемешанными доменами, неявные связи между компонентами через общие данные. В экосистеме Vue стандарт — **Pinia** (официальная замена Vuex); простые случаи закрываются `reactive`/composable с состоянием на уровне модуля или provide/inject, а для **серверных данных** часто удобнее специализированные кеши запросов (TanStack Query, `useFetch`/`useAsyncData` в Nuxt).

## Вопрос

Что такое менеджер состояния и зачем во Vue-приложении централизованный стор?

## Без стора

```text
App
├── Header → CartBadge         (нужно: количество товаров)
├── Catalog → ProductCard × N  (нужно: добавить в корзину)
└── Checkout → CartSummary     (нужно: товары, сумма)

Без стора: состояние в App, props вниз через 3–4 уровня, события вверх — prop drilling
```

## Со стором

```ts
export const useCartStore = defineStore('cart', () => {
  const items = ref<CartItem[]>([]);
  const total = computed(() => items.value.reduce((s, i) => s + i.price * i.qty, 0));

  function add(p: Product) {
    const item = items.value.find((i) => i.id === p.id);
    item ? item.qty++ : items.value.push({ ...p, qty: 1 });
  }

  return { items, total, add };
});

// любой компонент
const cart = useCartStore();
cart.add(product);
```

## Простейший стор без библиотеки

```ts
// store.ts — для маленьких SPA без SSR
export const store = reactive({
  user: null as User | null,
  setUser(u: User | null) { this.user = u; },
});
```

Работает, но без devtools, плагинов, изоляции в SSR и соглашений — по мере роста приложения переходят на Pinia.

## Экосистема

| Решение | Когда |
| --- | --- |
| Pinia | Стандарт для Vue 3: общее клиентское состояние |
| Vuex 4 | Легаси-проекты; в новых не используется |
| `reactive` / composable на уровне модуля | Маленькие SPA без SSR |
| provide / inject | Контекст поддерева, составные компоненты |
| TanStack Query (Vue Query), Pinia Colada | Серверное состояние: кеш, повторы, инвалидация |
| `useState` (Nuxt) | Простое SSR-безопасное общее состояние |

## Преимущества и недостатки

| Преимущества | Недостатки |
| --- | --- |
| Один источник истины | Дополнительный слой и шаблонный код |
| Devtools, история, time-travel | Соблазн хранить всё глобально |
| SSR-гидрация | Неявные связи через общие данные |
| Тестируемая бизнес-логика | «God store» без границ доменов |
| Нет prop drilling | Устаревшие данные, если нет инвалидации |

## Однонаправленный поток в сторе

```text
Компонент ──вызов action──► Store меняет state ──реактивность──► все компоненты обновляются
```

Компоненты читают состояние и вызывают actions; изменения логики концентрируются в сторе.

## Как не превратить стор в свалку

- Отдельный стор на домен: `user`, `cart`, `catalog`, `notifications`.
- Только общее состояние; локальное UI — в компонентах.
- Производные данные — getters/computed, а не дублирующее состояние.
- Серверный кеш — с явной стратегией обновления или в специализированной библиотеке.

## Частые ошибки

- Стор ради стора в маленьком приложении.
- Один огромный стор на всё приложение.
- Копировать ответы API в стор без инвалидации — устаревшие данные.
- Менять состояние стора из компонентов в обход actions там, где важна единая логика.

## Что важно помнить

- Менеджер состояния — централизованные сторы с правилами изменения.
- Pinia — стандарт для Vue 3; Vuex — легаси.
- Сторы — по доменам и только для общего состояния; серверные данные — отдельная задача.

## Мини-шпаргалка

- `defineStore('name', setup)`.
- Компоненты: читать state/getters, вызывать actions.
- Маленькое SPA — `reactive` модуля; SSR — Pinia/Nuxt `useState`.
- Данные API — TanStack Query / Pinia Colada.
