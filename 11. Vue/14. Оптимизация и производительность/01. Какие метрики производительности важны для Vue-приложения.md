# Какие метрики производительности важны для Vue-приложения

> [!NOTE]
> Производительность измеряют, а не угадывают. **Core Web Vitals** — метрики реального пользовательского опыта, которые Google использует в ранжировании: **LCP** (Largest Contentful Paint, появление основного контента, хорошо ≤ 2,5 с), **INP** (Interaction to Next Paint, задержка реакции на действия, хорошо ≤ 200 мс) и **CLS** (Cumulative Layout Shift, «прыжки» вёрстки, хорошо ≤ 0,1). Вспомогательные: **TTFB** (ответ сервера), **FCP** (первый контент), **TBT** (суммарное время блокировки главного потока в лабораторных замерах — коррелирует с INP). Для SPA на Vue дополнительно важны **размер JS-бандла** (его нужно скачать, распарсить и выполнить до появления интерфейса), **время гидратации** при SSR, время перехода между маршрутами, время рендера тяжёлых компонентов, **память** (утечки подписок, таймеров, отсоединённых DOM-узлов) и **FPS** при скролле и анимациях. Инструменты: Lighthouse/PageSpeed Insights (лаборатория), Chrome DevTools Performance и Memory, вкладка Performance во Vue DevTools, библиотека `web-vitals` для сбора данных реальных пользователей (RUM). Порядок работы: измерить → найти узкое место → исправить → измерить снова.

## Вопрос

Какие метрики производительности вы знаете и какие из них особенно важны для Vue-приложения?

## Core Web Vitals

| Метрика | Что измеряет | Хорошо | Что ухудшает во Vue |
| --- | --- | --- | --- |
| **LCP** | Появление крупнейшего элемента | ≤ 2,5 с | Большой бандл в CSR, рендер только на клиенте, тяжёлые изображения |
| **INP** | Задержка реакции на клик/ввод | ≤ 200 мс | Долгие синхронные обработчики, перерендер больших списков |
| **CLS** | Сдвиги вёрстки | ≤ 0,1 | Изображения без размеров, контент, появляющийся после загрузки данных |

Пороги оцениваются по 75-му перцентилю реальных пользователей.

## Вспомогательные метрики

| Метрика | Смысл |
| --- | --- |
| TTFB | Как быстро сервер начал отвечать |
| FCP | Когда появился первый контент |
| TBT | Сколько главный поток был заблокирован задачами > 50 мс |

## Что важно именно для SPA

```text
Первая загрузка: скачать JS → распарсить → выполнить → createApp → рендер → (гидратация при SSR)
После загрузки: переходы между маршрутами, отзывчивость ввода, плавность скролла, рост памяти
```

| Показатель | Как смотреть |
| --- | --- |
| Размер бандла и чанков | `vite build` + `rollup-plugin-visualizer` |
| Время рендера компонентов | Vue DevTools → Performance, `app.config.performance = true` |
| Долгие задачи | DevTools → Performance (красные Long Tasks) |
| Утечки памяти | DevTools → Memory, heap snapshot до и после навигации |
| FPS | DevTools → Performance, Rendering → Frame rendering stats |

## Сбор метрик у пользователей

```ts
import { onCLS, onINP, onLCP } from 'web-vitals';

function send(metric: { name: string; value: number; id: string }) {
  navigator.sendBeacon('/analytics/vitals', JSON.stringify(metric));
}

onLCP(send);
onINP(send);
onCLS(send);
```

## Пример анализа

```vue
<ProductCard v-for="p in products" :key="p.id" :product="p" />
```

10 000 товаров разом: долгая задача при рендере (TBT/INP), тысячи экземпляров компонентов в памяти, медленный скролл. Решения — пагинация, [виртуализация](<05. Как оптимизировать большие таблицы и списки - виртуализация.md>), более лёгкие элементы списка.

## Частые ошибки

- Оптимизировать «на глаз» без профилирования.
- Мерить только Lighthouse на мощном ноутбуке — у реальных пользователей слабые телефоны (используйте CPU throttling и RUM).
- Смотреть только на первую загрузку и игнорировать INP и утечки памяти.
- Измерять в dev-режиме — production-сборка значительно быстрее.

## Что важно помнить

- Core Web Vitals: LCP, INP, CLS.
- Для SPA: размер бандла, гидратация, рендер компонентов, память.
- Лабораторные замеры + данные реальных пользователей.

## Мини-шпаргалка

- LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1.
- `web-vitals`: `onLCP`, `onINP`, `onCLS`.
- `app.config.performance = true` — тайминги в DevTools.
- Мерить production-сборку с throttling.
