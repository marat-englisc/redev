# Как работает hydration persisted state

> [!NOTE]
> **Гидрация** в контексте persisted state — восстановление сохранённых значений в стор. Плагин выполняет её **один раз, когда стор создаётся** (при первом вызове `useXxxStore()`): читает запись из хранилища, десериализует и применяет к state через `$patch` — сохранённые поля **перекрывают** начальные значения, остальные остаются по умолчанию. Хуки **`beforeHydrate`** и **`afterHydrate`** позволяют подготовить или проверить данные (миграция старой схемы, валидация, логирование). Отсюда вытекают практические вопросы: **изменение структуры** стора (старые данные в новом формате — нужны версии ключа или миграции), **несовпадение при SSR** (на сервере `localStorage` нет, поэтому сервер рендерит значение по умолчанию, а клиент — сохранённое: возникают hydration mismatch и «мигание», решение — cookies или клиентская отрисовка зависимых частей), **синхронизация вкладок** (изменение в одной вкладке не попадёт в другую сама по себе — нужно событие `storage` + `$hydrate()`), а также недоступное или переполненное хранилище (приватный режим, квота).

## Вопрос

Как происходит гидрация persisted state и какие с ней бывают проблемы?

## Последовательность

```text
1. createPinia() → pinia.use(persistedstate) → app.use(pinia)
2. компонент вызывает useSettingsStore() впервые
3. стор создаётся с начальным state: { theme: 'light', locale: 'ru' }
4. beforeHydrate(context)
5. плагин читает localStorage['settings'] = {"theme":"dark"}
6. $patch → { theme: 'dark', locale: 'ru' }
7. afterHydrate(context)
8. дальше каждое изменение state записывается обратно
```

## Миграция схемы

```ts
export const useSettingsStore = defineStore('settings', {
  state: () => ({ theme: 'system' as 'light' | 'dark' | 'system', density: 'comfortable' as 'compact' | 'comfortable' }),
  persist: {
    key: 'settings:v2',                 // новая версия ключа — старые данные не читаются
    beforeHydrate: () => {
      const legacy = localStorage.getItem('settings');           // v1: { darkMode: true }
      if (legacy && !localStorage.getItem('settings:v2')) {
        const { darkMode } = JSON.parse(legacy);
        localStorage.setItem('settings:v2', JSON.stringify({ theme: darkMode ? 'dark' : 'light' }));
        localStorage.removeItem('settings');
      }
    },
    afterHydrate: ({ store }) => {
      if (!['light', 'dark', 'system'].includes(store.theme)) store.$reset();   // защита от мусора
    },
  },
});
```

## SSR

```text
Сервер: localStorage нет → рендер theme = 'light'
Клиент: гидрация стора → theme = 'dark' → HTML не совпадает → предупреждение и мигание
```

Решения:

| Подход | Когда |
| --- | --- |
| Cookies как хранилище | Значение нужно серверу (тема, язык) |
| `<ClientOnly>` / рендер после `onMounted` | Значение влияет на небольшой фрагмент |
| Значение по умолчанию + анимация перехода | Не критично |

В Nuxt модуль плагина по умолчанию использует cookies именно поэтому.

## Синхронизация вкладок

```ts
window.addEventListener('storage', (e) => {
  if (e.key === 'settings') useSettingsStore().$hydrate();
});
```

## Недоступное хранилище

```ts
persist: { debug: true }          // логировать ошибки чтения и записи
```

В приватном режиме и при переполнении квоты запись может бросить исключение — критичная логика не должна от неё зависеть; данные стоит держать небольшими.

## Гидрация persisted state и SSR-гидрация Pinia

| | Persisted state | SSR-гидрация Pinia |
| --- | --- | --- |
| Источник | localStorage/sessionStorage/cookie | State, сериализованный сервером в HTML |
| Когда | При создании стора на клиенте | До монтирования приложения |
| Цель | Пережить перезагрузку | Не загружать данные повторно после SSR |

## Частые ошибки

- Изменить формат state без версии ключа и миграции.
- `localStorage` для значения, которое рендерится сервером, — hydration mismatch.
- Ожидать, что изменения синхронизируются между вкладками автоматически.
- Хранить в persisted state данные, зависящие от прав, без перепроверки на сервере.

## Что важно помнить

- Гидрация — при первом создании стора; сохранённые поля перекрывают начальные.
- `beforeHydrate`/`afterHydrate` — миграции и валидация.
- SSR требует cookies или клиентского рендера зависимых частей.

## Мини-шпаргалка

- `key: 'store:v2'` при смене схемы.
- `beforeHydrate`, `afterHydrate`.
- `store.$hydrate()` + событие `storage`.
- SSR → cookies.
