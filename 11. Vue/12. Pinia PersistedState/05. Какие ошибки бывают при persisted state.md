# Какие ошибки бывают при persisted state

> [!NOTE]
> Большинство проблем persisted state — **архитектурные**, а не технические. Сохраняют **секреты** (access/refresh-токены в `localStorage` доступны любому XSS — для аутентификации предпочтительнее httpOnly-cookie); **доверяют** сохранённым ролям и флагам (`isAdmin: true` в storage пользователь может выставить сам — права всегда проверяет сервер, а клиент использует их только для UI); кладут **серверные данные** (списки товаров, заказы) — они устаревают, упираются в квоту ~5 МБ, замедляют старт; не очищают хранилище **при выходе** — следующий пользователь устройства видит чужие данные; меняют **структуру state** без версии ключа — приложение падает на старых данных; сохраняют **временные флаги** (`isLoading: true` навсегда «зависает» после перезагрузки); используют `localStorage` при **SSR** — hydration mismatch; не учитывают **приватный режим** и ошибки записи. Защита: явный `pick`, версии ключей, `$reset` + очистка при logout, проверка данных в `afterHydrate`, cookies для SSR-значений.

## Вопрос

Какие ошибки чаще всего допускают при использовании persisted state?

## 1. Весь auth-стор в localStorage

```ts
// ✗
export const useAuthStore = defineStore('auth', {
  state: () => ({ user: null, accessToken: null, refreshToken: null, permissions: [], isLoading: false }),
  persist: true,
});

// ✓ токены — в httpOnly-cookie (сервер), в сторе — только то, что безопасно и нужно UI
persist: { pick: ['lastEmail'] }
```

## 2. Доверие к сохранённым правам

```json
localStorage['auth'] = {"user":{"role":"admin"}}   // пользователь может это написать сам
```

Клиент может скрывать кнопки по роли, но сервер обязан проверять права на каждый запрос.

## 3. Серверные данные в хранилище

```ts
// ✗ 2000 товаров в localStorage
persist: { pick: ['products'] }
```

Лучше повторный запрос, кеш запросов (TanStack Query, Pinia Colada) или HTTP-кеш.

## 4. Нет очистки при выходе

```ts
async function logout() {
  await authApi.logout();
  useCartStore().$reset();             // $reset запишет пустое состояние в storage
  useDraftsStore().$reset();
  localStorage.removeItem('shop:recent-searches');
}
```

## 5. Смена схемы без версии

```ts
// было: { filters: 'price' }, стало: { filters: { sort: 'price' } }
// старые данные → filters.sort === undefined → ошибка в коде
persist: { key: 'catalog-ui:v2' }      // новая версия ключа или миграция в beforeHydrate
```

## 6. Временные флаги

```ts
// ✗ isLoading: true сохранился в момент перезагрузки → спиннер навсегда
persist: true

// ✓
persist: { pick: ['view', 'pageSize'] }
```

## 7. SSR и localStorage

Сервер не видит `localStorage` → разное HTML на сервере и клиенте. Для значений, влияющих на SSR-рендер, — cookies.

## 8. Ошибки хранилища

- Приватный режим, отключённые cookies, переполненная квота — запись бросает исключение.
- Не делайте корректность приложения зависимой от успешной записи; включите `debug` в dev.

## Чек-лист

- [ ] Явный `pick` вместо `persist: true` для растущих сторов.
- [ ] Нет токенов, паролей, персональных данных.
- [ ] Права не используются для решений о доступе.
- [ ] Версия в `key`, миграции при смене формата.
- [ ] Очистка при logout.
- [ ] Для SSR — cookies.
- [ ] Небольшой объём данных.

## Частые ошибки

- Использовать persisted state как «бесплатное» хранилище всего подряд.
- Проверять корректность сохранённых данных только «на глаз» — без `afterHydrate` мусор из старой версии ломает интерфейс.
- Забывать, что каждое изменение state синхронно пишет в storage: частые изменения больших объектов замедляют UI.

## Что важно помнить

- Persisted state — для настроек и черновиков, не для секретов и серверных данных.
- Сохранённые значения контролирует пользователь — сервер проверяет всё сам.
- Явный `pick`, версии ключей, очистка при выходе, cookies для SSR.

## Мини-шпаргалка

- `pick` — только нужное.
- Токены — httpOnly-cookie.
- `key: 'x:v2'`.
- `$reset()` при logout.
- SSR → cookies.
