# Почему props readonly и что такое однонаправленный поток данных

> [!NOTE]
> **Однонаправленный поток данных (one-way data flow)** — правило, по которому данные передаются **сверху вниз** (родитель → ребёнок через props), а изменения инициирует **владелец данных**: ребёнок не меняет полученное значение, а сообщает о намерении событием (`emit`), и родитель решает, обновлять ли своё состояние. Поэтому **props доступны только для чтения**: в dev-режиме попытка присвоить `props.x = ...` вызывает предупреждение, а при каждом обновлении родителя props всё равно перезапишутся. Правило делает поток изменений предсказуемым: у каждого значения один источник истины, и по коду видно, кто и где его меняет. Технически мутации **вложенных** объектов и массивов из props не перехватываются (Vue не может это запретить без дорогих проверок), но они нарушают тот же принцип. Правильные приёмы: локальная копия для **начального** значения, `computed` для преобразования, `emit` или `v-model`/`defineModel` для изменения.

## Вопрос

Почему props нельзя изменять в дочернем компоненте и что такое однонаправленный поток данных?

## Поток

```text
Родитель (владелец state)
   │  props: value
   ▼
Ребёнок ── emit('update', newValue) ──► Родитель меняет state ──► новый prop ──► Ребёнок
```

## Неправильно

```vue
<script setup lang="ts">
const props = defineProps<{ count: number; filters: Filters }>();

function inc() {
  props.count++;                 // ✗ предупреждение: prop is readonly
  props.filters.q = 'new';       // ✗ не перехватывается, но меняет состояние родителя «за его спиной»
}
</script>
```

## Правильные варианты

```ts
// 1. Событие — изменение решает родитель
const emit = defineEmits<{ 'update:count': [value: number] }>();
function inc() { emit('update:count', props.count + 1); }

// 2. defineModel — двусторонняя привязка как контракт (3.4+)
const count = defineModel<number>('count', { required: true });
function inc() { count.value++; }     // под капотом emit('update:count')

// 3. Начальное значение — локальная копия (дальше живёт независимо)
const props = defineProps<{ initialQuery: string }>();
const query = ref(props.initialQuery);

// 4. Преобразование — computed
const normalizedTitle = computed(() => props.title.trim().toUpperCase());

// 5. Объект для редактирования — копия, а сохранение через событие
const draft = ref(structuredClone(toRaw(props.filters)));
function apply() { emit('apply', draft.value); }
```

## Почему это важно

| Если мутировать props | Последствие |
| --- | --- |
| Значение перезаписывается при ререндере родителя | Изменения «пропадают» |
| Несколько детей меняют одни данные | Невозможно понять, кто изменил |
| Мутация вложенного объекта | Родитель меняется без его ведома, сложно отлаживать |
| Тесты компонентов | Поведение зависит от скрытых побочных эффектов |

## Аналогия со стором

Pinia следует тому же принципу: состояние меняется через **actions** стора (или явно), а компоненты читают его. Глобальный стор не отменяет однонаправленность — меняет данные владелец (стор), а не тот, кто их отображает.

## Частые ошибки

- `props.x = ...` или `v-model="props.x"` внутри ребёнка.
- Мутировать массив из props (`props.items.push(...)`).
- Копировать prop в `ref` и ожидать, что копия будет обновляться при изменении prop (для этого — `computed` или `watch`).
- Использовать `defineModel`, когда родитель не должен получать изменения — тогда нужна локальная копия.

## Что важно помнить

- Данные вниз через props, изменения вверх через события.
- Props readonly; вложенные мутации технически возможны, но запрещены по смыслу.
- Копия — для начального значения, `computed` — для преобразования, `emit`/`defineModel` — для изменения.

## Мини-шпаргалка

- `emit('update:x', v)` вместо `props.x = v`.
- `defineModel()` для двусторонней привязки.
- `ref(props.initial)` — локальная копия.
- `computed(() => f(props.x))`.
