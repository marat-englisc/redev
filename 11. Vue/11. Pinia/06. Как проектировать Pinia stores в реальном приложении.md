# Как проектировать Pinia stores в реальном приложении

> [!NOTE]
> Хороший стор хранит **только действительно общее** состояние, отвечает за **один домен** и имеет явный публичный API. Деление — по доменам/фичам (`auth`, `cart`, `catalog`, `notifications`, `settings`), а не по техническим признакам и не «один `global` на всё». Локальное UI-состояние (открыт ли дропдаун, значение поля до отправки, hover) остаётся в компонентах. Логика изменения — в **actions**, производные данные — в **getters** (без дублирования state), детали HTTP — в **API-слое**, который вызывают actions. Сторы могут использовать друг друга, но без циклов: если два стора зависят друг от друга — выделите общий. Для **серверных данных** (списки, детали сущностей) продумайте инвалидацию и кеширование или используйте специализированные инструменты (Pinia Colada, TanStack Query). Важно также: сброс пользовательских сторов при выходе, осторожность с хранением токенов (XSS), SSR-безопасность (никакого состояния на уровне модуля), тестируемость (сторы без жёстких зависимостей от роутера и DOM).

## Вопрос

Как проектировать сторы Pinia в реальном приложении?

## Что хранить

| В Pinia | В компоненте |
| --- | --- |
| Текущий пользователь, права | Открыт ли дропдаун/модалка |
| Корзина | Значения формы до отправки |
| Выбранная организация/проект | Hover, фокус, анимации |
| Уведомления, тосты | Данные только для пары родитель–ребёнок |
| Кеш справочников | Временные флаги загрузки одного виджета |

## Структура по доменам

```text
src/
├── api/
│   ├── http.ts            # fetch-обёртка: baseURL, заголовки, ошибки
│   ├── auth.api.ts
│   └── orders.api.ts
└── stores/
    ├── auth.ts
    ├── cart.ts
    ├── orders.ts
    └── notifications.ts
```

## Стор с API-слоем

```ts
export const useOrdersStore = defineStore('orders', () => {
  const list = ref<OrderSummary[]>([]);
  const loading = ref(false);
  const loadedAt = ref<number | null>(null);
  const notifications = useNotificationsStore();

  const isStale = computed(() => !loadedAt.value || Date.now() - loadedAt.value > 60_000);

  async function fetchList({ force = false } = {}) {
    if (!force && !isStale.value) return;          // простой кеш на минуту
    loading.value = true;
    try {
      list.value = await ordersApi.list();
      loadedAt.value = Date.now();
    } catch {
      notifications.error('Не удалось загрузить заказы');
    } finally {
      loading.value = false;
    }
  }

  async function cancel(id: string) {
    await ordersApi.cancel(id);
    const order = list.value.find((o) => o.id === id);
    if (order) order.status = 'CANCELLED';          // оптимистично обновить локальный кеш
  }

  function $reset() { list.value = []; loadedAt.value = null; }

  return { list, loading, isStale, fetchList, cancel, $reset };
});
```

## Выход пользователя — сброс сторов

```ts
export const useAuthStore = defineStore('auth', () => {
  const user = ref<User | null>(null);

  async function logout() {
    await authApi.logout();
    user.value = null;
    useCartStore().$reset();
    useOrdersStore().$reset();
  }

  return { user, logout };
});
```

## Зависимости между сторами

```text
checkout ──► cart, user        ✓
cart ──► catalog               ✓
cart ◄──► checkout             ✗ цикл — вынести общее в отдельный стор или composable
```

Вызывайте другие сторы **внутри** actions/getters (или в начале setup store), а не на уровне модуля.

## Токены

Не храните access/refresh-токены в Pinia с сохранением в localStorage без модели угроз: любой XSS прочитает их. Предпочтительно — httpOnly-cookie на стороне сервера; в сторе — данные пользователя и флаг входа.

## Серверное состояние

| Подход | Когда |
| --- | --- |
| Pinia + ручной кеш (`loadedAt`, `isStale`) | Немного сущностей, простая инвалидация |
| Pinia Colada / TanStack Query | Много запросов, кеш по ключам, повторы, фоновое обновление |
| `useFetch`/`useAsyncData` (Nuxt) | SSR-данные страниц |

## Частые ошибки

- Один `global` стор с разнородными данными.
- Дублирование: `items` в state и отдельно `count` в state вместо getter.
- Компоненты, вызывающие `fetch` в обход стора, при этом стор тоже грузит те же данные.
- Циклические зависимости сторов.
- Нет сброса при выходе — данные предыдущего пользователя видны следующему.

## Что важно помнить

- Стор — общий домен с явным API; локальное — в компонентах.
- Actions → API-слой; производные — getters.
- Продумать кеш серверных данных, сброс при выходе, безопасность токенов.

## Мини-шпаргалка

- Сторы по доменам, файл на стор.
- `api/*` — HTTP-детали.
- `$reset` при logout.
- `loadedAt` + `isStale` — простой кеш.
- Без циклов между сторами.
