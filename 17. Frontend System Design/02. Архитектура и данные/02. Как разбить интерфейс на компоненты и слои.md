# Как разбить интерфейс на компоненты и слои

> [!NOTE]
> На шаге Architecture интерфейс раскладывают на **компоненты** (что рисуется) и **слои** (кто за что отвечает): UI-компоненты отображают данные и сообщают о действиях, слой логики (хуки, контроллеры, store) управляет состоянием, слой данных (API-клиент + кеш) общается с сервером. Хорошая схема показывает, где живет каждое состояние, как идут данные и события и какие части можно загружать лениво.

## Вопрос

Как на system design интервью разбить интерфейс на компоненты? Какие слои выделить и как показать потоки данных?

## Шаг 1: дерево компонентов

Пример — лента новостей:

```text
<App>
 ├─ <Header>            поиск, аватар, уведомления
 ├─ <Feed>              контейнер: загрузка, пагинация, виртуализация
 │   ├─ <Composer>      создание поста (ленивый чанк)
 │   ├─ <PostCard> × N  презентационный
 │   │   ├─ <PostMedia>
 │   │   ├─ <PostActions>   лайк, комментарий, поделиться
 │   │   └─ <CommentsPreview>
 │   └─ <FeedLoader>    skeleton / «загрузить еще» / ошибка
 └─ <Sidebar>           рекомендации (не критично, грузится позже)
```

Обозначьте, какие компоненты **контейнеры** (получают данные), а какие **презентационные** (только props).

## Шаг 2: слои

```text
┌───────────── View ─────────────┐  компоненты, только отображение и события
│ PostCard, PostActions, Composer │
└──────────────┬──────────────────┘
               │ props / callbacks
┌──────────────▼──────────────────┐  состояние экрана и бизнес-логика
│ useFeed(), useLike(), store     │
└──────────────┬──────────────────┘
               │ вызовы
┌──────────────▼──────────────────┐  запросы, кеш, нормализация, realtime
│ API client, query cache, WS     │
└──────────────┬──────────────────┘
               ▼
          Сервер / BFF
```

Слои дают тестируемость и возможность заменить источник данных (REST → GraphQL) без переписывания UI.

## Шаг 3: потоки данных

Покажите два направления:

- **чтение**: API → кеш → хук → компонент;
- **действие**: клик «лайк» → хук → оптимистичное обновление кеша → запрос → подтверждение или откат.

```text
[PostActions] --onLike--> useLike() --optimistic--> cache --re-render--> [PostCard]
                               └──── POST /posts/:id/like ──▶ сервер
                                     ◀── 200 / ошибка → откат
```

## Шаг 4: что грузить лениво

| Сразу | Лениво |
| --- | --- |
| оболочка, первые посты, шапка | редактор поста, эмодзи-пикер |
| критичный CSS | модалки, просмотрщик фото |
| | sidebar, рекомендации, аналитика |

## Чек-лист архитектуры

- где живет каждое состояние: локально, в кеше запросов, в глобальном store, в URL;
- какие компоненты переиспользуемые (дизайн-система), а какие фичевые;
- границы ошибок (Error Boundary) и загрузки (Suspense) по смысловым блокам;
- что рендерится на сервере, а что только на клиенте;
- какие части изолированы в отдельные модули или пакеты при росте команды.

## Что важно помнить

- Рисуйте 5–10 крупных блоков, а не 40 мелких компонентов: детали — при углублении.
- Состояние держите как можно ближе к месту использования (colocation), глобально — только общее.
- Серверное состояние — в кеше запросов, а не дублируется в глобальном store.
- Явно назовите границы ленивой загрузки и ошибок — это быстро показывает зрелость решения.
- Связанные темы: [Container–Presentational](<../../06. React/08. Паттерны и подходы/03. Container–Presentational и Smart–Dumb компоненты.md>), [выбор state-менеджера](<../../06. React/15. Redux Toolkit/09. Redux Toolkit, Zustand, Context или TanStack Query - что выбрать.md>).

## Мини-шпаргалка

Дерево компонентов (контейнеры и презентационные) → слои View / логика / данные → потоки чтения и действий → ленивые части → границы ошибок и Suspense. 5–10 крупных блоков, состояние — ближе к месту использования.
