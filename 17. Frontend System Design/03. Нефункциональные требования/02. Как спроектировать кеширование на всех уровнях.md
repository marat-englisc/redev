# Как спроектировать кеширование на всех уровнях

> [!NOTE]
> Кеш во фронтенде многоуровневый: **HTTP-кеш браузера** (заголовки `Cache-Control`, `ETag`), **CDN** (статика и иногда HTML и API), **Service Worker** (офлайн и стратегии вроде stale-while-revalidate), **кеш запросов в памяти** (TanStack Query, RTK Query, Apollo) и **постоянное хранилище** (IndexedDB, `localStorage`). На интервью важно не перечислить уровни, а объяснить, **что** кешировать, **сколько** и **как инвалидировать** после изменений.

## Вопрос

Как спроектировать кеширование во фронтенд-приложении? Какие уровни кеша есть и как решать проблему устаревших данных?

## Уровни

```text
Компонент → кеш запросов (память) → Service Worker → HTTP-кеш браузера → CDN → сервер / BFF
```

| Уровень | Что кешировать | Инвалидация |
| --- | --- | --- |
| HTTP-кеш | статика, публичные ответы API | `max-age`, `ETag`/`Last-Modified`, новые имена файлов |
| CDN | JS/CSS/изображения, публичные страницы | TTL, purge, `s-maxage`, `stale-while-revalidate` |
| Service Worker | оболочка приложения, медиа, офлайн-данные | версия кеша при деплое |
| Кеш запросов | серверные данные экрана | `staleTime`, `invalidateQueries`, теги, realtime |
| IndexedDB | данные для офлайна, большие списки | синхронизация по версиям или времени |

## Статика

```http
# app.3f9a1c.js — хеш в имени меняется при каждом изменении
Cache-Control: public, max-age=31536000, immutable

# index.html — всегда проверять новую версию
Cache-Control: no-cache
```

Так пользователи мгновенно получают новые версии без «вечного» старого HTML.

## Данные API

```typescript
useQuery({
  queryKey: ["feed", { filter }],
  queryFn: fetchFeed,
  staleTime: 30_000,          // 30 с без повторного запроса
  gcTime: 5 * 60_000,         // неиспользуемые данные живут 5 минут
  refetchOnWindowFocus: true, // обновить при возврате на вкладку
});
```

Паттерн **stale-while-revalidate**: сразу показать кешированные данные, параллельно запросить свежие и тихо обновить.

## Инвалидация

| Событие | Действие |
| --- | --- |
| пользователь создал или изменил сущность | `invalidateQueries` / `invalidatesTags` или прямое обновление кеша ответом мутации |
| событие с сервера (WebSocket/SSE) | точечное обновление по id или инвалидация ключа |
| выход пользователя | очистить весь клиентский кеш и персональные данные |
| новый деплой | новые хеши файлов, новая версия кеша Service Worker |

## Персональные данные

- `Cache-Control: private` или `no-store` для ответов с персональными данными — их нельзя кешировать на CDN;
- ключ кеша на клиенте должен учитывать пользователя или очищаться при смене аккаунта;
- не держите чувствительные данные в `localStorage`, если есть риск XSS.

## Что важно помнить

- Для каждого типа данных назовите **срок свежести** и **способ инвалидации** — это главный вопрос.
- Дедупликация: несколько компонентов с одним `queryKey` делают один запрос.
- Предзагружайте вероятные данные (`prefetchQuery` при наведении) — мгновенная навигация.
- Кеш — источник ошибок: устаревшие данные, утечка чужих данных, неограниченный рост памяти. Ограничивайте размер и время жизни.

## Мини-шпаргалка

Уровни: кеш запросов → Service Worker → HTTP-кеш → CDN. Статика — хеш в имени + `immutable`, HTML — `no-cache`. Данные — `staleTime`, stale-while-revalidate, инвалидация после мутаций и по событиям. Персональное — `private`, очистка при выходе.
