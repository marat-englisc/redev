# Как обеспечить наблюдаемость: логи, метрики и feature flags

> [!NOTE]
> **Наблюдаемость (observability)** фронтенда — возможность узнать, что происходит у реальных пользователей: какие ошибки возникают (**error tracking**: Sentry), насколько быстро работает приложение (**RUM**: Core Web Vitals с реальных устройств), как используются функции (**продуктовая аналитика**) и как связаны действия пользователя с запросами к бэкенду (**трассировка**). Вместе с **feature flags** и постепенной выкаткой это позволяет безопасно выпускать изменения и быстро находить проблемы.

## Вопрос

Как обеспечить наблюдаемость фронтенд-приложения? Что собирать, как связать ошибки фронтенда с бэкендом и зачем нужны feature flags?

## Что собирать

| Тип | Примеры | Инструменты |
| --- | --- | --- |
| Ошибки | исключения JS, отклоненные промисы, ошибки Error Boundary, сбои загрузки чанков | Sentry, Bugsnag |
| Производительность (RUM) | LCP, INP, CLS, TTFB, долгие задачи | `web-vitals`, Sentry Performance, Datadog RUM |
| Сеть | ошибки и время ответов API | интерцептор API-клиента |
| Продукт | клики, конверсии, воронки | Amplitude, Mixpanel, PostHog |
| Сессии | запись сессии для воспроизведения бага | Sentry Replay, LogRocket |

## Ошибки

```typescript
import * as Sentry from "@sentry/react";

Sentry.init({
  dsn: import.meta.env.VITE_SENTRY_DSN,
  release: import.meta.env.VITE_RELEASE,     // связать с версией и source maps
  environment: import.meta.env.MODE,
  tracesSampleRate: 0.1,                     // трассировать 10% сессий
});

window.addEventListener("unhandledrejection", (e) => Sentry.captureException(e.reason));
```

- source maps загружаются в Sentry при сборке, а не раздаются публично;
- контекст: id пользователя (без персональных данных), маршрут, версия, браузер;
- группировка и алерты на рост ошибок после релиза.

## RUM-метрики

```typescript
import { onCLS, onINP, onLCP } from "web-vitals";

function send(metric: { name: string; value: number; id: string }) {
  navigator.sendBeacon("/api/rum", JSON.stringify({ ...metric, page: location.pathname }));
}

onLCP(send);
onINP(send);
onCLS(send);
```

Смотрят на перцентили (p75), а не на среднее: важен опыт медленных пользователей.

## Связь с бэкендом

- `traceparent` (W3C Trace Context) в заголовках запросов — один trace от клика до базы данных;
- `requestId` в ответах API показывают в сообщении об ошибке («Код ошибки: a1b2c3») — поддержка найдет запрос в логах.

## Feature flags и выкатка

```tsx
const showNewCheckout = useFlag("new-checkout");     // LaunchDarkly, Unleash, GrowthBook
return showNewCheckout ? <NewCheckout /> : <OldCheckout />;
```

- постепенная выкатка: 1% → 10% → 50% → 100% с наблюдением за ошибками и метриками;
- kill switch: выключить сломанную функцию без деплоя;
- A/B-тесты: сравнить варианты по продуктовым метрикам;
- флаги удаляют после полной выкатки, иначе код обрастает ветками.

## Что важно помнить

- Без мониторинга вы узнаете о проблемах от пользователей — назовите на интервью хотя бы ошибки и RUM.
- Ограничивайте объем: сэмплирование трассировок и сессий, батчинг событий, `sendBeacon` при уходе со страницы.
- Персональные данные не отправляются в логи и записи сессий — маскирование полей ввода.
- Ошибки загрузки чанков после деплоя (`ChunkLoadError`) — частая проблема: перезагрузка страницы или хранение старых версий файлов.

## Мини-шпаргалка

Ошибки — Sentry + source maps + release. Производительность — RUM через `web-vitals`, смотреть p75. Сеть — время и ошибки API. Связь с бэкендом — `traceparent`, `requestId`. Feature flags — постепенная выкатка, kill switch, A/B. Сэмплирование и без персональных данных.
