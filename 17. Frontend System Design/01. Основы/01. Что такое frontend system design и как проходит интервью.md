# Что такое frontend system design и как проходит интервью

> [!NOTE]
> **Frontend system design** — проектирование клиентской части продукта целиком: из каких компонентов состоит интерфейс, где и как хранятся данные, как клиент общается с сервером, как обеспечить скорость, надежность, доступность и безопасность. На интервью вам дают открытую задачу — «спроектируй ленту новостей», «автокомплит», «чат» — и за 45–60 минут оценивают не готовый код, а **ход мысли**: умение задать вопросы, выбрать архитектуру, обосновать компромиссы и углубиться в важные детали.

## Вопрос

Что такое frontend system design? Чем он отличается от backend system design, как проходит такое интервью и что на нем оценивают?

## Основная идея

Backend system design фокусируется на серверах, базах, шардировании и очередях. Frontend system design — на том, что происходит **в браузере и на границе с API**:

| Backend system design | Frontend system design |
| --- | --- |
| масштабирование серверов, балансировка | архитектура рендеринга: CSR, SSR, SSG, streaming |
| схемы БД, шардирование, репликация | модель данных и state на клиенте, кеш |
| очереди, микросервисы | компоненты, модули, дизайн-система |
| RPS и пропускная способность | Core Web Vitals, размер бандла, плавность UI |
| согласованность данных | оптимистичные обновления, офлайн, realtime |

Обычно API считается заданным или проектируется только в части контракта клиент — сервер.

## Два типа задач

| Тип | Примеры | Фокус |
| --- | --- | --- |
| **Приложение** | лента новостей, чат, маркетплейс, Google Docs, видеоплатформа | архитектура, данные, API, производительность |
| **Компонент / UI-виджет** | автокомплит, карусель, data table, date picker, модальное окно, загрузчик файлов | API компонента (props), состояния, доступность, расширяемость |

## Как проходит интервью

```text
0–5 мин    уточнение требований и ограничений
5–15 мин   общая архитектура: схема компонентов и потоков данных
15–25 мин  модель данных и API (запросы, форматы, пагинация, realtime)
25–45 мин  углубление: производительность, кеш, ошибки, a11y, безопасность
45–60 мин  вопросы интервьюера, альтернативы, что улучшить дальше
```

Рисуют обычно на доске (Excalidraw, Miro): блоки компонентов, стрелки запросов, структуры данных.

## Что оценивают

- **Сбор требований**: задаете ли вопросы, а не начинаете рисовать сразу.
- **Структура ответа**: двигаетесь от общего к частному по понятному плану.
- **Компромиссы (trade-offs)**: объясняете, почему SSR, а не CSR, cursor, а не offset, WebSocket, а не polling.
- **Глубина**: знаете детали — виртуализацию, debounce, кеш, гонки запросов, a11y.
- **Продуктовое мышление**: думаете о пользователе — состояния загрузки, ошибки, медленная сеть, мобильные.
- **Коммуникация**: проговариваете решения, принимаете подсказки.

## Типичные ошибки

- Сразу писать код компонентов вместо архитектуры.
- Не уточнять масштаб и приоритеты — проектировать «всё для всех».
- Называть технологии без обоснования: «возьму Redux, потому что все берут».
- Забыть про ошибки, пустые состояния, загрузку и доступность.
- Уйти глубоко в одну деталь и не успеть показать общую картину.

## Что важно помнить

- Правильного единственного ответа нет — оценивают рассуждения и обоснованные компромиссы.
- Используйте фреймворк ответа (например, RADIO), чтобы не потеряться во времени.
- На уровне middle достаточно уверенно пройти все этапы и углубиться в 2–3 темы; от senior ждут больше масштаба и компромиссов.
- Тренируйтесь вслух на типовых задачах: лента, автокомплит, чат, каталог с фильтрами, редактор.

## Мини-шпаргалка

Frontend system design — архитектура клиента: компоненты, данные, API, производительность, надежность, a11y, безопасность. Задачи: приложение или UI-компонент. Ход интервью: требования → архитектура → данные и API → углубление. Оценивают вопросы, структуру, компромиссы и глубину.
