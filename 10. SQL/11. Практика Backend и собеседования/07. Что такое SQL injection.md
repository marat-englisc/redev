# Что такое SQL injection

> [!NOTE]
> **SQL-инъекция** — уязвимость, при которой пользовательский ввод попадает в текст SQL-запроса и **меняет его структуру**: `' OR '1'='1` обходит проверку пароля, `'; DROP TABLE users; --` выполняет произвольную команду, `UNION SELECT` вытаскивает чужие данные. Причина всегда одна — **склейка строк** (конкатенация, шаблонные строки) с данными. Защита — **параметризованные запросы** (`$1`, `?`, prepared statements): запрос и данные передаются базе отдельно, и данные никогда не интерпретируются как SQL. Параметрами нельзя передать **идентификаторы** (имена столбцов, направление сортировки) — их берут только из **белого списка**. Дополнительные слои: ORM/query builder (с осторожностью к `raw`-методам), минимальные права роли приложения, отсутствие подробных SQL-ошибок в ответах API.

## Вопрос

Что такое SQL-инъекция и как от неё защититься?

## Уязвимый код

```ts
// ✗ склейка строк
const sql = `SELECT * FROM users WHERE email = '${email}' AND password_hash = '${hash}'`;
```

```text
email = admin@x.com' --
→ SELECT * FROM users WHERE email = 'admin@x.com' --' AND password_hash = '...'
  всё после -- стало комментарием → вход без пароля
```

```text
id = 1 UNION SELECT id, email, password_hash FROM users
→ SELECT id, title, body FROM posts WHERE id = 1 UNION SELECT id, email, password_hash FROM users
```

## Защита: параметры

```ts
// node-postgres
await db.query("SELECT * FROM users WHERE email = $1", [email]);

// mysql2
await conn.execute("SELECT * FROM users WHERE email = ?", [email]);

// Prisma — tagged template безопасен
await prisma.$queryRaw`SELECT * FROM users WHERE email = ${email}`;

// ✗ а это — нет
await prisma.$queryRawUnsafe(`SELECT * FROM users WHERE email = '${email}'`);
```

Значение передаётся отдельно от текста запроса, поэтому `admin@x.com' --` — просто строка, которой нет в таблице.

## Динамические идентификаторы

```ts
// сортировка из query-параметра: параметром передать нельзя
const SORTABLE = { created: "created_at", price: "price", title: "title" } as const;
const column = SORTABLE[req.query.sort as keyof typeof SORTABLE] ?? "created_at";
const direction = req.query.dir === "asc" ? "ASC" : "DESC";

await db.query(`SELECT * FROM products ORDER BY ${column} ${direction} LIMIT $1`, [limit]);
```

Если всё же нужно экранировать идентификатор — `pg-format` `%I` или `quote_ident()` в PostgreSQL, но белый список надёжнее.

## Списки значений

```ts
// ✗ `WHERE id IN (${ids.join(",")})`
// ✓
await db.query("SELECT * FROM products WHERE id = ANY($1::bigint[])", [ids]);
```

## Инъекции внутри базы

```sql
-- ✗ динамический SQL в PL/pgSQL
EXECUTE 'SELECT * FROM ' || tbl || ' WHERE name = ''' || val || '''';

-- ✓
EXECUTE format('SELECT * FROM %I WHERE name = $1', tbl) USING val;
```

## Эшелонированная защита

| Слой | Что даёт |
| --- | --- |
| Параметризованные запросы | Устраняют причину |
| Белые списки идентификаторов | Закрывают ORDER BY, имена таблиц |
| Роль приложения с минимальными правами | Нет `DROP`, нет доступа к чужим схемам |
| Скрытие ошибок | Атакующий не видит структуру запроса |
| Валидация входных данных (zod, class-validator) | Отсекает мусор раньше, но **не заменяет** параметры |
| Линтеры, SAST, code review | Ловят `queryRawUnsafe`, конкатенацию |

## Частые ошибки

- Экранировать кавычки вручную вместо параметров.
- `$queryRawUnsafe`, `sequelize.literal`, `knex.raw` с пользовательскими данными.
- Подставлять в `ORDER BY` значение из запроса без белого списка.
- Думать, что ORM полностью защищает: raw-методы и динамические фрагменты — та же склейка.

## Что важно помнить

- Причина инъекции — данные внутри текста SQL.
- Параметры для значений, белый список для идентификаторов.
- Минимальные права роли ограничивают ущерб.

## Мини-шпаргалка

- `query("... WHERE x = $1", [x])`.
- `= ANY($1::type[])` для списков.
- `ORDER BY` — только из белого списка.
- `format('%I', ...)` + `USING` в PL/pgSQL.
