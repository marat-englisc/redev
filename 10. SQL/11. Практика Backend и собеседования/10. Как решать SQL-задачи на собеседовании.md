# Как решать SQL-задачи на собеседовании

> [!NOTE]
> Успешное решение SQL-задачи — это процесс, а не угадывание синтаксиса: **уточнить** требования (что вернуть, как обрабатывать `NULL`, равные значения, пустые группы, временные зоны), **описать данные** — какие таблицы и связи, какая кардинальность; определить **уровень детализации результата** («одна строка на пользователя» или «на заказ»); **собрать запрос по шагам**, лучше через CTE; **проверить** на граничных случаях (нет заказов, дубли, `NULL`, ничья) и затем обсудить **производительность** — какие индексы нужны. Большинство задач сводятся к нескольким шаблонам: агрегация с `LEFT JOIN`, anti join, top-N per group, сравнение с предыдущим периодом, накопительные суммы, gaps and islands, дубли, N-е значение.

## Вопрос

Как подходить к решению SQL-задач на собеседовании?

## Алгоритм

```text
1. Уточнить: что на выходе? одна строка на что? NULL? ничьи? пустые группы? период и часовой пояс?
2. Схема: таблицы, ключи, 1:N или M:N?
3. Гранулярность: GROUP BY по чему?
4. Шаги: CTE «отфильтровать → агрегировать → ранжировать → отобрать»
5. Проверка: пустые группы, дубли, NULL, равные значения
6. Производительность: индексы, объём данных, альтернативы
```

## Шаблоны задач

| Формулировка | Шаблон |
| --- | --- |
| «Для каждого пользователя посчитать… включая тех, у кого ничего нет» | `LEFT JOIN` + `count(r.id)` + `COALESCE` |
| «Кто никогда не…» | `NOT EXISTS` |
| «Топ-3 в каждой категории» | `row_number() OVER (PARTITION BY ...)` |
| «Вторая по величине зарплата» | `dense_rank() = 2` |
| «Рост к прошлому месяцу» | `date_trunc` + `lag` |
| «Накопительная сумма / баланс» | `sum() OVER (ORDER BY ...)` |
| «Самая длинная серия дней подряд» | gaps and islands |
| «Найти дубликаты» | `GROUP BY ... HAVING count(*) > 1` |
| «Купили во всех категориях» | `HAVING count(DISTINCT ...) = (SELECT count(*) ...)` |
| «Доля от общего» | `x / sum(x) OVER ()` |

## Пример: выручка и место в рейтинге по месяцам

**Задача:** для каждого месяца 2026 года вывести трёх покупателей с наибольшей суммой оплаченных заказов, их сумму и долю от выручки месяца.

```sql
WITH paid AS (
  SELECT user_id, date_trunc('month', created_at) AS month, total
  FROM orders
  WHERE status = 'paid'
    AND created_at >= '2026-01-01' AND created_at < '2027-01-01'
),
monthly AS (
  SELECT month, user_id, sum(total) AS revenue
  FROM paid
  GROUP BY month, user_id
),
ranked AS (
  SELECT month, user_id, revenue,
         round(revenue / sum(revenue) OVER (PARTITION BY month) * 100, 1) AS share_pct,
         row_number() OVER (PARTITION BY month ORDER BY revenue DESC, user_id) AS rn
  FROM monthly
)
SELECT r.month, u.email, r.revenue, r.share_pct
FROM ranked r
JOIN users u ON u.id = r.user_id
WHERE r.rn <= 3
ORDER BY r.month, r.rn;
```

Что проговорить:

- Полуоткрытый интервал по `created_at` — индекс работает, ничего не теряется.
- Сначала агрегация, потом окно — доля считается от суммы по месяцу.
- `row_number` с tie-breaker `user_id`; если нужны все делящие третье место — `rank`.
- Индекс: `orders (status, created_at)` или частичный `(created_at) WHERE status = 'paid'`.

## Пример: пользователи без заказов за последние 30 дней

```sql
SELECT u.id, u.email
FROM users u
WHERE NOT EXISTS (
  SELECT 1 FROM orders o
  WHERE o.user_id = u.id
    AND o.created_at >= now() - interval '30 days'
);
```

Почему не `NOT IN` — из-за `NULL`; почему не `LEFT JOIN ... IS NULL` — можно, но `NOT EXISTS` нагляднее.

## Проверка решения

```text
- пользователь без заказов → попадает ли он туда, куда должен?
- два одинаковых значения → какое поведение ожидается?
- NULL в ключевых столбцах → не теряются ли строки?
- пустой месяц → нужна ли строка с нулём (generate_series)?
- заказ в 23:30 по Москве → в какой день он попадёт?
```

## Коммуникация

- Думайте вслух: интервьюер оценивает рассуждение, а не только итог.
- Начните с простого рабочего варианта, затем улучшайте.
- Если не помните синтаксис функции — опишите идею («нужна функция, которая возьмёт значение из предыдущей строки — `lag`»).
- Называйте допущения явно: «считаю, что `status = 'paid'` означает оплаченный заказ».

## Частые ошибки

- Сразу писать запрос, не уточнив гранулярность и граничные случаи.
- Агрегировать после JOIN нескольких one-to-many таблиц.
- Забыть про пользователей без данных (`INNER` вместо `LEFT`).
- Использовать `LIMIT` для top-N в каждой группе.
- Не упомянуть индексы и объём данных.

## Что важно помнить

- Уточнить → схема → гранулярность → шаги → проверка → производительность.
- Большинство задач — комбинация нескольких шаблонов.
- CTE делают решение читаемым и удобным для обсуждения.

## Мини-шпаргалка

- `LEFT JOIN` + `count(r.id)`.
- `NOT EXISTS`.
- `row_number() OVER (PARTITION BY ... ORDER BY ..., id)`.
- `lag`, `sum() OVER`, `dense_rank`.
- `generate_series` для пустых периодов.
