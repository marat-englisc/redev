# Что такое реплики, партиционирование и шардинг

> [!NOTE]
> Три разных способа масштабировать базу. **Реплики (read replicas)** — копии основного сервера (primary), которые получают поток WAL и обслуживают **чтение**; они повышают отказоустойчивость (failover) и разгружают primary, но при асинхронной репликации отстают (replication lag) — пользователь может не увидеть только что записанное. **Партиционирование** — разбиение **одной** большой таблицы на части внутри одного сервера (по диапазону дат, списку значений, хешу): запросы читают только нужные партиции (partition pruning), а старые данные удаляются мгновенно через `DROP`/`DETACH PARTITION`. **Шардинг** — распределение данных по **разным серверам** по ключу (tenant_id, user_id): масштабирует запись и объём, но усложняет всё — межшардовые JOIN и транзакции, ребалансировку, уникальность. Порядок обычно такой: индексы и оптимизация запросов → вертикальное масштабирование → реплики → партиционирование → и только потом шардинг (Citus, Vitess, приложенческий).

## Вопрос

Что такое реплики, партиционирование и шардинг и когда их применять?

## Реплики

```text
           запись
App ───────────────► Primary ──WAL──► Replica 1  ◄── чтение (отчёты, списки)
     ◄───── чтение ─────────────────► Replica 2
```

```ts
// разделение чтения и записи
await primary.query("INSERT INTO comments ...");
const feed = await replica.query("SELECT ... FROM posts ORDER BY created_at DESC LIMIT 20");
```

| Проблема | Решение |
| --- | --- |
| Read-your-writes: после записи читаем с реплики старые данные | Читать с primary сразу после записи, «липкость» к primary на N секунд |
| Lag растёт под нагрузкой | Мониторинг `pg_stat_replication`, синхронная реплика для критичного |
| Долгие запросы на реплике конфликтуют с репликацией | `hot_standby_feedback`, отдельная реплика для аналитики |

## Партиционирование

```sql
CREATE TABLE events (
  id         bigint GENERATED ALWAYS AS IDENTITY,
  user_id    bigint NOT NULL,
  type       text   NOT NULL,
  created_at timestamptz NOT NULL,
  PRIMARY KEY (id, created_at)          -- ключ партиционирования входит в PK/UNIQUE
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_10 PARTITION OF events
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
CREATE TABLE events_2026_11 PARTITION OF events
  FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

-- читает только events_2026_10
SELECT count(*) FROM events WHERE created_at >= '2026-10-10' AND created_at < '2026-10-11';

-- удаление старых данных — мгновенно, без DELETE и bloat
ALTER TABLE events DETACH PARTITION events_2025_10 CONCURRENTLY;
DROP TABLE events_2025_10;
```

| Вид | Ключ | Пример |
| --- | --- | --- |
| `RANGE` | Диапазон | По месяцам для логов и событий |
| `LIST` | Список значений | По региону или стране |
| `HASH` | Хеш | Равномерно по `user_id` |

Партиции создают заранее (cron, расширение `pg_partman`). Запросы без условия по ключу партиционирования сканируют все партиции — выигрыша не будет.

## Шардинг

```text
user_id % 4 = 0 → shard A        user_id % 4 = 2 → shard C
user_id % 4 = 1 → shard B        user_id % 4 = 3 → shard D
```

| Плюсы | Минусы |
| --- | --- |
| Масштабирование записи и объёма | JOIN и транзакции между шардами сложны |
| Изоляция арендаторов | Ребалансировка при добавлении шардов |
| | Глобальная уникальность и последовательности |
| | Отчёты по всем данным — scatter-gather |

Ключ шардирования выбирают так, чтобы почти все запросы шли в один шард (например, `tenant_id` в B2B SaaS). Готовые решения: Citus (расширение PostgreSQL), Vitess (MySQL), распределённые SQL-базы (CockroachDB, YugabyteDB).

## Сравнение

| | Реплики | Партиционирование | Шардинг |
| --- | --- | --- | --- |
| Где данные | Полные копии на нескольких серверах | Одна таблица → части на одном сервере | Разные данные на разных серверах |
| Масштабирует | Чтение, отказоустойчивость | Управление большими таблицами | Запись и объём |
| Сложность для приложения | Низкая (lag) | Низкая | Высокая |

## Частые ошибки

- Шардинг до того, как исчерпаны индексы, оптимизация и вертикальное масштабирование.
- Читать с реплики сразу после записи.
- Партиционировать таблицу, запросы к которой не фильтруют по ключу партиций.
- Не создавать будущие партиции — вставка падает с ошибкой.

## Что важно помнить

- Реплики — для чтения и отказоустойчивости, учитывайте lag.
- Партиционирование — для управления огромными таблицами в одном сервере.
- Шардинг — последний шаг, когда один сервер не справляется с записью и объёмом.

## Мини-шпаргалка

- `pg_stat_replication` — lag.
- `PARTITION BY RANGE | LIST | HASH`.
- `DETACH PARTITION CONCURRENTLY` + `DROP`.
- `pg_partman` — автоматизация.
- Шардинг: Citus, Vitess, ключ = `tenant_id`.
