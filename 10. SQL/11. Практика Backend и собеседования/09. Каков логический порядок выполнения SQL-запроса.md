# Каков логический порядок выполнения SQL-запроса

> [!NOTE]
> SQL-запрос пишется в порядке `SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT`, но **логически обрабатывается** иначе: `FROM`/`JOIN` (собрать строки) → `WHERE` (отфильтровать строки) → `GROUP BY` (сгруппировать) → агрегаты → `HAVING` (отфильтровать группы) → оконные функции → `SELECT` (вычислить выражения и алиасы) → `DISTINCT` → `ORDER BY` → `LIMIT`/`OFFSET`. Этот порядок объясняет многие ошибки: почему алиас из `SELECT` недоступен в `WHERE`, почему агрегат нельзя писать в `WHERE`, почему оконную функцию фильтруют во внешнем запросе, а `ORDER BY` видит алиасы. **Физический** порядок, выбранный планировщиком, может быть другим (фильтры проталкиваются внутрь JOIN, `LIMIT` останавливает чтение раньше), но результат обязан совпадать с логическим.

## Вопрос

В каком порядке логически выполняются части SQL-запроса и почему это важно?

## Порядок

```sql
SELECT   u.country, count(*) AS orders,                 -- 7. SELECT
         rank() OVER (ORDER BY count(*) DESC) AS place   -- 6. окна
FROM     users u                                         -- 1. FROM
JOIN     orders o ON o.user_id = u.id                    -- 1. JOIN
WHERE    o.status = 'paid'                               -- 2. WHERE
GROUP BY u.country                                       -- 3. GROUP BY (4. агрегаты)
HAVING   count(*) > 10                                   -- 5. HAVING
ORDER BY orders DESC                                     -- 9. ORDER BY (8. DISTINCT)
LIMIT    5;                                              -- 10. LIMIT
```

| Шаг | Часть | Что доступно |
| --- | --- | --- |
| 1 | `FROM`, `JOIN`, `ON` | Столбцы таблиц |
| 2 | `WHERE` | Столбцы строк, без агрегатов и алиасов `SELECT` |
| 3–4 | `GROUP BY`, агрегаты | Ключи группировки |
| 5 | `HAVING` | Ключи и агрегаты |
| 6 | Оконные функции | Результат после `HAVING` |
| 7 | `SELECT` | Здесь появляются алиасы |
| 8 | `DISTINCT` | Значения из `SELECT` |
| 9 | `ORDER BY` | Алиасы `SELECT` и исходные столбцы |
| 10 | `LIMIT`, `OFFSET` | Готовый отсортированный набор |

## Что из этого следует

```sql
-- ✗ алиас ещё не существует
SELECT price * qty AS total FROM order_items WHERE total > 1000;
-- ✓
SELECT price * qty AS total FROM order_items WHERE price * qty > 1000;

-- ✗ агрегат в WHERE
SELECT user_id FROM orders WHERE count(*) > 5 GROUP BY user_id;
-- ✓
SELECT user_id FROM orders GROUP BY user_id HAVING count(*) > 5;

-- ✗ окно в WHERE
SELECT * FROM orders WHERE row_number() OVER (...) = 1;
-- ✓ подзапрос
SELECT * FROM (SELECT o.*, row_number() OVER (...) AS rn FROM orders o) t WHERE rn = 1;

-- ✓ алиас в ORDER BY допустим
SELECT price * qty AS total FROM order_items ORDER BY total DESC;
```

## LEFT JOIN и WHERE

Так как `WHERE` выполняется после `JOIN`, условие на правую таблицу в `WHERE` отбрасывает строки с `NULL`, превращая `LEFT JOIN` в `INNER` — см. [INNER и LEFT JOIN](<../03. JOIN и связи таблиц/03. Чем отличаются INNER JOIN и LEFT JOIN.md>).

## Логический и физический порядок

```sql
EXPLAIN SELECT * FROM orders o JOIN users u ON u.id = o.user_id WHERE o.status = 'new' LIMIT 10;
```

Планировщик применит фильтр `status = 'new'` при чтении `orders` (до соединения) и остановится после 10 строк — это оптимизация, не меняющая результат.

## Частые ошибки

- Алиас `SELECT` в `WHERE`/`HAVING`.
- Агрегаты и оконные функции в `WHERE`.
- Ожидать, что `LIMIT` применится до `ORDER BY`.
- `DISTINCT` + `ORDER BY` по столбцу, которого нет в выборке.

## Что важно помнить

- `FROM → WHERE → GROUP BY → HAVING → окна → SELECT → DISTINCT → ORDER BY → LIMIT`.
- Алиасы рождаются в `SELECT` и видны только дальше.
- Физический план может отличаться, результат — нет.

## Мини-шпаргалка

- Фильтр строк — `WHERE`, групп — `HAVING`, окон — внешний запрос.
- Алиас — в `ORDER BY` да, в `WHERE` нет.
- Повторить выражение или вынести в CTE/`LATERAL`.
