# Как работают EXISTS и IN и что выбрать

> [!NOTE]
> `EXISTS (подзапрос)` возвращает `true`, если подзапрос вернул **хотя бы одну строку**; содержимое `SELECT` внутри не важно (пишут `SELECT 1`), и выполнение может остановиться на первой найденной строке. `x IN (подзапрос | список)` проверяет, входит ли значение в набор. Для положительной проверки современный PostgreSQL обычно строит одинаковый план (semi join) для обеих форм, поэтому выбирают по смыслу: `IN` — короткий список значений или простой подзапрос по `NOT NULL` столбцу, `EXISTS` — сложное условие связи с несколькими столбцами. Для **отрицания** используйте `NOT EXISTS`: `NOT IN` при наличии `NULL` в подзапросе всегда даёт пустой результат.

## Вопрос

Как работают `EXISTS` и `IN`, чем они отличаются и что выбрать?

## EXISTS

```sql
-- пользователи с хотя бы одним оплаченным заказом за 30 дней
SELECT u.id, u.email
FROM users u
WHERE EXISTS (
  SELECT 1
  FROM orders o
  WHERE o.user_id = u.id
    AND o.status = 'paid'
    AND o.created_at >= now() - interval '30 days'
);
```

## IN

```sql
-- список констант
SELECT * FROM orders WHERE status IN ('paid', 'shipped');

-- подзапрос
SELECT * FROM users
WHERE id IN (SELECT user_id FROM orders WHERE status = 'paid');

-- массив из приложения (PostgreSQL)
SELECT * FROM products WHERE id = ANY($1::bigint[]);
```

`= ANY($1)` удобнее, чем генерировать `IN ($1, $2, …, $500)`: один prepared statement на любой размер списка.

## NOT IN и NULL

```sql
-- orders.user_id может быть NULL
SELECT * FROM users WHERE id NOT IN (SELECT user_id FROM orders);   -- ✗ пусто, если есть NULL

SELECT * FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);  -- ✓
```

Логика: `5 NOT IN (1, NULL)` → `5 <> 1 AND 5 <> NULL` → `true AND NULL` → `NULL` → строка отброшена.

## Сравнение

| | `EXISTS` | `IN` |
| --- | --- | --- |
| Проверяет | Наличие строк | Вхождение значения |
| Несколько столбцов связи | Естественно | Через кортеж `(a, b) IN (SELECT a, b ...)` |
| Список констант | Неудобно | Идеально |
| Отрицание и `NULL` | `NOT EXISTS` — корректно | `NOT IN` — ловушка |
| Производительность в PostgreSQL | Semi/Anti join | Semi join; `NOT IN` хуже оптимизируется |

## EXISTS вместо JOIN + DISTINCT

```sql
-- ✗ дубли и лишняя работа
SELECT DISTINCT u.* FROM users u JOIN orders o ON o.user_id = u.id;

-- ✓
SELECT u.* FROM users u WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
```

## Индексы

Обе формы эффективны, когда есть индекс по столбцу связи в подзапросе (`orders (user_id)` или `orders (user_id, status)`).

## Частые ошибки

- `NOT IN` по nullable столбцу.
- `SELECT *` внутри `EXISTS` в надежде что-то «вернуть» — значения не используются.
- Огромный `IN (...)` из тысяч литералов, сгенерированный в коде.
- `count(*) > 0` в подзапросе вместо `EXISTS` — считает все строки вместо остановки на первой.

## Что важно помнить

- `EXISTS` — «есть ли хотя бы одна строка».
- `IN` — «входит ли значение в набор».
- Для отрицания — только `NOT EXISTS`.

## Мини-шпаргалка

- `WHERE EXISTS (SELECT 1 FROM ... WHERE link)`.
- `WHERE x IN ('a', 'b')`.
- `WHERE id = ANY($1::bigint[])`.
- `NOT EXISTS` вместо `NOT IN`.
