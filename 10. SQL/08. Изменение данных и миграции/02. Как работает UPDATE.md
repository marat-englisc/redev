# Как работает UPDATE

> [!NOTE]
> `UPDATE таблица SET столбец = выражение WHERE условие` изменяет строки, подходящие под условие; **без `WHERE` будут изменены все строки**. В `SET` можно ссылаться на текущие значения (`stock = stock - 1`) — такое **атомарное** изменение безопаснее схемы «прочитать в приложении → посчитать → записать», которая теряет обновления при конкурентных запросах. PostgreSQL поддерживает `UPDATE … FROM` (обновление с использованием другой таблицы) и `RETURNING`. Из-за MVCC каждое обновление создаёт **новую версию строки**, поэтому массовый `UPDATE` миллионов строк порождает много «мёртвых» версий и долго держит блокировки — его делают пачками. Количество изменённых строк (`rowCount`) проверяют в приложении: 0 часто означает «не найдено» или «конфликт версий».

## Вопрос

Как работает `UPDATE` и как обновлять данные безопасно?

## Базовое обновление

```sql
UPDATE users
SET name = 'Anna Ivanova', updated_at = now()
WHERE id = 1
RETURNING id, name, updated_at;
```

## Атомарное изменение

```sql
-- ✗ гонка: два запроса прочитали stock = 5, оба записали 4
-- const { stock } = SELECT stock ...; UPDATE products SET stock = $1 (stock - 1)

-- ✓ база вычисляет новое значение сама и не даёт уйти в минус
UPDATE products
SET stock = stock - 1
WHERE id = $1 AND stock > 0
RETURNING stock;
```

Если `RETURNING` вернул 0 строк — товара нет в наличии. Подробнее — [lost update](<../09. Транзакции и конкурентность/09. Что такое lost update.md>).

## UPDATE ... FROM

```sql
-- обновить цены из таблицы импорта
UPDATE products p
SET price = i.price, updated_at = now()
FROM import_prices i
WHERE i.sku = p.sku
  AND i.price IS DISTINCT FROM p.price;    -- не трогать строки без изменений
```

Условие `IS DISTINCT FROM` уменьшает число новых версий строк и срабатываний триггеров. Если одной строке цели соответствует несколько строк источника, результат непредсказуем — источник должен быть уникален по ключу.

## Подзапрос в SET

```sql
UPDATE orders o
SET total = (SELECT COALESCE(sum(qty * unit_price), 0) FROM order_items WHERE order_id = o.id)
WHERE o.id = $1;
```

## Оптимистичная блокировка

```sql
UPDATE documents
SET body = $1, version = version + 1
WHERE id = $2 AND version = $3;   -- 0 строк → кто-то изменил документ раньше
```

## Массовое обновление пачками

```sql
-- повторять, пока затронуто > 0 строк
UPDATE users SET newsletter = false
WHERE id IN (
  SELECT id FROM users
  WHERE newsletter AND last_login_at < now() - interval '2 years'
  LIMIT 5000
);
```

Короткие транзакции быстрее отпускают блокировки, не раздувают WAL одномоментно и дают autovacuum успевать.

## Безопасность в ручной работе

```sql
BEGIN;
UPDATE orders SET status = 'cancelled' WHERE created_at < '2026-01-01' AND status = 'new';
-- UPDATE 1532 — проверить, ожидаемое ли число
SELECT ... ;          -- проверить результат
COMMIT;               -- или ROLLBACK
```

## Частые ошибки

- `UPDATE` без `WHERE`.
- Read-modify-write в приложении вместо атомарного выражения.
- Игнорировать число затронутых строк.
- Огромный `UPDATE` одной транзакцией в рабочее время.
- `UPDATE ... FROM` с неуникальным источником.

## Что важно помнить

- `WHERE` определяет, что меняется; проверяйте его через `SELECT` перед изменением.
- Атомарные выражения в `SET` защищают от потерянных обновлений.
- Массовые изменения — пачками.

## Мини-шпаргалка

- `UPDATE t SET a = ... WHERE ... RETURNING ...`.
- `SET x = x + 1`.
- `UPDATE t SET ... FROM s WHERE s.k = t.k`.
- `WHERE version = $v` — optimistic lock.
- `IS DISTINCT FROM` — пропустить неизменённые.
