# Как работает DELETE

> [!NOTE]
> `DELETE FROM таблица WHERE условие` удаляет подходящие строки; **без `WHERE` удаляются все**. В PostgreSQL есть `DELETE … USING` (условие с другой таблицей) и `RETURNING` (получить удалённые строки — например, чтобы переложить их в архив). Удаление проверяет внешние ключи: если на строку ссылаются дети, сработает политика `ON DELETE` (`RESTRICT`/`CASCADE`/`SET NULL`). Физически из-за MVCC строки не исчезают сразу — они помечаются удалёнными и очищаются `VACUUM`, поэтому массовое удаление делают пачками. Во многих продуктах вместо физического удаления используют **soft delete** (`deleted_at`), чтобы можно было восстановить данные и сохранить историю.

## Вопрос

Как работает `DELETE` и как удалять данные безопасно?

## Базовое удаление

```sql
DELETE FROM sessions
WHERE expires_at < now()
RETURNING id;
```

## DELETE ... USING

```sql
-- удалить позиции заказов отменённых более года назад
DELETE FROM order_items oi
USING orders o
WHERE o.id = oi.order_id
  AND o.status = 'cancelled'
  AND o.created_at < now() - interval '1 year';
```

## Перенос в архив

```sql
WITH deleted AS (
  DELETE FROM orders
  WHERE created_at < now() - interval '3 years'
  RETURNING *
)
INSERT INTO orders_archive SELECT * FROM deleted;
```

## Внешние ключи

```sql
DELETE FROM users WHERE id = 1;
-- ERROR: update or delete on table "users" violates foreign key constraint "orders_user_fk"
```

| Политика FK | Что произойдёт |
| --- | --- |
| `NO ACTION` / `RESTRICT` | Ошибка, пока есть дети |
| `CASCADE` | Дети удалятся вместе с родителем |
| `SET NULL` | В детях ссылка станет `NULL` |

Без индекса на FK-столбце детской таблицы каждое удаление родителя сканирует её целиком — см. [индексы на внешних ключах](<../10. Индексы и оптимизация запросов/04. Почему внешние ключи часто нужно индексировать.md>).

## Массовое удаление пачками

```sql
DELETE FROM events
WHERE id IN (
  SELECT id FROM events
  WHERE created_at < now() - interval '90 days'
  LIMIT 10000
);
-- повторять, пока удаляется > 0 строк
```

Для регулярной очистки больших журналов эффективнее [партиционирование](<../11. Практика Backend и собеседования/12. Что такое реплики, партиционирование и шардинг.md>): старую партицию удаляют мгновенно через `DROP TABLE` / `DETACH PARTITION`.

## Soft delete

```sql
ALTER TABLE articles ADD COLUMN deleted_at timestamptz;

UPDATE articles SET deleted_at = now() WHERE id = $1;          -- «удалить»
SELECT * FROM articles WHERE deleted_at IS NULL;               -- обычные запросы

CREATE INDEX articles_active_idx ON articles (created_at) WHERE deleted_at IS NULL;
CREATE UNIQUE INDEX articles_slug_active_uniq ON articles (slug) WHERE deleted_at IS NULL;
```

| | Hard delete | Soft delete |
| --- | --- | --- |
| Восстановление | Только из бэкапа | `SET deleted_at = NULL` |
| Запросы | Простые | Нужно помнить про фильтр (view, scope в ORM) |
| Уникальность | Обычный `UNIQUE` | Частичный индекс |
| GDPR / право на удаление | Выполняет | Нужна отдельная процедура реального удаления |

## Частые ошибки

- `DELETE` без `WHERE` (проверяйте условие через `SELECT count(*)` и транзакцию).
- `CASCADE` на критичных данных.
- Удаление миллионов строк одной транзакцией.
- Soft delete без частичных индексов и единого фильтра.

## Что важно помнить

- `DELETE` учитывает FK и политику `ON DELETE`.
- `RETURNING` + CTE — перенос в архив одной командой.
- Большие объёмы — пачками или через партиции.

## Мини-шпаргалка

- `DELETE FROM t WHERE ... RETURNING ...`.
- `DELETE FROM t USING s WHERE ...`.
- `WITH d AS (DELETE ... RETURNING *) INSERT ...`.
- Soft delete: `deleted_at` + `WHERE deleted_at IS NULL`.
