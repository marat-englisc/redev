# Что такое ACID

> [!NOTE]
> **ACID** — четыре гарантии транзакций. **Atomicity** (атомарность) — все операции транзакции применяются целиком или не применяются вовсе. **Consistency** (согласованность) — транзакция переводит базу из одного корректного состояния в другое: соблюдаются ограничения (`PK`, `FK`, `CHECK`, `UNIQUE`), а бизнес-инварианты — ответственность ещё и приложения. **Isolation** (изоляция) — параллельные транзакции не мешают друг другу в пределах выбранного уровня изоляции; полная изоляция (`SERIALIZABLE`) дорога, поэтому по умолчанию используется более слабая. **Durability** (долговечность) — после `COMMIT` данные не пропадут даже при сбое питания: PostgreSQL сначала записывает изменения в **WAL** (журнал упреждающей записи) и сбрасывает его на диск.

## Вопрос

Что такое ACID и как каждая гарантия реализуется?

## Четыре свойства

| Свойство | Гарантия | Механизм в PostgreSQL |
| --- | --- | --- |
| Atomicity | Всё или ничего | MVCC + статус транзакции в commit log: версии строк от неподтверждённой транзакции просто не видны |
| Consistency | Ограничения соблюдены | Constraints, триггеры, проверки при `COMMIT` для `DEFERRABLE` |
| Isolation | Параллельные транзакции не видят «полуготовые» изменения друг друга | MVCC-снимки, блокировки, SSI для `SERIALIZABLE` |
| Durability | Подтверждённое не теряется | WAL + `fsync`, репликация |

## Atomicity на примере

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 999;   -- такого счёта нет, но ошибки нет!
COMMIT;
```

Атомарность не спасёт от логической ошибки: второй `UPDATE` затронул 0 строк, и деньги «исчезли». Приложение должно проверять результат, а база — иметь ограничения (`CHECK (balance >= 0)`), чтобы ошибка превратилась в откат.

## Consistency — общая ответственность

```sql
CREATE TABLE accounts (
  id bigint PRIMARY KEY,
  balance numeric(14, 2) NOT NULL CHECK (balance >= 0)
);
```

Правило «сумма всех балансов не меняется при переводе» база сама не знает — его обеспечивают транзакция и корректный код.

## Isolation — компромисс

Чем выше уровень изоляции, тем меньше аномалий и тем больше ожиданий или откатов. По умолчанию PostgreSQL использует `READ COMMITTED` — см. [уровни изоляции](<04. Какие бывают уровни изоляции транзакций.md>).

## Durability и настройки

| Параметр | Эффект |
| --- | --- |
| `fsync = on` (по умолчанию) | WAL реально записывается на диск |
| `synchronous_commit = off` | Быстрее, но при сбое можно потерять последние ~доли секунды подтверждённых транзакций (без порчи данных) |
| Синхронная реплика | `COMMIT` ждёт подтверждения от реплики — данные переживут потерю сервера |

## ACID и BASE

NoSQL и распределённые системы часто выбирают модель **BASE** (Basically Available, Soft state, Eventual consistency): доступность и масштабирование ценой временной несогласованности. Многие современные NoSQL (MongoDB 4+) поддерживают ACID-транзакции, но с ограничениями. Подробнее — [SQL и NoSQL](<../01. Основы SQL и реляционных БД/08. Чем SQL-базы отличаются от NoSQL.md>).

## Частые ошибки

- Считать, что ACID гарантирует корректность бизнес-логики.
- Путать Consistency из ACID с Consistency из CAP-теоремы (там — согласованность реплик).
- Думать, что изоляция по умолчанию полная.
- Отключать `fsync` в проде ради скорости.

## Что важно помнить

- A — всё или ничего, C — ограничения, I — параллельность, D — сохранность после `COMMIT`.
- Durability обеспечивает WAL.
- Изоляция по умолчанию — не `SERIALIZABLE`.

## Мини-шпаргалка

- Atomicity → `ROLLBACK` при ошибке.
- Consistency → constraints.
- Isolation → уровни изоляции, MVCC.
- Durability → WAL, `fsync`, реплики.
