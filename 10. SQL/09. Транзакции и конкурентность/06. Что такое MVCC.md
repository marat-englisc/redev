# Что такое MVCC

> [!NOTE]
> **MVCC (Multi-Version Concurrency Control)** — способ параллельной работы, при котором база хранит **несколько версий строки**, и каждая транзакция видит ту, что соответствует её **снимку** (snapshot). Благодаря этому **читатели не блокируют писателей, а писатели — читателей**: `SELECT` не ждёт `UPDATE` и наоборот; ждать друг друга приходится только двум транзакциям, меняющим одну и ту же строку. В PostgreSQL `UPDATE` создаёт новую версию строки (tuple), а старую помечает устаревшей через служебные поля `xmin`/`xmax`; `DELETE` только помечает. Устаревшие версии, которые уже никто не может увидеть, очищает **VACUUM** (обычно autovacuum). Обратная сторона: раздувание таблиц (bloat) при массовых изменениях и **долгие транзакции**, которые мешают очистке.

## Вопрос

Что такое MVCC и как он работает в PostgreSQL?

## Версии строки

```text
UPDATE products SET price = 120 WHERE id = 1;   -- транзакция 200

версия | xmin | xmax | price
v1     | 100  | 200  | 100     ← видна транзакциям со снимком до 200
v2     | 200  | 0    | 120     ← видна после фиксации 200
```

```sql
SELECT xmin, xmax, * FROM products WHERE id = 1;   -- служебные столбцы можно посмотреть
```

## Читатели и писатели не мешают друг другу

```text
T1: BEGIN; UPDATE products SET price = 120 WHERE id = 1;   (не зафиксировано)
T2: SELECT price FROM products WHERE id = 1;   → 100, без ожидания
T3: UPDATE products SET price = 130 WHERE id = 1;   → ждёт T1 (та же строка)
```

## Снимок

Снимок — список транзакций, которые на момент его создания были зафиксированы. В Read Committed новый снимок берётся для каждого оператора, в Repeatable Read и Serializable — один на транзакцию. Подробнее — [уровни изоляции](<04. Какие бывают уровни изоляции транзакций.md>).

## VACUUM

| Что делает | Зачем |
| --- | --- |
| Удаляет мёртвые версии строк | Освобождает место для повторного использования внутри таблицы |
| Обновляет visibility map | Делает возможным index-only scan |
| Замораживает старые `xmin` (freeze) | Защищает от переполнения 32-битного счётчика транзакций (wraparound) |

`VACUUM FULL` переписывает таблицу целиком и возвращает место ОС, но берёт эксклюзивную блокировку. Подробнее — [VACUUM, ANALYZE и статистика](<../10. Индексы и оптимизация запросов/13. Что такое VACUUM, ANALYZE и статистика планировщика.md>).

## Почему долгие транзакции опасны

```sql
-- транзакции, открытые дольше 5 минут
SELECT pid, state, xact_start, now() - xact_start AS age, left(query, 80)
FROM pg_stat_activity
WHERE xact_start < now() - interval '5 minutes'
ORDER BY xact_start;
```

Пока открыта старая транзакция (даже `idle in transaction`), VACUUM не может удалить версии строк, которые она теоретически может увидеть, — таблицы и индексы раздуваются, запросы замедляются.

## HOT-обновления

Если `UPDATE` не меняет индексированные столбцы и на странице есть место, PostgreSQL делает **HOT update** — индексы не обновляются. Поэтому лишние индексы и `fillfactor` влияют на скорость частых обновлений.

## Частые ошибки

- Отключать autovacuum «ради производительности».
- Долгие или забытые открытые транзакции.
- Массовый `UPDATE` всей таблицы — таблица удваивается в размере.
- Думать, что `DELETE` сразу уменьшает размер файла таблицы.

## Что важно помнить

- MVCC = версии строк + снимки.
- Читатели и писатели не блокируют друг друга.
- VACUUM убирает мёртвые версии; долгие транзакции ему мешают.

## Мини-шпаргалка

- `xmin`, `xmax` — служебные поля версий.
- `UPDATE` = новая версия, `DELETE` = пометка.
- Autovacuum — включён всегда.
- `pg_stat_activity` — искать долгие транзакции.
