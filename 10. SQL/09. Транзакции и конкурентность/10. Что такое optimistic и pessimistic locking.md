# Что такое optimistic и pessimistic locking

> [!NOTE]
> Это две стратегии защиты от конфликтующих изменений. **Pessimistic locking** предполагает, что конфликт вероятен, и **заранее блокирует** данные (`SELECT … FOR UPDATE`): остальные ждут, пока транзакция не завершится. **Optimistic locking** предполагает, что конфликты редки: данные читают без блокировки, а при записи **проверяют**, не изменились ли они (по столбцу `version` или `updated_at`); если изменились — запись отклоняется и операция повторяется или пользователю показывается конфликт. Пессимистичный подход хорош для коротких горячих операций в одной транзакции (списание остатка, бронирование места), оптимистичный — для долгих сценариев с участием пользователя (редактирование формы), где держать блокировку минутами невозможно.

## Вопрос

Чем отличаются optimistic и pessimistic locking и когда что использовать?

## Pessimistic

```sql
BEGIN;
SELECT * FROM seats WHERE id = $1 AND event_id = $2 FOR UPDATE;   -- остальные ждут
-- проверить, что место свободно
UPDATE seats SET booked_by = $3 WHERE id = $1;
COMMIT;
```

```sql
-- не ждать: сразу сообщить, что место кто-то бронирует
SELECT * FROM seats WHERE id = $1 FOR UPDATE NOWAIT;
```

## Optimistic

```sql
ALTER TABLE articles ADD COLUMN version int NOT NULL DEFAULT 1;

-- чтение (без блокировки)
SELECT id, title, body, version FROM articles WHERE id = $1;   -- version = 7

-- запись
UPDATE articles
SET title = $2, body = $3, version = version + 1
WHERE id = $1 AND version = $4          -- $4 = 7
RETURNING version;
```

```ts
const { rowCount } = await db.query(sql, [id, title, body, version]);
if (rowCount === 0) throw new ConflictException("Статья изменена другим пользователем");
```

## Поддержка в ORM

```ts
// TypeORM
@VersionColumn() version: number;      // проверка версии при save()

// Prisma — вручную
await prisma.article.update({
  where: { id, version },               // требует уникального составного условия или updateMany
  data: { title, version: { increment: 1 } },
});
```

## Сравнение

| | Pessimistic | Optimistic |
| --- | --- | --- |
| Когда проверяется конфликт | До изменения (блокировка) | При записи (версия) |
| Ожидания | Да | Нет |
| Deadlock'и | Возможны | Нет |
| Длительность операции | Короткая, в одной транзакции | Может быть долгой (минуты в UI) |
| При высокой конкуренции | Очередь, но всё выполняется | Много отказов и повторов |
| Пример | Списание баланса, бронирование | Редактирование статьи, CMS, настройки |

## Комбинация с HTTP

```http
GET /articles/1
ETag: "7"

PUT /articles/1
If-Match: "7"
→ 412 Precondition Failed или 409 Conflict, если версия изменилась
```

## Частые ошибки

- Держать `FOR UPDATE` пока пользователь заполняет форму.
- Оптимистичная блокировка без проверки `rowCount`.
- Использовать `updated_at` с низкой точностью как версию — два изменения в одну миллисекунду не различаются.
- Оптимистичный подход для «горячей» строки (общий счётчик) — бесконечные повторы.

## Что важно помнить

- Pessimistic — заблокировать заранее; optimistic — проверить при записи.
- Короткие транзакции в бэкенде — pessimistic или атомарный `UPDATE`.
- Долгие пользовательские сценарии — optimistic с версией.

## Мини-шпаргалка

- `SELECT ... FOR UPDATE [NOWAIT]`.
- `UPDATE ... SET version = version + 1 WHERE id = $1 AND version = $2`.
- `rowCount === 0` → конфликт.
- `ETag` / `If-Match`.
