# Что такое блокировки

> [!NOTE]
> **Блокировки** координируют доступ транзакций к одним и тем же данным. В PostgreSQL есть **блокировки строк** — `UPDATE`/`DELETE` автоматически блокируют изменяемые строки до конца транзакции, а явно их берут через `SELECT … FOR UPDATE` (или более слабые `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE`); **блокировки таблиц** — от `ACCESS SHARE` (обычный `SELECT`) до `ACCESS EXCLUSIVE` (`DROP`, многие `ALTER TABLE`, `TRUNCATE`); и **advisory locks** — произвольные блокировки по числовому ключу для координации на уровне приложения. Ожидание блокировки ограничивают `lock_timeout` или модификаторами `NOWAIT` / `SKIP LOCKED`. Блокировки держатся до конца транзакции, поэтому длинные транзакции превращаются в очереди ожидания.

## Вопрос

Какие бывают блокировки в PostgreSQL и как их использовать?

## Неявные блокировки строк

```text
T1: BEGIN; UPDATE accounts SET balance = balance - 100 WHERE id = 1;
T2: UPDATE accounts SET balance = balance + 50 WHERE id = 1;   → ждёт COMMIT/ROLLBACK T1
T2: SELECT balance FROM accounts WHERE id = 1;                → не ждёт (MVCC)
```

## SELECT ... FOR UPDATE

```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;   -- заблокировать строку для изменения
-- проверить бизнес-правила в приложении
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

| Режим | Блокирует |
| --- | --- |
| `FOR UPDATE` | Любые изменения и другие `FOR UPDATE/SHARE` |
| `FOR NO KEY UPDATE` | То же, но не мешает вставке детей с FK на эту строку (берёт обычный `UPDATE` не-ключевых столбцов) |
| `FOR SHARE` | Изменения, но разрешает другим `FOR SHARE` |
| `FOR KEY SHARE` | Только удаление и изменение ключа (берётся при проверке FK) |

## NOWAIT и SKIP LOCKED

```sql
SELECT * FROM seats WHERE id = 42 FOR UPDATE NOWAIT;      -- ошибка сразу, если занято
SELECT * FROM jobs WHERE status = 'pending'
ORDER BY id LIMIT 10 FOR UPDATE SKIP LOCKED;              -- взять незанятые строки
```

`SKIP LOCKED` — основа очереди задач в PostgreSQL, см. [очередь через SKIP LOCKED](<11. Как сделать очередь задач через SELECT FOR UPDATE SKIP LOCKED.md>).

## Блокировки таблиц

| Режим | Кто берёт | С чем конфликтует |
| --- | --- | --- |
| `ACCESS SHARE` | `SELECT` | Только `ACCESS EXCLUSIVE` |
| `ROW EXCLUSIVE` | `INSERT`, `UPDATE`, `DELETE` | DDL-блокировки (`SHARE`, `EXCLUSIVE`, `ACCESS EXCLUSIVE`…) |
| `SHARE` | `CREATE INDEX` (без `CONCURRENTLY`) | Записи |
| `SHARE UPDATE EXCLUSIVE` | `VACUUM`, `CREATE INDEX CONCURRENTLY`, `ANALYZE` | Сами с собой и DDL |
| `ACCESS EXCLUSIVE` | `DROP`, `TRUNCATE`, большинство `ALTER TABLE` | Со всем, даже с `SELECT` |

## Очередь блокировок

```text
T1: долгий SELECT (ACCESS SHARE)
T2: ALTER TABLE ... (ждёт ACCESS EXCLUSIVE)
T3, T4, ...: обычные SELECT → встают в очередь ЗА T2 → сервис «лежит»
```

Поэтому миграции запускают с `SET lock_timeout = '5s'` и повторяют при неудаче.

## Advisory locks

```sql
-- только один экземпляр cron-задачи одновременно
SELECT pg_try_advisory_lock(42);     -- true → работаем, false → другой инстанс уже выполняет
-- ...
SELECT pg_advisory_unlock(42);

-- на время транзакции
SELECT pg_advisory_xact_lock(hashtext('import:' || $1));
```

## Диагностика

```sql
SELECT pid, pg_blocking_pids(pid) AS blocked_by, wait_event_type, left(query, 80)
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

## Частые ошибки

- `FOR UPDATE` без транзакции (в autocommit блокировка снимается сразу).
- Длинные транзакции с заблокированными строками.
- DDL без `lock_timeout` на нагруженной таблице.
- Сессионные advisory locks через пул соединений — блокировка «застревает» на чужом соединении.

## Что важно помнить

- `UPDATE`/`DELETE` блокируют строки до конца транзакции; `SELECT` не блокирует.
- `FOR UPDATE` — явная блокировка для read-modify-write.
- `ACCESS EXCLUSIVE` блокирует даже чтение — осторожно с DDL.

## Мини-шпаргалка

- `SELECT ... FOR UPDATE [NOWAIT | SKIP LOCKED]`.
- `SET lock_timeout = '5s'`.
- `pg_try_advisory_lock(key)`, `pg_advisory_xact_lock(key)`.
- `pg_blocking_pids(pid)`.
