# Что такое deadlock

> [!NOTE]
> **Deadlock (взаимная блокировка)** — ситуация, когда транзакции ждут друг друга по кругу: T1 держит строку A и ждёт B, а T2 держит B и ждёт A. Сами они никогда не завершатся, поэтому PostgreSQL периодически (через `deadlock_timeout`, по умолчанию 1 с) проверяет граф ожиданий и **отменяет одну из транзакций** с ошибкой `40P01 deadlock_detected`; вторая продолжает работу. Главная профилактика — **единый порядок захвата ресурсов** (например, блокировать строки по возрастанию id), короткие транзакции и явная блокировка нужных строк в начале. Поскольку полностью исключить deadlock'и трудно, приложение должно уметь **повторять** транзакцию при `40P01`.

## Вопрос

Что такое deadlock, почему он возникает и как его избежать?

## Пример

```text
T1: BEGIN; UPDATE accounts SET ... WHERE id = 1;    -- держит 1
T2: BEGIN; UPDATE accounts SET ... WHERE id = 2;    -- держит 2
T1: UPDATE accounts SET ... WHERE id = 2;           -- ждёт T2
T2: UPDATE accounts SET ... WHERE id = 1;           -- ждёт T1 → цикл
→ ERROR: deadlock detected (одна из транзакций откатывается)
```

Типичный сценарий — встречные переводы: A → B и B → A одновременно.

## Профилактика: единый порядок

```sql
-- блокировать оба счёта в порядке возрастания id, независимо от направления перевода
BEGIN;
SELECT id FROM accounts WHERE id IN ($1, $2) ORDER BY id FOR UPDATE;
UPDATE accounts SET balance = balance - $3 WHERE id = $1;
UPDATE accounts SET balance = balance + $3 WHERE id = $2;
COMMIT;
```

```ts
// массовое обновление — сортировать ключи перед отправкой
const ids = [...items].map((i) => i.id).sort((a, b) => a - b);
```

## Другие источники deadlock'ов

| Источник | Решение |
| --- | --- |
| Разный порядок обновления строк в разных местах кода | Единый порядок |
| Массовый `UPDATE ... WHERE id IN (...)` из параллельных воркеров | Сортировка, пачки поменьше, `SKIP LOCKED` |
| FK + обновление родителя и вставка детей | `FOR NO KEY UPDATE`, порядок операций |
| Повышение уровня блокировки (`FOR SHARE` → `UPDATE`) | Сразу брать `FOR UPDATE` |
| DDL посреди рабочей нагрузки | Миграции с `lock_timeout` |

## Повтор при deadlock

```ts
for (let attempt = 1; attempt <= 3; attempt++) {
  try {
    await transfer(from, to, amount);
    break;
  } catch (e: any) {
    if (e.code !== "40P01" || attempt === 3) throw e;
    await sleep(20 * attempt + Math.random() * 50);   // небольшая случайная задержка
  }
}
```

Повторять можно только транзакцию целиком и только если она идемпотентна или полностью откатилась.

## Диагностика

```sql
-- в логе PostgreSQL при deadlock — подробности: какие процессы и запросы участвовали
SHOW log_lock_waits;   -- включить, чтобы логировать ожидания дольше deadlock_timeout

SELECT deadlocks FROM pg_stat_database WHERE datname = current_database();
```

## Deadlock и lock wait

| | Lock wait | Deadlock |
| --- | --- | --- |
| Что происходит | Транзакция ждёт другую | Транзакции ждут друг друга по кругу |
| Разрешится само | Да, когда держатель завершится | Нет — PostgreSQL отменит одну |
| Защита | `lock_timeout`, короткие транзакции | Порядок захвата, retry |

## Частые ошибки

- Не обрабатывать `40P01` в приложении.
- Блокировать строки в порядке, пришедшем от пользователя.
- Длинные транзакции с большим числом обновлений.
- Повышать `deadlock_timeout`, «чтобы было меньше ошибок» — deadlock'и не исчезнут, только дольше будут висеть.

## Что важно помнить

- Deadlock — циклическое ожидание; PostgreSQL разрывает его откатом одной транзакции.
- Единый порядок блокировок — главная профилактика.
- Retry при `40P01` — обязательная часть кода.

## Мини-шпаргалка

- `40P01 deadlock_detected`.
- `ORDER BY id FOR UPDATE`.
- `deadlock_timeout`, `log_lock_waits`.
- Retry с jitter.
