# Что такое lost update

> [!NOTE]
> **Lost update (потерянное обновление)** — две транзакции читают одно значение, каждая вычисляет новое в приложении и записывает своё; второе сохранение **перезаписывает** первое, и одно изменение теряется. Классика: два покупателя одновременно уменьшают остаток 5 → 4, и итог — 4 вместо 3; два редактора сохраняют документ, и правки первого исчезают. На уровне Read Committed PostgreSQL от этого не защищает. Решения: **атомарный `UPDATE`** с вычислением в базе (`stock = stock - 1 WHERE stock > 0`); **пессимистичная блокировка** `SELECT … FOR UPDATE`; **оптимистичная блокировка** по версии (`WHERE version = $v`); уровень `REPEATABLE READ`/`SERIALIZABLE` с повтором транзакции.

## Вопрос

Что такое lost update и как его предотвратить?

## Как возникает

```ts
// ✗ read-modify-write в приложении
const { rows: [p] } = await db.query("SELECT stock FROM products WHERE id = $1", [id]);  // 5
if (p.stock < 1) throw new Error("Нет в наличии");
await db.query("UPDATE products SET stock = $1 WHERE id = $2", [p.stock - 1, id]);       // 4
// параллельный запрос сделал то же самое → итог 4, продано 2 штуки
```

```text
T1: SELECT stock → 5          T2: SELECT stock → 5
T1: UPDATE stock = 4          T2: UPDATE stock = 4   ← обновление T1 потеряно
```

## Решение 1: атомарный UPDATE

```sql
UPDATE products
SET stock = stock - $2
WHERE id = $1 AND stock >= $2
RETURNING stock;
```

0 строк — не хватило остатка. Самый простой и быстрый способ, когда логика выражается в SQL.

## Решение 2: SELECT FOR UPDATE

```sql
BEGIN;
SELECT stock, reserved FROM products WHERE id = $1 FOR UPDATE;   -- второй запрос ждёт здесь
-- сложная проверка в приложении
UPDATE products SET stock = $2, reserved = $3 WHERE id = $1;
COMMIT;
```

Подходит, когда решение принимается кодом по нескольким полям.

## Решение 3: оптимистичная блокировка

```sql
UPDATE documents
SET body = $1, version = version + 1, updated_at = now()
WHERE id = $2 AND version = $3;     -- $3 — версия, которую пользователь видел
```

0 строк → документ изменили параллельно; API возвращает `409 Conflict`, клиент показывает «документ изменён, обновите». Подробнее — [optimistic и pessimistic locking](<10. Что такое optimistic и pessimistic locking.md>).

## Решение 4: изоляция

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT stock FROM products WHERE id = 1;
UPDATE products SET stock = 4 WHERE id = 1;   -- при конкурентном изменении → ERROR 40001
COMMIT;
```

Требует повтора транзакции в приложении.

## Lost update в HTTP API

```text
GET /documents/1  → { body, version: 7 }
PUT /documents/1  { body, version: 7 }   → если версия в базе уже 8 → 409
```

Без версии (или `ETag` / `If-Match`) «последняя запись побеждает» — и правки теряются даже без параллельных транзакций в базе, просто из-за двух вкладок.

## Сравнение

| Подход | Плюсы | Минусы |
| --- | --- | --- |
| Атомарный `UPDATE` | Быстро, без ожиданий | Только если логика выражается в SQL |
| `FOR UPDATE` | Простая модель, любые проверки | Ожидания, риск deadlock'ов |
| Версия строки | Нет блокировок, подходит для долгих правок в UI | Нужно обрабатывать конфликт |
| `REPEATABLE READ` / `SERIALIZABLE` | Общая защита | Retry-логика |

## Частые ошибки

- Read-modify-write без блокировки и версии.
- `SELECT ... FOR UPDATE` вне транзакции.
- Игнорировать число затронутых строк при оптимистичной блокировке.
- ORM `save()` целой сущности, перезаписывающий все поля, включая изменённые другими.

## Что важно помнить

- Lost update — результат read-modify-write без координации.
- Лучшее решение — атомарное выражение в `UPDATE`.
- Для UI-редактирования — оптимистичная блокировка с версией.

## Мини-шпаргалка

- `SET x = x - 1 WHERE x > 0`.
- `SELECT ... FOR UPDATE`.
- `WHERE version = $v` + `version = version + 1`.
- `409 Conflict`, `ETag` / `If-Match`.
