# Что такое первичный и внешний ключ

> [!NOTE]
> **Первичный ключ (PRIMARY KEY)** однозначно идентифицирует строку: он уникален, не может быть `NULL`, у таблицы он один (может состоять из нескольких столбцов) и автоматически индексируется. **Внешний ключ (FOREIGN KEY, `REFERENCES`)** гарантирует, что значение в дочерней таблице ссылается на существующую строку родительской — это **ссылочная целостность**. Поведение при удалении и изменении родителя задаётся явно: `RESTRICT`/`NO ACTION` (запретить), `CASCADE` (удалить дочерние), `SET NULL`, `SET DEFAULT`. В PostgreSQL индекс на столбец внешнего ключа **не создаётся автоматически** — его обычно добавляют вручную.

## Вопрос

Что такое первичный и внешний ключ и как они работают?

## Первичный ключ

```sql
CREATE TABLE users (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text NOT NULL UNIQUE
);
```

`PRIMARY KEY` = `UNIQUE` + `NOT NULL` + индекс. Значения генерирует база (`IDENTITY`) или приложение (`uuid`) — см. [выбор первичного ключа](<../07. Схема данных, DDL и constraints/09. Как выбрать первичный ключ - identity, UUID и естественные ключи.md>).

**Составной ключ** — для таблиц-связок:

```sql
CREATE TABLE post_tags (
  post_id bigint REFERENCES posts(id) ON DELETE CASCADE,
  tag_id  bigint REFERENCES tags(id)  ON DELETE CASCADE,
  PRIMARY KEY (post_id, tag_id)
);
```

## Внешний ключ

```sql
CREATE TABLE orders (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id bigint NOT NULL REFERENCES users(id) ON DELETE RESTRICT
);

CREATE INDEX orders_user_id_idx ON orders (user_id);
```

```sql
INSERT INTO orders (user_id) VALUES (999);
-- ERROR: insert or update on table "orders" violates foreign key constraint
```

Без внешнего ключа такой «висячий» заказ сохранился бы, и приложение получило бы сироту.

## Поведение при удалении родителя

| Действие | Что происходит с дочерними строками | Когда |
| --- | --- | --- |
| `NO ACTION` (по умолчанию) / `RESTRICT` | Удаление родителя запрещено | Заказы нельзя терять при удалении пользователя |
| `CASCADE` | Удаляются вместе с родителем | Части агрегата: позиции заказа, теги поста |
| `SET NULL` | Ссылка становится `NULL` | Необязательная связь: автор удалён, пост остаётся |
| `SET DEFAULT` | Ссылка получает значение по умолчанию | Редко |

`CASCADE` удобен, но может молча удалить большое дерево данных — используйте его только для настоящих «частей» сущности.

## Зачем индекс на внешний ключ

- Быстрый `JOIN` и выборка «все заказы пользователя».
- При удалении или изменении родителя база ищет дочерние строки — без индекса это полный перебор дочерней таблицы под блокировкой.

PostgreSQL индексирует только первичные и уникальные ключи; MySQL InnoDB создаёт индекс на FK автоматически.

## Внешние ключи и производительность

Проверка FK стоит немного при каждой вставке. В высоконагруженных системах их иногда сознательно не ставят (шардирование, независимые сервисы), перенося проверку в код, — но для обычного приложения внешние ключи обязательны.

## Частые ошибки

- Не ставить внешние ключи «для скорости» и потом чистить сирот.
- `ON DELETE CASCADE` на связях, где данные нельзя терять.
- Забыть индекс на столбец FK в PostgreSQL.
- Использовать в качестве первичного ключа изменяемые данные (email, телефон).

## Что важно помнить

- PK идентифицирует строку, FK защищает связь.
- Поведение `ON DELETE` выбирают по смыслу связи.
- Индекс на FK — почти всегда.

## Мини-шпаргалка

- `PRIMARY KEY` = уникально + не NULL + индекс.
- `REFERENCES parent(id)` — ссылочная целостность.
- `RESTRICT`, `CASCADE`, `SET NULL`.
- `CREATE INDEX` на столбец FK.
- Составной PK — для таблиц-связок.
