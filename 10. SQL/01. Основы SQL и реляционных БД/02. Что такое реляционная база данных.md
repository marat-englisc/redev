# Что такое реляционная база данных

> [!NOTE]
> **Реляционная база данных** хранит данные в **таблицах** (отношениях) со строго заданной структурой: строка — запись о сущности или факте, столбец — атрибут определённого типа. Связи между таблицами задаются **ключами**: внешний ключ одной таблицы ссылается на первичный ключ другой. Целостность обеспечивают **ограничения** (`NOT NULL`, `UNIQUE`, `CHECK`, `FOREIGN KEY`), согласованность при изменениях — **транзакции**, а для чтения используется SQL с соединениями таблиц (`JOIN`). Такая модель минимизирует дублирование и даёт сильные гарантии корректности данных.

## Вопрос

Что такое реляционная база данных и почему данные разбивают на несколько таблиц?

## Таблицы и связи

```sql
CREATE TABLE users (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email      text NOT NULL UNIQUE,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE orders (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id bigint NOT NULL REFERENCES users(id),
  total   numeric(12, 2) NOT NULL CHECK (total >= 0)
);
```

```text
users                 orders
┌────┬─────────────┐  ┌────┬─────────┬───────┐
│ id │ email       │  │ id │ user_id │ total │
├────┼─────────────┤  ├────┼─────────┼───────┤
│ 1  │ anna@x.com  │◀─┤ 10 │ 1       │ 990   │
│ 2  │ boris@x.com │  │ 11 │ 1       │ 1500  │
└────┴─────────────┘  └────┴─────────┴───────┘
```

`orders.user_id` ссылается на `users.id` — так записывается связь «у пользователя много заказов».

## Почему не одна большая таблица

```text
orders: id, user_email, user_name, product_title, product_price, quantity
```

Проблемы такой таблицы (аномалии):

- **обновления**: сменился email — нужно обновить все заказы пользователя, пропустили одну строку — данные противоречат друг другу;
- **вставки**: нельзя добавить пользователя, пока у него нет заказа;
- **удаления**: удалили последний заказ — потеряли информацию о пользователе.

Разбиение на `users`, `orders`, `products`, `order_items` — это **нормализация**: каждый факт хранится в одном месте.

## Гарантии реляционной БД

| Механизм | Что даёт |
| --- | --- |
| Схема и типы | Невозможно записать строку вместо числа |
| Ограничения | Нет дублей email, нет заказа без пользователя |
| Транзакции (ACID) | Перевод денег выполняется целиком или не выполняется |
| SQL и JOIN | Любые выборки из связанных данных без изменения структуры |
| Индексы | Быстрый поиск даже в миллионах строк |

## Сравнение с документной моделью

В документной БД (MongoDB) заказ может хранить копию данных пользователя внутри документа. Это удобно для чтения одного объекта, но дублирует данные и переносит контроль целостности в код. Подробнее — в уроке [SQL и NoSQL](<08. Чем SQL-базы отличаются от NoSQL.md>).

## Частые ошибки

- Хранить связанные сущности в одной таблице «чтобы было проще».
- Не задавать внешние ключи, полагаясь только на код.
- Хранить списки через запятую в одной ячейке (`tags = 'css,html'`).

## Что важно помнить

- Реляционная модель — это таблицы + ключи + ограничения + транзакции.
- Нормализация убирает аномалии, денормализация — осознанный компромисс ради скорости чтения.
- Целостность данных лучше всего защищает сама база, а не только код приложения.

## Мини-шпаргалка

- Таблица = отношение, строка = запись, столбец = атрибут.
- Связи — через первичные и внешние ключи.
- Каждый факт хранится в одном месте.
- Ограничения и транзакции защищают данные.
