# Что такое селективность индекса

> [!NOTE]
> **Селективность** условия — доля строк таблицы, которые ему соответствуют. Высокая селективность (мало строк: `email = $1`, `id = $1`) — индекс очень выгоден. Низкая (много строк: `is_active = true` для 95% пользователей) — дешевле прочитать таблицу целиком последовательно, чем делать тысячи случайных переходов из индекса в heap; поэтому планировщик **может не использовать индекс, и это правильно**. Важна селективность **конкретного значения**, а не столбца в целом: `status = 'failed'` (0,1% строк) селективно, а `status = 'done'` (90%) — нет. Для таких перекосов подходят **частичные индексы**. Оценки селективности планировщик берёт из статистики (`pg_stats`: частые значения, гистограммы), поэтому устаревшая статистика ведёт к плохим планам.

## Вопрос

Что такое селективность и как она влияет на использование индекса?

## Примеры

| Условие | Доля строк | Индекс выгоден |
| --- | --- | --- |
| `id = 42` | 1 строка | Да |
| `email = 'anna@x.com'` | 1 строка | Да |
| `user_id = 7` | 0,01% | Да |
| `status = 'failed'` | 0,1% | Да |
| `status = 'done'` | 90% | Нет — Seq Scan |
| `is_active` | 95% | Нет |

Граница зависит от размера строк, кеша и настроек (`random_page_cost`), но ориентир — единицы процентов.

## Почему много строк через индекс медленнее

```text
Seq Scan:   читаем 10 000 страниц подряд (последовательно, быстро)
Index Scan: 900 000 строк → до 900 000 переходов к разным страницам (случайный доступ)
```

Промежуточный вариант — Bitmap Heap Scan: сначала собрать номера страниц из индекса, затем читать их по порядку.

## Перекос значений и частичный индекс

```sql
-- задачи в работе — малая доля, по ним ищут постоянно
CREATE INDEX jobs_pending_idx ON jobs (created_at) WHERE status = 'pending';

SELECT * FROM jobs WHERE status = 'pending' ORDER BY created_at LIMIT 100;
```

Индекс маленький (только pending), быстро обновляется и не содержит 99% «done»-строк.

## Статистика

```sql
SELECT attname, n_distinct, most_common_vals, most_common_freqs
FROM pg_stats
WHERE tablename = 'orders' AND attname = 'status';
```

```text
most_common_vals  = {done, cancelled, new, failed}
most_common_freqs = {0.9, 0.06, 0.035, 0.005}
```

Планировщик знает, что `status = 'done'` вернёт 90% строк, а `failed` — 0,5%, и выбирает разные планы для разных параметров.

## Коррелированные столбцы

```sql
-- city = 'Moscow' (10%) и country = 'RU' (30%) — планировщик считает независимыми: 3%
-- на деле все Moscow — в RU: 10%
CREATE STATISTICS users_city_country (dependencies) ON city, country FROM users;
ANALYZE users;
```

## Кардинальность и селективность

**Кардинальность** столбца — число различных значений. Высокая кардинальность (email, id) обычно означает высокую селективность равенства, но при перекосе распределения одного числа мало — смотрите на частоты значений.

## Частые ошибки

- Индекс по boolean или столбцу со статусом без условия.
- «Заставлять» планировщик использовать индекс, когда Seq Scan действительно дешевле.
- Не делать `ANALYZE` после массовой загрузки.
- Оценивать селективность по столбцу, а не по реальным значениям в запросах.

## Что важно помнить

- Селективность = доля строк, подходящих под условие.
- Индекс выгоден, когда строк мало.
- Перекос значений — повод для частичного индекса.

## Мини-шпаргалка

- Мало строк → Index Scan.
- Много строк → Seq Scan / Bitmap.
- `pg_stats.most_common_vals/freqs`.
- `CREATE INDEX ... WHERE rare_condition`.
- `CREATE STATISTICS` для коррелированных столбцов.
