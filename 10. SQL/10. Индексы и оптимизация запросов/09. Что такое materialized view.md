# Что такое materialized view

> [!NOTE]
> **Материализованное представление** — запрос, результат которого **сохранён на диск** как таблица. Чтение из него быстрое (можно строить индексы), но данные **актуальны на момент последнего обновления**: `REFRESH MATERIALIZED VIEW` полностью пересчитывает результат. Обычный `REFRESH` блокирует чтение на время пересчёта; `REFRESH … CONCURRENTLY` не блокирует читателей, но требует **уникального индекса** и работает дольше. В PostgreSQL нет встроенного инкрементального обновления — только полный пересчёт (по расписанию через cron/pg_cron или после событий). Применение: тяжёлые отчёты и агрегаты для дашбордов, где допустима задержка данных; для данных «здесь и сейчас» — обычные запросы с индексами или таблица-агрегат, обновляемая приложением.

## Вопрос

Что такое materialized view и как с ним работать?

## Создание

```sql
CREATE MATERIALIZED VIEW daily_revenue AS
SELECT created_at::date AS day,
       count(*)         AS orders,
       sum(total)       AS revenue
FROM orders
WHERE status = 'paid'
GROUP BY 1;

CREATE UNIQUE INDEX daily_revenue_day_idx ON daily_revenue (day);

SELECT * FROM daily_revenue WHERE day >= current_date - 30 ORDER BY day;
```

## Обновление

```sql
REFRESH MATERIALIZED VIEW daily_revenue;               -- блокирует SELECT на время пересчёта
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_revenue;  -- не блокирует, нужен UNIQUE индекс
```

```sql
-- по расписанию (расширение pg_cron)
SELECT cron.schedule('refresh-daily-revenue', '*/15 * * * *',
  'REFRESH MATERIALIZED VIEW CONCURRENTLY daily_revenue');
```

## WITH NO DATA

```sql
CREATE MATERIALIZED VIEW heavy_report AS SELECT ... WITH NO DATA;  -- создать без вычисления
REFRESH MATERIALIZED VIEW heavy_report;                            -- заполнить позже
```

До первого `REFRESH` чтение выдаст ошибку.

## View, materialized view, таблица-агрегат

| | View | Materialized view | Таблица-агрегат |
| --- | --- | --- | --- |
| Хранит данные | Нет | Да | Да |
| Актуальность | Всегда | До `REFRESH` | Обновляется приложением/триггером |
| Обновление | — | Полный пересчёт | Инкрементальное (`UPDATE ... SET count = count + 1`) |
| Индексы | Нет | Да | Да |
| Когда | Инкапсуляция запроса | Тяжёлые отчёты с допустимой задержкой | Счётчики в реальном времени |

## Ограничения

- Полный пересчёт: если исходные данные огромные, `REFRESH` может занимать минуты и нагружать базу.
- `CONCURRENTLY` вычисляет новую версию и сравнивает со старой — дольше обычного `REFRESH`.
- Нельзя напрямую `INSERT`/`UPDATE` в материализованное представление.
- Изменение определения — только `DROP` + `CREATE`.

## Частые ошибки

- Забыть настроить обновление — данные «застывают».
- `REFRESH` без `CONCURRENTLY` в рабочее время — дашборды ждут.
- Использовать для данных, которые пользователь ожидает видеть мгновенно (баланс, корзина).
- Нет уникального индекса — `CONCURRENTLY` не работает.

## Что важно помнить

- Materialized view — сохранённый результат запроса.
- Обновляется только явно и целиком.
- `CONCURRENTLY` + уникальный индекс — обновление без блокировки чтения.

## Мини-шпаргалка

- `CREATE MATERIALIZED VIEW name AS SELECT ...`.
- `CREATE UNIQUE INDEX ... ON name (...)`.
- `REFRESH MATERIALIZED VIEW CONCURRENTLY name`.
- `pg_cron` — расписание.
