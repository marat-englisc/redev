# Как выбрать первичный ключ - identity, UUID и естественные ключи

> [!NOTE]
> **Первичный ключ** уникально и неизменно идентифицирует строку. **Естественный ключ** — бизнес-атрибут (email, ИНН, SKU): кажется удобным, но бизнес-значения меняются и иногда повторяются, поэтому его обычно делают `UNIQUE`, а PK — **суррогатным**. Варианты суррогатного ключа: **`bigint GENERATED ALWAYS AS IDENTITY`** — компактный (8 байт), быстрый, упорядоченный, но раскрывает количество записей и генерируется только базой; **UUID** (16 байт) — можно создать в приложении до вставки, удобен для распределённых систем и публичных URL, но случайный **UUIDv4** фрагментирует B-tree индекс, поэтому для ключей предпочитают упорядоченный по времени **UUIDv7** (`uuidv7()` встроен в PostgreSQL 18). `serial` — устаревший способ, вместо него `identity`.

## Вопрос

Как выбрать первичный ключ: автоинкремент, UUID или естественный ключ?

## Естественный и суррогатный

```sql
-- ✗ email как PK: пользователь сменит email → обновлять все FK
CREATE TABLE users (email text PRIMARY KEY, ...);

-- ✓ суррогатный PK + бизнес-уникальность
CREATE TABLE users (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text NOT NULL UNIQUE
);
```

Естественный ключ хорош для неизменных справочников: коды валют (`'RUB'`), коды стран ISO, связующие таблицы с составным ключом `(post_id, tag_id)`.

## Identity

```sql
CREATE TABLE orders (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  ...
);

INSERT INTO orders (user_id, total) VALUES (1, 500) RETURNING id;
```

| `serial` | `identity` |
| --- | --- |
| Нестандартный, создаёт отдельную sequence «сбоку» | Стандарт SQL, sequence принадлежит столбцу |
| Можно случайно вставить своё значение | `ALWAYS` запрещает ручные значения (кроме `OVERRIDING SYSTEM VALUE`) |

Значения sequence не транзакционны: при откате вставки номер «сгорает», поэтому в id бывают дыры — это нормально.

## UUID

```sql
-- PostgreSQL 18+
CREATE TABLE events (
  id uuid PRIMARY KEY DEFAULT uuidv7(),
  ...
);

-- до 18: gen_random_uuid() (v4, PG 13+) или генерация v7 в приложении
```

## Сравнение

| Критерий | `bigint identity` | UUIDv4 | UUIDv7 |
| --- | --- | --- | --- |
| Размер | 8 байт | 16 байт | 16 байт |
| Генерация в приложении до INSERT | Нет | Да | Да |
| Упорядоченность (локальность в B-tree) | Да | Нет — случайные вставки по всему индексу | Да (по времени) |
| Угадываемость / раскрытие объёма | Да (`/orders/1001`) | Нет | Нет, но видно время создания |
| Слияние данных из разных баз | Конфликты | Без конфликтов | Без конфликтов |

## Публичный идентификатор

Распространённый компромисс: внутренний `bigint` PK для JOIN и FK + отдельный `public_id uuid UNIQUE` или короткий slug для URL и API.

```sql
CREATE TABLE orders (
  id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  public_id uuid NOT NULL UNIQUE DEFAULT gen_random_uuid(),
  ...
);
```

## Частые ошибки

- Email, телефон или ИНН как первичный ключ.
- `integer` вместо `bigint` — переполнение на 2,1 млрд и болезненная миграция.
- UUIDv4 как PK огромной таблицы с интенсивной вставкой.
- Хранить UUID в `text` (36+ байт и медленные сравнения) вместо `uuid`.
- Показывать последовательные id там, где это раскрывает бизнес-метрики или упрощает перебор (IDOR).

## Что важно помнить

- PK должен быть уникальным, неизменным и компактным.
- По умолчанию — `bigint GENERATED ALWAYS AS IDENTITY`.
- UUID — для распределённой генерации и публичных id; для ключей — UUIDv7.

## Мини-шпаргалка

- `bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY`.
- `uuid DEFAULT uuidv7()` (PG 18+), `gen_random_uuid()` (v4).
- Естественный ключ → `UNIQUE`.
- Внутренний id + `public_id` для API.
