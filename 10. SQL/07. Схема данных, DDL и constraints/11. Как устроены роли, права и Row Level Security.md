# Как устроены роли, права и Row Level Security

> [!NOTE]
> В PostgreSQL и пользователи, и группы — это **роли**: роль с `LOGIN` может подключаться, роль без него служит группой прав, и одни роли входят в другие (`GRANT readonly TO analyst`). Права выдаются на объекты через `GRANT`/`REVOKE`: `CONNECT` на базу, `USAGE` на схему, `SELECT`/`INSERT`/`UPDATE`/`DELETE` на таблицы (можно и на отдельные столбцы). Принцип наименьших привилегий: приложение подключается не суперпользователем и не владельцем таблиц, миграции — отдельной ролью. **Row Level Security (RLS)** добавляет фильтр на уровне строк: политики (`CREATE POLICY`) определяют, какие строки роль может видеть и изменять, — основа мультиарендности в одной таблице и подхода Supabase, где клиент обращается к базе напрямую.

## Вопрос

Как в PostgreSQL устроены роли и права и что такое Row Level Security?

## Роли

```sql
CREATE ROLE readonly NOLOGIN;                        -- группа
CREATE ROLE app_user LOGIN PASSWORD '...';           -- пользователь приложения
CREATE ROLE migrator LOGIN PASSWORD '...';           -- владелец схемы, только для миграций
GRANT readonly TO analyst;                           -- членство в группе
```

## Выдача прав

```sql
GRANT CONNECT ON DATABASE shop TO app_user;
GRANT USAGE ON SCHEMA public TO app_user;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app_user;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO app_user;

-- для будущих таблиц, созданных migrator
ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_user;

-- права на отдельные столбцы
GRANT SELECT (id, name, avatar_url) ON users TO support;
```

## Принцип наименьших привилегий

| Роль | Права |
| --- | --- |
| `migrator` | Владелец схемы, `CREATE`, DDL |
| `app_user` | Только DML на нужные таблицы |
| `readonly` / `analyst` | `SELECT`, часто на реплике |
| `postgres` (superuser) | Только администрирование, не в приложении |

Если приложение взломают через SQL-инъекцию, ущерб ограничен правами его роли: `DROP TABLE` или чтение `pg_shadow` будут недоступны.

## Row Level Security

```sql
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

-- пользователь видит и меняет только документы своей организации
CREATE POLICY tenant_isolation ON documents
  USING (tenant_id = current_setting('app.tenant_id')::bigint)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::bigint);
```

```ts
// в начале транзакции приложение задаёт контекст
await tx.query("SELECT set_config('app.tenant_id', $1, true)", [String(tenantId)]);  // true = только эта транзакция
const docs = await tx.query("SELECT * FROM documents");    // фильтр применится автоматически
```

| Часть политики | Что делает |
| --- | --- |
| `USING (...)` | Какие существующие строки видны для `SELECT`/`UPDATE`/`DELETE` |
| `WITH CHECK (...)` | Каким условиям должны удовлетворять новые/изменённые строки |
| `FOR SELECT | INSERT | UPDATE | DELETE` | Для каких операций |
| `TO role` | Для каких ролей |

## Нюансы RLS

- Владелец таблицы и суперпользователь обходят RLS (для владельца — `ALTER TABLE ... FORCE ROW LEVEL SECURITY`).
- Если RLS включён, но политик нет, — доступ запрещён ко всем строкам (default deny).
- Условие политики добавляется к каждому запросу — нужен индекс по `tenant_id`.
- С пулом соединений контекст задают на транзакцию (`set_config(..., true)` / `SET LOCAL`), иначе он «протечёт» к другому запросу.

## Частые ошибки

- Приложение работает под `postgres` или владельцем таблиц.
- Забыть `ALTER DEFAULT PRIVILEGES` — новые таблицы недоступны приложению.
- Задать tenant через `SET` на уровне сессии при пуле соединений.
- Считать RLS заменой проверок авторизации в API — это дополнительный слой.

## Что важно помнить

- Роль = пользователь или группа.
- `GRANT` на базу, схему и объекты; минимум прав для приложения.
- RLS фильтрует строки политиками на уровне базы.

## Мини-шпаргалка

- `CREATE ROLE name LOGIN | NOLOGIN`.
- `GRANT ... ON ... TO ...`, `REVOKE`.
- `ALTER DEFAULT PRIVILEGES`.
- `ENABLE ROW LEVEL SECURITY`, `CREATE POLICY ... USING ... WITH CHECK ...`.
- `set_config('app.x', v, true)`.
