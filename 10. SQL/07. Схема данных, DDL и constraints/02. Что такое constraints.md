# Что такое constraints

> [!NOTE]
> **Constraints (ограничения)** — правила целостности, которые база проверяет при каждой вставке и изменении и отклоняет операцию при нарушении. Основные: `NOT NULL`, `PRIMARY KEY`, `UNIQUE`, `FOREIGN KEY`, `CHECK`, `DEFAULT` (строго говоря, значение по умолчанию, а не ограничение) и в PostgreSQL — `EXCLUDE`. Ограничения — **последняя линия защиты**: валидация в приложении может быть обойдена другим сервисом, скриптом или гонкой двух запросов, а база гарантирует правило всегда. Ограничениям дают понятные имена: по имени из ошибки (`23505 unique_violation`, `orders_total_check`) приложение превращает исключение в осмысленный ответ API.

## Вопрос

Что такое constraints и зачем они нужны?

## Виды ограничений

| Ограничение | Гарантирует |
| --- | --- |
| `NOT NULL` | Значение обязательно |
| `PRIMARY KEY` | Уникальный и не-`NULL` идентификатор строки |
| `UNIQUE` | Нет повторов значения или набора столбцов |
| `FOREIGN KEY` | Ссылка указывает на существующую строку |
| `CHECK` | Значение удовлетворяет условию |
| `EXCLUDE` (PostgreSQL) | Нет пересекающихся строк по оператору (например, интервалы бронирований) |

## Пример

```sql
CREATE TABLE orders (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id    bigint NOT NULL,
  status     text   NOT NULL DEFAULT 'new',
  total      numeric(12, 2) NOT NULL,
  promo_code text,
  created_at timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT orders_user_fk      FOREIGN KEY (user_id) REFERENCES users (id),
  CONSTRAINT orders_status_check CHECK (status IN ('new', 'paid', 'shipped', 'cancelled')),
  CONSTRAINT orders_total_check  CHECK (total >= 0),
  CONSTRAINT orders_promo_uniq   UNIQUE (user_id, promo_code)
);
```

## Почему не только валидация в приложении

```text
Запрос A: проверил, что email свободен → INSERT
Запрос B: проверил, что email свободен → INSERT     ← гонка: два одинаковых email
```

Проверка «SELECT, потом INSERT» не защищает от конкурентных запросов — `UNIQUE` защищает.

## Обработка ошибок в приложении

```ts
try {
  await db.query("INSERT INTO users (email) VALUES ($1)", [email]);
} catch (e) {
  if (e.code === "23505" && e.constraint === "users_email_key") {
    throw new ConflictException("Email уже зарегистрирован");
  }
  throw e;
}
```

| SQLSTATE | Ошибка |
| --- | --- |
| `23502` | `not_null_violation` |
| `23503` | `foreign_key_violation` |
| `23505` | `unique_violation` |
| `23514` | `check_violation` |
| `23P01` | `exclusion_violation` |

## Добавление ограничения к большой таблице

```sql
-- без долгой блокировки: сначала только для новых строк
ALTER TABLE orders ADD CONSTRAINT orders_total_check CHECK (total >= 0) NOT VALID;
-- затем проверка старых строк без блокировки записи
ALTER TABLE orders VALIDATE CONSTRAINT orders_total_check;
```

## Отложенная проверка

```sql
ALTER TABLE employees
  ADD CONSTRAINT employees_manager_fk FOREIGN KEY (manager_id) REFERENCES employees (id)
  DEFERRABLE INITIALLY DEFERRED;   -- проверяется при COMMIT, а не на каждой команде
```

Полезно для циклических ссылок и массовых перестановок.

## Частые ошибки

- Полагаться только на валидацию в коде.
- Безымянные ограничения — непонятные ошибки в логах.
- `NOT NULL` забыт на обязательных полях — «грязные» данные копятся годами.
- Добавлять `CHECK`/`FK` к большой таблице без `NOT VALID`.

## Что важно помнить

- Ограничения гарантируют целостность независимо от приложения.
- Только база защищает от гонок при проверке уникальности.
- Имена ограничений — часть контракта с приложением.

## Мини-шпаргалка

- `NOT NULL`, `PRIMARY KEY`, `UNIQUE`, `FOREIGN KEY`, `CHECK`, `EXCLUDE`.
- `CONSTRAINT name ...`.
- `NOT VALID` + `VALIDATE CONSTRAINT`.
- `DEFERRABLE INITIALLY DEFERRED`.
