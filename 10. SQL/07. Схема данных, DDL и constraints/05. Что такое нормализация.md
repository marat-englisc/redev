# Что такое нормализация

> [!NOTE]
> **Нормализация** — проектирование схемы так, чтобы каждый факт хранился **в одном месте**. Это устраняет **аномалии**: обновления (поменяли адрес клиента в одном заказе, а в других остался старый), вставки (нельзя завести товар без заказа) и удаления (удалили последний заказ — потеряли клиента). Практически важны три нормальные формы: **1НФ** — атомарные значения, без списков в ячейке и повторяющихся групп; **2НФ** — неключевые атрибуты зависят от **всего** составного ключа; **3НФ** — нет транзитивных зависимостей (неключевой атрибут не зависит от другого неключевого). **Денормализация** — осознанное дублирование ради скорости чтения (счётчики, снимок цены в заказе, материализованные представления) с механизмом поддержания согласованности.

## Вопрос

Что такое нормализация и когда допустима денормализация?

## Ненормализованная таблица

```text
orders
id | customer_name | customer_email | customer_city | products
1  | Anna          | anna@x.com     | Moscow        | Keyboard, Mouse
2  | Anna          | anna@x.com     | Moscow        | Monitor
```

Проблемы: email Анны дублируется (аномалия обновления), список товаров в одной строке (нельзя посчитать продажи по товару), нельзя завести клиента без заказа.

## 1НФ — атомарность

```text
✗ products = 'Keyboard, Mouse'
✓ отдельная таблица order_items (order_id, product_id, qty)
```

Массивы и JSON в PostgreSQL формально не нарушают работу, но если по элементам нужно фильтровать, соединять и считать — это сигнал вынести их в таблицу.

## 2НФ — зависимость от всего ключа

```text
order_items (order_id, product_id, qty, product_title)
                                        ↑ зависит только от product_id
```

`product_title` переносим в `products`.

## 3НФ — без транзитивных зависимостей

```text
users (id, city_id, city_name)
                    ↑ зависит от city_id, а не от id
```

`city_name` переносим в `cities`.

## Нормализованная схема

```sql
CREATE TABLE customers (id bigint PRIMARY KEY, name text NOT NULL, email text NOT NULL UNIQUE);
CREATE TABLE products  (id bigint PRIMARY KEY, title text NOT NULL, price numeric(12,2) NOT NULL);
CREATE TABLE orders    (id bigint PRIMARY KEY, customer_id bigint NOT NULL REFERENCES customers (id),
                        created_at timestamptz NOT NULL DEFAULT now());
CREATE TABLE order_items (
  order_id   bigint NOT NULL REFERENCES orders (id) ON DELETE CASCADE,
  product_id bigint NOT NULL REFERENCES products (id),
  qty        int    NOT NULL CHECK (qty > 0),
  unit_price numeric(12,2) NOT NULL,      -- снимок цены на момент покупки
  PRIMARY KEY (order_id, product_id)
);
```

`unit_price` в `order_items` — не нарушение: это **исторический факт** (цена в момент заказа), а не копия текущей цены.

## Денормализация

| Приём | Зачем | Как поддерживать |
| --- | --- | --- |
| Счётчик `posts.comments_count` | Не считать `count(*)` на каждый просмотр | Триггер или обновление в той же транзакции |
| `orders.total` | Быстрые отчёты | Пересчёт при изменении позиций |
| Materialized view | Тяжёлые агрегаты | `REFRESH MATERIALIZED VIEW` по расписанию |
| Копия данных в поисковом индексе / кеше | Скорость | События, CDC |

Правило: сначала нормализованная схема, денормализация — по измеренной проблеме производительности.

## Частые ошибки

- Списки через запятую в ячейке.
- Копировать имя/email пользователя в каждую связанную таблицу.
- Путать снимок исторического значения с дублированием.
- Денормализация без механизма синхронизации — расхождения данных.

## Что важно помнить

- Нормализация: один факт — одно место.
- 1НФ — атомарность, 2НФ — весь ключ, 3НФ — без транзитивных зависимостей.
- Денормализация — осознанный компромисс с планом согласованности.

## Мини-шпаргалка

- Повторяющиеся данные → отдельная таблица + FK.
- Список в ячейке → связующая таблица.
- Исторические значения (цена в заказе) — хранить снимок.
- Денормализация: счётчики, MV, кеш.
