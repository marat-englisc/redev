# Что такое UNIQUE

> [!NOTE]
> `UNIQUE` гарантирует, что значение столбца (или комбинация столбцов) **не повторяется** в таблице. В PostgreSQL ограничение реализуется уникальным B-tree индексом, поэтому сразу ускоряет поиск по этому ключу. Важные нюансы: `NULL` по умолчанию **не считаются равными** — строк с `NULL` может быть сколько угодно (в PostgreSQL 15+ это меняет `UNIQUE NULLS NOT DISTINCT`); уникальность «без учёта регистра» делают индексом по выражению `lower(email)` или типом `citext`; уникальность только среди части строк (например, неудалённых) — **частичным уникальным индексом**. Это единственная надёжная защита от дублей при конкурентных запросах.

## Вопрос

Что такое `UNIQUE` и какие у него нюансы?

## Одиночный и составной

```sql
CREATE TABLE users (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text NOT NULL UNIQUE
);

CREATE TABLE memberships (
  user_id bigint NOT NULL REFERENCES users (id),
  team_id bigint NOT NULL REFERENCES teams (id),
  role    text   NOT NULL,
  UNIQUE (user_id, team_id)        -- пользователь в команде один раз
);
```

Составной `UNIQUE (a, b)` разрешает одинаковые `a` с разными `b`.

## UNIQUE и PRIMARY KEY

| | `PRIMARY KEY` | `UNIQUE` |
| --- | --- | --- |
| Сколько в таблице | Один | Сколько угодно |
| `NULL` | Запрещён | Разрешён (по умолчанию несколько) |
| Назначение | Идентификатор строки | Бизнес-уникальность (email, sku, slug) |

## NULL в уникальных столбцах

```sql
CREATE TABLE devices (serial text UNIQUE);
INSERT INTO devices VALUES (NULL), (NULL);    -- ✓ обе строки вставятся

-- PostgreSQL 15+
CREATE TABLE devices (serial text UNIQUE NULLS NOT DISTINCT);
INSERT INTO devices VALUES (NULL), (NULL);    -- ✗ второй NULL — нарушение
```

## Без учёта регистра

```sql
CREATE UNIQUE INDEX users_email_lower_uniq ON users (lower(email));
-- 'Anna@X.com' и 'anna@x.com' теперь конфликтуют

-- или расширение citext
CREATE EXTENSION IF NOT EXISTS citext;
ALTER TABLE users ALTER COLUMN email TYPE citext;
```

## Частичный уникальный индекс

```sql
-- slug уникален только среди неудалённых статей (soft delete)
CREATE UNIQUE INDEX articles_slug_active_uniq ON articles (slug) WHERE deleted_at IS NULL;

-- у пользователя только один основной адрес
CREATE UNIQUE INDEX addresses_one_primary ON addresses (user_id) WHERE is_primary;
```

Частичный индекс — это индекс, а не constraint, поэтому для `ON CONFLICT` указывают столбцы и то же условие: `ON CONFLICT (slug) WHERE deleted_at IS NULL`.

## UNIQUE и upsert

```sql
INSERT INTO product_stats (product_id, views) VALUES ($1, 1)
ON CONFLICT (product_id) DO UPDATE SET views = product_stats.views + 1;
```

`ON CONFLICT` требует уникального ограничения или индекса на этих столбцах. Подробнее — [UPSERT](<../08. Изменение данных и миграции/03. Что такое UPSERT.md>).

## Частые ошибки

- Проверять уникальность `SELECT`-ом в приложении вместо ограничения.
- Ожидать, что `UNIQUE` запрещает несколько `NULL`.
- Уникальный email с учётом регистра.
- Soft delete + обычный `UNIQUE` — удалённая запись блокирует повторное создание.

## Что важно помнить

- `UNIQUE` = уникальный индекс + гарантия от гонок.
- `NULL` по умолчанию не конфликтуют между собой.
- Выражения и частичные индексы решают реальные бизнес-правила.

## Мини-шпаргалка

- `col text UNIQUE`, `UNIQUE (a, b)`.
- `UNIQUE NULLS NOT DISTINCT` (PG 15+).
- `CREATE UNIQUE INDEX ... (lower(email))`.
- `CREATE UNIQUE INDEX ... WHERE deleted_at IS NULL`.
