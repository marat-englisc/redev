# Почему JOIN может создавать дубли

> [!NOTE]
> JOIN возвращает строку на **каждую подходящую пару**, поэтому при связи one-to-many строка «одной» стороны повторяется столько раз, сколько у неё совпадений. Это не ошибка СУБД, а следствие кардинальности. Проблемы начинаются, когда: (1) соединяют **две независимые one-to-many** ветки (заказы и тикеты пользователя) — получается произведение `orders × tickets` и завышенные суммы («fan-out»); (2) условие `ON` неполное (забыт `tenant_id`, версия, дата действия). Лечат не `DISTINCT`, а правильной структурой: **агрегировать каждую ветку до JOIN**, использовать `EXISTS` вместо JOIN для проверки наличия, проверять уникальность ключа справа.

## Вопрос

Почему после JOIN появляются дубли и как это исправить?

## Нормальное размножение строк

```sql
SELECT u.name, o.id
FROM users u
JOIN orders o ON o.user_id = u.id;
-- Anna | 10
-- Anna | 11     ← Anna дважды, потому что у неё два заказа
```

Это ожидаемо: результат — на уровне заказов.

## Fan-out: две ветки one-to-many

```sql
-- ✗ у Anna 2 заказа и 3 тикета → 6 строк, sum(total) утроена
SELECT u.id, sum(o.total) AS revenue, count(t.id) AS tickets
FROM users u
LEFT JOIN orders o  ON o.user_id = u.id
LEFT JOIN tickets t ON t.user_id = u.id
GROUP BY u.id;
```

```sql
-- ✓ агрегировать каждую ветку отдельно
SELECT u.id,
       COALESCE(o.revenue, 0) AS revenue,
       COALESCE(t.tickets, 0) AS tickets
FROM users u
LEFT JOIN (
  SELECT user_id, sum(total) AS revenue FROM orders GROUP BY user_id
) o ON o.user_id = u.id
LEFT JOIN (
  SELECT user_id, count(*) AS tickets FROM tickets GROUP BY user_id
) t ON t.user_id = u.id;
```

Альтернатива — скалярные подзапросы или `LATERAL`.

## Неполное условие ON

```sql
-- ✗ цена берётся из всех версий прайса
JOIN prices p ON p.product_id = oi.product_id

-- ✓ только действующая на дату заказа
JOIN prices p ON p.product_id = oi.product_id
             AND o.created_at >= p.valid_from
             AND (p.valid_to IS NULL OR o.created_at < p.valid_to)
```

В мультиарендных системах типичный баг — соединение без `tenant_id`.

## Проверка наличия — EXISTS, не JOIN

```sql
-- ✗ пользователь повторяется на каждый оплаченный заказ
SELECT u.* FROM users u JOIN orders o ON o.user_id = u.id AND o.status = 'paid';

-- ✓
SELECT u.* FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id AND o.status = 'paid');
```

## Как найти причину

```sql
-- уникален ли ключ справа?
SELECT product_id, count(*) FROM prices GROUP BY product_id HAVING count(*) > 1;

-- сравнить число строк до и после JOIN
SELECT count(*) FROM orders;
SELECT count(*) FROM orders o JOIN prices p ON p.product_id = o.product_id;
```

## Частые ошибки

- «Чинить» дубли `DISTINCT` или `count(DISTINCT ...)` без понимания причины — `sum` всё равно останется завышенной.
- Агрегировать после JOIN нескольких one-to-many таблиц.
- Не учитывать историчность (версии, периоды) в `ON`.

## Что важно помнить

- Количество строк после JOIN = количество подходящих пар.
- Две one-to-many ветки в одном запросе → произведение строк.
- Агрегируйте до JOIN и проверяйте уникальность ключа справа.

## Мини-шпаргалка

- 1:N — повтор «одной» стороны — норма.
- Несколько 1:N — pre-aggregate в подзапросах/CTE.
- Наличие — `EXISTS`.
- Проверка: `GROUP BY key HAVING count(*) > 1`.
