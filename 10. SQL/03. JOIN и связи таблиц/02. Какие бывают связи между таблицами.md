# Какие бывают связи между таблицами

> [!NOTE]
> Связи описывают, сколько строк одной таблицы соответствует строке другой. **One-to-many** (пользователь → заказы) — внешний ключ на стороне «многих». **One-to-one** (пользователь → профиль) — внешний ключ с `UNIQUE` (часто он же и первичный ключ). **Many-to-many** (статьи ↔ теги) — через **связующую таблицу** с двумя внешними ключами и составным первичным ключом; в неё же кладут атрибуты связи (роль, дата, количество). Связь фиксируют внешним ключом с `ON DELETE`-политикой, а обязательность — через `NOT NULL`. Понимание кардинальности нужно, чтобы предсказать число строк после JOIN.

## Вопрос

Какие бывают связи между таблицами и как их реализовать?

## One-to-many

```sql
CREATE TABLE users (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text NOT NULL UNIQUE
);

CREATE TABLE orders (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id bigint NOT NULL REFERENCES users (id),
  total numeric(12, 2) NOT NULL
);

CREATE INDEX orders_user_id_idx ON orders (user_id);   -- PostgreSQL не создаёт его сам
```

Самая частая связь: категория → товары, пост → комментарии.

## One-to-one

```sql
CREATE TABLE user_profiles (
  user_id bigint PRIMARY KEY REFERENCES users (id) ON DELETE CASCADE,
  bio text,
  avatar_url text
);
```

`PRIMARY KEY` на внешнем ключе гарантирует не больше одного профиля на пользователя. Зачем выносить в отдельную таблицу: редко используемые или тяжёлые поля, разные права доступа, опциональная часть сущности.

## Many-to-many

```sql
CREATE TABLE tags (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL UNIQUE
);

CREATE TABLE post_tags (
  post_id bigint NOT NULL REFERENCES posts (id) ON DELETE CASCADE,
  tag_id  bigint NOT NULL REFERENCES tags (id)  ON DELETE CASCADE,
  created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (post_id, tag_id)
);

CREATE INDEX post_tags_tag_id_idx ON post_tags (tag_id);  -- для поиска постов по тегу
```

```sql
SELECT p.title
FROM posts p
JOIN post_tags pt ON pt.post_id = p.id
JOIN tags t       ON t.id = pt.tag_id
WHERE t.name = 'sql';
```

Составной PK запрещает дубли пары и сам служит индексом для поиска тегов поста.

## Политики ON DELETE

| Политика | Поведение | Когда |
| --- | --- | --- |
| `NO ACTION` / `RESTRICT` | Запрет удаления родителя с детьми | По умолчанию, бизнес-данные |
| `CASCADE` | Удалить детей | Зависимые данные (профиль, связи m2m) |
| `SET NULL` | Обнулить ссылку | Необязательная связь |
| `SET DEFAULT` | Значение по умолчанию | Редко |

## Связь с кардинальностью JOIN

| Связь | Строк после JOIN от «одной» стороны |
| --- | --- |
| 1:1 | Не больше одной на строку |
| 1:N | N строк на строку |
| M:N | Произведение — легко получить «взрыв» строк |

## Полиморфные связи

```sql
-- ✗ comments(commentable_type, commentable_id) — внешний ключ невозможен
-- ✓ отдельные nullable FK + CHECK, что заполнен ровно один
CREATE TABLE comments (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  post_id  bigint REFERENCES posts (id),
  photo_id bigint REFERENCES photos (id),
  CHECK (num_nonnulls(post_id, photo_id) = 1)
);
```

## Частые ошибки

- Хранить many-to-many в массиве или строке через запятую (`tags = 'sql,db'`).
- Забыть индекс на внешнем ключе.
- Связующая таблица без уникальности пары.
- `ON DELETE CASCADE` на критичных данных (удаление пользователя стирает платежи).

## Что важно помнить

- FK всегда на стороне «многих».
- 1:1 — FK + `UNIQUE` / `PRIMARY KEY`.
- M:N — связующая таблица с составным ключом и атрибутами связи.

## Мини-шпаргалка

- `REFERENCES parent (id)`.
- `ON DELETE CASCADE | SET NULL | RESTRICT`.
- `PRIMARY KEY (a_id, b_id)` в связующей таблице.
- Индекс на каждый FK.
