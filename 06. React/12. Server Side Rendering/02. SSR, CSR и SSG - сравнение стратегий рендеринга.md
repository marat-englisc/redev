# SSR, CSR и SSG: сравнение стратегий рендеринга

> [!NOTE]
> **CSR (Client-Side Rendering)** — сервер отдает почти пустой HTML и JS-бандл, а страницу строит браузер. **SSR (Server-Side Rendering)** — HTML генерируется на сервере на каждый запрос. **SSG (Static Site Generation)** — HTML генерируется один раз при сборке и раздается с CDN. Промежуточные варианты: **ISR** (статика с периодической перегенерацией) и **PPR / streaming** (статическая оболочка + динамические части). Выбор зависит от того, как часто меняются данные, нужны ли SEO и персонализация.

## Вопрос

Чем SSR отличается от CSR и от SSG? Когда выбрать каждую стратегию?

## Как выглядит ответ сервера

```html
<!-- CSR -->
<body>
  <div id="root"></div>
  <script src="/bundle.js"></script>
</body>

<!-- SSR / SSG -->
<body>
  <div id="root"><h1>iPhone 16</h1><p>Цена: 99 990 ₽</p>...</div>
  <script src="/bundle.js"></script>
</body>
```

## Сравнение

| | CSR | SSR | SSG |
| --- | --- | --- | --- |
| Где строится HTML | браузер | сервер, на каждый запрос | сервер, при сборке |
| TTFB | быстрый (статичный файл) | медленнее (рендер + данные) | самый быстрый (CDN) |
| FCP / LCP | медленный — после загрузки JS | быстрый | самый быстрый |
| SEO | хуже, зависит от рендеринга JS ботом | хорошее | хорошее |
| Актуальность данных | всегда свежие (запрос с клиента) | свежие на момент запроса | на момент сборки |
| Персонализация | да | да | нет (только на клиенте) |
| Нагрузка на сервер | минимальная | высокая | минимальная |
| Хостинг | любой статический | Node / edge | любой статический / CDN |
| Навигация после загрузки | мгновенная (SPA) | SPA после гидрации | SPA после гидрации |

## Когда что выбирать

| Стратегия | Подходит |
| --- | --- |
| CSR | админки, дашборды, приложения за логином, где SEO не важен |
| SSR | каталоги с часто меняющимися ценами, персонализированные страницы, поиск |
| SSG | документация, блог, лендинги, маркетинговые страницы |
| ISR | каталог товаров, статьи с редкими изменениями — статика + обновление по таймеру или событию |

## Пример в Next.js App Router

```jsx
// SSG: по умолчанию, если нет динамических API
export default async function Page() {
  const posts = await fetch("https://api.example.com/posts", { cache: "force-cache" }).then((r) => r.json());
  return <PostList posts={posts} />;
}

// ISR: перегенерация не чаще раза в час
export const revalidate = 3600;

// SSR: динамический рендер на каждый запрос
export const dynamic = "force-dynamic";
```

## Что важно помнить

- Стратегии комбинируются: разные маршруты одного приложения могут рендериться по-разному.
- После гидрации SSR и SSG-страницы работают как SPA.
- Googlebot выполняет JS, но с задержкой, а другие боты и превью соцсетей — часто нет.
- Метрики Core Web Vitals (LCP, INP, CLS) обычно лучше у SSR/SSG при правильной оптимизации JS.

## Мини-шпаргалка

CSR — HTML в браузере, просто, но медленный первый показ и слабое SEO. SSR — HTML на каждый запрос, свежие данные и SEO, нагрузка на сервер. SSG — HTML при сборке, быстрее всего, данные устаревают. ISR — статика с обновлением.
