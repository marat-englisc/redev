# Streaming SSR: как работает и чем отличается от обычного SSR

> [!NOTE]
> **Streaming SSR** — отправка HTML **частями по мере готовности**, а не одним ответом после рендера всей страницы. Сервер сразу отдает оболочку (shell) с fallback-ами границ `<Suspense>`, а когда медленные части готовы, дописывает их HTML в тот же поток вместе с небольшим скриптом, который вставляет их на место. В React 18 это делает `renderToPipeableStream` (Node) и `renderToReadableStream` (Web Streams, edge). В связке с selective hydration части становятся интерактивными независимо.

## Вопрос

Что такое streaming SSR и как он работает? Чем он отличается от обычного SSR?

## Обычный SSR: «всё или ничего»

```text
запрос → [загрузить ВСЕ данные] → [отрендерить ВСЮ страницу] → [отправить HTML]
         → [загрузить ВЕСЬ JS] → [гидрировать ВСЁ]
```

Самый медленный запрос (например, комментарии) задерживает всю страницу.

## Streaming SSR

```jsx
function ProductPage() {
  return (
    <Layout>
      <ProductInfo />                       {/* быстро */}
      <Suspense fallback={<ReviewsSkeleton />}>
        <Reviews />                         {/* медленный запрос */}
      </Suspense>
    </Layout>
  );
}
```

```text
t=50ms   → shell: Layout + ProductInfo + <ReviewsSkeleton/>   (браузер уже рисует)
t=800ms  → <template id="B:1">...HTML отзывов...</template>
           <script>$RC("B:1", ...)</script>                    (скрипт заменяет skeleton)
```

```jsx
import { renderToPipeableStream } from "react-dom/server";

app.get("/", (req, res) => {
  const { pipe, abort } = renderToPipeableStream(<App />, {
    bootstrapScripts: ["/client.js"],
    onShellReady() {
      res.statusCode = 200;
      res.setHeader("content-type", "text/html");
      pipe(res);                     // начинаем стримить оболочку
    },
    onShellError() {
      res.statusCode = 500;
      res.send("<h1>Ошибка</h1>");
    },
  });
  setTimeout(abort, 10_000);        // не держать соединение бесконечно
});
```

## Сравнение

| | Обычный SSR | Streaming SSR |
| --- | --- | --- |
| API React | `renderToString` | `renderToPipeableStream`, `renderToReadableStream` |
| Когда уходит первый байт | после рендера всей страницы | сразу после готовности shell |
| Медленные данные | блокируют всё | блокируют только свою границу Suspense |
| Suspense и `lazy` | не поддерживаются | поддерживаются |
| Гидрация | целиком | по частям (selective hydration) |
| TTFB, FCP | хуже | лучше |

## Нюансы

- **Статус и заголовки** отправляются вместе с shell — после начала стрима их нельзя изменить. Ошибки внутри границ обрабатываются на клиенте.
- **Боты**: для поисковиков можно ждать полной готовности (`onAllReady`), чтобы отдать полный HTML.
- **Прокси и буферизация**: некоторые прокси (nginx с `proxy_buffering`) и сжатие могут буферизовать поток.
- **Порядок контента**: HTML частей приходит в конце документа и переставляется скриптом — без JS части не встанут на место.

## Streaming в Next.js

App Router стримит автоматически: `loading.tsx` создает границу Suspense для сегмента, а `async` Server Components внутри `<Suspense>` догружаются потоком.

## Что важно помнить

- Границы Suspense определяют «куски» стрима — проектируйте их осознанно.
- Shell должен быть быстрым: не кладите медленные запросы вне границ Suspense.
- `renderToString` с Suspense отдаст fallback и не дождется данных.

## Мини-шпаргалка

Streaming SSR: shell сразу, медленные части — потоком по границам Suspense. `renderToPipeableStream` / `renderToReadableStream`. Лучше TTFB и FCP, selective hydration. Статус ответа — до начала стрима.
