# Context и SSR

> [!NOTE]
> Обычный React Context работает при серверном рендеринге, если Provider передаёт данные конкретного запроса. Первый клиентский контекст должен совпадать с серверным.

## Вопрос

Можно ли использовать Context на сервере и как избежать смешивания данных пользователей?

## Основная идея

Context передаёт значение вниз по React-дереву. При традиционном SSR сервер может отрендерить Provider и читающие его компоненты, например с темой или локалью. Сам механизм не требует DOM, поэтому обычное чтение контекста доступно при таком рендере.

Опасность возникает не из-за Context, а из-за общего изменяемого состояния. Если серверный модуль хранит `currentUser` и меняет его для каждого запроса, параллельные запросы могут увидеть чужие данные. Контекст запроса и его store нужно создавать или передавать отдельно для каждого рендера.

RSC — отдельный случай: серверные компоненты не используют клиентский Context как универсальное серверное хранилище. В RSC-фреймворке Provider обычно объявляют в клиентском компоненте и размещают достаточно глубоко. Server Component может отрендерить такой Provider вокруг детей, но не прочитать его клиентское значение через `useContext`.

## Пример

Учебный JSX-модуль, выполняемый на сервере Node.js после преобразования JSX сборщиком. `renderToString` здесь используется для наглядности; клиентский bundle и HTTP-сервер добавляются отдельно.

```jsx
import { createContext, useContext } from 'react';
import { renderToString } from 'react-dom/server';

const LocaleContext = createContext('ru');
function Greeting() {
  const locale = useContext(LocaleContext);
  return <h1>{locale === 'ru' ? 'Здравствуйте!' : 'Hello!'}</h1>;
}
export function renderPage(locale) {
  return renderToString(
    <LocaleContext.Provider value={locale}>
      <Greeting />
    </LocaleContext.Provider>
  );
}
console.log(renderPage('ru'));
console.log(renderPage('en'));
```

Каждый вызов получает собственное значение. Здесь нет глобального изменяемого `locale`, поэтому один рендер не подменяет данные другого. Для гидрации нужно восстановить соответствующий Provider с той же локалью.

## Что важно помнить

- Не создавайте общий QueryClient или пользовательский store для всех SSR-запросов.
- Default value контекста — запасное значение, а не автоматически полученные данные запроса.
- В RSC-окружении учитывайте границу клиентского модуля и поддерживаемые способы передачи props.

## Мини-шпаргалка

Традиционный SSR → Provider работает. Данные → на запрос. Hydration → то же значение. RSC → отдельные ограничения.
