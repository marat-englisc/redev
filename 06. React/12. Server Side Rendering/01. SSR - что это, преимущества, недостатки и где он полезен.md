# SSR: что это, преимущества, недостатки и где он полезен

> [!NOTE]
> **Server-Side Rendering (SSR)** — генерация HTML страницы на сервере **на каждый запрос**. Браузер сразу получает готовую разметку с контентом, показывает ее, а затем загружает JS и гидрирует страницу. Плюсы: быстрый первый показ контента, SEO, корректные превью в соцсетях, работа на слабых устройствах. Минусы: нагрузка на сервер, более долгий TTFB, сложность инфраструктуры и гидрации. SSR особенно полезен для публичных, контентных и персонализированных страниц, которые важны для поиска.

## Вопрос

Что такое SSR? Какие у него преимущества и недостатки и в каких проектах он особенно полезен?

## Как работает

```text
Браузер → GET /product/42 → Сервер
                            ├─ загрузка данных (БД, API)
                            ├─ рендер React-дерева в HTML
                            └─ HTML + данные + ссылки на JS
Браузер ← HTML: контент виден (FCP)
         → загрузка JS → гидрация → интерактивность (TTI)
```

```jsx
// упрощенно на Express
app.get("*", async (req, res) => {
  const data = await loadData(req.url);
  const { pipe } = renderToPipeableStream(<App url={req.url} data={data} />, {
    bootstrapScripts: ["/client.js"],
    onShellReady() {
      res.setHeader("content-type", "text/html");
      pipe(res);
    },
  });
});
```

На практике SSR берут из фреймворка: Next.js, Remix / React Router, TanStack Start.

## Преимущества

| Преимущество | Почему |
| --- | --- |
| Быстрый FCP и LCP | контент в первом ответе, без ожидания JS |
| SEO | поисковики получают готовый HTML |
| Превью ссылок | Open Graph теги заполнены для конкретной страницы |
| Слабые устройства и медленная сеть | меньше работы до первого показа |
| Персонализация | страница рендерится с данными конкретного пользователя |
| Работа без JS | базовый контент виден, даже если JS упал |

## Недостатки

| Недостаток | Почему |
| --- | --- |
| Нагрузка на сервер | рендер на каждый запрос, нужно масштабирование |
| TTFB выше, чем у статики | сервер ждет данные и рендер |
| Гидрация | двойной рендер, mismatch-ошибки, «мертвый» период до TTI |
| Сложность | серверная инфраструктура, кеширование, ограничения кода (`window` нет) |
| Стоимость | нужен Node-сервер или edge-функции, а не CDN со статикой |

## Где SSR полезен

| Подходит | Можно без SSR |
| --- | --- |
| e-commerce: каталог, карточки товаров | админки и внутренние панели |
| новостные и контентные сайты, блоги с частыми обновлениями | личный кабинет за авторизацией |
| маркетплейсы, доски объявлений | дашборды с данными в реальном времени |
| лендинги с персонализацией | редакторы, игры, сложные SPA-инструменты |
| страницы, на которые ведут ссылки из соцсетей | |

Если контент меняется редко и одинаков для всех — выгоднее SSG или ISR.

## Что важно помнить

- SSR ускоряет **показ** контента, но не всегда **интерактивность** — TTI зависит от размера JS.
- Кеширование (CDN, `Cache-Control`, кеш данных) снимает большую часть нагрузки.
- Streaming SSR снижает влияние медленных запросов на TTFB.
- В Next.js App Router режим рендера выбирается на уровне маршрута: статический, динамический, ISR.

## Мини-шпаргалка

SSR = HTML на сервере на каждый запрос → быстрый контент, SEO, превью. Минусы: нагрузка, TTFB, гидрация, сложность. Для публичных, контентных и персонализированных страниц. Для приватных SPA — не обязателен.
