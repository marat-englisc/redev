# Кеширование результатов запросов и инвалидация кеша

> [!NOTE]
> **Кеширование** запросов — хранение полученных данных на клиенте, чтобы не запрашивать их повторно: при возврате на страницу, монтировании второго компонента с тем же запросом, переключении вкладок. Это ускоряет UI, снижает нагрузку на сервер и позволяет показывать данные мгновенно (stale-while-revalidate). **Инвалидация** — пометка закешированных данных как устаревших после изменения на сервере, чтобы они были перезапрошены. Именно инвалидация — самая сложная часть кеширования.

## Вопрос

Зачем кешировать результаты запросов? Что такое инвалидация кеша и как ее выполнять?

## Зачем кеш

| Без кеша | С кешем |
| --- | --- |
| каждый переход на страницу — спиннер | мгновенный показ из кеша, обновление в фоне |
| два компонента с одним запросом — два запроса | дедупликация: один запрос |
| лишняя нагрузка на API | меньше трафика |
| сложно синхронизировать данные между компонентами | один источник данных по ключу |

## Кеш в TanStack Query

```jsx
const { data } = useQuery({
  queryKey: ["products", { category, page }], // ключ кеша
  queryFn: () => fetchProducts(category, page),
  staleTime: 60_000,        // 1 минуту данные «свежие» — без повторного запроса
  gcTime: 5 * 60_000,       // неиспользуемый кеш удаляется через 5 минут
});
```

- **staleTime** — сколько данные считаются свежими;
- **gcTime** (раньше `cacheTime`) — сколько хранить неиспользуемые данные;
- устаревшие данные перезапрашиваются при монтировании, фокусе окна, восстановлении сети.

## Инвалидация

```jsx
const queryClient = useQueryClient();

const mutation = useMutation({
  mutationFn: (product) => api.updateProduct(product),
  onSuccess: (updated) => {
    // 1. пометить устаревшими все запросы списков товаров
    queryClient.invalidateQueries({ queryKey: ["products"] });
    // 2. или сразу обновить конкретную запись
    queryClient.setQueryData(["product", updated.id], updated);
  },
});
```

Стратегии:

| Стратегия | Когда |
| --- | --- |
| по времени (TTL, `staleTime`) | данные меняются предсказуемо редко |
| по событию (после мутации) | пользователь изменил данные сам |
| ручное обновление кеша (`setQueryData`) | ответ мутации уже содержит новые данные |
| по push-сообщению (WebSocket, SSE) | данные меняют другие пользователи |
| полный сброс | выход пользователя из аккаунта |

## Уровни кеширования

```text
Браузер: HTTP-кеш (Cache-Control, ETag) → Service Worker
Клиент: TanStack Query / SWR / RTK Query
CDN / прокси: s-maxage, stale-while-revalidate
Сервер: Redis, кеш данных фреймворка (Next.js fetch cache, revalidateTag)
```

## Что важно помнить

- Ключ кеша должен включать **все** параметры запроса — иначе разные данные смешаются.
- Кеш на клиенте нужно сбрасывать при смене пользователя.
- Персональные данные не кешируют на CDN (`Cache-Control: private`).
- «В информатике две сложные вещи: инвалидация кеша и именование» — цитата Фила Карлтона, популярная на собеседованиях.

## Мини-шпаргалка

Кеш запросов = мгновенный UI, дедупликация, меньше нагрузки. Ключ — все параметры. `staleTime` — свежесть, `gcTime` — хранение. Инвалидация после мутаций: `invalidateQueries` или `setQueryData`. Уровни: HTTP, клиент, CDN, сервер.
