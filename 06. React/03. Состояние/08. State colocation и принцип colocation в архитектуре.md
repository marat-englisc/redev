# State colocation и принцип colocation в архитектуре

> [!NOTE]
> **Colocation** — держать код и данные как можно ближе к месту, где они используются. Для состояния это значит: хранить state в самом нижнем компоненте, которому он нужен, и поднимать его только когда он нужен нескольким компонентам. В архитектуре — располагать стили, тесты, хуки и типы рядом с компонентом. Colocation уменьшает лишние ререндеры, связанность и упрощает удаление кода.

## Вопрос

Что такое state colocation? Как принцип colocation применяется в архитектуре компонентов?

## State colocation

```jsx
// плохо: state поиска живет в App, и ввод в поле перерендеривает всё приложение
function App() {
  const [query, setQuery] = useState("");
  return (
    <>
      <Header />
      <SearchBox query={query} onChange={setQuery} />
      <Dashboard />
    </>
  );
}

// хорошо: state там, где он нужен
function SearchBox() {
  const [query, setQuery] = useState("");
  return <input value={query} onChange={(e) => setQuery(e.target.value)} />;
}
```

Алгоритм:

1. Начните с состояния внутри компонента, который его использует.
2. Если значение понадобилось соседу — поднимите state в ближайшего общего родителя.
3. Если общий родитель далеко и prop drilling мешает — композиция через `children`, контекст или store.
4. Если state больше не нужен соседям — опустите его обратно.

Плюсы:

- ререндерится только та часть дерева, где изменился state;
- компонент самодостаточен — его легко переиспользовать и удалить;
- меньше props и связей между компонентами.

## Colocation в структуре файлов

```text
features/cart/
├── CartWidget.tsx
├── CartWidget.module.css
├── CartWidget.test.tsx
├── CartWidget.stories.tsx
├── useCart.ts
├── cart.api.ts
└── types.ts
```

Вместо структуры по типам файлов (`components/`, `styles/`, `tests/`, `hooks/`) всё, что относится к одной функции, лежит рядом. Так проще найти связанный код и удалить фичу целиком. Эта же идея лежит в основе Feature-Sliced Design и папок маршрутов в Next.js App Router.

## Серверное состояние

Данные с сервера тоже можно «колоцировать»: компонент сам вызывает `useQuery({ queryKey: ["user", id] })`, а библиотека кеширует и дедуплицирует запросы. Не нужно загружать всё наверху и передавать вниз.

## Что важно помнить

- Colocation не противоречит подъему состояния: поднимайте ровно настолько, насколько нужно.
- Глобальный store для всего подряд — антипаттерн: каждое изменение затрагивает больше подписчиков, а код связывается.
- Общий код (UI-кит, утилиты) выносят в `shared`, когда он реально переиспользуется в нескольких местах.
- Kent C. Dodds сформулировал правило: «Place code as close to where it's relevant as possible».

## Мини-шпаргалка

State — в самом нижнем компоненте, которому он нужен. Поднимать — только для общих данных. Файлы фичи — рядом. Меньше ререндеров и связанности, проще удаление.
