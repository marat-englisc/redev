# Плоское состояние

> [!NOTE]
> **Плоское состояние** уменьшает ненужную вложенность и дублирование. Его цель - упростить обновления, а не обязательно разнести каждое поле в отдельный useState.

## Вопрос

Когда стоит упростить структуру state и чем плоское представление отличается от нормализации?

## Основная идея

При глубоком объекте `course.sections[0].lessons[2].progress` одно изменение требует скопировать каждый уровень пути. Это усложняет обработчики и повышает риск мутации.

Можно хранить сущности по ID, а отношения - идентификаторами. Такой прием называют нормализацией. Одно описание урока находится в одном месте, даже если он используется в нескольких подборках.

Независимые UI-значения удобно хранить отдельно. Но тесно связанные поля иногда лучше объединить в объект или reducer, чтобы обновлять их согласованно. Плоское состояние не означает «никогда не использовать объекты».

## Пример: уроки по ID

```jsx
import { useState } from "react";

export default function Course() {
  const [lessonsById, setLessonsById] = useState({
    jsx: { id: "jsx", title: "JSX", done: false },
    state: { id: "state", title: "State", done: false },
  });
  const lessonIds = ["jsx", "state"];

  function complete(id) {
    setLessonsById(previous => ({
      ...previous,
      [id]: { ...previous[id], done: true },
    }));
  }

  return (
    <ul>
      {lessonIds.map(id => {
        const lesson = lessonsById[id];
        return (
          <li key={id}>
            {lesson.title}
            <button disabled={lesson.done} onClick={() => complete(id)}>
              {lesson.done ? "Готово" : "Завершить"}
            </button>
          </li>
        );
      })}
    </ul>
  );
}
```

Для обновления не нужно искать урок во вложенных разделах. Новую версию получает словарь и только выбранный объект.

## Что не стоит обещать

Упрощенная структура сама по себе не гарантирует меньше рендеров. Это зависит от того, какие данные передаются детям, как устроены подписки и есть ли подходящие оптимизации.

Для маленькой формы `{ name, email }` вполне понятен один объект. Нормализация добавляет косвенность и полезна прежде всего при связях и повторном использовании сущностей.

## Что важно помнить

- Глубоко вложенный state сложно обновлять иммутабельно и легко рассинхронизировать.
- Нормализуйте: сущности по id в объекте `byId` и массив `ids` для порядка.
- Храните id выбранного элемента, а не копию объекта.
- Redux Toolkit предоставляет `createEntityAdapter` для нормализованных коллекций.

## Мини-шпаргалка

- Убирай ненужную вложенность.
- Храни один факт в одном месте.
- Для связанных сущностей используй ID.
- Не дроби согласованные данные механически.
- Структура выбирается по операциям приложения.
