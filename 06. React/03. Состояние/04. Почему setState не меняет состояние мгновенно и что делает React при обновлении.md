# Почему setState не меняет состояние мгновенно и что делает React при обновлении

> [!NOTE]
> Вызов сеттера не меняет переменную state сразу — он **ставит обновление в очередь** и просит React перерендерить компонент. Текущий рендер продолжает видеть старое значение (снимок), а новое появится в следующем вызове компонента. React накапливает обновления (batching), затем рендерит компонент, сравнивает результат с прошлым и применяет изменения к DOM в фазе commit.

## Вопрос

Почему `setState` не изменяет состояние мгновенно? Что делает React при обновлении состояния?

## Основная идея

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    console.log(count); // 0 — в этом рендере count всё еще 0
  }

  return <button onClick={handleClick}>{count}</button>;
}
```

Значение `count` — константа **внутри конкретного рендера**. Обработчик замкнул снимок, и сеттер его не меняет. Новый рендер вызовет функцию компонента снова, и тогда `useState` вернет обновленное значение.

Зачем так сделано:

- **batching** — несколько обновлений в одном обработчике дают один рендер;
- **согласованность** — во время рендера props и state не меняются под ногами;
- **приоритеты** — React может отложить несрочные обновления (transitions).

## Что происходит при обновлении

```text
setState(next)
  → обновление в очередь (с приоритетом)
  → React планирует рендер
  → render phase: вызов компонента, вычисление нового JSX, reconciliation
  → commit phase: изменения DOM, ref
  → useLayoutEffect → браузер рисует → useEffect
```

Если новое значение равно старому по `Object.is`, React может пропустить рендер (bailout).

## Как получить актуальное значение

```jsx
// функциональное обновление — получает последнее значение из очереди
setCount((prev) => prev + 1);
setCount((prev) => prev + 1); // итог +2

// вычислить следующее значение заранее
const next = count + 1;
setCount(next);
console.log(next);

// отреагировать на изменение после рендера
useEffect(() => {
  console.log("count изменился:", count);
}, [count]);
```

`flushSync` заставляет применить обновление синхронно, но используется редко — например, перед прокруткой к новому элементу.

## Что важно помнить

- В классовых компонентах `this.setState` тоже асинхронен, а второй аргумент — колбэк после обновления.
- «Асинхронный» здесь не означает Promise: `await setCount()` ничего не ждет.
- Для чтения последнего значения в долгоживущих колбэках (интервалы, подписки) используйте функциональное обновление или `useRef`.
- Логи в консоли сразу после сеттера показывают старое значение — это ожидаемое поведение.

## Мини-шпаргалка

Сеттер ставит обновление в очередь, а не меняет переменную. Рендер видит снимок state. Новое значение — в следующем рендере. На основе предыдущего — `setX(prev => ...)`. После рендера — `useEffect`.
