# SRP в React: одна связная ответственность

> [!NOTE]
> Single Responsibility Principle предлагает выделять модули по причинам изменения. Для React это означает понятные обязанности компонентов и логических частей.

## Вопрос

Как понять, что компонент пора разделить? Нарушает ли SRP наличие state, эффекта и JSX одновременно?

## Смотрите на причины изменений

Форма заказа закономерно имеет state, обработчики и JSX: все это может относиться к одной связной задаче. Само количество hooks или строк не доказывает нарушение SRP. Проблема появляется, когда компонент одновременно реализует независимые правила скидки, формат сервера, отслеживание аналитики и сложную верстку.

Полезный вопрос: кто и зачем попросит изменить этот код? Изменение расчета цены, дизайна карточки и протокола API — разные причины. Их можно разделить на доменную функцию, представление и адаптер. При этом не нужно превращать каждое выражение в отдельный файл.

Выделение кастомного хука тоже не гарантирует SRP. Хук `usePageEverything`, в котором собраны все несвязанные процессы страницы, остается сложным модулем. Хорошая граница имеет предметное имя и небольшой контракт; связи между частями можно объяснить без просмотра всей реализации.

## Пример

```jsx
import { useState } from 'react';

function calculateTotal(price, quantity) {
  return price * quantity;
}

function OrderSummary({ title, total }) {
  return (
    <section>
      <h2>{title}</h2>
      <p>Итого: {total} ₽</p>
    </section>
  );
}

export default function OrderForm() {
  const [quantity, setQuantity] = useState(1);
  const total = calculateTotal(900, quantity);
  return (
    <>
      <label>
        Количество
        <select
          value={quantity}
          onChange={(event) => setQuantity(Number(event.target.value))}
        >
          <option value={1}>1</option>
          <option value={2}>2</option>
          <option value={3}>3</option>
        </select>
      </label>
      <OrderSummary title="Билеты в театр" total={total} />
    </>
  );
}
```

`calculateTotal` отвечает за правило, `OrderSummary` — за отображение результата, `OrderForm` — за выбор количества и композицию. Пока пример маленький, они могут оставаться в одном файле. При усложнении скидки ее логику можно менять и проверять отдельно от JSX.

## Когда разделение помогает

- Одна и та же логика копируется на нескольких экранах.
- Изменение верстки требует разбираться в несвязанной интеграции.
- Для проверки простого правила нужно поднимать целое приложение.
- Название компонента перестает объяснять его обязанности.

Не делите компонент только ради лимита строк. Слишком мелкие абстракции увеличивают связанность через длинные списки props и затрудняют чтение сценария.

## Что важно помнить

- SRP — одна причина для изменения, а не одна строка кода или один хук.
- Признаки нарушения: компонент меняется из-за несвязанных требований, сложно тестировать и называть.
- Бизнес-логику выносите в хуки и чистые функции, разметку — в презентационные компоненты.
- Чрезмерное дробление тоже вредно — связанную логику держите вместе.

## Мини-шпаргалка

```text
SRP → связная обязанность и понятная причина изменения
Наличие hooks + JSX само по себе допустимо
Разделение должно уменьшать сложность
```
