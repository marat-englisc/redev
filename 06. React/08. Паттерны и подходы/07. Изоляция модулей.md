# Изоляция модулей и публичный API

> [!NOTE]
> Изолированный модуль скрывает внутреннюю реализацию и предоставляет небольшой контракт для других частей приложения.

## Вопрос

Как публичные границы позволяют менять фичу, не переписывая весь проект?

## Зависеть от назначения, а не внутренностей

Представьте модуль корзины. Другой части приложения важно показать кнопку добавления и передать ID товара. Ей не обязательно знать, где хранится состояние, какая библиотека его обслуживает и как называется внутренний reducer.

Если соседние модули импортируют все внутренние файлы напрямую, любое переименование распространяется по проекту. Публичный API, например `index.ts`, показывает, что разрешено использовать снаружи. Реализация за этой границей может меняться при сохранении контракта.

Изоляция не означает полное отсутствие связей. Модули взаимодействуют через функции, компоненты, типы или события. Необходимо договориться о направлении зависимостей и не создавать циклы. Проверка линтером помогает сохранить договоренности, потому что обычная папка не запрещает глубокий импорт технически.

## Пример

```tsx
// cart/ui/AddToCartButton.tsx
import { useState } from 'react';

type Props = { productId: string; onAdd: (id: string) => void };
export function AddToCartButton({ productId, onAdd }: Props) {
  const [added, setAdded] = useState(false);
  return (
    <button
      onClick={() => {
        onAdd(productId);
        setAdded(true);
      }}
    >
      {added ? 'Добавить еще' : 'В корзину'}
    </button>
  );
}
```

```typescript
// cart/index.ts
export { AddToCartButton } from './ui/AddToCartButton';
```

```tsx
// Catalog.tsx
import { useState } from 'react';
import { AddToCartButton } from './cart';

export default function Catalog() {
  const [count, setCount] = useState(0);
  return (
    <>
      <p>Добавлено: {count}</p>
      <AddToCartButton
        productId="book-42"
        onAdd={() => setCount((n) => n + 1)}
      />
    </>
  );
}
```

Каталог использует публичный модуль `cart`. В настоящем проекте внутренний способ отправки события или хранения данных можно изменить, сохранив внешний договор. Пример показывает границу, не реализацию полного общего store.

## Нюансы

- `index.ts` с экспортом всего подряд не создает полезной инкапсуляции.
- Внутренние файлы модуля лучше связывать относительными импортами, не обходя собственный public API по кругу.
- TypeScript-типы защищают контракт при сборке, но не проверяют неизвестные данные сервера во время выполнения.
- Отдельная папка не обеспечивает изоляцию ошибок, CSS или безопасности.

## Что важно помнить

- Модуль экспортирует небольшой публичный API, а внутренности остаются скрытыми.
- Импорт в обход публичного API (`feature/model/internal`) связывает модули и мешает рефакторингу.
- Границы можно проверять ESLint-правилами `no-restricted-imports` или `eslint-plugin-boundaries`.
- Изоляция упрощает удаление, замену и тестирование фич.

## Мини-шпаргалка

```text
Снаружи → public API
Внутри → детали реализации
Маленький контракт + явное направление зависимостей
```
