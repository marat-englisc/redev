# Layered Architecture: разделение UI, сценариев и данных

> [!NOTE]
> Слоистая архитектура группирует код по ответственности. Конкретное направление зависимостей зависит от выбранного варианта архитектуры и должно быть согласованным.

## Вопрос

Какие слои полезны во frontend и должен ли домен напрямую зависеть от HTTP-клиента?

## Разделяем причины изменений

**Presentation** описывает интерфейс и пользовательские события. **Application** координирует сценарии: получить данные, применить правило, обновить состояние. **Domain** содержит смысловые правила, например расчет скидки. **Infrastructure/Data** реализует запросы к API и хранение.

Это полезная карта ответственности, но не универсальная обязательная последовательность импортов `UI → Application → Domain → Data`. Если домен должен быть независимым, он не импортирует `fetch` и конкретную базу. Application может использовать доменные функции и адаптер данных рядом либо получать реализацию через договоренный интерфейс.

Горизонтальные технические слои можно сочетать с вертикальными функциональными модулями. Например, внутри корзины есть `ui`, `model` и `api`, а не отдельные гигантские папки всех компонентов и всех запросов приложения. Дополнительные уровни оправданы, когда помогают разбирать изменения.

## Пример

```tsx
import { useState } from 'react';

// Domain: правило расчета, не зависит от React или fetch.
function applyDiscount(price: number) {
  return Math.round(price * 0.9);
}

// Data adapter: учебный источник вместо HTTP API.
async function loadPrice() {
  return 1000;
}

// Application: координация сценария.
function useOffer() {
  const [offer, setOffer] = useState<number | null>(null);
  const [pending, setPending] = useState(false);
  async function refresh() {
    setPending(true);
    try {
      setOffer(applyDiscount(await loadPrice()));
    } finally {
      setPending(false);
    }
  }
  return { offer, pending, refresh };
}

// Presentation: отображение состояния и команда пользователя.
export default function Offer() {
  const { offer, pending, refresh } = useOffer();
  return (
    <>
      <p>{offer === null ? 'Запросите цену' : `${offer} ₽`}</p>
      <button disabled={pending} onClick={refresh}>
        Получить предложение
      </button>
    </>
  );
}
```

Здесь все показано в одном файле для изучения. В проекте правило, адаптер и хук можно разделить. При замене источника цены `applyDiscount` не меняется; при изменении скидки не нужно переписывать JSX. Для реального запроса добавляют состояние ошибки.

## Нюансы

- Слой — ответственность и ограничения зависимостей, а не только имя папки.
- Не требуется отдельный класс или абстракция для каждой функции.
- Правила цены и полномочий повторно проверяет сервер.
- Избыточные слои способны усложнить небольшой CRUD-экран.

## Что важно помнить

- Типичные слои: UI → прикладная логика (хуки, сценарии) → доменная логика → инфраструктура (API, хранилища).
- Зависимости направлены в одну сторону: верхние слои зависят от нижних, не наоборот.
- UI не должен знать о формате ответов API — между ними адаптеры и маппинг.
- Слишком много слоев в маленьком проекте — overengineering.

## Мини-шпаргалка

```text
UI → отображение
Application → сценарий
Domain → правила
Data → внешний мир
Независимый Domain не импортирует конкретный HTTP adapter
```
