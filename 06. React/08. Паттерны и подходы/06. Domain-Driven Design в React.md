# Domain-Driven Design в React-приложении

> [!NOTE]
> Domain-Driven Design, DDD, помогает строить модель программы вокруг предметной области, ее языка, правил и границ. Организация папок — лишь одно из возможных следствий.

## Вопрос

Что означает DDD для frontend и почему папка `domains` сама по себе не создает доменную модель?

## Начинаем с понятий бизнеса

В интернет-магазине важны корзина, заказ, товар и правила скидки. Названия функций и типов должны отражать эти понятия: `calculateOrderTotal` понятнее, чем `processData`. Общий язык разработчиков и специалистов предметной области называют **ubiquitous language**.

**Bounded context** — граница, внутри которой термины и модель имеют определенный смысл. «Товар» для каталога описывает фотографии и характеристики, для склада — остатки и размещение, для доставки — размеры и вес. Необязательно превращать все эти модели в один универсальный frontend-тип с десятками необязательных полей.

На клиенте DDD особенно полезен, когда есть существенные бизнес-правила: расчет предложения, редактирование сложного документа, ограничения переходов заказа. Доменные функции удобно держать независимыми от React и транспорта. Однако окончательная проверка цены и прав доступа должна оставаться на сервере: клиентским вычислениям нельзя доверять как защите.

## Пример

```tsx
import { useState } from 'react';

type OrderLine = { price: number; quantity: number };

function calculateOrderTotal(lines: OrderLine[], discountPercent: number) {
  const subtotal = lines.reduce(
    (sum, line) => sum + line.price * line.quantity,
    0,
  );
  return Math.round(subtotal * (1 - discountPercent / 100));
}

export default function OrderPreview() {
  const [member, setMember] = useState(false);
  const lines = [{ price: 1000, quantity: 2 }];
  const total = calculateOrderTotal(lines, member ? 10 : 0);
  return (
    <section>
      <label>
        <input
          type="checkbox"
          checked={member}
          onChange={(event) => setMember(event.target.checked)}
        />
        Участник клуба
      </label>
      <p>Предварительная сумма: {total} ₽</p>
    </section>
  );
}
```

Правило расчета выражено отдельной функцией в терминах заказа. Его можно проверять без рендера компонента и использовать в другом UI. Для денежных вычислений большого приложения дополнительно определяют единицы хранения и правила округления.

## Нюансы

- DDD не равно «разложить все по бизнес-папкам» и не требует микросервисов.
- Не каждый bounded context совпадает с маленькой фичей или одним React-компонентом.
- API-модель можно преобразовывать в клиентскую доменную модель на границе модуля.
- Для простой страницы с CRUD сложная доменная архитектура может быть лишней.

## Что важно помнить

- DDD на фронтенде — организация кода вокруг предметных областей, а не технических слоев.
- Доменная логика должна быть отделена от React-компонентов и легко тестироваться.
- Единый язык (ubiquitous language) с бизнесом отражается в именах модулей и типов.
- Полный DDD часто избыточен для фронтенда — берут идеи bounded context и изоляции домена.

## Мини-шпаргалка

```text
Общий язык + модель правил + bounded contexts
Доменная логика независима от JSX и способа получения данных
```
