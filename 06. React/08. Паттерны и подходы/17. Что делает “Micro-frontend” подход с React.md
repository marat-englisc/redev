# Micro-frontend: независимые части одного продукта

> [!NOTE]
> Micro-frontend разделяет frontend по продуктовым областям, за которые команды могут отвечать и которые могут поставлять относительно независимо.

## Вопрос

Когда микрофронтенды оправданы и какие задачи не решаются простым динамическим импортом?

## Масштабирование разработки

У большого продукта каталог, оформление заказа и кабинет могут развиваться разными командами. Микрофронтенд задает границы владения, контракт интеграции и независимый цикл поставки. Для пользователя эти части образуют один продукт.

Интеграция бывает разной: отдельные маршруты и серверная композиция, iframe, Web Components, runtime-модули. Webpack Module Federation — один распространенный инструмент, но не обязательный «стандарт React». Он позволяет сборкам предоставлять модули и загружать их из других сборок.

Цена — сложность контрактов, версий зависимостей, маршрутизации, наблюдаемости и дизайна. Независимые релизы не означают отсутствие согласования. Особенно важно определить, кто владеет авторизацией и общими данными. Для небольшой команды модульный монолит часто проще и дает нужные границы без дополнительных сетевых и организационных затрат.

## Пример

Ниже — часть shell-приложения **после настройки Module Federation**. Имя `catalogApp/BookWidget` — remote-модуль, а не путь, который обычный сборщик понимает автоматически.

```jsx
// Shell.jsx
import { Component, lazy, Suspense } from 'react';

const BookWidget = lazy(() => import('catalogApp/BookWidget'));

class WidgetBoundary extends Component {
  state = { failed: false };
  static getDerivedStateFromError() {
    return { failed: true };
  }
  render() {
    return this.state.failed ? (
      <p>Каталог временно недоступен.</p>
    ) : (
      this.props.children
    );
  }
}

export default function Shell() {
  return (
    <main>
      <h1>Книжный магазин</h1>
      <WidgetBoundary>
        <Suspense fallback={<p>Загружаем каталог…</p>}>
          <BookWidget onSelect={(id) => alert(`Выбрана книга ${id}`)} />
        </Suspense>
      </WidgetBoundary>
    </main>
  );
}
```

```jsx
// Remote: экспортируемый модуль BookWidget.jsx
export default function BookWidget({ onSelect }) {
  return <button onClick={() => onSelect('book-42')}>Дюна</button>;
}
```

Shell предоставляет оболочку, ожидание и область восстановления после ошибок. Remote соблюдает договор `onSelect(id)`. Конфигурации сборок должны связать remote-имя, адрес и экспортируемый модуль.

## Нюансы

- Изоляция сбоев не появляется автоматически: нужны границы ошибок и продуманное поведение при недоступном remote.
- При совместном React-дереве согласуйте React и React DOM, часто через singleton shared-зависимости.
- CSS, дизайн-система и данные требуют явных границ.
- Техническое code splitting само по себе еще не делает приложение микрофронтендным.

## Что важно помнить

- Микрофронтенды позволяют командам независимо разрабатывать и деплоить части приложения.
- Способы интеграции: Module Federation, import maps, iframe, Web Components, серверная сборка.
- Риски: дублирование зависимостей, разные версии React, согласованность UI и рост сложности.
- Подход оправдан для больших организаций; маленькой команде он обычно не нужен.

## Мини-шпаргалка

```text
Граница продукта + владелец + контракт + поставка
Module Federation — один способ интеграции
Независимость команд требует договоренностей
```
