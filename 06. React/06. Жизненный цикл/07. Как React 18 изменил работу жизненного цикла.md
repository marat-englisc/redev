# Как React 18 изменил модель обновлений

> [!NOTE]
> React 18 расширил конкурентную подготовку дерева, автоматический batching и разработческие проверки эффектов. Mount/update/unmount сохранились, но нельзя считать каждый render единственной завершённой попыткой.

## Вопрос

Какие изменения React 18 важны для понимания жизненного цикла?

## Основная идея

Concurrent rendering позволяет React готовить некоторые обновления прерываемо: уступать управление, обрабатывать срочную работу и отбрасывать устаревшие варианты. Это постепенная возможность, используемая конкурентными API, а не обещание, что любое обновление теперь асинхронно и обязательно прерывается. Зафиксированный DOM по-прежнему обновляется согласованно.

С modern root появился расширенный automatic batching: обновления из Promise, таймеров и других источников могут объединяться, а не только обновления внутри React-события. Меньше промежуточных render не меняет правило снимков: уже выполняющийся обработчик по-прежнему видит прежний state.

StrictMode в разработке усилил проверку ресурсов дополнительным setup/cleanup/setup. Чистота render и симметрия эффектов стали ещё заметнее. Старые небезопасные componentWill*-методы не следует использовать для подписок и других внешних действий. Однако production тоже может повторять подготовку дерева; нельзя объяснять все повторные render исключительно StrictMode.

## Пример

```tsx
import { useState } from 'react';

export default function BatchDemo() {
  const [count, setCount] = useState(0);
  const [ready, setReady] = useState(false);

  function updateLater() {
    window.setTimeout(() => {
      setCount(c => c + 1);
      setReady(true);
    }, 100);
  }

  return <>
    <p>{count} задач; статус: {ready ? 'готово' : 'ожидание'}</p>
    <button onClick={updateLater}>Обновить два поля</button>
  </>;
}
```

В приложении с createRoot обновления двух полей из одного timeout могут объединяться. Пользователь получает согласованное представление, а не обязан видеть промежуточный count с прежним ready. Пример показывает batching, который является отдельной возможностью от transition.

## Что важно помнить

- Для React 18 исторически важен переход с legacy ReactDOM.render на createRoot.
- StrictMode-проверки не включаются в production, но реальные remount и изменения зависимостей остаются.
- Effect не обязан быть чистым вычислением: он делает побочные действия, но должен корректно их отменять/синхронизировать.
- Transition не выполняет тяжёлый JS в другом потоке.
- Формулировка «в production каждый lifecycle всегда один раз» неверна для повторных монтирований и обновлений.

## Мини-шпаргалка

React 18: concurrent-возможности + больше batching + StrictMode-проверка ресурсов. Практика: чистый render, корректные deps, симметричный cleanup.
