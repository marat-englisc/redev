# Redux Toolkit, Zustand, Context или TanStack Query — что выбрать

> [!NOTE]
> Выбор зависит от **типа состояния**. Серверные данные (списки, профили) — в инструменты кеширования: TanStack Query, SWR или RTK Query. Глобальное клиентское состояние (UI-настройки, корзина, черновики) — в Redux Toolkit, Zustand или Jotai. Редко меняющиеся зависимости (тема, текущий пользователь, i18n) — в Context. Локальное — в `useState`. Redux Toolkit оправдан в больших командах и сложных приложениях, где важны строгая структура, DevTools и единые правила.

## Вопрос

Чем отличаются Redux Toolkit, Zustand, Context и TanStack Query? Когда выбрать каждый и зачем Redux, если есть Context?

## Типы состояния

| Тип | Пример | Инструмент |
| --- | --- | --- |
| Локальное UI | открыта ли модалка, текст в поле | `useState`, `useReducer` |
| URL | фильтры, страница, вкладка | `useSearchParams`, роутер |
| Серверное | товары, заказы, профиль | TanStack Query, SWR, RTK Query |
| Глобальное клиентское | корзина, настройки, сложный редактор | Redux Toolkit, Zustand, Jotai |
| Зависимости дерева | тема, локаль, auth-пользователь | Context |
| Формы | значения, ошибки, touched | react-hook-form |

## Сравнение

| | Context | Zustand | Redux Toolkit | TanStack Query |
| --- | --- | --- | --- | --- |
| Назначение | передача значений по дереву | глобальный клиентский state | глобальный клиентский state + серверный через RTK Query | серверный state |
| Boilerplate | минимум | минимум | средний | минимум |
| Ререндеры | все потребители при смене value | только по селектору | только по селектору | по ключу запроса |
| DevTools | React DevTools | через middleware | Redux DevTools с time-travel | свои DevTools |
| Структура | нет | свободная | строгая (slices, actions) | ключи запросов |
| Провайдер | нужен | не нужен | нужен | нужен QueryClientProvider |

## Зачем Redux, если есть Context

Context — механизм **передачи** данных, а не управления состоянием:

- при изменении `value` перерендериваются все потребители; у Redux — только компоненты, чей селектор вернул новое значение;
- нет middleware, DevTools, истории изменений и стандартного способа асинхронной логики;
- для сложной логики всё равно понадобится `useReducer` — то есть ручной «мини-Redux».

## Как ответить на собеседовании

- Начинаю с локального state и поднимаю его только при необходимости.
- Серверные данные не дублирую в глобальном store — беру TanStack Query или RTK Query.
- Для небольшого глобального состояния выбираю Zustand: мало кода, селекторы, нет провайдера.
- Redux Toolkit — для больших приложений и команд: строгие соглашения, DevTools, middleware, единая архитектура, плюс RTK Query, если проект уже на Redux.
- Context — для темы, локали, DI и compound-компонентов.

## Что важно помнить

- Главная ошибка — хранить серверные данные в глобальном store вручную: кеш, гонки и инвалидацию придется писать самому.
- Можно и нужно комбинировать: TanStack Query + Zustand, RTK + RTK Query, Context + useState.
- MobX — альтернатива с реактивной моделью (observable), Jotai и Recoil — атомарная модель состояния.
- Инструмент не исправит плохую структуру: минимальный state, производные данные через селекторы, colocation.

## Мини-шпаргалка

Локальное — `useState`; URL — роутер; серверное — TanStack Query / RTK Query; глобальное клиентское — Zustand (просто) или Redux Toolkit (большие проекты); тема и локаль — Context; формы — react-hook-form. Context ≠ state-менеджер.
