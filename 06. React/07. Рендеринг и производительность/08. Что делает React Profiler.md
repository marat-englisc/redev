# React Profiler: измерение стоимости рендеров

> [!NOTE]
> Profiler помогает измерить render-работу React и найти дорогие обновления. Это инструмент проверки гипотез, а не автоматическое указание «добавить memo».

## Вопрос

Как определить, какой компонент замедляет взаимодействие, и проверить оптимизацию?

## Сценарий важнее отдельного числа

Сначала выберите действие: ввод в поиск, раскрытие строки таблицы, переключение темы. В React Developer Tools запишите профиль во время этого действия. Дерево и графики помогают увидеть, какие части участвовали в обновлении и где потрачено время.

В коде можно использовать `<Profiler>`. Его `onRender` вызывается, когда профилируемое дерево коммитит обновление. `actualDuration` показывает измеренное время render-работы обновления, а `baseDuration` оценивает стоимость рендера поддерева без оптимизаций по имеющимся измерениям. Это не время HTTP-запроса и не полный промежуток от клика до появления пикселей.

После изменения повторите тот же сценарий на сопоставимом устройстве и с теми же данными. Development-проверки, шум измерений и включенный Profiler влияют на цифры. Для близких к production измерений React предусматривает специальную сборку с поддержкой профилирования. Обычный production build не включает все измерения Profiler.

## Пример

```jsx
import { Profiler, useState } from 'react';

function Catalog({ query }) {
  const books = ['Дюна', 'Солярис', 'Основание'];
  return (
    <ul>
      {books
        .filter((book) => book.includes(query))
        .map((book) => (
          <li key={book}>{book}</li>
        ))}
    </ul>
  );
}

function report(id, phase, actualDuration, baseDuration) {
  console.table({ id, phase, actualDuration, baseDuration });
}

export default function App() {
  const [query, setQuery] = useState('');
  return (
    <>
      <input
        aria-label="Поиск книги"
        value={query}
        onChange={(event) => setQuery(event.target.value)}
      />
      <Profiler id="Catalog" onRender={report}>
        <Catalog query={query} />
      </Profiler>
    </>
  );
}
```

Ввод символа приводит к записи измерения `Catalog`. На трех книгах время будет маленьким: пример показывает подключение. Для диагностики подставляют реальные данные, а не делают вывод о скорости по учебному массиву.

## Как интерпретировать результаты

- Дорогой render может требовать более простого алгоритма, меньшего списка или локализации state.
- Частый render не обязательно медленный; важна суммарная стоимость и заметная задержка.
- Для layout, paint, сети и длинных JavaScript-задач дополнительно используйте браузерную вкладку Performance.
- Не считайте цвет блока универсальным доказательством конкретной причины тормозов.

## Что важно помнить

- Профилируйте production-подобную сборку: dev-режим медленнее и рендерит дважды.
- Flamegraph показывает время рендера каждого компонента, ranked — самые медленные.
- Включите «Record why each component rendered», чтобы видеть причину ререндера.
- Программно можно измерять компонентом `<Profiler id onRender>`.

## Мини-шпаргалка

```text
Одинаковый сценарий → запись → гипотеза → изменение → повторное измерение
actualDuration → текущая render-работа
Profiler не измеряет весь пользовательский путь
```
