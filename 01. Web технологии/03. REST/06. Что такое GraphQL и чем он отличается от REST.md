# Что такое GraphQL и чем он отличается от REST

> [!NOTE]
> **GraphQL** — язык запросов к API и среда его выполнения. Сервер описывает данные **строго типизированной схемой**, а клиент в одном запросе (обычно `POST /graphql`) указывает, какие поля ему нужны, и получает ровно их. Это решает проблемы REST с **over-fetching** (лишние поля) и **under-fetching** (нужно несколько запросов), но усложняет кеширование, защиту от тяжелых запросов и серверную часть.

## Вопрос

Что такое GraphQL? Чем он отличается от REST, какие у него плюсы и минусы и когда его выбирать?

## Основная идея

Схема на сервере:

```graphql
type User {
  id: ID!
  name: String!
  posts(first: Int): [Post!]!
}

type Post {
  id: ID!
  title: String!
}

type Query {
  user(id: ID!): User
}

type Mutation {
  createPost(title: String!): Post!
}
```

Запрос клиента — только нужные поля, вложенные связи в одном запросе:

```graphql
query UserCard($id: ID!) {
  user(id: $id) {
    name
    posts(first: 3) {
      title
    }
  }
}
```

```json
{ "data": { "user": { "name": "Анна", "posts": [{ "title": "GraphQL за 5 минут" }] } } }
```

С REST для того же понадобились бы `GET /users/1` и `GET /users/1/posts?limit=3`, и каждый ответ вернул бы все поля.

## Операции

| Операция | Для чего | Аналог в REST |
| --- | --- | --- |
| `query` | чтение | `GET` |
| `mutation` | изменение | `POST`, `PUT`, `PATCH`, `DELETE` |
| `subscription` | события в реальном времени (обычно через WebSocket) | SSE, WebSocket |

На сервере каждое поле вычисляет **резолвер** — функция, которая знает, откуда взять данные.

## REST и GraphQL

| | REST | GraphQL |
| --- | --- | --- |
| Endpoints | много URL-ресурсов | обычно один `/graphql` |
| Форма ответа | определяет сервер | определяет клиент |
| Over/under-fetching | частая проблема | решается выбором полей |
| Типизация | опционально (OpenAPI) | обязательная схема, интроспекция |
| HTTP-кеширование | простое: `GET` + `Cache-Control`, CDN | сложнее: POST-запросы, нужен клиентский нормализованный кеш |
| Ошибки | HTTP-статусы | часто `200` + массив `errors` в ответе |
| Версионирование | `/v1`, `/v2` | эволюция схемы, `@deprecated` |
| Загрузка файлов | просто | требует расширений |

## Клиенты и инструменты

- **Apollo Client**, **urql**, **Relay** — запросы, нормализованный кеш, оптимистичные обновления.
- **GraphQL Code Generator** — TypeScript-типы и хуки из схемы и запросов.
- Для простых случаев достаточно `fetch`:

```javascript
const res = await fetch("/graphql", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ query: "query($id: ID!) { user(id: $id) { name } }", variables: { id: "1" } }),
});
const { data, errors } = await res.json();
```

## Проблемы, о которых спрашивают

- **N+1 на сервере**: резолвер `posts` вызывается для каждого пользователя отдельно — решается батчингом через **DataLoader**.
- **Тяжелые запросы**: клиент может запросить глубокую вложенность — нужны ограничения глубины и сложности, persisted queries, rate limiting.
- **Кеширование**: CDN плохо кеширует POST — используют persisted queries через GET и кеш клиента.
- **Ошибки**: проверяйте не только HTTP-статус, но и поле `errors`, данные могут прийти частично.

## Когда выбирать

| GraphQL подходит | REST проще |
| --- | --- |
| много разных клиентов (web, mobile) с разными потребностями | простой CRUD |
| сложные связанные данные, экраны собирают данные из многих сущностей | публичный API с HTTP-кешированием |
| BFF-слой над несколькими микросервисами | маленькая команда без опыта GraphQL |

## Что важно помнить

- GraphQL — не база данных и не замена бэкенда: это слой API над любыми источниками.
- Один endpoint не означает отсутствие авторизации: права проверяются в резолверах для каждого поля.
- В production часто отключают интроспекцию схемы или ограничивают ее.
- tRPC — альтернатива для fullstack TypeScript-проектов: типобезопасность без схемы GraphQL.

## Мини-шпаргалка

GraphQL: схема типов, один endpoint, клиент выбирает поля. `query`, `mutation`, `subscription`, резолверы. Плюсы: нет over/under-fetching, типизация. Минусы: кеширование, N+1 (DataLoader), защита от тяжелых запросов, ошибки при статусе 200. Клиенты: Apollo, urql, Relay.
