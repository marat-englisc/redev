# Что нужно знать фронтендеру о Docker

> [!NOTE]
> **Docker** упаковывает приложение вместе с окружением (ОС-слой, Node.js, зависимости) в **образ**, из которого запускаются изолированные **контейнеры**. Фронтендеру Docker нужен, чтобы одинаково собирать проект локально и в CI, раздавать собранную статику через nginx, запускать SSR-приложение (Next.js) и поднимать зависимости разработки — API, базу, Redis — через `docker compose`.

## Вопрос

Что такое Docker и чем образ отличается от контейнера? Как написать Dockerfile для фронтенд-приложения и что такое multi-stage сборка?

## Основные понятия

| Понятие | Что это |
| --- | --- |
| Image (образ) | неизменяемый шаблон: слои файловой системы + команда запуска |
| Container | запущенный экземпляр образа |
| Dockerfile | инструкции сборки образа |
| Layer | слой образа; неизмененные слои берутся из кеша |
| Registry | хранилище образов (Docker Hub, GHCR) |
| Volume | данные, переживающие пересоздание контейнера |
| Docker Compose | описание нескольких сервисов в `compose.yaml` |

Контейнер — не виртуальная машина: он использует ядро хоста и запускается за секунды.

## SPA: сборка + nginx (multi-stage)

```dockerfile
# Этап 1: сборка
FROM node:22-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci                      # слой кешируется, пока не изменился lockfile
COPY . .
RUN npm run build

# Этап 2: только статика, без Node.js и node_modules
FROM nginx:1.27-alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
```

```nginx
# nginx.conf
server {
  listen 80;
  root /usr/share/nginx/html;

  location / {
    try_files $uri /index.html;          # клиентский роутинг SPA
  }

  location /assets/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
  }
}
```

Итоговый образ весит десятки мегабайт вместо сотен.

## SSR: Next.js

```dockerfile
FROM node:22-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci

FROM node:22-alpine AS build
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm run build               # в next.config: output: "standalone"

FROM node:22-alpine AS run
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app/.next/standalone ./
COPY --from=build /app/.next/static ./.next/static
COPY --from=build /app/public ./public
USER node
EXPOSE 3000
CMD ["node", "server.js"]
```

## docker compose для разработки

```yaml
# compose.yaml
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD: dev
    ports: ["5432:5432"]
    volumes: [pgdata:/var/lib/postgresql/data]
  redis:
    image: redis:7
    ports: ["6379:6379"]
volumes:
  pgdata:
```

Фронтенд при этом можно запускать локально через `npm run dev`, а зависимости — в контейнерах.

## Что важно помнить

- Порядок инструкций важен для кеша: сначала `package*.json` и `npm ci`, потом остальной код.
- Добавьте `.dockerignore` (`node_modules`, `.git`, `dist`, `.env`), иначе образ раздуется, а секреты попадут внутрь.
- Переменные `VITE_*` и `NEXT_PUBLIC_*` встраиваются при **сборке**: один образ на разные окружения требует runtime-конфига (например, `config.js`, генерируемого при старте контейнера).
- Не запускайте процесс от root (`USER node`), фиксируйте версии базовых образов.
- Контейнер должен корректно завершаться по `SIGTERM` — важно для SSR-сервера при перезапусках.

## Мини-шпаргалка

Образ — шаблон, контейнер — запущенный экземпляр. Multi-stage: собрать в `node`, отдать статику через `nginx` или запустить `standalone` Next.js. Кеш слоев: lockfile → `npm ci` → код. `.dockerignore`, `USER node`. Compose — БД и сервисы для разработки.
