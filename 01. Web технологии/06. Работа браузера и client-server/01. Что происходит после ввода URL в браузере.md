# Что происходит после ввода URL в браузере?

> [!NOTE]
> После ввода URL браузер разбирает адрес, проверяет cache и service worker, ищет IP через DNS, устанавливает TCP-соединение и TLS для HTTPS, отправляет HTTP request, получает response, парсит HTML и загружает дополнительные ресурсы. DNS отвечает «куда идти», TCP — «как надежно доставить байты», TLS — «как защитить канал», HTTP — «что запросить и что вернуть».

## Вопрос

Что происходит от ввода URL в адресную строку до отображения страницы? Какую роль играют DNS, TCP, TLS и HTTP?

## Упрощенная цепочка

```txt
URL
 -> проверка cache / service worker
 -> DNS lookup
 -> TCP connection
 -> TLS handshake
 -> HTTP request
 -> HTTP response
 -> HTML parsing
 -> CSS/JS/images loading
 -> render
```

В реальности browser может использовать cache, service worker, HTTP/2 connection reuse, preload scanner, HSTS и другие оптимизации.

## 1. Browser разбирает URL

```txt
https://example.com:443/products?page=2#reviews
```

Browser выделяет:

- scheme: `https`;
- host: `example.com`;
- port: `443`;
- path: `/products`;
- query: `page=2`;
- fragment: `reviews`.

Fragment `#reviews` не отправляется на server. Он нужен browser/client-side code. Если в адресной строке не URL, а текст, браузер отправляет его в поисковую систему. Если домен в списке HSTS, браузер сразу заменит `http://` на `https://`.

## 2. DNS lookup

DNS превращает domain name в IP address:

```txt
example.com -> 93.184.216.34
```

Порядок поиска: cache браузера → cache ОС (и файл `hosts`) → DNS resolver провайдера или публичный (8.8.8.8, 1.1.1.1) → рекурсивный обход root → `.com` → authoritative сервер. Если DNS не работает, browser не знает, куда подключаться.

## 3. TCP

TCP обеспечивает надежную упорядоченную доставку байтов. Соединение открывается через three-way handshake: `SYN` → `SYN-ACK` → `ACK`. Это один round-trip до отправки данных. В HTTP/3 вместо TCP используется QUIC поверх UDP.

## 4. TLS

Для HTTPS поверх TCP запускается TLS handshake. TLS:

- проверяет server certificate (домен, срок, доверенный CA);
- договаривается о ключах шифрования;
- шифрует данные и защищает от подмены в пути.

TLS 1.3 требует одного round-trip, а при повторном подключении возможен 0-RTT.

## 5. HTTP request и response

```http
GET /products?page=2 HTTP/2
Host: example.com
Accept: text/html
Cookie: sid=abc
```

Сервер (часто через CDN, балансировщик и reverse proxy) возвращает status, headers и HTML. Возможны redirect (`301`/`302`) — тогда цикл повторяется для нового URL.

## 6. Browser строит страницу

Browser парсит HTML и строит DOM, находит CSS, JS, images, fonts и отправляет дополнительные requests. CSS строит CSSOM, затем render tree, layout, paint и composite. Подробнее — в заметке [Как браузер строит страницу](<02. Как браузер строит страницу.md>).

## Где это видно?

В DevTools → Network → Timing у каждого запроса:

| Этап | Что означает |
|---|---|
| Queueing / Stalled | ожидание в очереди браузера |
| DNS Lookup | поиск IP |
| Initial connection | TCP handshake |
| SSL | TLS handshake |
| Request sent | отправка запроса |
| Waiting for server response (TTFB) | обработка на сервере |
| Content Download | получение тела ответа |

Повторные запросы к тому же origin обычно не тратят время на DNS, TCP и TLS: соединение переиспользуется.

## Что важно помнить

- `<link rel="preconnect" href="https://api.example.com">` заранее выполняет DNS + TCP + TLS для важного стороннего origin, `dns-prefetch` — только DNS.
- Каждый лишний round-trip заметен на мобильной сети: поэтому важны CDN, HTTP/2–3, keep-alive и меньше редиректов.
- На собеседовании хорошо отвечать по уровням и уметь углубиться в любой из них: DNS, TLS, cache, рендеринг.

## Мини-шпаргалка

- URL разбирается на scheme, host, port, path, query, fragment.
- DNS → IP, TCP → надежное соединение, TLS → защищенный канал, HTTP → request/response.
- Fragment не уходит на server.
- HTML запускает цепочку дополнительных requests и рендеринг.
- DevTools Timing показывает, на каком этапе задержка.
