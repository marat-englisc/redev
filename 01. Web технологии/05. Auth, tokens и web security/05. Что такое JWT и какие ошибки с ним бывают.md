# Что такое JWT и какие ошибки с ним бывают?

> [!NOTE]
> JWT - компактный signed token с header, payload и signature. Он удобен для передачи claims, но его нельзя использовать как магическое решение auth: нужно проверять подпись, срок жизни, issuer, audience и стратегию отзыва.

## Вопрос

Что такое JWT, из чего он состоит и какие ошибки при его использовании встречаются чаще всего?

## Структура JWT

```txt
header.payload.signature
```

Payload может содержать claims:

```json
{
  "sub": "42",
  "role": "admin",
  "iat": 1760000000,
  "exp": 1760000900
}
```

Payload не зашифрован. Его легко прочитать после base64url decoding. Подпись защищает от подмены, но не скрывает данные.

## Что нужно проверять?

Server должен проверять:

- signature;
- `exp`;
- `nbf`, если используется;
- `iss`, если есть issuer;
- `aud`, если есть audience;
- algorithm policy;
- revocation strategy, если token может быть отозван.

## Частые ошибки

| Ошибка | Почему опасно |
|---|---|
| хранить секрет в frontend | любой сможет подписывать tokens |
| класть sensitive data в payload | payload читается клиентом |
| делать access token долгоживущим | украденный token долго работает |
| не проверять `exp` | token может жить бесконечно |
| использовать JWT вместо session без причины | сложнее logout/revocation |
| доверять `role` на frontend | frontend можно изменить |

## JWT vs session

JWT удобен, когда:

- много services проверяют token;
- нужен stateless access token;
- есть отдельный auth server.

Session удобнее, когда:

- нужен простой logout;
- нужно мгновенно отзывать доступ;
- приложение browser-first и есть server-side store.

## Что важно помнить

- Атака `alg: none` и подмена алгоритма (RS256 → HS256): сервер должен жестко задавать допустимые алгоритмы.
- Декодировать JWT на frontend (например, чтобы прочитать `exp`) можно без секрета, но решения о правах принимает только сервер.
- Чем больше claims, тем длиннее токен, а он уходит в каждом запросе.
- Для мгновенного отзыва JWT используют короткий срок жизни и denylist по `jti`, либо возвращаются к сессиям.

## Мини-шпаргалка

- JWT signed, но не обязательно encrypted.
- Payload нельзя считать секретным.
- Access JWT должен жить недолго.
- Refresh token требует особой защиты.
- Logout с JWT требует revocation strategy.
- Frontend может читать claims, но backend обязан проверять права сам.
