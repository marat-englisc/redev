# Что такое INP и как его улучшать

> [!NOTE]
> **INP (Interaction to Next Paint)** — метрика отзывчивости: время от клика, тапа или нажатия клавиши до следующей отрисовки кадра. Учитываются все взаимодействия за визит, итоговое значение близко к худшему. Хорошо — ≤ 200 мс. Задержка состоит из **input delay** (основной поток занят другой задачей), **processing time** (выполнение обработчиков) и **presentation delay** (пересчёт стилей, layout, отрисовка). Плохой INP почти всегда означает **длинные задачи в основном потоке**: тяжёлый JS, дорогие обработчики, массовые перерендеры, гидрация, сторонние скрипты. INP заменил FID в марте 2024.

## Вопрос

Что такое INP и как улучшить отзывчивость страницы?

## Из чего складывается

```text
клик ─▶ [input delay] ─▶ [обработчики события] ─▶ [style/layout/paint] ─▶ кадр
         основной поток     ваш код                 браузер
         занят другим
```

## Причины плохого INP

| Причина | Пример |
| --- | --- |
| Длинные задачи при загрузке | Гидрация большого приложения, разбор огромного бандла |
| Тяжёлые обработчики | Фильтрация 10 000 строк синхронно при вводе |
| Массовые перерендеры | Изменение состояния, перерисовывающее всю страницу |
| Большой DOM | Таблица на тысячи строк без виртуализации |
| Сторонние скрипты | Аналитика, чаты, A/B-тесты в основном потоке |
| Layout thrashing | Чередование чтения `offsetHeight` и записи стилей в цикле |

## Как улучшать

**Разбивать длинные задачи и уступать основной поток:**

```ts
async function processItems(items: Item[]) {
  for (const chunk of chunked(items, 200)) {
    handle(chunk);
    await scheduler.yield?.() ?? new Promise((r) => setTimeout(r, 0)); // дать браузеру отрисовать кадр
  }
}
```

**Сначала обновить UI, потом выполнять тяжёлое:**

```ts
button.addEventListener("click", () => {
  showSpinner();                                    // мгновенная обратная связь
  requestAnimationFrame(() => setTimeout(heavyWork, 0)); // тяжёлое — после отрисовки
});
```

**Меньше JS и гидрации:**
- code splitting и динамический импорт тяжёлых компонентов;
- отложенная гидрация (`hydrate-on-visible` в Nuxt), Server Components в Next.js;
- удаление неиспользуемых зависимостей.

**Оптимизировать рендер:**
- `useTransition`/`useDeferredValue` в React, `debounce` для ввода;
- мемоизация и точечные обновления состояния;
- виртуализация длинных списков;
- `content-visibility: auto` для блоков вне экрана.

**Вынести вычисления:**
- Web Worker для парсинга, поиска, обработки данных.

**Ограничить сторонние скрипты:**
- загружать после взаимодействия или по согласию, фасады для виджетов.

## Как диагностировать

- PageSpeed Insights / Search Console — полевой INP и проблемные группы URL.
- DevTools → Performance: запись взаимодействия, поиск задач > 50 мс (красная метка Long task).
- `web-vitals` с атрибуцией (`onINP(cb, { reportAllChanges: true })` из `web-vitals/attribution`) — какой элемент и какой обработчик виноваты.
- TBT в Lighthouse — лабораторный индикатор проблем при загрузке.

## Частые ошибки

- Ориентироваться на Lighthouse: в нём нет взаимодействий, INP там не измеряется.
- Оптимизировать «на глаз» без профилирования.
- Тяжёлая синхронная работа прямо в обработчике `input`.
- Гидратировать всё приложение сразу.

## Что важно помнить

- INP — про основной поток: всё, что его блокирует, ухудшает метрику.
- Быстрая визуальная обратная связь важнее мгновенного выполнения всей работы.
- Объём JavaScript — главный рычаг для INP во frontend-приложениях.

## Мини-шпаргалка

- INP ≤ 200 мс, все взаимодействия визита.
- Input delay + обработчики + отрисовка.
- Разбивать задачи, `scheduler.yield()`.
- Меньше JS, отложенная гидрация, Web Worker.
- Профилировать в DevTools, атрибуция `web-vitals`.
