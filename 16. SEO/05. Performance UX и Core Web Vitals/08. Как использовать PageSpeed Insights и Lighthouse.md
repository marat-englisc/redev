# Как использовать PageSpeed Insights и Lighthouse

> [!NOTE]
> **PageSpeed Insights (PSI)** показывает два типа данных: сверху — **полевые** (CrUX, реальные пользователи Chrome за 28 дней, 75-й процентиль LCP, INP, CLS), снизу — **лабораторные** (прогон Lighthouse с эмуляцией медленного мобильного). **Lighthouse** — лабораторный аудит производительности, доступности, best practices и базового SEO, который запускается в DevTools, CLI или CI. Полевые данные отвечают на вопрос «хорошо ли пользователям», лабораторные — «почему». Балл Lighthouse — не цель: задача — найти конкретную причину плохой метрики на важном шаблоне.

## Вопрос

Как пользоваться PageSpeed Insights и Lighthouse для диагностики производительности?

## Инструменты

| Инструмент | Данные | Для чего |
| --- | --- | --- |
| PageSpeed Insights | Поле (CrUX) + лаборатория | Быстрая оценка URL и происхождения |
| Lighthouse | Лаборатория | Диагностика, сравнение до и после, CI |
| Search Console → Core Web Vitals | Поле по группам URL | Какие шаблоны проблемные |
| CrUX Dashboard / API | Поле, история | Тренды по сайту |
| DevTools → Performance | Трассировка | Глубокий разбор задач и рендера |
| WebPageTest | Лаборатория, разные локации | Waterfall, фильмы загрузки, сравнения |

## Как читать PSI

1. **Полевые данные**: прошла ли страница (или весь origin) оценку Core Web Vitals, отдельно мобильные и десктоп.
2. **LCP-элемент** и разбивка LCP на фазы.
3. **Диагностика и возможности**: «Уменьшите неиспользуемый JavaScript», «Устраните ресурсы, блокирующие отрисовку», «Изображения без размеров».
4. **Сторонний код** и его вклад.

Если у URL мало трафика, полевых данных для него нет — показываются данные всего origin.

## Lighthouse в работе

```bash
npx lighthouse https://example.com/products/keychron-k2 --preset=desktop --view
```

Lighthouse CI в пайплайне ловит регрессии до релиза:

```json
{
  "ci": {
    "collect": { "url": ["http://localhost:3000/", "http://localhost:3000/products/demo"] },
    "assert": {
      "assertions": {
        "largest-contentful-paint": ["error", { "maxNumericValue": 2500 }],
        "cumulative-layout-shift": ["error", { "maxNumericValue": 0.1 }],
        "total-blocking-time": ["warn", { "maxNumericValue": 300 }]
      }
    }
  }
}
```

Запускайте несколько прогонов: результат одного запуска шумит на 10–20%.

## Как ставить задачи

```text
✗ Сделать Lighthouse 100.

✓ Шаблон карточки товара: полевой LCP на мобильных 4,1 с (p75).
  LCP-элемент — hero-изображение 2,4 МБ JPEG, загружается после JS слайдера.
  Сделать: <img> в HTML, AVIF 800/1200 px, fetchpriority="high", убрать lazy.
  Ожидание: LCP < 2,5 с в лаборатории, проверить поле через 28 дней.
```

## Частые ошибки

- Гнаться за баллом вместо метрик пользователей.
- Тестировать с быстрого ноутбука и сети без эмуляции.
- Сравнивать единичные прогоны.
- Чинить всё подряд из списка рекомендаций без приоритета.
- Тестировать только главную, а не ключевые шаблоны.

## Что важно помнить

- Поле — оценка, лаборатория — диагностика.
- Проверяют шаблоны страниц (главная, категория, товар, статья), а не отдельные URL.
- Lighthouse в CI защищает от регрессий производительности.

## Мини-шпаргалка

- PSI: CrUX сверху, Lighthouse снизу.
- Search Console — проблемные группы URL.
- Lighthouse CLI и CI с порогами.
- Несколько прогонов, мобильная эмуляция.
- Задача = шаблон + метрика + причина + решение.
