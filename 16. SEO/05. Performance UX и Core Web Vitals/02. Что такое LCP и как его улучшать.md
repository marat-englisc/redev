# Что такое LCP и как его улучшать

> [!NOTE]
> **LCP (Largest Contentful Paint)** — время от начала навигации до отрисовки самого крупного элемента в видимой области: hero-изображения, постера видео, фонового изображения или большого блока текста. Хороший LCP — ≤ 2,5 с для 75% визитов. LCP раскладывается на четыре части: **TTFB** (ответ сервера), **задержка загрузки ресурса** (когда браузер узнал о картинке), **длительность загрузки ресурса** и **задержка рендера** (блокирующие CSS/JS, шрифты, гидрация). Улучшение начинается с определения LCP-элемента и самой длинной из этих частей.

## Вопрос

Что такое LCP, из чего он складывается и как его улучшить?

## Какие элементы бывают LCP

- `<img>`, `<image>` внутри `<svg>`, `<picture>`;
- `poster` у `<video>` (и первый кадр видео);
- элемент с `background-image` через CSS;
- блок текста (заголовок, абзац).

LCP-элемент виден в PageSpeed Insights («Элемент, отрисовка которого заняла больше всего времени») и в панели Performance DevTools.

## Из чего складывается

```text
LCP = TTFB + задержка загрузки ресурса + время загрузки ресурса + задержка рендера
       │           │                          │                     │
     сервер    браузер поздно узнал       тяжёлый файл,       блокирующие CSS/JS,
     и CDN     о картинке                 медленная сеть      шрифты, гидрация
```

Ориентир: TTFB ~40%, загрузка ресурса ~40%, задержки — минимальны.

## Что делать

**TTFB:**
- кэшировать HTML на CDN (SSG, ISR/SWR для динамических страниц);
- ускорить запросы к БД и API при SSR;
- использовать стриминг SSR.

**Задержка обнаружения ресурса:**
- LCP-изображение должно быть в HTML как `<img src>`, а не появляться после выполнения JS;
- не ставить `loading="lazy"` на LCP-изображение;
- `fetchpriority="high"` для LCP-изображения;
- `<link rel="preload">` для изображений из CSS или с адаптивными источниками.

```html
<img src="/hero.avif" alt="Панель аналитики" width="1200" height="630" fetchpriority="high">

<link rel="preload" as="image" href="/hero.avif" imagesrcset="/hero-800.avif 800w, /hero-1600.avif 1600w" imagesizes="100vw" fetchpriority="high">
```

**Время загрузки:**
- AVIF/WebP, правильный размер через `srcset`/`sizes`, сжатие;
- CDN рядом с пользователем;
- не грузить шрифты и сторонние скрипты раньше LCP-ресурса.

**Задержка рендера:**
- критический CSS inline, остальной — асинхронно;
- `defer` для скриптов, отказ от синхронных скриптов в `<head>`;
- `font-display: swap` или `optional`, preload основного шрифта;
- при CSR — переход на SSR/SSG: в клиентском рендеринге LCP ждёт загрузку и выполнение всего бандла и запрос данных.

## Во фреймворках

- Next.js: `<Image priority>` (или `preload`/`fetchPriority="high"` в новых версиях) для hero.
- Nuxt: `<NuxtImg preload fetchpriority="high">`.
- Не оборачивать первый экран в компоненты, которые рендерятся только на клиенте.

## Частые ошибки

- Ленивая загрузка hero-изображения.
- Hero как CSS-фон без preload.
- Слайдер на первом экране, инициализируемый JS.
- Изображение 3000 px для мобильного экрана.
- Медленный TTFB из-за SSR без кэша и последовательных запросов.

## Что важно помнить

- Сначала найти LCP-элемент, потом разложить LCP на части.
- Изображение должно быть обнаружено браузером как можно раньше.
- CSR почти всегда ухудшает LCP контентных страниц.

## Мини-шпаргалка

- LCP ≤ 2,5 с.
- TTFB + обнаружение + загрузка + рендер.
- `<img src>` в HTML, `fetchpriority="high"`, без lazy.
- AVIF/WebP, `srcset`, CDN.
- SSR/SSG и кэш HTML.
