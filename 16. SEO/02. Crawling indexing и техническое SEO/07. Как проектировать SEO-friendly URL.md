# Как проектировать SEO-friendly URL

> [!NOTE]
> Хороший URL — **читаемый** (по нему понятна тема), **стабильный** (не меняется годами), **короткий** и **единообразный**: строчные буквы, слова через дефис, без служебных параметров в канонической версии, с одной политикой слеша на конце. Структура URL отражает иерархию сайта, но не уходит в глубокую вложенность. Сам URL — слабый фактор ранжирования, но он влияет на CTR, удобство ссылок и, главное, на количество дублей и рисков при миграциях.

## Вопрос

Как проектировать URL, удобные для пользователей и поисковиков?

## Хорошо и плохо

```text
✓ https://example.com/blog/javascript-event-loop
✓ https://shop.example.com/laptops/macbook-pro-14
✗ https://example.com/page?id=8912&ref=main&session=ab12
✗ https://example.com/Blog/JavaScript_Event_Loop/
✗ https://example.com/catalog/category/subcategory/type/brand/model/variant/item-123
```

## Правила

| Правило | Почему |
| --- | --- |
| Строчные буквы | `/Blog` и `/blog` — разные URL для сервера и поисковика |
| Дефисы между словами | Google трактует дефис как разделитель слов, подчёркивание — нет |
| Без служебных параметров в canonical | Сессии, UTM, сортировки порождают дубли |
| Единая политика слеша | `/page` и `/page/` — разные URL; один вариант + 301 на него |
| Без расширений и технических деталей | `/about`, а не `/about.php` — переживёт смену стека |
| Без даты, если контент не привязан ко времени | Иначе «устаревший» URL при обновлении статьи |
| Неглубокая вложенность | 2–3 уровня обычно достаточно |
| Параметры — в query-строке | Фильтры: `/laptops?ram=16`, а не `/laptops/ram-16/color-…` без смысла |

## Кириллица

Кириллические URL допустимы: Google и Яндекс их понимают, а в выдаче показывают читаемо. Но при копировании они превращаются в percent-encoding:

```text
/статьи/как-работает-seo
→ /%D1%81%D1%82%D0%B0%D1%82%D1%8C%D0%B8/...
```

Поэтому для технических и международных проектов обычно выбирают транслитерацию или английские слова: `/blog/kak-rabotaet-seo`. Главное — выбрать один подход и не смешивать.

## Идентификаторы

```text
/products/keychron-k2-42      ← slug + id: стабильно даже при переименовании
/products/42                  ← стабильно, но неинформативно
/products/keychron-k2         ← красиво, но при смене названия нужен 301
```

Схема `slug-id` удобна: по id находим товар, а при изменённом slug отдаём 301 на актуальный.

## Иерархия

```text
/docs/vue/router/navigation-guards
/catalog/laptops/apple
```

Структура URL помогает пользователю и даёт основу для хлебных крошек. Но товар, доступный в нескольких категориях, должен иметь один канонический URL (`/products/...`), а не по одному на категорию.

## Смена URL

Любое изменение URL требует 301 со старого на новый, обновления внутренних ссылок, canonical и sitemap. Поэтому структуру продумывают до запуска — менять её потом дорого.

## Частые ошибки

- Разный регистр и смешение слеша.
- Сессионные идентификаторы в URL.
- Менять URL при каждом редизайне без редиректов.
- Несколько URL одного товара в разных категориях без canonical.
- Генерация URL из пользовательского ввода без нормализации (пробелы, спецсимволы).

## Что важно помнить

- Стабильность важнее «идеальной» красоты: каждый переезд — риск.
- Нормализация URL (регистр, слеш, параметры) — задача роутера и сервера.
- URL — часть контракта сайта, его меняют только с планом редиректов.

## Мини-шпаргалка

- Строчные, дефисы, коротко, читаемо.
- Одна политика слеша, 301 на неё.
- Без служебных параметров в canonical.
- `slug-id` для сущностей.
- Смена URL = 301 + ссылки + canonical + sitemap.
