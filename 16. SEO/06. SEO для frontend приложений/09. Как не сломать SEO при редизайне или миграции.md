# Как не сломать SEO при редизайне или миграции

> [!NOTE]
> Миграция — смена домена, URL-структуры, CMS, фреймворка или режима рендеринга — главная причина резкой потери органического трафика. Чтобы её избежать: **инвентаризация** старых URL с трафиком и ссылками, **карта редиректов** 301 «старый → релевантный новый» (без цепочек и массовых редиректов на главную), сохранение контента, мета-тегов, заголовков и structured data на ключевых шаблонах, проверка staging (без утечки `noindex` в production), новый sitemap, а после релиза — **мониторинг** 404, редиректов, индексации и трафика в течение нескольких месяцев. Редиректы держат минимум год.

## Вопрос

Как провести редизайн или миграцию сайта без потери SEO-трафика?

## Что может измениться

- Домен или протокол.
- URL-структура.
- CMS или фреймворк (например, SPA → Next.js/Nuxt).
- Режим рендеринга (CSR ↔ SSR).
- Контент, заголовки, мета-теги, structured data.
- Навигация и внутренние ссылки.
- Скорость и Core Web Vitals.

Чем больше меняется одновременно, тем сложнее понять причину просадки. Безопаснее менять поэтапно.

## До релиза

1. **Инвентаризация**: все URL из краулера, sitemap, Search Console (страницы с показами), аналитики, внешних ссылок (Ahrefs, Вебмастер).
2. **Карта редиректов**:

```csv
old_url,new_url,status
/blog/old-seo,/blog/seo-guide,301
/services/seo-audit,/seo-audit,301
/catalog/Phones/,/catalog/phones/,301
/promo-2023,/sale,301
```

3. **Сравнение шаблонов**: title, description, h1, canonical, structured data, основной текст, внутренние ссылки — на staging против production.
4. **Staging**: закрыт авторизацией или `noindex` через заголовок сервера, чтобы не утечь в индекс и не перенестись в production.
5. **Новый sitemap** с новыми URL.
6. **Бенчмарк** метрик: трафик, позиции, индексация, Core Web Vitals — чтобы было с чем сравнивать.

## День релиза

- Включить редиректы и проверить выборку URL (`curl -sIL`): один переход, код 301, правильная цель.
- Убедиться, что в production нет `noindex` и `Disallow: /`.
- Обновить внутренние ссылки, canonical и hreflang на новые URL.
- Отправить новый sitemap; старый можно временно оставить, чтобы ускорить обход редиректов.
- При смене домена — инструмент «Изменение адреса» в Search Console и переезд в Вебмастере.

## После релиза

| Что | Где |
| --- | --- |
| 404 на старых URL | Логи, Search Console, краулер |
| Цепочки и петли редиректов | Краулер |
| Индексация новых страниц | Search Console, Вебмастер |
| Клики и показы по шаблонам | Search Console |
| Ошибки сервера | Мониторинг, логи |
| Core Web Vitals | CrUX, RUM |
| Structured data | Отчёты «Улучшения» |

Временная просадка на 2–6 недель при смене URL — нормальна; продолжительное падение — сигнал искать ошибку.

## Частые ошибки

- Нет списка старых URL — редиректы делают «по памяти».
- Массовые редиректы на главную.
- `noindex` со staging в production.
- Смена URL, контента и рендеринга одновременно.
- Удаление редиректов через пару месяцев.
- Переход с SSR на CSR «заодно с редизайном».

## Что важно помнить

- Миграция без карты редиректов — гарантированная потеря трафика.
- Ключевые шаблоны должны сохранить контент и мета-теги.
- Мониторинг после релиза так же важен, как подготовка.

## Мини-шпаргалка

- Инвентаризация URL → карта 301 → проверка staging.
- Без `noindex` в production, без цепочек.
- Обновить ссылки, canonical, sitemap.
- Мониторить 404, индексацию, трафик.
- Редиректы — минимум год.
