# Почему frontend-приложения могут иметь SEO-проблемы

> [!NOTE]
> SPA и другие JS-тяжёлые приложения формируют контент, мета-теги и ссылки в браузере. Поэтому типичные проблемы: **пустой HTML** до выполнения JavaScript (контент виден только после рендеринга, который у поисковика откладывается и может не случиться), **одинаковые мета-теги** на всех маршрутах, **неверные статус-коды** (сервер отдаёт 200 на любой путь), ссылки на `div` и `button` вместо `<a href>`, контент только **после действия пользователя**, structured data и canonical, не обновляемые при навигации, тысячи URL из фильтров, тяжёлый JS, ухудшающий Core Web Vitals. Решения — SSR/SSG/prerender для публичных страниц и дисциплина в роутинге и `<head>`.

## Вопрос

Почему frontend-приложения часто имеют проблемы с SEO?

## Где обычно ломается

| Проблема | Последствие |
| --- | --- |
| Пустой HTML `<div id="app">` | Контент появляется только после рендеринга JS — позже или никогда |
| Один title и description на все маршруты | Дубли сниппетов, плохой CTR |
| 200 на несуществующие пути | Soft 404, мусор в индексе |
| Ссылки без `href` | Робот не находит страницы |
| Контент по клику, скроллу, наведению | Робот не взаимодействует — не видит контент |
| Hash-роутинг `/#/products` | Фрагмент после `#` не считается отдельным URL |
| Canonical и JSON-LD не обновляются | Неверные сигналы для каждой страницы |
| Фильтры в URL без правил | Тысячи дублей, расход crawl budget |
| Тяжёлый бандл и гидрация | Плохие LCP и INP |
| Ошибка JS | Пустая страница для робота |
| API требует cookies или блокирует ботов | Робот не получает данные |

## Пустой HTML

```html
<!doctype html>
<html>
  <head><title>App</title></head>
  <body>
    <div id="app"></div>
    <script type="module" src="/assets/index-a1b2.js"></script>
  </body>
</html>
```

Google выполнит JS, но в очереди на рендеринг. Яндекс, Bing, боты соцсетей и мессенджеров, ИИ-краулеры часто не выполняют JS вовсе — для них страница пуста.

## Почему это и UX-проблема

- Долгий первый экран (LCP) — нужно скачать и выполнить бандл, затем запросить данные.
- Медленная реакция на клики при гидрации (INP).
- Прыгающий макет при догрузке данных (CLS).
- Плохие превью ссылок в мессенджерах.

## Что помогает

- SSR, SSG, ISR или prerender для публичных страниц — контент и мета в HTML.
- History API роутинг вместо hash.
- Мета-теги на каждый маршрут, в серверном HTML.
- Правильные 404 и 301 на уровне сервера.
- `<a href>` для навигации.
- Правила для фильтров и параметров.
- Контроль размера JS и гидрации.
- Проверка итогового HTML (`curl`, URL Inspection) в CI и после релиза.

## Когда CSR допустим

Закрытые разделы (личный кабинет, админка, дашборды) поиску не нужны — там CSR нормален. Важно разделить публичную и закрытую части и для первой выбрать серверный рендеринг.

## Что важно помнить

- SPA может индексироваться, но требует аккуратности и проверки.
- Проблемы SPA для SEO и для пользователей во многом одни и те же.
- Самый надёжный путь для SEO-страниц — HTML с контентом с сервера.

## Мини-шпаргалка

- Пустой HTML, общие мета, 200 на всё, ссылки без href.
- Контент по действию и hash-URL не индексируются.
- Не все роботы выполняют JS.
- SSR/SSG/prerender для публичного, CSR — для закрытого.
