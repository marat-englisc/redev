# Как масштабировать фронтенд: монорепозиторий, модули и микрофронтенды

> [!NOTE]
> Когда над фронтендом работают несколько команд, архитектура должна позволять **менять код независимо**: четкие **границы модулей** с публичным API (Feature-Sliced Design, доменные модули), **монорепозиторий** с общими пакетами (UI-кит, утилиты, конфиги) и инструментами сборки (Turborepo, Nx, pnpm workspaces), а при необходимости — **микрофронтенды**, которые собираются и деплоятся отдельно. Правило: начинать с модульного монолита и переходить к микрофронтендам только при реальной организационной необходимости.

## Вопрос

Как масштабировать фронтенд-приложение и кодовую базу, когда растет команда? Что такое монорепозиторий и микрофронтенды и когда они оправданы?

## Ступени масштабирования

```text
1. Модульный монолит      одно приложение, границы фич, публичные API модулей
2. Монорепозиторий        несколько приложений и общие пакеты в одном репозитории
3. Микрофронтенды         независимые сборки и деплои частей интерфейса
```

## 1. Модули с границами

```text
src/
  app/            инициализация, провайдеры, роутинг
  pages/          страницы
  widgets/        крупные блоки страниц
  features/       пользовательские действия: add-to-cart, auth-by-phone
  entities/       бизнес-сущности: user, product, order
  shared/         UI-кит, api-клиент, утилиты
```

- импорт только сверху вниз по слоям и только через `index.ts` модуля;
- правила проверяются линтером (`eslint-plugin-boundaries`, Steiger для FSD);
- владельцы кода (`CODEOWNERS`) для каждой зоны.

## 2. Монорепозиторий

```text
apps/
  web/            основное приложение (Next.js)
  admin/          админка (Vite)
packages/
  ui/             дизайн-система
  api-client/     сгенерированный из OpenAPI клиент
  config/         eslint, tsconfig, prettier
  utils/
```

| Плюсы | Минусы |
| --- | --- |
| атомарные изменения во всех пакетах одним PR | сборка и CI растут без кеширования |
| общие версии зависимостей и конфиги | нужна дисциплина границ |
| переиспользование без публикации в npm | инструменты требуют настройки |

Инструменты: **pnpm workspaces** (связывание пакетов), **Turborepo** или **Nx** (граф задач, кеш сборки и тестов, запуск только затронутого — `affected`), **Changesets** (версии пакетов).

## 3. Микрофронтенды

Каждая команда владеет частью интерфейса от разработки до деплоя: каталог, корзина, личный кабинет.

| Способ интеграции | Как работает | Особенности |
| --- | --- | --- |
| Разные маршруты (multi-zone) | `/shop/*` — одно приложение, `/account/*` — другое | проще всего, переход между зонами — полная загрузка |
| Module Federation | приложение загружает модули другого в рантайме | общий React как singleton, сложная настройка версий |
| Web Components | части оформлены как custom elements | изоляция Shadow DOM, сложнее SSR |
| iframe | полная изоляция | плохо для UX, SEO, a11y |
| Серверная композиция | сервер или edge собирает HTML фрагментов | хорошо для SEO, сложная инфраструктура |

Обязательные договоренности: общая дизайн-система, общий способ авторизации, коммуникация через события или URL (а не через общий глобальный store), контроль размера бандла (нет пяти копий React), сквозной мониторинг.

## Когда что выбирать

| Ситуация | Решение |
| --- | --- |
| одна-две команды | модульный монолит |
| несколько приложений с общими компонентами | монорепозиторий |
| много автономных команд, независимые релизы, разные циклы | микрофронтенды |
| миграция legacy-приложения по частям | микрофронтенды как временный шаг |

## Что важно помнить

- Микрофронтенды решают **организационную** проблему (независимость команд), а не техническую; цена — сложность, производительность и согласованность UX.
- Границы модулей важнее инструментов: без них и монорепо, и микрофронтенды превращаются в связанный монолит.
- Кеш сборки и запуск только затронутого кода (affected) — основа быстрого CI в монорепозитории.

Что делает “Micro-frontend” подход с React.md>), [изоляция модулей](<../../06. React/08. Паттерны и подходы/07. Изоляция модулей.md>).

## Мини-шпаргалка

Модульный монолит (слои, публичные API, линтер границ) → монорепо (pnpm workspaces, Turborepo/Nx, общие пакеты, affected) → микрофронтенды (маршруты, Module Federation, Web Components, серверная композиция) только при многих автономных командах. Общие: дизайн-система, auth, события, мониторинг.
