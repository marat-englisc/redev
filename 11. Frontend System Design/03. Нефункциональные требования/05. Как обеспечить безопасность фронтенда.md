# Как обеспечить безопасность фронтенда

> [!NOTE]
> Фронтенд не защищает данные сам по себе — финальные проверки всегда на сервере, — но он отвечает за то, чтобы не открыть дыры: **XSS** (выполнение чужого скрипта), **CSRF** (запрос от имени пользователя с чужого сайта), утечку токенов, clickjacking и уязвимые зависимости. На интервью обсуждают: где хранить токены, как выводить пользовательский контент, какие заголовки (CSP, `X-Frame-Options`) нужны и что делать со сторонними скриптами.

## Вопрос

Как обеспечить безопасность фронтенд-приложения на system design интервью? Где хранить токены и как защититься от XSS и CSRF?

## Угрозы и защита

| Угроза | Защита |
| --- | --- |
| XSS | экранирование вывода (React делает по умолчанию), без `dangerouslySetInnerHTML` или с санитизацией (DOMPurify), CSP, Trusted Types |
| CSRF | cookie `SameSite=Lax/Strict`, CSRF-токен для форм, проверка `Origin` |
| Кража токена | httpOnly cookie вместо `localStorage`, короткоживущие access-токены |
| Clickjacking | `Content-Security-Policy: frame-ancestors 'none'` или `X-Frame-Options: DENY` |
| Открытые редиректы | allowlist адресов для `?redirect=` |
| Уязвимые зависимости | lockfile, `npm audit`, Dependabot/Renovate |
| Сторонние скрипты | минимизировать, `integrity` (SRI), загрузка в iframe-песочнице, CSP |
| Утечка данных | не логировать токены и персональные данные, `Cache-Control: private` |

## Где хранить токены

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| httpOnly + Secure + SameSite cookie | недоступен JS → не украдут через XSS | нужна защита от CSRF |
| `localStorage` | просто | доступен любому скрипту → XSS = кража токена |
| Память (переменная) + refresh в httpOnly cookie | access-токен не хранится постоянно | сложнее, токен теряется при перезагрузке |
| BFF держит токены, браузер — сессионную cookie | токены внешних API не попадают в браузер | нужен серверный слой |

Рекомендуемый вариант для веба — сессия или refresh-токен в **httpOnly cookie**, а лучше — BFF.

## Пользовательский контент

```tsx
// безопасно — React экранирует
<p>{comment.text}</p>

// опасно без санитизации
<div dangerouslySetInnerHTML={{ __html: comment.html }} />

// с санитизацией
import DOMPurify from "dompurify";
<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(comment.html) }} />
```

Также опасны `href={userUrl}` с `javascript:`, `eval`, `new Function`, вставка в `innerHTML`.

## Заголовки безопасности

```http
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-r4nd0m'; img-src 'self' https://cdn.example.com; frame-ancestors 'none'
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

## Что важно помнить

- Всё, что пришло в браузер, видно пользователю: никаких секретных ключей в бандле (`NEXT_PUBLIC_*`, `VITE_*` — публичные).
- Проверки прав на клиенте — для UX; настоящая авторизация — на сервере для каждого запроса.
- CSP — второй рубеж от XSS: даже если вставили скрипт, он не выполнится.
- Валидация ввода на клиенте не защищает: сервер проверяет всё заново.
- Связанные темы: [защита от XSS](<../../01. Web технологии/05. Auth, tokens и web security/07. Как защищаться от XSS.md>), [CSRF и SameSite](<../../01. Web технологии/05. Auth, tokens и web security/09. Как защищаться от CSRF и чем помогают SameSite cookies.md>).

## Мини-шпаргалка

XSS — экранирование, санитизация, CSP. CSRF — SameSite, CSRF-токен, проверка Origin. Токены — httpOnly cookie или BFF, не `localStorage`. Clickjacking — `frame-ancestors`. Зависимости — lockfile и аудит. Секретов в бандле нет, авторизация — на сервере.
