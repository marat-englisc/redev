# Кэширование в Next.js и его уровни

> [!NOTE]
> **Кэширование** — сохранение результата, чтобы повторно использовать его вместо новой загрузки или вычисления. В Next.js кэш данных, кэш готового маршрута и кэш навигации существуют отдельно: изменение одного механизма не отключает остальные.

## Вопрос

Зачем нужен кэш, какие уровни кэширования есть в App Router и как понять, почему приложение показывает сохраненный результат?

## Основная идея

Представь каталог из тысячи книг. Если все посетители запрашивают одинаковые названия, серверу необязательно каждый раз обращаться к внешнему API. Он может сохранить результат и переиспользовать его. Но после изменения каталога сохраненная копия станет устаревшей. Поэтому у кэширования две стороны: оно сокращает повторную работу и требует понятных правил обновления. Статичная справка допускает долгое хранение, а личный баланс требует свежих данных и строгого разделения пользователей.

Материал использует Next.js 16 App Router **без `cacheComponents`**.

| Механизм | Что хранит | Где | Пример |
| --- | --- | --- | --- |
| Request Memoization | Результат одинакового GET `fetch` внутри одного серверного рендера | Сервер, на время рендера | Два компонента запрашивают одного автора |
| Data Cache | Ответы явно кэшируемых запросов | Сервер, между запросами | Общедоступный каталог |
| Full Route Cache | HTML и RSC payload статического маршрута | Сервер | Подготовленная страница статьи |
| Router Cache | RSC payload сегментов | Память браузера | Повторное использование при навигации |

**RSC payload** — описание результата Server Components. Оно используется в этих механизмах, а не образует отдельный «RSC Cache». ISR — способ обновлять статический результат, а не еще одно хранилище. HTTP-кэш браузера, CDN и кэш изображений — дополнительные отдельные механизмы.

```text
API -> Data Cache -> рендер -> Full Route Cache
                                  |
                                  v
                           браузер пользователя -> Router Cache
```

## Request Memoization и Data Cache

Одинаковые GET-запросы `fetch` с одинаковыми параметрами дедуплицируются в рамках одного серверного рендера: несколько компонентов запрашивают одно и то же, но работа не дублируется. Это временная мемоизация — при следующем рендере она начинается заново.

**Data Cache** хранит данные между запросами. Для его явного использования задают `cache: "force-cache"` или положительное `next.revalidate`. Обычный `fetch(url)` по умолчанию постоянный Data Cache не включает.

## Пример: свежий заголовок и сохраненный список

JSONPlaceholder — открытый учебный API. Один динамический маршрут может использовать запросы с разными правилами.

```tsx
// app/page.tsx
export default async function Page() {
  const [freshResponse, cachedResponse] = await Promise.all([
    fetch("https://jsonplaceholder.typicode.com/posts/1", {
      cache: "no-store",
    }),
    fetch("https://jsonplaceholder.typicode.com/posts?_limit=3", {
      next: { revalidate: 300, tags: ["catalog"] },
    }),
  ]);
  if (!freshResponse.ok || !cachedResponse.ok) {
    throw new Error("Не удалось получить записи");
  }

  const post = await freshResponse.json();
  const posts: { id: number; title: string }[] = await cachedResponse.json();
  return <><h1>{post.title}</h1><ul>{posts.map(item => (
    <li key={item.id}>{item.title}</li>
  ))}</ul></>;
}
```

Первый запрос не использует постоянный Data Cache. Второй сохраняется на 300 секунд: после интервала следующий запрос может получить старые данные и запустить обновление в фоне. Тег `catalog` позволяет позже инвалидировать запись через `revalidateTag`. Наличие динамической части не требует отказываться от кэширования всех публичных данных.

## Что важно помнить

- Сначала выясни, **какой** результат сохраняется, затем найди настройку соответствующего уровня.
- Обычный `fetch` по умолчанию не включает Data Cache, но статический HTML маршрута может быть сохранен отдельно — отсутствие кэша у запроса не означает рендер на каждое посещение.
- `cache: "no-store"` отключает постоянное хранение конкретного запроса; он не отключает кэш браузера, CDN и клиентского роутера.
- `router.refresh()` запрашивает новый серверный результат, но сам не очищает Data Cache.
- Не назначай Router Cache универсальный срок: поведение зависит от сегмента, предварительной загрузки и навигации.
- При `cacheComponents: true` используется другая модель с `use cache`, `cacheLife` и `cacheTag`; ее правила нельзя механически смешивать с этой.

## Мини-шпаргалка

- Четыре уровня: Request Memoization, Data Cache, Full Route Cache, Router Cache.
- Data Cache включают явно: `force-cache` или `next.revalidate`.
- `no-store` одного запроса не выключает весь кэш приложения.
- ISR — механизм обновления, а не отдельный кэш.
