# Зачем нужны транзакции и защита от гонок

> [!NOTE]
> Транзакция объединяет несколько изменений в одну операцию: фиксируются все либо ни одно. Для защиты от конкурентных запросов также нужны ограничения, блокировки или атомарные условия обновления.

## Вопрос

Как создать две связанные записи и не оставить половину результата при ошибке?

## Основная идея

Допустим, кнопка создает пару учебных задач. Если первая запись создана, а вторая завершилась ошибкой, пользователь должен получить либо всю пару, либо ничего. Для этого нужны `BEGIN`, `COMMIT` и `ROLLBACK`.

## Пример: одна транзакция на одном соединении

```ts
// lib/task-transaction.ts
import "server-only";
import { z } from "zod";
import { pool } from "./db";
import { requireUser } from "./session";

export async function createTaskPair(raw: unknown) {
  const user = await requireUser();
  const titles = z.tuple([
    z.string().trim().min(1).max(200),
    z.string().trim().min(1).max(200),
  ]).parse(raw);
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    for (const title of titles) {
      await client.query(
        "INSERT INTO tasks(owner_id, title) VALUES ($1, $2)",
        [user.id, title],
      );
    }
    await client.query("COMMIT");
  } catch (error) {
    await client.query("ROLLBACK");
    throw error;
  } finally {
    client.release();
  }
}
```

Вызывай эту функцию из Action или API, не из рендера страницы. Обе записи используют один `client`: отдельные вызовы `pool.query` могли бы попасть на разные соединения.

## Что важно помнить

Транзакция сама по себе не отменяет все гонки. Для покупки последнего товара опасна схема «прочитать остаток → проверить в JavaScript → уменьшить». Надежнее атомарный запрос с условием `WHERE stock > 0`, проверка числа обновленных строк и нужные ограничения.

Для сложных сценариев применяют блокировки `SELECT ... FOR UPDATE`, версию записи или подходящий уровень изоляции. Взаимоблокировки и конфликты сериализации могут требовать ограниченного повтора всей транзакции.

Не держи транзакцию открытой, пока ждешь внешний платежный API. Изменения внешней системы не откатятся вместе с PostgreSQL; для них проектируют идемпотентность, статусы и надежную доставку событий.

## Мини-шпаргалка

- Одна транзакция — одно соединение.
- Ошибка ведет к откату, соединение освобождается в `finally`.
- Атомарность и защита от гонок — связанные, но разные задачи.
- Внешний HTTP-вызов не входит автоматически в транзакцию БД.
