# Как описать схему БД и применять миграции

> [!NOTE]
> Схема определяет таблицы и ограничения, а миграции сохраняют последовательность изменений схемы. Они позволяют одинаково подготовить базы разработчика, тестового окружения и production.

## Вопрос

Как создать таблицу задач и не потерять данные при дальнейшем развитии приложения?

## Основная идея

Сначала выполни [настройку авторизации](<../12. Авторизация формы и безопасность/01. Как подключить авторизацию и серверные сессии.md>): она создаст таблицу `"user"`. Только после этого применяй миграцию задач — у нее есть ссылка на пользователя.

## Пример: таблица задач

```sql
-- migrations/001_tasks.sql
BEGIN;

CREATE TABLE tasks (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  owner_id text NOT NULL REFERENCES "user"(id) ON DELETE CASCADE,
  title text NOT NULL CHECK (char_length(btrim(title)) BETWEEN 1 AND 200),
  completed boolean NOT NULL DEFAULT false,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX tasks_owner_created_idx
  ON tasks(owner_id, created_at DESC, id DESC);

COMMIT;
```

При работающем контейнере из предыдущей темы:

```powershell
Get-Content -Raw -Encoding UTF8 migrations/001_tasks.sql | docker compose exec -T db psql -U next_app -d next_tasks -v ON_ERROR_STOP=1
```

Это **одноразовое** применение учебной миграции. Повторный запуск встретит уже существующую таблицу. Для команды нужен migration runner с таблицей примененных версий; ORM обычно предоставляет такой инструмент.

`PRIMARY KEY` задает уникальный идентификатор. `REFERENCES` запрещает задачу без существующего владельца. `CHECK` защищает данные даже при записи из другого приложения. Индекс помогает читать задачи конкретного владельца в заданном порядке.

## Пример: проверка входных данных приложения

```ts
// lib/task-schema.ts
import { z } from "zod";

export const taskIdSchema = z.string().uuid();
export const taskSchema = z.object({
  title: z.string().trim().min(1).max(200),
  completed: z.boolean().default(false),
});
export const taskPatchSchema = z.object({
  title: z.string().trim().min(1).max(200).optional(),
  completed: z.boolean().optional(),
}).refine(
  value => value.title !== undefined || value.completed !== undefined,
  "Передайте хотя бы одно изменяемое поле",
);
export type TaskInput = z.infer<typeof taskSchema>;
```

Схема Zod проверяет запрос, SQL-ограничения защищают хранилище. Это два разных уровня.

## Что важно помнить

Изменения делают новой миграцией, например `002_add_priority.sql`. Не исправляй уже примененную миграцию с расчетом, что чужая база автоматически изменится. Перед опасным изменением данных нужны резервная копия и проверенный план восстановления.

## Мини-шпаргалка

- Сначала таблицы авторизации, затем задачи.
- Миграция применяется один раз на базу.
- Ограничения БД дополняют валидацию приложения.
- Новое изменение — новая миграция.
