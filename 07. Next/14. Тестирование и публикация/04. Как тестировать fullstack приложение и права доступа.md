# Как тестировать fullstack-приложение и права доступа

> [!NOTE]
> Fullstack-проверка должна подтверждать не только отображение страницы, но и реальные изменения БД, обработку неверного ввода и изоляцию пользователей.

## Вопрос

Как убедиться, что чужую задачу нельзя удалить прямым запросом к API?

## Основная идея

Разделяй уровни: unit-тесты проверяют чистую валидацию, интеграционные тесты — DAL с отдельной PostgreSQL, сквозные тесты — форму, сессию и HTTP. Подмена всех запросов БД не доказывает корректность SQL и ограничений.

## Пример: два пользователя и чужая запись

Нужен запущенный учебный проект с примененными миграциями и **отдельной тестовой БД**. `TEST_BASE_URL` должен совпадать с origin в `BETTER_AUTH_URL` этого экземпляра приложения.

```powershell
npm install -D @playwright/test
npx playwright test
```

```ts
// tests/task-access.spec.ts
import { test, expect, request } from "@playwright/test";
import { randomUUID } from "node:crypto";

test("пользователь не удаляет чужую задачу", async () => {
  const baseURL = process.env.TEST_BASE_URL ?? "http://localhost:3000";
  const options = { baseURL, extraHTTPHeaders: { origin: new URL(baseURL).origin } };
  const owner = await request.newContext(options);
  const other = await request.newContext(options);
  const guest = await request.newContext(options);
  const suffix = randomUUID();
  try {
    for (const [client, name] of [[owner, "owner"], [other, "other"]] as const) {
      const signup = await client.post("/api/auth/sign-up/email", { data: {
        name, email: `${name}-${suffix}@example.com`, password: "ExamplePassword_123!",
      } });
      expect(signup.ok()).toBeTruthy();
    }
    const created = await owner.post("/api/tasks", { data: { title: "Моя задача" } });
    expect(created.status()).toBe(201);
    const { id } = await created.json();

    expect((await other.delete(`/api/tasks/${id}`)).status()).toBe(404);
    expect((await guest.get("/api/tasks")).status()).toBe(401);
    expect((await owner.post("/api/tasks", { data: { title: "   " } })).status()).toBe(422);

    const list = await owner.get("/api/tasks");
    expect((await list.json()).some((task: { id: string }) => task.id === id)).toBe(true);
    expect((await owner.delete(`/api/tasks/${id}`)).status()).toBe(204);
  } finally {
    await owner.dispose();
    await other.dispose();
    await guest.dispose();
  }
});
```

Каждый APIRequestContext хранит собственные cookie. Тест действительно регистрирует пользователей и создает запись; дополнительных браузерных бинарников для этого API-теста не требуется.

## Что важно помнить

После прогона в тестовой базе остаются аккаунты, а при сбое может остаться задача. Используй одноразовую тестовую БД или контролируемую очистку fixtures. Никогда не направляй такой тест на production.

Дополнительно проверь UI через браузер: ввод, pending, сообщение об ошибке, перезагрузку после сохранения и выход. Для RSC и серверных переходов сквозная проверка часто полезнее попытки отрисовать асинхронную страницу в обычном DOM unit-тесте.

## Мини-шпаргалка

- SQL и миграции проверяют с настоящей тестовой БД.
- Права проверяют минимум двумя пользователями.
- Проверяй ошибки, а не только успешный сценарий.
- Тестовые данные должны быть изолированы и очищаемы.
