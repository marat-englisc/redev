# Серверная загрузка данных в Next.js и какие проблемы она решает

> [!NOTE]
> При серверной загрузке Next.js обращается к API или базе данных до передачи результата интерфейса браузеру. Это позволяет подготовить основной контент, обращаться к закрытым источникам и сократить работу, выполняемую браузером.

## Вопрос

Как получить данные на сервере, что происходит между запросом пользователя и показом страницы и какие трудности клиентской загрузки это уменьшает?

## Как это работает

В App Router страница по умолчанию является Server Component. Ее можно объявить `async`, получить данные и вернуть JSX. Браузер не выполняет запрос к внешнему источнику самостоятельно: он получает результат работы приложения.

Момент загрузки зависит от стратегии маршрута. Общедоступную страницу можно подготовить при сборке, страницу с актуальными или персональными данными — вычислять при запросе. «На сервере» не означает автоматически «при каждом посещении».

Источником данных может быть HTTP API через `fetch` или база данных через серверную библиотеку. Для собственного сервера необязательно создавать промежуточный API-маршрут: Server Component может вызвать функцию доступа к базе напрямую.

## Какие проблемы решает

Если получать текст статьи только в эффекте, браузер должен загрузить JavaScript, запустить его, обратиться к API и дождаться ответа. Серверная загрузка убирает эту цепочку:

- **Понятный начальный контент.** Посетитель и робот получают заголовок и текст из серверного результата.
- **Доступ к закрытым источникам.** Сервер работает с базой данных и приватными ключами.
- **Меньше клиентского кода.** Библиотеку базы и логику получения данных не нужно отправлять в браузер.
- **Контроль повторной работы.** Публичные результаты можно явно кэшировать между запросами.

## Пример: независимые запросы параллельно

Next.js 16 App Router без `cacheComponents`. JSONPlaceholder — учебный открытый API.

```tsx
// app/page.tsx
async function loadJson(url: string) {
  const response = await fetch(url, { cache: "no-store" });
  if (!response.ok) throw new Error("Источник данных недоступен");
  return response.json();
}

export default async function Page() {
  const [user, post] = await Promise.all([
    loadJson("https://jsonplaceholder.typicode.com/users/1"),
    loadJson("https://jsonplaceholder.typicode.com/posts/1"),
  ]);

  return <article>
    <h1>{post.title}</h1>
    <p>Автор: {user.name}</p>
    <p>{post.body}</p>
  </article>;
}
```

`Promise.all` запускает независимые операции без последовательного ожидания. Если одна завершится ошибкой, общий результат тоже завершится ошибкой.

## Пример: ожидание только для медленной части

```tsx
// app/page.tsx
import { Suspense } from "react";

async function Article() {
  const response = await fetch(
    "https://jsonplaceholder.typicode.com/posts/1",
    { cache: "no-store" }
  );
  if (!response.ok) throw new Error("Статья не загрузилась");
  const post = await response.json();
  return <article><h2>{post.title}</h2><p>{post.body}</p></article>;
}

export default function Page() {
  return <main>
    <h1>Учебный блог</h1>
    <Suspense fallback={<p>Загружаем статью…</p>}>
      <Article />
    </Suspense>
  </main>;
}
```

Серверная загрузка не отменяет ожидание. Во время него доступен заголовок блога и сообщение загрузки, затем результат статьи заменит fallback. `Suspense` отвечает за ожидание, а не за ошибки.

## Что важно помнить

- Серверная загрузка сама по себе не гарантирует безопасность или скорость: проверяй права на приватные данные, оптимизируй запросы, выбирай кэширование по задаче.
- `no-store` запрещает хранить ответы в Data Cache, но не отменяет кэш внешнего API и другие механизмы.
- Всё, что попало в HTML и клиентские props, доступно пользователю. Секретный ключ нельзя возвращать вместе с результатом.
- В настоящем проекте внешние ответы проверяют по ожидаемой структуре (runtime-валидация).

## Мини-шпаргалка

- `async` Server Component получает данные до показа.
- Свою БД — напрямую, без своего API.
- Независимые запросы — `Promise.all`.
- Медленные части — в `Suspense`.
