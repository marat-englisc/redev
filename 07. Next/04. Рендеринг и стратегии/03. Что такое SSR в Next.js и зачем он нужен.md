# Что такое SSR в Next.js и зачем он нужен

> [!NOTE]
> **SSR, Server-Side Rendering**, — подготовка HTML на сервере во время запроса. В Next.js его связывают с динамическим рендерингом: результат может зависеть от данных, которые заранее неизвестны, например cookies текущего посетителя.

## Вопрос

Когда нужен рендеринг по запросу, чем SSR отличается от выполнения React в браузере и от статической генерации?

## Основная идея

При клиентском рендеринге браузер сначала получает документ и JavaScript, а затем строит интерфейс. При SSR сервер сначала получает необходимые данные и подготавливает HTML. Браузер может показать текст до завершения загрузки клиентской логики.

Страница с расписанием магазина может быть общей для всех. Страница «Мои заказы» зависит от вошедшего пользователя: серверу нужно прочитать данные запроса, проверить права и получить нужную информацию.

После подготовки ответа браузер показывает HTML. Клиентские компоненты внутри страницы проходят гидратацию: React подключает к существующей разметке состояние и обработчики событий.

В App Router серверные компоненты используются по умолчанию, но это не делает каждый маршрут динамическим. Их результат можно подготовить и заранее. Важно различать **место выполнения компонента** и **момент создания страницы**.

## Пример: приветствие из cookie

```tsx
// app/greeting/page.tsx
import { cookies } from "next/headers";

export default async function Page() {
  const cookieStore = await cookies();
  const name = cookieStore.get("displayName")?.value ?? "гость";

  return (
    <main>
      <h1>Здравствуйте, {name}!</h1>
      <p>Имя получено из cookie текущего запроса.</p>
    </main>
  );
}
```

В обычном App Router без включенного `cacheComponents` обращение к `cookies()` переводит маршрут в динамический рендеринг. Если cookie отсутствует, получится «Здравствуйте, гость!». При `displayName=Анна` появится приветствие для Анны.

Cookie используется только для демонстрации. Пользователь может подменить ее значение, поэтому она не подтверждает личность и не заменяет проверку сессии.

## Пример: время серверного рендеринга

```tsx
// app/server-time/page.tsx
export const dynamic = "force-dynamic";

export default function ServerTimePage() {
  const renderedAt = new Date().toISOString();
  return (
    <main>
      <h1>Время на сервере</h1>
      <p>{renderedAt}</p>
    </main>
  );
}
```

`force-dynamic` явно требует рендеринг при запросе, поэтому при каждом обновлении `/server-time` в HTML будет время нового выполнения. Это отметка момента подготовки ответа, а не часы: после открытия страницы время само не обновляется.

## Что важно помнить

- SSR не гарантирует быстрый ответ: если сервер ждет медленный API, пользователь тоже ждет. Streaming, `Suspense` и `loading.tsx` позволяют показывать готовые части постепенно.
- SSR не гарантирует свежесть всех данных: внутри ответа могут использоваться явно кэшированные источники.
- Серверные компоненты сами по себе не гидратируются — гидратация нужна клиентским компонентам.
- Данные, попавшие в HTML или переданные клиентскому компоненту, доступны пользователю. Серверное выполнение не делает выведенный результат секретным.
- В Pages Router аналогичная задача решается через `getServerSideProps`; этот API нельзя переносить в папку `app`.

## Мини-шпаргалка

- SSR готовит ответ во время запроса.
- `await cookies()` читает cookies текущего посетителя и делает маршрут динамическим.
- Серверный компонент не обязательно выполняется на каждом запросе.
- Персональные данные требуют проверки доступа.
