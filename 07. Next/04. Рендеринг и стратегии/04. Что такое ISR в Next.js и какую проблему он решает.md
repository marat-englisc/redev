# Что такое ISR в Next.js и какую проблему он решает

> [!NOTE]
> **ISR, Incremental Static Regeneration**, — обновление предварительно подготовленных страниц после сборки, без пересборки всего приложения.

## Вопрос

Как совместить выдачу готовой страницы с периодическим обновлением ее содержимого?

## Основная идея

Представь блог с тысячами статей или магазин с тысячей публичных карточек товаров. Пересобирать весь сайт после каждой правки неудобно, а формировать каждую страницу заново для каждого посетителя дорого. ISR позволяет многократно использовать готовую страницу и обновлять ее по выбранным правилам.

При обновлении по времени `revalidate` задает интервал, после которого результат можно считать устаревшим:

1. Пока интервал не истек, посетители получают сохраненную страницу.
2. Первый запрос после истечения интервала может получить прежний результат и запустить регенерацию в фоне.
3. После успешного обновления следующие запросы получают новую версию.
4. При неудачной регенерации последняя успешная версия продолжает обслуживать запросы.

Интервал не является таймером, который сам запускает работу каждые N секунд. Если посетителей нет, обновление не запускается.

## Пример: время создания версии

Пример для Next.js 16 App Router без включенного `cacheComponents`:

```tsx
// app/catalog/page.tsx
export const revalidate = 60;

export default function Page() {
  const generatedAt = new Date().toISOString();

  return (
    <main>
      <h1>Каталог книг</h1>
      <p>Эта версия страницы создана: {generatedAt}</p>
    </main>
  );
}
```

Здесь нет внешнего API: время показывает, когда Next.js сформировал текущую версию. Запусти `next build` и `next start`. Несколько запросов подряд покажут одно время. После интервала и запуска обновления появится новая отметка.

## Пример: интервал для конкретного запроса

JSONPlaceholder — открытый учебный источник данных.

```tsx
// app/posts/page.tsx
type Post = { id: number; title: string };

export default async function PostsPage() {
  const response = await fetch(
    "https://jsonplaceholder.typicode.com/posts?_limit=5",
    { next: { revalidate: 60 } },
  );
  if (!response.ok) throw new Error("Не удалось загрузить статьи");
  const posts: Post[] = await response.json();

  return <ul>{posts.map(post => <li key={post.id}>{post.title}</li>)}</ul>;
}
```

Положительный `revalidate` в `fetch` включает сохранение данных с интервалом обновления. Такой маршрут может обновляться без новой сборки. Кэш ответа API и кэш готового маршрута при этом остаются разными уровнями.

В Pages Router ISR настраивают через `revalidate` в результате `getStaticProps`. Обновление по событию выполняют `revalidatePath` и `revalidateTag`.

## Что важно помнить

- ISR допускает временно устаревшее содержимое. Он подходит для публичных статей и каталогов, но не гарантирует актуальность баланса, остатка товара в момент оплаты или прав доступа — при операции сервер должен проверить реальные данные заново.
- `60` не гарантирует, что данные устареют максимум на минуту: время до следующего запроса, длительность обновления и ошибки увеличивают задержку.
- ISR — механизм обновления, а не отдельный «уровень кэша».
- Проверяй поведение в production-режиме: в `next dev` оно отличается.
- ISR требует серверного развертывания; обычный статический экспорт в файлы фоновое обновление не выполняет. При включенном `cacheComponents` используются другие средства управления кэшем.

## Мини-шпаргалка

- `revalidate` задает возможность обновления после интервала.
- Первый ответ после интервала может быть старым.
- Новая версия заменяет старую после успешной регенерации.
- Обновление не требует полной сборки сайта.
