# Как защищать API от CSRF, SQL-инъекций и перегрузки

> [!NOTE]
> Серверный endpoint доступен независимо от кнопок интерфейса. Его защита включает проверку личности, прав, входных данных, источника изменяющего запроса и допустимой нагрузки.

## Вопрос

Какие проверки нужны собственным Route Handlers помимо валидации формы?

## Основная идея

| Риск | Защита |
| --- | --- |
| Чужая запись | Проверка сессии и владельца в DAL |
| SQL-инъекция | Параметризованные запросы и допустимые варианты сортировки |
| CSRF — действие через cookie жертвы с другого сайта | Подходящая политика cookie, Origin/CSRF-проверки |
| XSS — выполнение недоверенного HTML | Безопасный вывод, очистка HTML, политика CSP |
| Перегрузка | Лимиты частоты, размера тела, времени и конкуренции |

В учебном API уже используются SQL-параметры, Zod и `assertMutationRequest`. Защита Server Actions, предусмотренная Next.js, не переносится автоматически на произвольные HTTP-обработчики.

## Пример: безопасный вывод текста

```tsx
// React экранирует значение как текст
export function TaskTitle({ title }: { title: string }) {
  return <h2>{title}</h2>;
}
```

Строка `<script>...</script>` здесь показывается как текст, а не выполняется. Если продукту нужен настоящий HTML, потребуется отдельная проверенная очистка. `dangerouslySetInnerHTML` не выполняет ее за тебя.

## Что важно помнить

**CORS** управляет чтением ответа браузером другого origin. Он не является авторизацией и не останавливает все межсайтовые записи. Для cookie-аутентификации нельзя бездумно разрешить любой origin; проверка Origin также не заменяет проверку пользователя.

Rate limiting использует общее хранилище или возможности платформы. Счетчик в памяти одного serverless-экземпляра не ограничивает остальные экземпляры. Для входа лимиты нужны до успешной авторизации; адрес клиента следует получать с учетом доверенных прокси, а не из любого присланного заголовка.

Проверка `Content-Length` не гарантирует фактический размер тела. Ограничения устанавливают и на стороне сервера/прокси. При превышении лимита частоты обычно возвращают 429 и уместный `Retry-After`.

## Мини-шпаргалка

- Endpoint проверяет запрос самостоятельно.
- CORS не заменяет CSRF-защиту или авторизацию.
- SQL-параметры защищают значения, сортировку выбирают из списка.
- Лимиты должны работать для всех экземпляров приложения.
