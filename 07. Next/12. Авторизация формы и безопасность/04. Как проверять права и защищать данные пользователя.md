# Как проверять права и защищать данные пользователя

> [!NOTE]
> Вход подтверждает личность, но не дает доступа ко всем записям. Каждая операция должна проверить, разрешено ли этому пользователю работать именно с указанным ресурсом.

## Вопрос

Почему недостаточно скрыть кнопку удаления или проверить вход в layout?

## Основная идея

Пользователь может подменить `id` в запросе, вызвать API напрямую или отправить Action вне предусмотренного интерфейса. Ошибка, при которой это открывает чужую запись, называется IDOR — небезопасная прямая ссылка на объект.

Защита должна находиться возле данных. Страница, API и Action используют один DAL, который берет пользователя из проверенной сессии и включает его идентификатор в запрос.

## Пример: чтение конкретной задачи

```ts
// lib/read-task.ts
import "server-only";
import { pool } from "./db";
import { requireUser } from "./session";
import { taskIdSchema } from "./task-schema";
import { AppError } from "./errors";
import type { Task } from "./tasks";

export async function readTask(rawId: unknown): Promise<Task> {
  const user = await requireUser();
  const id = taskIdSchema.parse(rawId);
  const result = await pool.query<Task>(
    "SELECT id, title, completed FROM tasks WHERE id = $1 AND owner_id = $2",
    [id, user.id],
  );
  if (!result.rows[0]) throw new AppError(404, "Задача не найдена");
  return result.rows[0];
}
```

Чужая и отсутствующая задача дают одинаковый результат. API не раскрывает, существует ли запись другого пользователя. В основном DAL аналогичное условие стоит у UPDATE и DELETE.

## Что важно помнить

Проверка в layout улучшает навигацию, но не заменяет проверку каждой серверной операции. Перенаправление на вход в Proxy также не закрывает все способы обращения к данным.

Для администратора роль берут из доверенного серверного источника. Поле `role: "admin"`, присланное браузером, не создает право администратора. В базовом примере Better Auth роли не настроены; их добавляют отдельной моделью или соответствующим плагином.

Не сохраняй персональный ответ в общий публичный кэш. Не отправляй лишние закрытые поля через props, JSON или журналы. Для финансовых операций дополнительно проверяются состояние ресурса и конкурентные изменения.

## Мини-шпаргалка

- Проверка входа и проверка доступа — разные действия.
- Владелец определяется по сессии.
- Проверки нужны в RSC, Actions и API через общий DAL.
- Тест с двумя пользователями обязателен для проверки изоляции.
