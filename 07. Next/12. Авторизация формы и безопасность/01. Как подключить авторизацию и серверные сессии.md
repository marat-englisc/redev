# Как подключить авторизацию и серверные сессии

> [!NOTE]
> Аутентификация устанавливает личность пользователя, сессия связывает запросы с этой личностью, а авторизация определяет разрешенные действия. Это три разные задачи.

## Вопрос

Как получить настоящего текущего пользователя, а не доверять `userId` из браузера?

## Основная идея

Для учебного приложения используем Better Auth с PostgreSQL. Библиотека обрабатывает пароли и сессии; собственную криптографию писать не нужно. Сначала подготовь `.env`, пакеты и пул из раздела 11, тем 02–03. Примеры используют App Router и Node.js runtime без Cache Components.

## Пример: серверная конфигурация

```ts
// lib/auth.ts — конфигурация для серверного обработчика и CLI
import "dotenv/config";
import { betterAuth } from "better-auth";
import { pool } from "./db-pool";

export const auth = betterAuth({
  database: pool,
  emailAndPassword: { enabled: true },
});
```

`dotenv/config` загружает `.env` при запуске CLI; Next.js загружает свои env-файлы сам. Better Auth читает `BETTER_AUTH_SECRET` и `BETTER_AUTH_URL`. Серверную конфигурацию не импортируют в Client Components.

```ts
// app/api/auth/[...all]/route.ts
import { toNextJsHandler } from "better-auth/next-js";
import { auth } from "@/lib/auth";

export const runtime = "nodejs";
export const { GET, POST } = toNextJsHandler(auth);
```

Теперь создай служебные таблицы библиотеки:

```powershell
npx auth@latest migrate --config ./lib/auth.ts
```

Для воспроизводимой командной работы фиксируют версии библиотеки и CLI, сохраняют и проверяют миграции. Здесь команда предназначена для новой локальной базы.

## Пример: проверка сессии возле данных

```ts
// lib/errors.ts
export class AppError extends Error {
  constructor(public status: number, message: string) {
    super(message);
    this.name = "AppError";
  }
}
```

```ts
// lib/session.ts
import "server-only";
import { cache } from "react";
import { headers } from "next/headers";
import { auth } from "./auth";
import { AppError } from "./errors";

export const getCurrentUser = cache(async () => {
  const session = await auth.api.getSession({ headers: await headers() });
  return session?.user ?? null;
});

export async function requireUser() {
  const user = await getCurrentUser();
  if (!user) throw new AppError(401, "Требуется вход");
  return user;
}
```

`requireUser()` вернет проверенного пользователя либо прекратит защищенную операцию. В RSC `cache` помогает повторно использовать проверку внутри запроса; это не общий кэш сессий разных посетителей.

## Что важно помнить

Cookie с произвольным `userId` не является доказательством личности. Используй серверную проверку библиотеки. Не включай общий постоянный кэш для результата `getCurrentUser`.

Для публичного продукта отдельно настраивают подтверждение почты, восстановление пароля, лимиты попыток и HTTPS. Отсутствие этих функций в минимальном учебном примере не означает, что они не нужны.

## Мини-шпаргалка

- Библиотека проверяет сессию, DAL проверяет доступ к записи.
- Серверный `auth` и клиентский `authClient` — разные модули.
- Сначала миграция авторизации, затем таблица задач.
