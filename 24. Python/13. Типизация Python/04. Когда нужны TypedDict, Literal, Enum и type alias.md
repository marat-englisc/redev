# Когда нужны TypedDict, Literal, Enum и type alias

> [!NOTE]
> TypedDict описывает ожидаемые ключи обычного dict для статической проверки. Literal ограничивает тип конкретными значениями, Enum создаёт именованные runtime-константы, type alias даёт имя составному типу. TypedDict не создаёт валидатор JSON и не меняет реальный тип словаря. Обязательность ключа и возможность значения None — разные свойства.

## Вопрос

Как описать API-запись с обязательным id и необязательным email? Чем Literal отличается от Enum?

## Форма словаря

```python
from typing import Literal, NotRequired, TypedDict

class UserRecord(TypedDict):
    id: int
    role: Literal["reader", "editor"]
    email: NotRequired[str | None]

user: UserRecord = {"id": 7, "role": "reader"}
print(type(user).__name__)  # dict
```

Email можно не передавать, либо передать str/None. Аннотация `email: str | None` без NotRequired делала бы ключ обязательным.

## Runtime-константы

```python
from enum import Enum

class Status(Enum):
    READY = "ready"
    FAILED = "failed"

status = Status("ready")
print(status is Status.READY)  # True
print(status.value)  # ready
```

Неизвестное значение вызовет ValueError. Enum действительно существует в runtime, а Literal влияет на анализ типов. Сериализацию enum-поля нужно выбирать явно, например через value.

## Псевдоним

Python 3.12+:

```python
type UserId = int
type UserMap = dict[UserId, str]

users: UserMap = {1: "Anna"}
print(users[1])  # Anna
```

Alias не создаёт новый защищённый числовой тип. Для статического различения UserId/OrderId бывает нужен NewType, но и он не выполняет предметную runtime-валидацию.

## Граница системы

После json.loads значение ещё нужно проверить. Cast к UserRecord лишь обещает анализатору корректность, не проверяя ключи и типы. Это различие обязательно для обработки недоверенного ввода.

## Практика

Опиши union успешного и ошибочного ответа с Literal-дискриминатором. Проверь, какие ключи доступны после ветвления по статусу в выбранном type checker.
