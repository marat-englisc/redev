# Когда нужны partial, cache и lru_cache

> [!NOTE]
> Partial фиксирует часть аргументов функции и создаёт новый callable. Cache и lru_cache запоминают результаты по хешируемым аргументам; lru_cache может ограничивать число записей. Кеш полезен для повторяемого вычисления с подходящим контрактом, но удерживает ссылки и может возвращать устаревшие данные. Это не универсальный кеш с TTL и не гарантия единственного выполнения при конкуренции.

## Вопрос

Как убрать повторные расчёты и когда кеширование меняет поведение функции?

## Частичное применение

```python
from functools import partial

parse_hex = partial(int, base=16)
print(parse_hex("ff"))  # 255
```

Partial удобен, когда нужна существующая функция с закреплёнными настройками. Это не вызов int заранее: вычисление происходит, когда вызывают parse_hex.

## Кеш результата

```python
from functools import lru_cache

@lru_cache(maxsize=128)
def square(number):
    print("calculate")
    return number * number

print(square(4))  # calculate, затем 16
print(square(4))  # 16 без нового calculate
print(square.cache_info().hits)  # 1
square.cache_clear()
```

Ключи должны быть хешируемыми. Передача list вызовет TypeError. Разные формы keyword-вызова могут образовать разные записи: это не обязательно логическая нормализация аргументов.

## Главные риски

```python
from functools import cache

@cache
def make_list(size):
    return [0] * size

first = make_list(2)
first[0] = 9
print(make_list(2))  # [9, 0] — возвращён тот же изменённый объект
```

Кеш не создаёт копию результата. Функции с временем, случайностью, I/O и изменяемым результатом требуют отдельного решения.

Cache не ограничивает размер, lru_cache ограничивает количество ключей, но не общий объём байтов. Потокобезопасность структуры кеша не означает, что при одновременном miss вычисление обязательно выполнится один раз.

## Практика

Добавь lru_cache к чистой функции с повторяющимися входами, проверь hits/misses. Объясни, почему нельзя без изменений кешировать функцию записи заказа в БД.
