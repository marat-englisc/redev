# Как ограничивать конкурентность - Semaphore, Queue и backpressure

> [!NOTE]
> Semaphore ограничивает число одновременно выполняемых участков, Queue с maxsize ограничивает буфер между producer и workers. Если очередь заполнена, await put замедляет producer: это backpressure. Ограничение одновременной работы не равнозначно ограничению числа созданных tasks и не задаёт само по себе rate limit в запросах в секунду.

## Вопрос

Как обработать поток записей несколькими workers, не создавая task на каждую запись заранее?

## Ограниченная очередь

```python
import asyncio

async def worker(queue, results):
    while True:
        item = await queue.get()
        try:
            if item is None:
                return
            await asyncio.sleep(0)
            results.append(item * 2)
        finally:
            queue.task_done()

async def main():
    queue = asyncio.Queue(maxsize=2)
    results = []
    async with asyncio.TaskGroup() as group:
        for _ in range(2):
            group.create_task(worker(queue, results))
        for value in range(5):
            await queue.put(value)
        for _ in range(2):
            await queue.put(None)
        await queue.join()
    print(sorted(results))  # [0, 2, 4, 6, 8]

asyncio.run(main())
```

Каждому worker нужен сигнал завершения. Task_done вызывается для каждой полученной записи, включая sentinel. TaskGroup не оставит ошибку worker незамеченной.

## Semaphore

`async with semaphore:` удобно вокруг HTTP-запроса, когда весь набор tasks небольшой. Но миллион заранее созданных tasks с одним semaphore всё ещё занимает память. Очередь workers позволяет ограничить и число выполняющихся задач, и буфер.

## Ошибки и результаты

Порядок завершения workers не обязан совпадать с порядком входа. Если порядок важен, сохраняй идентификатор позиции и организуй выдачу отдельно. Results-list в примере растёт по числу результатов: это **не полностью bounded** пайплайн. Для больших данных результат нужно сразу передавать ограниченному writer.

## Практика

Добавь ошибочную запись и выбери политику: завершить весь пайплайн или сохранить ошибку записи и продолжить. Проверь, что join не зависает из-за пропущенного task_done.
