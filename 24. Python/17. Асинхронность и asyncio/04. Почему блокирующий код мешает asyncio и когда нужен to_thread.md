# Почему блокирующий код мешает asyncio и когда нужен to_thread

> [!NOTE]
> Обычный time.sleep, синхронный HTTP-клиент или тяжёлый цикл блокирует поток event loop, даже внутри async def. To_thread позволяет вынести подходящую синхронную I/O-операцию в thread. Это не универсальное ускорение CPU-кода и не гарантированная остановка функции потока при отмене ожидающей coroutine. По возможности используй API с нужным async-контрактом.

## Вопрос

Почему сервер с async-функциями иногда обслуживает запросы последовательно? Исправляет ли await перед любой функцией блокировку?

## Корректное вынесение

```python
import asyncio
import time

def blocking_read():
    time.sleep(0.02)  # модель блокирующего I/O
    return "data"

async def main():
    result = await asyncio.to_thread(blocking_read)
    print(result)  # data

asyncio.run(main())
```

Важно передать **функцию**, а не вызвать её заранее: `to_thread(blocking_read())` сначала выполнит блокирующую работу в loop и затем передаст результат вместо callable.

## Нельзя await обычную строку

`await blocking_read()` не делает функцию асинхронной: сначала она блокирующе вызывается, потом Python пытается await её результат и обычно получает TypeError.

## CPU-bound

В обычной GIL-сборке CPython чистый CPU Python-код в нескольких threads обычно не получает параллельного исполнения байткода на ядрах. Для тяжёлых расчётов рассматривают процессы, отдельный сервис или нативную библиотеку, освобождающую GIL. Free-threaded-сборки имеют другую модель, но требуют корректной синхронизации.

## Отмена и нагрузка

Если ожидающая Task отменена, уже выполняющаяся thread-функция может продолжить работу. Внешнему API всё равно нужен timeout, а числу фоновых операций — предел. Не запускай тысячи to_thread без управления очередью.

## Практика

Запусти «тикер» с asyncio.sleep вместе с blocking_read. Сравни прямой вызов и to_thread: тикер должен продолжать получать управление во втором варианте. Не проверяй точную скорость жёстким универсальным порогом.
