# Как использовать debugger, Ruff, mypy и проверки в CI

> [!NOTE]
> Тесты проверяют примеры поведения, type checker — совместимость аннотаций, линтер — отдельные ошибки и правила, formatter — единый стиль. Эти инструменты решают разные задачи и не заменяют друг друга. Breakpoint помогает исследовать реальное состояние процесса. CI запускает согласованный набор проверок в воспроизводимой среде.

## Вопрос

Что найдёт mypy, чего не найдёт formatter? Как отлаживать ошибку без случайных print во всех функциях?

## Инструменты

| Инструмент | Назначение |
| --- | --- |
| pytest | Поведение на выбранных сценариях |
| mypy / Pyright | Статические типовые контракты |
| Ruff check | Выбранные lint-правила |
| Ruff format | Форматирование |
| pdb / debugger IDE | Состояние во время выполнения |

После установки инструментов в dev-окружение:

```bash
python -m pytest -q
python -m mypy src
python -m ruff check .
python -m ruff format --check .
```

Настройки и набор правил фиксируются проектом. Не включай вслепую все возможные правила в существующем репозитории.

## Почему mypy может пропустить ошибку

По умолчанию mypy не проверяет тело функции, у которой нет аннотаций ни у параметров, ни у результата. Например, в файле `untyped_demo.py`:

```python
def broken():
    return 1 + "2"
```

Без дополнительных настроек mypy пропустит эту ошибку, хотя вызов broken завершится TypeError. Проверку таких тел можно включить флагом:

```bash
python -m mypy --check-untyped-defs untyped_demo.py
```

Теперь mypy сообщит о несовместимых операндах int и str. Но неаннотированные параметры всё ещё получают Any: флаг не восстанавливает за автора полный контракт функции. Аннотируй входы и результат явно.

Для нового учебного проекта добавь в `pyproject.toml`:

```toml
[tool.mypy]
python_version = "3.12"
check_untyped_defs = true
disallow_untyped_defs = true
```

`check_untyped_defs` включает проверку тел без аннотаций, `disallow_untyped_defs` дополнительно требует аннотации в определениях функций. С этой конфигурацией исходная команда `python -m mypy src` применяет обе проверки. В существующем проекте их можно включать постепенно; успешный запуск mypy следует оценивать вместе с настройками и использованием Any.

## Отладчик

```python
def normalize(value):
    cleaned = value.strip()
    breakpoint()  # интерактивно: посмотреть cleaned и стек
    return cleaned.casefold()
```

Pdb понимает команды n — следующий шаг, s — войти, c — продолжить, p expression — посмотреть значение, where — стек. Не оставляй breakpoint в unattended-задаче или production-сервисе.

## Что статическая проверка не знает

JSON может не соответствовать обещанному типу, база — вернуть неожиданные данные, а сеть — завершиться timeout. Даже идеальный отчёт mypy не отменяет runtime-валидацию и обработку отказов.

## CI

Обычно CI выбирает поддерживаемую версию Python, устанавливает закреплённые зависимости, запускает проверки и сохраняет результат. Для кроссплатформенного кода полезно тестировать несколько ОС; поведение путей и multiprocessing может различаться.

## Практика

Сделай одну ошибку типа, одну неиспользуемую переменную/импорт по включённому правилу и одну логическую ошибку. Зафиксируй, какой инструмент обнаруживает каждую. Сравни проверку broken с настройками mypy по умолчанию и с check_untyped_defs, затем добавь аннотацию результата и повтори проверку.
