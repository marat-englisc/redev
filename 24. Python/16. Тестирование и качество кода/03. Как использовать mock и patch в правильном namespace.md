# Как использовать mock и patch в правильном namespace

> [!NOTE]
> Mock заменяет зависимость управляемым объектом, patch временно подменяет имя там, где его ищет тестируемый код. После `from module import function` подменять часто нужно имя в модуле-потребителе. Моки полезны для границ вроде сети, но чрезмерное мокирование внутренних вызовов делает тест хрупким и не доказывает интеграцию.

## Вопрос

Почему patch исходной функции не меняет вызов в другом модуле? Когда fake понятнее mock?

## Два файла

`service.py`:

```python
from time import time

def issued_at():
    return int(time())
```

`test_service.py`:

```python
from unittest.mock import patch
import service

def test_issued_at():
    with patch("service.time", return_value=123.9) as clock:
        assert service.issued_at() == 123
        clock.assert_called_once_with()
```

Service хранит своё имя time. Подмена `time.time` после такого импорта не обязана заменить `service.time`. Если сервис использует `import time` и обращается `time.time()`, lookup устроен иначе.

## Stub, fake и mock

| Подход | Задача |
| --- | --- |
| Stub | Вернуть заранее заданный ответ |
| Fake | Дать простую рабочую реализацию, например memory repository |
| Mock | Позволить дополнительно проверять взаимодействие |

Для собственного sender часто проще передать объект с messages, чем настраивать дерево магических mock-атрибутов.

## Спецификация

Autospec/spec помогают ловить неверные методы и сигнатуры. Но даже правильно настроенный mock не проверяет реальный SQL, HTTP-схему и поведение сервера. Для этого нужны отдельные интеграционные тесты.

Проверяй вызов, если он и есть часть контракта: например, уведомление должно отправиться один раз. Не привязывайся к каждой приватной helper-функции без причины.

## Практика

Измени import сервиса на `import time` и адаптируй patch к lookup. Затем вынеси часы в передаваемую зависимость и сравни тесты.
