# Как избегать eval, pickle-инъекций и небезопасных путей

> [!NOTE]
> Недоверенные данные не должны превращаться в исполняемый код. Eval/exec исполняют выражения/инструкции, pickle при загрузке способен выполнять код, shell=True открывает shell-разбор, SQL-строка с конкатенацией допускает инъекцию. Выбирай парсер данных, параметры запросов и ограниченные интерфейсы, затем проверяй схему, размер и полномочия.

## Вопрос

Почему нельзя загрузить полученный извне pickle? Достаточно ли JSON-парсера для безопасности API?

## Формат данных

```python
import json

payload = '{"limit": 10}'
data = json.loads(payload)
if not isinstance(data, dict) or type(data.get("limit")) is not int:
    raise ValueError("invalid config")
if not 1 <= data["limit"] <= 1000:
    raise ValueError("limit is outside allowed range")
print(data["limit"])  # 10
```

JSON не выполняет Python-код как pickle, но большой или глубоко вложенный вход всё равно расходует ресурсы. Парсер не знает разрешённые бизнес-операции.

## Пути

`base / user_input` не гарантирует нахождение внутри base: ввод может быть абсолютным или содержать `..`. Разрешение пути и проверка через relative_to помогают для доверенной локальной структуры:

```python
from pathlib import Path

base = Path("uploads").resolve()
candidate = (base / "reports" / "result.csv").resolve()
relative = candidate.relative_to(base)
print(relative.parts)  # ('reports', 'result.csv')
```

При выходе за base relative_to выбросит ValueError. Но race со сменой symlink между проверкой и open требует более строгих ОС-механизмов; простая проверка пути не является полноценной sandbox.

## Другие границы

- Для SQL — параметры значений и allowlist структуры запроса.
- Для subprocess — список аргументов, проверка опций и timeout.
- Для внешнего URL — политика схем, адресов и redirects против SSRF.
- Для токенов — secrets, ограниченный доступ и ротация при утечке.
- Для архивов — проверка путей и политики извлечения, а не распаковка куда угодно с широкими правами.
