# Как связаны __eq__, __hash__ и ключи словаря

> [!NOTE]
> Если объекты равны по ==, их hash должен совпадать. Обратное неверно: совпадение hash не гарантирует равенство. Hash ключа должен оставаться стабильным, пока ключ используется в dict/set. Если класс переопределяет __eq__ без подходящего __hash__, Python обычно делает его нехешируемым, чтобы не нарушить этот контракт.

## Вопрос

Почему не всякий неизменяемый снаружи объект подходит ключом? Что случится, если менять поле, от которого вычисляется hash?

## Согласованная модель

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class UserKey:
    tenant: str
    identifier: int

first = UserKey("team-a", 7)
second = UserKey("team-a", 7)
cache = {first: "Anna"}
print(first == second)  # True
print(hash(first) == hash(second))  # True
print(cache[second])  # Anna
```

Поля в примере сами хешируемы. Frozen dataclass с изменяемым list-полем не получит корректный вычислимый hash только из-за слова frozen.

## Коллизии нормальны

Hash сжимает множество значений в ограниченное пространство чисел, поэтому разные объекты могут иметь одинаковый hash. Dict использует и другие проверки, включая равенство, а не принимает hash за уникальный ID.

## Почему опасна мутация

Если ключ поместили в таблицу по старому hash, затем поменяли значимое поле и получили новый hash, поиск может больше не найти его ожидаемым способом. Не исправляй это случайным `unsafe_hash=True`: сначала определи неизменяемую идентичность ключа.

## Не для постоянного fingerprint

Hash строк и некоторых других типов может меняться между процессами из-за рандомизации. Встроенный hash не подходит для постоянной контрольной суммы файла, распределённого ID или цифровой подписи. Для целостности байтов существуют hashlib и конкретные криптографические алгоритмы.

## Практика

Объясни, почему tuple из строк подходит ключом, а tuple с list — нет. Создай два равных UserKey и проверь получение значения через второй.
